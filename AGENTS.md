## Plan-wide invariants (non-negotiable)

These are hard constraints from the spec. Violating any of them is a P0 bug regardless of test status.

1. **TDD per task.** Every task: failing test → minimal implementation → passing test → commit. Never write implementation before the test that exercises it.
2. **Per-show advisory lock.** Every code path that mutates `shows`, `crew_members`, `crew_member_auth`, `pending_syncs`, or `pending_ingestions` runs inside `pg_try_advisory_xact_lock(hashtext('show:' || drive_file_id))` (cron path) or `pg_advisory_xact_lock(...)` (admin/blocking path). Tests assert the lock is held. **Single-holder rule:** for any given hashkey, the lock is acquired at exactly one layer (JS-side wrapper, in-RPC, OR nested SECURITY DEFINER) — never two. Nested holders deadlock under burst (M5 R20 CRITICAL). Plans editing such code paths enumerate every existing holder and document the chosen layer; the structural guard test at `tests/auth/advisoryLockRpcDeadlock.test.ts` pins the topology and is the template for new lock surfaces.
3. **Email canonicalization at every boundary.** `lib/email/canonicalize.ts` is the only function that touches raw emails before they enter the system. Schema-level CHECK is the safety net, not the primary mechanism.
4. **No global sync cursor.** Per spec §3.2 / §5.2 / AC-X.4, no source file references `lastPollAt`. Each show is tracked via `shows.last_seen_modified_time`.
5. **No raw error codes in user-visible UI.** §12.4 is the catalog. UI reads codes through `lib/messages/lookup.ts` which returns the appropriate copy.
6. **Commit per task.** Use conventional-commits style: `<type>(<scope>): <summary>` OR `<type>: <summary>` for cross-cutting changes where no scope adds clarity. Common types: `feat`, `fix`, `test`, `docs`, `refactor`, `chore`. Common scopes/areas: `parser`, `db`, `sync`, `auth`, `crew-page`, `admin`, `report`, `onboarding`, `assets`, `infra`, `routing`, `plan`, `handoff`. The bare `infra:` form (no `feat()` wrapper) is the established convention for tooling/scaffolding/config commits — see the M0 commit history (`git log dcfd2cd..HEAD`). Don't batch multiple tasks into one commit, and don't allow the format to drift across milestones (e.g., M1 parser task commits should be `feat(parser):` or `test(parser):`, not bare `parser:`).
7. **Spec is canonical.** Three ratified amendments in `00-overview.md` are the only places where the plan supersedes the spec. Anywhere else the spec wins; open a question instead of silently fixing.
8. **UI quality gate (impeccable v3 critique + audit pair).** Every UI surface ships only after `/impeccable critique` AND `/impeccable audit` pass on the affected diff, with P0 and P1 findings either fixed or explicitly deferred via a `DEFERRED.md` entry (the skill tags findings P0–P3; older docs say "HIGH/CRITICAL" — same tier). UI surface = any file under `app/` except `app/api/**`, any file under `components/`, any new `app/globals.css` `@theme` token block, and any change to `DESIGN.md` or `tailwind.config.*`. The dual-command run is part of milestone close-out, _before_ adversarial review (Codex) and _before_ the milestone is marked closed in its handoff doc. Both commands run with the canonical v3 setup gates: `context.mjs` context load (PRODUCT.md + DESIGN.md) → register reference read (`brand.md` or `product.md`). (Skill ≥3.9 dropped the `IMPECCABLE_PREFLIGHT` structured signal; the gate is the setup steps themselves.) Findings + dispositions go in §12 of the milestone's handoff doc. (This is a UI-_evaluation_ contract, distinct from the no-raw-error-codes UI-_rendering_ contract in rule 5 — both apply.) Every `docs/superpowers/plans/` unit that names both gate halves must carry the machine-checkable closeout marker line (`impeccable-gate: …`, grammar in the 2026-08-01 invariant-8-closeout-enforcement spec §3.3; `impeccable-gate: N/A — no UI surface` for non-UI plans) — enforced by `tests/docs/_metaInvariant8Closeout.test.ts`. Style: directory units put it in `closeout.md`/`CLOSEOUT.md` or the handoff §12; flat plans in an in-plan `## 12` section or a stem-named sibling closeout file.
9. **Supabase call-boundary discipline.** Every Supabase client call destructures `{ data, error }` (not bare `data`); returned-error and thrown-error paths are distinguished; infra faults surface as discriminable typed results (e.g., `{ kind: 'infra_error' }` or a typed `*InfraError` thrown), never as silent `continue` or benign auth signals. Every helper subject to this contract is registered in the relevant structural meta-test — `tests/auth/_metaInfraContract.test.ts` for auth helpers; an analogous registry-style meta-test for new surfaces. New call sites EITHER add a registry row OR carry an inline `// not-subject-to-meta: <reason>` comment. Pre-emptively requiring the registry row at plan time eliminates a class that cost M5 six consecutive review rounds (R3–R22, closed only once the meta-test landed).

10. **Every mutation surface is instrumented — no surface is silently dark.** Every mutation surface unit — each mutating HTTP route handler (`POST` / `PUT` / `PATCH` / `DELETE`), each exported action in a module-level `"use server"` file, and each function-scoped inline `"use server"` action — MUST be covered, with the mechanism depending on whether it is an admin surface. **Non-admin surfaces** (crew/system actions; infra routes NOT under the admin API tree) MUST carry at least one code-carrying emit — `await logAdminOutcome(...)`, or a durable `code:` field on a `log.info`/`log.warn`/`log.error` call (a SHOUTY message alone does NOT count — it is not the persisted code) — OR an inline `// no-telemetry: <reason>` exemption, OR a `KNOWN_UNINSTRUMENTED` debt-ledger row with a backlog ref. Checked per function for actions, per file for routes. **Admin mutations** — admin-gated actions (body calls a `require`-gate such as `requireAdmin` / `requireAdminIdentity` / `requireDeveloper` / `requireDeveloperIdentity`) AND mutating routes under the `app/api/admin/` tree (matched by path prefix; require-gate detection is deliberately NOT used for routes, to avoid a false positive on crew routes that read admin identity only for role-detection, e.g. `app/api/report`) — MUST satisfy a stricter contract: membership in the `AUDITABLE_MUTATIONS` registry PLUS executable success-branch behavioral proof (a sink-spy that records only after observing the code on the committed-success branch), OR an explicit `ADMIN_SURFACE_EXEMPTIONS` row (a delegator to a registered surface, or a verified read-only accessor). A bare `// no-telemetry:` or `KNOWN_UNINSTRUMENTED` row is invalid for an admin surface. Enforced by `tests/log/_metaMutationSurfaceObservability.test.ts` (static discovery, filesystem-walked so a NEW surface fails-by-default) and `tests/log/adminOutcomeBehavior.test.ts` (executable admin behavioral coverage). Registry/exemption/ledger live in `tests/log/_auditableMutations.ts` and `tests/log/mutationSurface/exemptions.ts`. Emits are POST-COMMIT, outside any advisory-lock tx (invariant 2), and secrets are never logged (e.g. `rotateShareToken` emits `epoch_<n>`, never the share token).

11. **All work happens in an isolated worktree — never in the main checkout.** Every task that mutates tracked files — feature, fix, docs, spec/plan edit, one-line typo — begins by creating a git worktree off `origin/main` (`git worktree add -b <branch> ../FX-worktrees/<name> origin/main`), BEFORE the first edit. Do not edit in the main checkout `/Users/ericweiss/FX-Webpage-Template` and relocate afterward. The main checkout is read-only: inspection, `git log`, and post-merge fast-forward sync (`git pull --ff-only`, verifying `git rev-list --left-right --count main...origin/main` == `0  0`). Rationale: parallel agent sessions share the main checkout, and two writers in one working tree race — one session's staged edits get swept into the other's commit. Worktree setup for any task that runs tests: `pnpm install`, then `pnpm worktree:link-env` (symlinks the gitignored `.env.local`), then `pnpm preflight` (fails loud on missing secrets / unreachable local DB). Docs-only branches may skip `preflight` — declare the skip in the PR body. This invariant subsumes the worktree step already required by the autonomous-ship gate below; that gate is one caller, not the only one.

12. **Work in flight is declared in the ledger, not held in a head.** The moment a branch starts work traceable to a `BL-`/`DEF-` entry, that entry is marked in the ledger; the marker comes off in the PRs last commit, before the merge, so it never reaches main. (A graduating entrys marker comes off in the same commit that archives it — archives categorically reject in-progress entries, so it cannot ride along.) The form is a bold-run field on the entry's meta line, and it must point at something resolvable:

    ```
    **Status:** IN PROGRESS · **Branch:** feat/whatever
    **Status:** IN PROGRESS · **PR:** #681
    ```

    **Why it is declared and never inferred.** No signal in the corpus means "someone is on this". The tempting proxy — a recent edit — is wrong in the most misleading direction available: `**VERIFIED INCOMPLETE 2026-08-03 — do not archive.**` is an audit stamp on a _dormant_ entry, and reading it as in-flight would sort the least live item to the top of the queue. The ledger only ever reports what an author wrote down.

    **The failure mode this exists to stop is the stale marker, not the missing one.** Work starts, the entry is marked, the PR merges, the marker stays. Six weeks on, the queue claims three things are in flight and none are — and a reader burned once by that stops trusting the other five statuses too. `tests/docs/_metaLedgerInProgress.test.ts` is the enforcement: an in-progress entry must carry a `Branch`/`PR`, the value must be shaped like a real one, **the branch must still exist on `origin`**, archives may not hold in-flight work, and a flight field without the status that explains it fails (so ledger prose and the ledger viewer can never disagree about a state). Every rule is conditional on the entry opting in — an entry that declares nothing is untouched, so the convention costs nothing until it is used and becomes self-enforcing the moment it is. Ledger files are discovered from disk, so a new one is covered by default rather than silently exempt.

    **A claim is read from origin's branches, never from main.** The marker lives on the working branch for exactly as long as the work does, so main is structurally the one place the signal can never appear — which is why a session reading `origin/main` to pick its next task saw `**Status:** OPEN.` on two rows another branch had been holding for six hours. `pnpm ledger:claims` resolves claims across every live unmerged branch on origin. `pnpm preflight` prints that table, so any worktree running preflight sees live claims before its first edit; a docs-only branch that skips preflight per invariant 11 relies on the Stage 0 check below, which is not optional for anyone.

    Pipeline wiring, so this is a step rather than a good intention: **Stage 0**, in the same turn as the worktree and the pane labels, first runs `pnpm ledger:claims --check <ids>` for every entry the branch will close. **Exit 1 means another live branch already declares that row — stop and reconcile.** Exit 2 means the check itself could not be trusted (usage, an unverifiable branch universe, unresolved identity) and says nothing about any other branch: fix the check, and read it as neither a collision nor an all-clear. Then write the marker, commit it, and **push the branch immediately** — a marker that exists only in a local worktree is invisible to every other session, which is the whole defect this closes. **Stage 4.4** removes it in the PR's last commit, before the merge, not in the post-`0  0` turn: a marker that merges into main names a branch the merge just deleted, and the origin-existence rule in `tests/docs/_metaLedgerInProgress.test.ts` then fails on main until somebody clears it. A run that finds no matching ledger entry does nothing — this tracks ledger work, it does not require every branch to have a ledger row.

## Brainstorming gate: autonomous-ship checkpoint (mandatory)

This gate hooks `superpowers:brainstorming` and OVERRIDES its default flow (per the superpowers instruction-priority rule, user/AGENTS.md instructions outrank skill defaults).

**When:** during `superpowers:brainstorming`, at the moment requirements, intent, and design have converged — **immediately before writing the spec document, and before any code.** This is the single human decision point for autonomy.

**What:** STOP and ask the user whether to ship this feature autonomously. Summarize first: the agreed scope, expected complexity/blast radius, and whether the diff is expected to touch UI / DB / advisory-locks. Then ask explicitly: _"Ship this autonomously through to a merged PR?"_

**Branches:**

- **User declines (or no answer):** continue the normal interactive flow — write the spec, pause for the user's spec review, then plan with a user plan-review gate, etc. Default behavior; nothing is waived.
- **User approves:** drive the full autonomous pipeline — relocate into a fresh worktree off `origin/main` (`pnpm install`; then `pnpm worktree:link-env` to symlink the gitignored `.env.local` from the main checkout, then `pnpm preflight` to fail-loud on any missing secret / unreachable local DB before tests run; `--no-verify`); check and mark the ledger entries in progress, and push the branch (invariant 12); spec → self-review → Codex `adversarial-review` to APPROVE (no round budget); plan → self-review → Codex `adversarial-review` to APPROVE (no round budget); TDD-per-task implementation honoring every plan-wide invariant (incl. the invariant-8 impeccable dual-gate if UI is touched, and migration→validation parity); whole-diff Codex cross-model review to APPROVE; push → **real CI green** (not just local) → `gh pr merge --merge` → fast-forward local `main` (verify `rev-list --left-right --count main...origin/main` == `0  0`). Both user-review gates (spec, plan) are WAIVED; stop only for a genuine, unresolvable ambiguity.

This pipeline is the authoritative definition (it lives here in the tracked repo so it is cross-CLI durable). A local convenience command `/ship-feature <description>` runs the same pipeline triggered explicitly, but `.claude/` is gitignored on this repo, so that command is per-machine and may be absent in a fresh checkout — never rely on it existing; rely on this section.

### Never end your turn mid-pipeline (the dominant failure mode)

An autonomous run's expensive failure is not a bad diff — it is a **turn that ends while the pipeline is live**. Nobody is babysitting, so the session simply sits dead until a human notices. Two audited runs on 2026-07-19 each burned **~6.4h of idle wall clock**: one stopped after Task 3 of 9 to file a status report at a task boundary; the other's final words were "Starting Stage 2 now." with no tool call after them. Neither hit an error, a usage limit, a wedge, or a genuine ambiguity. Separately, PR #482 sat `CLEAN` with green CI, unmerged, for 5 hours. Combined productive work across both runs: ~2.5h.

Binding rules for any autonomous run, under any harness:

- **Never announce an action instead of emitting it.** If you write that you are about to do something, the next thing in that turn is the tool call that does it.
- **Never end a turn to report progress.** Report inline, while continuing. Reporting is never the terminal act of a turn.
- **Never re-ask for authorization.** Approval at the gate (or `/ship-feature`) is the consent. When woken mid-pipeline by anything — a notification, a `status?` — resume the next action immediately; do not offer "proceed, or pause here?"
- **Never dispatch a background subagent and end the turn.** Run subagents synchronously or work inline. One run dispatched three implementation tasks to background agents, ended its turn each time, and survived only on notification luck until the last notification was consumed.
- **Context pressure is not a reason to stop.** One run reasoned "the remaining pipeline won't fit in this context," adopted a handoff posture, and handed off to nobody. Continue and let the harness compact; if a handoff is genuinely required, dispatch it in the same turn.
- **Green CI is not a stopping point.** `gh pr merge --merge` follows CI-green in the same turn.

The run is complete only when `git rev-list --left-right --count main...origin/main` reports `0  0`. Ending a turn before that is a pipeline failure regardless of how much work got done.

**Asking is allowed; asking silently is not.** None of the above makes a decision that is genuinely the user's — scope, the disposition of a P0, which of several defensible designs ships — into the run's decision to make. Autonomy covers execution, not the user's calls, and a run must not reason its way into deciding one alone because stopping feels like a violation. What the rules forbid is re-asking for _authorization_ already given, which is a different act.

The real cost is not the question, it is the silence around it. `AskUserQuestion` ends the turn and emits **no stop event**, so no `Stop` hook can see it and no gate in this document applies. Measured 2026-07-25: 62 asks in a 19-hour window blocked 17.1h of wall clock; the five longest (339m, 290m, 200m, 47m, 36m) each landed right after an adversarial-review verdict, and each sat unseen. So when a run asks, all four of these, every time:

1. **Drain the answer-independent work first.** Whatever does not depend on the answer happens _before_ the question. Anything left behind the ask is dead wall-clock charged at the user's response latency — one of the five stalls had three untouched tasks sitting behind it.
2. **`PushNotification` in the same turn**, immediately before the ask, naming the decision in one line. It is the only mechanism that reaches the user away from the terminal, and the only reason the wait is minutes instead of hours.
3. **Set the marker's `blockedOn`** to what is being waited on — silences the Stop gate and quiets the nudge without cancelling either.
4. **Leave the nudge registered.** On the answer, clear `blockedOn` and resume in the same turn.

Offer a `(Recommended)` option whenever the run has a view; it makes the reply one tap instead of a research task. Having a recommendation is never itself a reason to skip the ask.

**10-minute nudge (Claude Code harness).** A `Stop` gate catches a stop at the moment it happens, but it can stand down, and a session that goes idle any other way has nothing to revive it — no external process can inject a turn into a running REPL. `CronCreate` can: it enqueues a prompt into the session and fires **only while the REPL is idle**, which is exactly the stall state. Stage 0 of an autonomous run registers a 10-minute job (off-minute, `7,17,27,37,47,57 * * * *`, local time — no timezone conversion) that re-reads the pipeline marker and resumes the next action; Stage 4.4 `CronDelete`s it. The prompt must run `date` first and treat the shell clock as the only source of truth, and must explicitly discard any earlier "blocked / out of context / standing down / handing off" framing in the conversation — that stale framing causing a false stand-down is the documented failure mode. **The nudge is cancelled only by shipping or supersession.** `CronDelete` is permitted at exactly two places: Stage 4.4, after the `0  0` check, and the supersession stand-down of a cross-account takeover (below). A genuine blocker does _not_ cancel it — the run sets the marker's `blockedOn` to a one-line description, escalates once, and leaves the job registered. It keeps firing, stays silent while `blockedOn` is unresolved, and resumes driving the moment it clears. Never delete the job because the run seems stuck, because context is tight, or because a handoff is imminent — **including to replace it with a better one.** A run that deleted its registered job mid-implementation so it could re-register a tighter cadence spent that whole window with no nudge at all; register the replacement first, confirm the ID, then delete, or simply leave both.

**The nudge cannot be self-arming, and the gate compensates.** Unlike the Stop gate, which derives its own arming from git, no shell hook can register a cron job — `CronCreate` is a model tool and jobs live in session memory, invisible to any script. Registration therefore remains a Stage 0 model action. What closes most of the gap: the Stop gate fires on _every_ stop attempt, and a session cannot go idle without attempting to stop, so that is the complete trigger surface. Whenever it blocks a strict-tier run whose marker has no `cronJobId`, it appends the `CronCreate` call to its message. A run that skipped Stage 0 gets told at the first moment the omission could cost anything. The soft tier carries a one-line version of the same prompt, since a marker-less autonomous run is exactly the case the gate cannot positively identify.

Deliberately across **all** hours, not just overnight: the audited stalls (05:04→11:24, 04:56→11:22, and 2026-07-25's 05:52 stop after Task 5 of 8) ran well past any night window, and the job self-deletes at Stage 4.4, so it costs nothing when no run is live. Cron jobs are session-only — gone if the REPL process exits — and auto-expire after 7 days.

The cadence was hourly until 2026-07-25 and is now 10 minutes, because **the nudge interval is the worst-case cost of every stall the Stop gate misses** — and the gate misses more than it was credited with (see the arming note below, plus `AskUserQuestion`, which ends a turn without ever emitting a stop event and therefore cannot reach the gate at all: 62 calls in one 19-hour window blocked 17.1h of wall clock, the five longest all firing immediately after an adversarial-review verdict that already carried a `(Recommended)` option). An hourly nudge prices a missed stop at up to an hour of dead session; 10 minutes prices it at ten, for a job that costs nothing while a run is healthy.

**Stop gate (Claude Code harness).** Because no prompt-side rule can catch "announced the dispatch, emitted nothing," Claude Code backs these rules with a `Stop` hook that refuses to end a session while branch work is unfinished.

**Arming is derived from git, never self-reported.** The first version armed only when the run remembered to write a marker at Stage 0 — a guard against unreliable model behavior that depended on reliable model behavior, which is the same weak link it was built to remove. The hook now infers the state from the repo, so nothing has to be remembered: an `FX-worktrees/` checkout, not on `main`, with commits ahead of `origin/main` or a dirty tree, means work is unfinished. Merging and syncing disarms it automatically.

**Which checkout that is comes from the session's tool calls, not its cwd.** Deriving it from the hook's `cwd` field silently disabled the gate for six days (2026-07-19 to 2026-07-25). A session is launched from the main checkout and drives its worktree with `git -C` and per-call `cd`; neither changes the session cwd, so `cwd` reads `/Users/ericweiss/FX-Webpage-Template` on branch `main` for a session's entire life — measured at 100% of events across four concurrently shipping sessions (1829/1322/1266/3200 events each). The `FX-worktrees/` test rejected every one. The gate ran on each stop and returned exit 0 in ~38ms, before even its `git fetch`, leaving `preventedContinuation: false` in the `stop_hook_summary` of the very turns it existed to block. The hook now recovers the worktree from the most recent `FX-worktrees/` path the session passed to a **tool** (Bash command, file path) in the last 600 transcript lines, requiring the path to recur so a single passing mention does not arm it. Consequences worth knowing:

- **Per-session by construction.** Each session reads its own `transcript_path`, so concurrent runs can never derive each other's worktree — an improvement on `cwd`, which was identical across every session.
- **Block counters are keyed by session + worktree**, not worktree alone. On a worktree-only key, a second session that merely inspects a live worktree spends the owner's six-block budget, and the gate stands down on a run that never got a single nudge.
- **`sessionId` in the marker selects the tier.** Stage 0 records the session's UUID (the directory segment of its scratchpad path). A session whose ID does not match gets the soft tier — "unfinished work here" — instead of being ordered to drive a pipeline that is not its own. Absent the field, every session that touches the worktree gets the strict tier, which is the pre-2026-07-25 behavior and still safe.

Two tiers, so failing safe does not wedge ordinary interactive sessions:

- **Strict** — `<worktree>/.claude/ship-state.json` present with `stage` != `"done"`, and either no `sessionId` recorded or one matching this session. Treated as an autonomous run: loud message, quotes `next`, blocks up to 6 no-progress stops.
- **Soft** — no marker, a marker owned by a different session, or git alone saying work is live. Blocks twice, and says plainly that stopping is correct if this is interactive work.

The marker (`{branch, stage, tasksRemaining, next, blockedOn, cronJobId, sessionId}`) therefore no longer arms the gate — it only raises the tier and supplies the next-action text. A non-empty `blockedOn` silences the gate until it clears, matching the nudge's pause-don't-cancel contract.

Safety valves: never re-blocks when `stop_hook_active` is set; stands down past the tier's block budget on an unchanged fingerprint; `touch <worktree>/.claude/ship-gate-off` opts a checkout out entirely. Gate state lives in `~/.claude/ship-gate/`, deliberately **outside** the worktree — an earlier version kept it in `<worktree>/.claude/` and the state file dirtied the very tree it was measuring, resetting the counter every run so the gate could never stand down. That stayed invisible only because this repo gitignores `.claude/`.

The hook lives in the per-machine `~/.claude/` tree, so a fresh checkout or a non-Claude harness will not have it. The rules above are what actually bind; the hook is only their enforcement on one harness.

**Cross-account takeover (multi-workspace).** This machine runs four herdr workspaces, one per Claude account (`CLAUDE_CONFIG_DIR` = `~/.claude`, `~/.claude-account2`…`4`, mapped by a label-keyed `~/.zshrc` hook). When a shipping session hits a usage limit, a session in another workspace may take over the live worktree instead of waiting for the reset. The infrastructure is already cross-account safe — the gate hook is installed identically in every account config dir, gate state is shared at `~/.claude/ship-gate/` with block counters keyed session+worktree, and the marker + worktree live in the shared checkout, visible to all accounts. What does NOT transfer is session-scoped state: the cron nudge (jobs live in session memory) and marker ownership (`sessionId`).

Takeover protocol — a new session, in any account, picking up a live pipeline:

1. Run `date` first; derive pipeline state from `git -C <worktree>` (branch, commits ahead of `origin/main`, dirty tree) plus the marker; explicitly discard the prior session's "blocked / usage limit / out of context" framing — it is stale by definition.
2. Overwrite the marker's `sessionId` with your own session UUID. This flips you to the strict tier and demotes the prior session to soft. Clear `blockedOn` if it names the usage limit.
3. Register your own 10-minute nudge with full Stage-0 semantics — including the supersession check below in the prompt — and write the new `cronJobId` into the marker.
4. Rename your pane **and your agent** to the arc per the pane + agent naming rule below.
5. Resume the marker's `next` action in the same turn.

Never rewrite `sessionId` merely to inspect a worktree — inspection sessions leave the marker untouched and take the soft tier by design.

**Supersession stand-down** — the second permitted `CronDelete` site alongside Stage 4.4, and mandatory in every nudge prompt: after `date`, re-read the marker; if `sessionId` is present and is not yours, you are superseded. `CronDelete` your own job, clear your pane and agent labels (`herdr pane rename "$HERDR_PANE_ID" --clear` and `herdr agent rename "$HERDR_PANE_ID" --clear`), then stand down silently, in that order, and never write to that worktree again. Rationale: `CronCreate` jobs survive a usage-limit pause, so the paused session's nudge WILL fire after the limit resets — without this check, two drivers race on one working tree, the same two-writers race invariant 11 exists to prevent.

**Pane + agent naming (herdr, mandatory).** Every session driving a pipeline labels itself with the feature arc — the branch name — so a human or a takeover session scanning four workspaces sees at a glance which session drives which live pipeline. Two labels, one arc string, always set and cleared together:

- **Pane label** — `herdr pane rename "$HERDR_PANE_ID" "<branch>"` / `--clear`. Names the pane in its tab.
- **Agent label** — `herdr agent rename "$HERDR_PANE_ID" "<branch>"` / `--clear`. Names the agent entry in the corner agent list. Without it every concurrent run reads as the detected agent label (`claude`) and the list cannot distinguish them; the per-agent `terminal_title` is derived from conversation topic and drifts on its own, so it is not a substitute. `herdr agent rename` accepts a pane id as its target, so the same `$HERDR_PANE_ID` drives both commands.

Lifecycle — both commands at every site:

- **Stage 0**, immediately after worktree creation: `[ -n "$HERDR_PANE_ID" ] && herdr pane rename "$HERDR_PANE_ID" "<branch>" && herdr agent rename "$HERDR_PANE_ID" "<branch>"` (e.g. `docs/agent-arc-naming`).
  Same turn, per invariant 12: run `pnpm ledger:claims --check <ids>` for every entry the branch will close (exit 1 means another live branch already declares it — stop and reconcile; exit 2 means the check could not be trusted), then mark each with `**Status:** IN PROGRESS · **Branch:** <branch>`, commit, and **push the branch immediately** so the marker is visible to every other session.
- **Stage 4.4**, after the `0  0` check: `herdr pane rename "$HERDR_PANE_ID" --clear` and `herdr agent rename "$HERDR_PANE_ID" --clear`.
  The ledger marker is NOT cleared here — it comes off earlier, in the PR''s last commit (invariant 12), so it never reaches main at all.
- **Takeover session**: sets both of its own labels to the same arc (protocol step 4).
- **Superseded session**: clears both during stand-down.

`HERDR_PANE_ID` is injected into every herdr pane shell — when it is empty (session not under herdr), skip silently; never guess a pane id. **Rename panes and agents only, NEVER the workspace** — the workspace label is load-bearing for account mapping (the label-keyed `~/.zshrc` hook resolves `CLAUDE_CONFIG_DIR` from it); renaming a workspace silently reverts its new panes to the main account.

#### Silent death: `exit 0`, no `-o` file, no error (2026-07-24 investigation)

Failure shape: `codex exec` runs for minutes doing real work, then the wrapper records `exitCode: 0`, `signal: null`, `killedReason: null`, `failureShape: "no_o_file"` and `status: "no_verdict"`. Nothing appears on codex's stderr — no error, no panic, no `tokens used` footer. The rollout under `~/.codex/sessions/**` ends mid-turn with no `task_complete` and no final assistant message. Full write-up: `docs/agents/codex-silent-death-2026-07-24.md`.

**Root cause is machine-local, not upstream and not the wrapper.** `~/.claude/hooks/reap-idle-codex.sh` (wired to `Stop` **and** `SubagentStop`) SIGTERMs every Codex process tree older than `CODEX_REAP_MIN_AGE` (120s) whenever its liveness gate sees no recent activity — and that gate deliberately does not watch `~/.codex/sessions`, the only path a running `codex exec` writes to. Any dispatch that outlives one turn boundary past 120s is killed. Measured base rate: **379 of 651 (58%)** `codex_exec` sessions with ≥1 tool call died this way between 2026-07-19 and 2026-07-24, across four CLI versions and two models.

The kill is invisible because `@openai/codex/bin/codex.js` is a Node shim that launders it: on a SIGINT/SIGTERM/SIGHUP death of the native binary it re-raises the signal at itself (`:246`) while its own handlers for those signals are still installed (`:224`), so the handler runs instead of the default terminate, Node falls off the event loop, and the shim **exits 0**. SIGKILL propagates correctly only because no handler is installed for it. Filed upstream as [openai/codex#24556](https://github.com/openai/codex/issues/24556) (open, patch prepared, awaiting a contribution invite) — **do not open a duplicate**; our impact measurements are already attached as a comment.

Consequences for anyone dispatching Codex from this repo:

- **A `no_verdict` / `no_o_file` result is not evidence the reviewer found nothing.** Treat it as an infrastructure fault. Do not re-dispatch blindly — three retries of a reaped run cost ~10 minutes and produce nothing.
- **The wrapper now defends itself.** It writes a liveness heartbeat to `$CODEX_HOME/log/codex-guard-heartbeat.log` on every poll where the child produced output, which satisfies the reaper's gate; and it invokes the vendored **native** binary directly rather than the Node shim, so a signal kill now classifies as `killed` / `external_signal` instead of masquerading as a clean empty run. Escape hatches: `CODEX_GUARD_NO_HEARTBEAT=1`, `CODEX_GUARD_NO_NATIVE=1`. `result.json` records `nativeBinaryResolved`.
- **`result.json` gained `recoveredFrom`.** `"rollout_scrape"` means the verdict was recovered from the session rollout after the `-o` write never landed; the recovered text is at `<out>/recovered-from-rollout.txt`.
- **Dispatches not routed through codex-guard are still exposed** — the heartbeat lives in the wrapper. This is one more reason direct `codex exec` should go through it.
- **The durable fix is in the hook, which is per-machine config outside this repo.** Applied on the origin machine 2026-07-24 and recorded in `docs/agents/codex-silent-death-2026-07-24.md` §8: `recent_log_activity()` now globs today's and yesterday's `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` (bounded to two day-directories, so the archive stays out of the scan); `CODEX_REAP_MIN_AGE` raised 120s → 600s; the `SubagentStop` wiring dropped, leaving only `Stop`; and every signalled process is now named in `~/.claude/hooks/codex-reap-kills.log` (pid, age, rss, role, command line) instead of only counted. **Any other machine or checkout needs the same three edits applied by hand** — the hook is not tracked here. A machine that has no such hook does not have the bug.
- **Diagnosing a recurrence:** the reaper's last action is in `~/.claude/hooks/.reap-codex-last`; a `reaped N procs (… live root(s))` line whose timestamp matches the death is the confirmation. `durationSecs` in `result.json` is quantised to `POLL_INTERVAL_SECS` (10s) and overestimates by up to that much — do not read precise timing from it.

## Cross-cutting discipline (from milestone retrospectives)

These are derived rules from M5-M11 retrospectives. They are not as load-bearing as the plan-wide invariants above but recur across milestones often enough to deserve durable repo-level documentation. Cite + apply when the relevant surface is in scope; mention in commit messages + handoff docs as pre-emption against adversarial-review relitigation.

- **PostgREST DML lockdown for RPC-gated tables.** Any table whose mutations should ONLY flow through a SECURITY DEFINER RPC MUST also have `INSERT`/`UPDATE`/`DELETE` REVOKEd from `authenticated` (and `anon`) at the schema level. RPC body checks (advisory locks, active-roster gates, JWT claims) are bypassable if the caller hits the table directly via PostgREST's `from('<table>').insert/update/delete` builder — the RPC is one entry point; the table is another. Plan-time checklist for every new RPC-gated table: REVOKE migration + structural meta-test pinning the invariant. (Surfaced M9.5 R5+R6 HIGH on `crew_member_auth`+`crew_members`; broader lockdown filed as `BL-ADMIN-POSTGREST-DML-LOCKDOWN` in BACKLOG.md.)

- **Every migration must reach the validation project; the `validation-schema-parity` gate enforces it.** `supabase db push` is BLOCKED on the persistent validation project `vzakgrxqwcalbmagufjh` (Phase-0 history divergence), so each new/altered migration is applied surgically — `supabase db query --linked "<SQL>"` or `psql "$TEST_DATABASE_URL" -f supabase/migrations/<file>.sql`, then `notify pgrst, 'reload schema';`. This is easy to forget per-migration and DRIFTS SILENTLY — a committed migration's `public` columns/tables can be missing live, surfacing as a degraded feature in production. **Post-migration checklist (lands in the same PR as any `supabase/migrations/**`change):** (1) apply locally + test (TDD invariant 1 already requires the local apply); (2)`pnpm gen:schema-manifest`(introspects the LOCAL all-migrations-applied DB →`supabase/**generated**/schema-manifest.json`) and commit the regenerated manifest; (3) apply the migration to the validation project surgically. The `validation-schema-parity` CI job (`tests/db/validation-schema-parity.test.ts`, in `x-audits.yml`) then asserts validation is a SUPERSET of the manifest — Layer 1 (DB-free tripwire) fails if you skipped step 2 for a new table or column; Layer 3 (local-stack freshness equality, in `unit-suite-db`) catches a stale manifest EXACTLY, including anything about functions — the DB-free layer deliberately makes no function claim, since DDL text is not a function identity; Layer 2 (psql vs `TEST_DATABASE_URL`) fails if you skipped step 3. Public schema only; the `dev.\*` shadow schema is local-seed infrastructure, not a deploy target.

- **Byte-comparison CI gates must pin BOTH the Docker image AND the host architecture.** Any CI gate asserting byte-level equality against a committed baseline (image diff, fixture parity, golden-file checksum, PDF page hash, anything non-text) MUST pin its execution environment, not just its capture script. Deterministic-looking scripts produce different bytes across OSes, Node/encoder versions, font hinting, Skia builds, and **host architecture** — arm64 dev hosts diverge from native-x64 CI runners even on an identical pinned Docker image tag. Pin via Docker image (`mcr.microsoft.com/playwright:vN.M.K-jammy` for Playwright workloads); regenerate baselines FROM the pinned image with `--platform linux/amd64` on arm64 hosts, never from a dev machine. Tie the Docker image tag to the package.json dependency version via a structural meta-test. (M11 Phase F R3+R5.)

- **Local-passes-CI-fails is its own bug class.** Local + Docker-on-dev + cross-CLI adversarial-review APPROVE is NECESSARY but NOT SUFFICIENT for CI-bound surfaces. Every milestone with new CI surface should treat "real CI green" as a separate close-out gate from "local + adversarial-review green," not a derivative one. Pattern: enable `workflow_dispatch:` on any CI workflow during the milestone so close-out can verify it via `gh workflow run` without waiting for the next cron/PR firing. (M11 Phase F R4 converged APPROVE locally but the first real Actions run revealed 4 distinct environment gaps.)

- **Mocked-only tests invite tautological APPROVE.** Adversarial review of audit / drift-detector / external-integration scripts MUST include a live-integration probe; mocks-only review observes what the test author thought the surface required, not what it actually requires. Structural defenses: live-integration smoke test + structural meta-test for producer pattern. (X.6 R1 retroactive REVERSAL 2026-05-20 surfaced 3 P0s a mocks-only review missed.)

- **Whole-milestone close-out is its own gate.** Per-pin / per-cluster / per-task reviews catch surface bugs in their scope; integration bugs (cross-pin composition, copy violations on shipped surfaces, missing guards, cross-phase contradictions) need a separate whole-milestone fresh-eyes pass. Don't claim milestone done until BOTH the per-task gates AND the whole-milestone fresh-eyes pass APPROVE. (M9 C3, M10 close-out, M11 Phase F+G all confirm.)

- **Class-sweep before patching adversarial findings.** When review surfaces a bug, grep the codebase for the same bug SHAPE (not the named instance) BEFORE patching only the named instance. Per-instance whack-a-mole burns review rounds without converging. Specify the bug shape + an explicit `rg` procedure; structural meta-tests must walk every file in the relevant subtree, not lexically scan a named file list. (Plan-wide writing-plans rule already covers "same-vector recurrence triggers comprehensive re-analysis" after 3+ rounds; this is the pre-emptive form: class-sweep on every finding, not after the third.) **This applies at EVERY round including round 1, to docs as well as code:** on any spec/plan finding, sweep the whole document for the same shape before resubmitting. Drip-feed — one test-shape finding per plan round, four consecutive spec rounds on a single watchpoint — was the dominant round-multiplier after speculative design in the 2026-07 retrospective (#478 WI-5 burned spec R2–R5; crew-row-controls plan burned 11 rounds largely one test-body defect at a time). Sweep to a derivation, not a longer list: a sweep verified by enumeration re-opens the moment someone adds a site, so its output is a derived cover — a registry asserted against the scanner, a field list derived from the fixture, a filesystem walk — and the filing measured the enumerated form failing three consecutive rounds on the very arc that cites this rule (`docs/review-rounds/feat/review-round-economy/48b280b949cc.md`, rule 3).

  **Repair direction under same-axis recurrence (2026-08-15).** The same-vector-recurrence trigger says WHEN to stop patching per instance; this says WHICH WAY the class repair points when the surface is a recognizer. When successive rounds each widen it — one new grammar feature, lexer case, or input family per round — the class-level repair is NARROWING: decline to fire on what the recognizer cannot classify and file the documented limit, or take the `2d9d0ba11`-style kill (split the hardening out of the shipping PR). Never parser growth — each widening is a bigger target for the next round, a rule the briefs already state to the REVIEWER while nothing bound the implementer. Measured on feat/speclint-prose-count-parity: 15 consecutive one-grammar-corner fix commits, a detector at 1207 lines with a 1992-line suite, and the finding rate still flat at diff round 20.

  **Disposition — the sweep fixes what it can, and every peer it does not fix states why.** Finding the class is half the rule; the other half is what happens to the instances it turned up, and the rule above is silent on it. **Default: every instance of one shape is repaired in the same PR.** The marginal cost of instances 2..N is near zero while you are already in that code holding the context; each deferral costs a full pipeline (worktree, spec, two adversarial reviews, CI, merge) to re-earn context you had for free. Deferring a peer is legitimate, but it is the EXCEPTION, and the `BL-`/`DEF-` entry must name which exception applies: (a) it needs a product or design decision the current PR cannot settle; (b) a ratified scope decision already fences it; (c) the repair is a redesign of a surface the PR does not otherwise touch, or spans enough sites to blow the review scope. **"Same defect, different file" is never sufficient on its own** — that is precisely the case the default covers. A filing that cannot name (a), (b), or (c) is work the sweep should have finished. Worked example to copy: `feat/sync-feed-undo-announce` (PR #694) repaired the failure-announcement defect on all three feed action buttons in-branch, then filed three peers each naming its reason — copy is an unsettled product decision (`BL-FEED-BUTTON-SUCCESS-ANNOUNCE`), a ratified out-of-scope fence (`BL-BULK-UNDO-ANNOUNCE-UNMOUNT`), and nineteen sites at M-per-surface (`BL-ANNOUNCE-REGION-UNMOUNT-CLASS`).

- **Compacting another session's pane (2026-08-16).** **The three sending modes ship DISABLED** — `--checkpoint`, `--compact` and `--resume` refuse before observing anything and name `BL-PANE-COMPACTION-SEND-AUTHORIZATION`; what ships is the classifier and the read-only surfaces (default report, `--check`, `--json`). Five adversarial rounds produced a P0 in every round, all in the send path from round 3 on, and two repairs introduced the next round's defect; the evidence is in `docs/review-rounds/feat/orchestrator-pane-compaction/7d332074ec97.md`. The protocol described below is the design the fenced modes will implement, not current behaviour. A session cannot compact itself — `/compact` is human-typed and auto-compaction fires at a threshold nobody chooses — so every compaction a long-running arc experiences lands at a position selected by nothing. An orchestrator can preempt that on the panes under its purview: `pnpm panes:compact` classifies the live `herdr` roster by context pressure (which gates eligibility) and arc position (which selects the moment), and `--checkpoint` / `--compact` / `--resume` drive one named target, each revalidating independently and returning immediately so the orchestrator sequences them rather than a script owning a multi-hour wait. Four rules are load-bearing and easy to lose: **nothing ever interrupts** — Esc was removed after two rounds found four defects on that one surface, and the driver tests pin the absence of any `\x1b` byte on both the dry-run and live send paths; **the checkpoint is proved by a single-use nonce**, not by an mtime, because any concurrent marker writer satisfies an mtime; **`--resume` has its own predicate**, since a successful compaction makes `COMPACT`/`FORCE` false exactly when resuming is correct; and **`--as <sessionId>` is always explicit**, because orchestrator panes have no worktree and so nothing can infer it. The bands, the twelve-rule precedence, the probe findings, and the absent-versus-mismatched traps (`gh` exits 1 for "no PR" and for auth failure alike) live in `docs/agents/orchestrator-pane-compaction.md`; the design is `docs/superpowers/specs/2026-08-16-orchestrator-pane-compaction-design.md`. Not restated here, because two copies drift.

- **Ledger filing bar (2026-08-04).** A `BL-`/`DEF-` row asserts work someone should schedule, so it carries the same admissibility bar as a review finding: filed with probe evidence (command + output, or a cited live mutant/test) OR a stated reachable live surface. A hypothetical whose worst case is conservative behavior plus a surfaced signal is a DOCUMENTED LIMIT — it belongs in the owning surface's limits record (spec §, guard-file header, or archive entry with cross-ref), not in the open queue. An entry may be filed unprobed only with an explicit `**Reachability:** INFERRED, NOT PROBED` field naming the probe that would settle it — and the probe, not the entry, is then the first scheduled step. Screen precedent and demotion procedure: `docs/superpowers/specs/2026-08-04-backlog-convergence-design.md` §2.

- **A guard states its premise executably (2026-08-04, `BL-GUARD-PREMISE-REACHABILITY`).** An assertion discriminates only under some condition — a fixture past the boundary, an environment richer than empty — and PR #701 shipped three guards whose condition was false where they ran, so they passed unconditionally and would have forever. The rule, the five measured shapes, and the placement constraint live in `docs/agents/writing-plans.md` under the anti-tautology rule; the helper is `tests/_shared/premise.ts`. Not restated here, because two copies drift.

- **Pre-code mechanical UI gate (2026-07-19 retrospective).** Before implementing any UI surface — and before the impeccable dual-gate, which is a verifier, not a discovery mechanism — run the already-written mechanical invariants as a pre-code checklist: em-dash ban in user-visible copy, apostrophe literals, 44px tap targets (`min-h-tap-min` and companions), canonical type/token classes (`text-xs/relaxed`, `text-subtle`). Pin contrast ratios for any NEW or repurposed color token in `DESIGN.md` with a contrast meta-test at spec time (the `bg-warning-bg` pattern from #500). ~50 impeccable P1–P3 findings in one month were pre-written invariants discovered post-code; each cost a fix commit + partial gate re-run that the checklist makes free.

- **§12.4 catalog row edits require three lockstep updates.** Editing any field on an error-code row in master spec §12.4 requires three updates landing in the same commit: (a) the master spec §12.4 prose at `docs/superpowers/specs/2026-04-30-fxav-crew-pages-v1.md`, (b) regen `pnpm gen:spec-codes` to refresh `lib/messages/__generated__/spec-codes.ts`, (c) update the matching row in `lib/messages/catalog.ts`. The `x1-catalog-parity` CI gate (`tests/cross-cutting/codes.test.ts:69`) compares the runtime catalog ↔ §12.4 prose directly — if any of the three drifts, x1 fails and blocks merge. Pre-commit checklist for any §12.4 prose edit: re-run `pnpm gen:spec-codes` + grep `lib/messages/catalog.ts` for the matching row + confirm both staged in the same commit as the spec edit. Applies to NEW rows too (insert in §12.4 + regen + add to catalog.ts), not just edits. (M12.1.) Applies to warning-card codes too: a new warn-severity ParseWarning code also gets a WARNING_CARD_COPY_CODES row + copy per docs/superpowers/specs/2026-07-20-warning-card-copy-restore.md §4.2.

- **API gateway `apikey` validation is independent of PostgREST JWT validation.** Any test scaffolding that bypasses PostgREST's session layer (typically: self-sign a JWT with the project's JWT secret, send as `Authorization: Bearer <jwt>`) must ALSO send a valid `apikey` header — and the Supabase API gateway accepts ONLY Supabase-issued keys (publishable or legacy anon JWT) for `apikey`, NOT the self-signed JWT. Two separate layers: the gateway validates `apikey` first (rejects unknown keys before forwarding); PostgREST then validates `Authorization: Bearer` for row-level role. Local Supabase is lenient on `apikey` and silently masks this — strict rejection only surfaces against real validation/prod. Pattern: Supabase-issued key for `apikey`; self-signed role JWTs go ONLY in `Authorization: Bearer`. (Surfaced Phase 0.B postgrest-dml-lockdown; local passed, real CI flagged it.) The Supabase **JWT Signing Keys migration is non-disruptive for HS256-signed `Authorization: Bearer` JWTs** — PostgREST still verifies against the legacy JWT secret; only the gateway's `apikey` acceptance got stricter.

- **Heavy local phases run under the machine-wide slot semaphore.** `pnpm heavy <cmd>` (equivalently `python3 scripts/with-heavy-slot.py -- <cmd>`) takes one of N flock'd slots in `/tmp/fx-heavy-slots` and then `execvp`s into the command, so the command IS the wrapper process: the caller sees its exit status unchanged, the environment is untouched apart from one reentrancy marker, and a crash — SIGKILL included — releases the slot at process death with zero cleanup code. This exists because roughly nine concurrent arcs, each individually well-behaved and each free to run a full suite, exhausted this machine's memory on 2026-08-10 (12 `vm-compressor-space-shortage` JetsamEvents, hard reset, ~2 h of wall clock lost across every live arc); no other layer imposes admission control ACROSS worktrees. Classification is by INVOCATION SHAPE, never by alias.

  Admission now REAPS FIRST. The `heavy` script is `tsx scripts/heavy-reap.ts --kill --quiet; python3 scripts/with-heavy-slot.py --`, so whenever anyone wants a slot, heavy-phase workers that outlived the harness owning them are cleared before the queue is joined. The semaphore bounds how many phases may START, and nothing bounded how long a worker may LIVE once its parent died, which on 2026-08-16 left eleven orphaned vitest workers burning a core each for over a day. The two commands are sequenced with `;` and never `&&`, so a reaper that errors, hangs to its own bounded timeout, or is absent cannot block admission, and the wrapper then runs with byte-identical argv and its own exit status intact. The wrapper stays the LAST segment because `pnpm` appends the caller's arguments to the END of the script body; a reaper placed after it would capture the caller's command instead. `scripts/with-heavy-slot.py` is untouched by this. Run the tool by hand as `pnpm heavy:reap`: it REPORTS and kills nothing by default, `--kill` is required before it signals anything, `--all` widens the report only and never the kill set, and `FX_REAP_MIN_AGE_S` overrides its 4 h age floor. It is deliberately not itself wrapped — one bulk `ps` read plus at most one more per kill target — since wrapping it would deadlock it against the semaphore it runs in front of. Spec: `docs/superpowers/specs/ci/2026-08-16-heavy-orphan-worker-lifetime-design.md`.

  Trigger 2 is a `Stop` hook, and like the codex-guard shim it is per-machine config this repo cannot install. Trigger 1 above already covers the contended case, so a checkout without the hook is DEGRADED rather than unprotected, which is the difference from the codex reaper whose absence leaves nothing at all. Install one-liner for other machines and checkouts:
  `mkdir -p ~/.claude/hooks && printf '#!/bin/sh\nexec pnpm --dir "$HOME/FX-Webpage-Template" heavy:reap --kill --quiet\n' > ~/.claude/hooks/heavy-reap.sh && chmod +x ~/.claude/hooks/heavy-reap.sh`
  Then register it under the `Stop` key of `$CLAUDE_CONFIG_DIR/settings.json`, the same file and key the codex reaper uses. `pnpm --dir` is load-bearing: the hook runs with an arbitrary cwd, and `tsx` resolves out of the repo's own `node_modules`, so a bare `pnpm heavy:reap` finds neither the script nor the interpreter. This machine has four Claude config dirs (the default plus three per-account siblings, per the cross-account section above), so the registration is repeated per config dir or the hook is live in only one account.

  **MUST wrap** — any full-suite vitest run: `pnpm test`, `pnpm test:fast`, or any `vitest run` not scoped to an explicit file list. Any non-interactive playwright run: `pnpm test:e2e` and its scoped-config aliases, any `playwright test` without an interactive flag, plus the screenshot captures `pnpm screenshot:gallery` and `pnpm screenshot:help` (their config runs an inner 8192 MB build, `playwright.screenshots.config.ts:128`). Any build: `pnpm build`, direct `next build`, or a `next build` run through `scripts/with-admin-dev-flag.mjs` — that script's own build lock is WORKTREE-LOCAL, because `ROOT = process.cwd()` (`scripts/with-admin-dev-flag.mjs:42`) and the lock file lives under that root (`scripts/with-admin-dev-flag.mjs:97-98`), so it bounds nothing across worktrees. The mutation harness: `pnpm mutation:guards`, `pnpm mutation:browser` (its gate spawns a real Playwright child per mutant), any `--project mutation` run, one slot per concurrently-running shard batch. **Transitive shape rule:** a command is classified by what it TRANSITIVELY launches, not by its own surface shape, so an explicitly-scoped or non-suite outer command whose body spawns a heavy phase is wrapped at its own outermost entry. Current known members: `RUN_BUILD_ARTIFACT_GATE_TEST=1 pnpm vitest run tests/admin/build-artifact-gate.test.ts` (scoped vitest, but its helper runs `pnpm build` twice, `tests/admin/build-artifact-gate.test.ts:73`; the env gate is load-bearing — without it the suite is `describe.skipIf(!RUN)` at line 103 and stays unwrapped) and `node scripts/share-link-flash-adversary-matrix.mjs` in full mode (it runs non-interactive playwright, `scripts/share-link-flash-adversary-matrix.mjs:1014`; the mode is load-bearing — `--quick` spawns none and stays unwrapped, line 1215). The derived cover is the sweep `rg -n -U 'execFileSync\("pnpm",\s*\["build"\]|execFileSync\("pnpm",\s*\["test:e2e'` over `tests/` + `scripts/` — rerun it when authoring changes to either tree rather than trusting that member list.

  **MUST NOT wrap** — any INTERACTIVE playwright invocation, identified by shape: `--ui` (including the `pnpm test:e2e:ui` alias), `--debug`, or a `PWDEBUG`-set environment. These are unbounded-lived and a slot held indefinitely starves every other arc; run them unwrapped and sparingly. Scoped vitest runs with an explicit file list, `pnpm typecheck`, `pnpm exec eslint .`, `pnpm format:check`, codex dispatches, CI polling, git/gh operations, and spec/plan authoring all stay unwrapped — wrapping them would put the phases that dominate arc latency behind a queue they never needed. Long-lived servers start OUTSIDE the wrapper: `next dev`, `next start`, and pre-warmed dev servers hold a slot for their whole lifetime, and the suite hitting them is the heavy phase, not the server.

  Wrap the OUTERMOST command only — an inner wrap under a live holder passes through with a surfaced notice instead of self-deadlocking, so it is harmless, not correct. Closeout and CI-stage runs set `FX_HEAVY_PRIORITY=1`, a best-effort bias toward the nearest merge rather than a queue position. NEVER set `FX_HEAVY_SLOT_DIR` in a production session: two dirs are two independent semaphores and the divergence is undetectable by design (tests point it at a per-case tmpdir, which is why the suite is safe to run under the wrapper). Capacity changes go through `python3 scripts/with-heavy-slot.py --recreate --slots <N>` ONLY — editing `config` by hand or `rm -rf`ing a live slot dir hand-builds the recreation races `--recreate` exists to prevent. Spec: `docs/superpowers/specs/2026-08-10-heavy-phase-semaphore-design.md`; guard: `tests/docs/agentsHeavyPhaseRule.test.ts`.

## Cross-CLI orchestrator discipline

These rules govern how prompts, briefs, and review focus text compose across CLI boundaries (Claude Code ↔ Codex). Apply when authoring any artifact a non-Opus implementer or reviewer will consume.

- **Memory files at `~/.claude/projects/<workspace>/memory/` are Opus-internal infrastructure.** Codex CLI cannot read them; fresh Opus subagent sessions do not auto-load them. They are also per-ACCOUNT under the multi-account herdr setup (`~/.claude-accountN/projects/<workspace>/memory/`) — a memory written in one account's session is invisible to the other three, including a cross-account takeover session resuming the same pipeline. NEVER cite memory file paths in Codex-bound prompts (kickoff briefs, review focus text, anything pasted into a Codex session) — the citation conveys zero information to Codex. When a load-bearing principle lives in a memory file and is needed cross-CLI or cross-account: (a) inline the principle in 1-3 sentences in the prompt itself, (b) promote it to AGENTS.md / a plan file / a handoff doc — the repo is the only durable cross-CLI, cross-account source of truth. Audit every Codex-bound prompt for `feedback_` or `~/.claude/projects/` matches before sending; any match is a leak.

- **Fresh-eyes posture in whole-milestone adversarial review.** Whole-milestone close-out reviews MUST anchor the reviewer's posture as "treat the entire diff as if you have not seen it before" — distinct from in-task reviews where the reviewer follows an iteration thread. The codex-companion template enforces this structurally for `/codex:adversarial-review`; for manual Codex CLI session briefs, the orchestrator must explicitly state the fresh-eyes posture and bound the focus text to a secondary regression checklist, not a primary review-direction signal.

- **Disagreement-loop preempts in review focus text.** Identify contracts the reviewer is likely to relitigate (intentional placeholders, scope-deferral decisions, ratified spec amendments, "won't ship until M<n+1>" exemptions, design choices the implementer already justified). Include an `EXPLICITLY DO NOT RELITIGATE: [list]` block in the review focus text, citing the ratification at `file:line` so the reviewer can verify the contract without re-deriving it. Cheap to author, expensive to omit.

- **Manual Codex CLI session briefs are self-contained.** When falling back from `/codex:adversarial-review` to a manual Codex interactive session (e.g., when the companion's `--background` mode produces a placeholder stub), the brief MUST embed everything the reviewer needs: fresh-eyes posture, scope, do-not-relitigate list, focus surfaces, expected output format, AND an explicit instruction NOT to invoke nested cross-model reviews (`/codex:adversarial-review`, the companion script, `/codex:review`) from within the Codex session — that would spawn cross-CLI loops or duplicate work. The reviewer's verdict comes from THEIR direct assistant output, not from a delegated sub-review.

- **Exhaust the vector per round — reviewer side (2026-07-19 retrospective).** Every adversarial-review brief instructs the reviewer: "Enumerate ALL instances of each finding class you identify in THIS round. A repeated vector dripped one instance per round is a review defect, not thoroughness." This is the reviewer-side twin of the implementer class-sweep rule; both sides must hold or the round count is set by whichever side drips.

- **Late-arc briefs state the closed criterion only — never point the reviewer at a fresh open axis (2026-08-15).** A brief past the round cap that says "the remaining high-value attack is X" mints the next rounds itself: the speclint-prose-count-parity round-17 diff brief named "reading the shipped accept-sets against the spec's normative text" as the remaining attack, and rounds 17-20 each returned one finding on exactly that axis. Once bound, fence, and probe domain are stated, the brief's only remaining instruction is "find nothing admissible → say so plainly and APPROVE." Opening a new axis after the cap is a re-scope decision that belongs to the orchestrator (ship-and-fence, documented limits, or mechanical oracle — the hook's three options), not a line in a review brief.

- **Convergence criterion, not just admissibility — the half that was always dropped (2026-08-04 measurement).** The admissibility contract below gates finding QUALITY. Nothing gated round COUNT, and the result is measured: 474 review rounds across 16 concurrent sessions, with arcs at 41 / 40 / 38 / 33 / 30 / 28. Seven were diagnosed and every one had the same shape — 70-80% of findings were "the guard does not pin what it claims", genuine design gaps front-loaded in rounds 1-4 and then stopped, and the deliverable ratcheted into a recognizer ("add `-X` at 71 psql sites" became a 2929-line shell-grammar parser; an 83-line component grew 3000 lines of guard tests with ZERO product-code change after round 2, killed by hand at `2d9d0ba11`). BLOCKING findings per round do **not** decay: 0.32 in rounds 1-3, 0.38 in rounds 11+. Medium is irrelevant — a code diff burned 41 rounds, prose burned 40.

  Zero briefs in that corpus stated a closable bound; several named an enumeration as the convergence criterion outright, one in the same sentence as "enumeration does not terminate". So **every guard/detector review brief MUST state all three**, and `~/.claude/hooks/review-convergence-gate.sh` blocks the dispatch when it does not (override `CONVERGENCE_ACK=1`, cap `REVIEW_ROUND_CAP`, default 4):
  1. **Consequence bound** — "every input is handled correctly OR signaled, never silently wrong; a conservative demote plus a surfaced warning is a DOCUMENTED LIMIT, not a finding." Closable — IF it ranges over the finite domain of bullet 2. A bound quantified over an open grammar is the unbounded form wearing the closable one's clothes: the feat/speclint-prose-count-parity diff brief stated bound and fence verbatim, but its bound — "never flagged wrongly", quantified over all CommonMark+JS documents — made every constructed grammar corner an admissible false-advisory probe, and the arc ran 20 diff rounds with the finding rate FLAT (1-2 per round from round 9 through round 20, zero decay) while the detector grew a JavaScript lexer one grammar corner per round (corpus: `docs/review-rounds/feat/speclint-prose-count-parity/`).

  2. **Probe domain (2026-08-15)** — a `PROBE DOMAIN:` line naming the enumerable input set an admissible probe must be drawn from: a live corpus path (`docs/**`), a fixture directory, a registry. A probe outside the domain, or more than one ordinary edit away from an input in it, files to documented limits, not to a finding. The closable statement of the speclint arc's intent is "zero false advisories on the live corpus" — finite, settled mechanically by a corpus scan the way a mutation score settles a suite claim. The hook blocks a detector brief without the line.
  3. **Threat-model fence** — who the guard defends against. "Accidental authoring mistakes by an ordinary contributor; adversarial obfuscation is out of scope and files to documented limits." Without it the scope ratchets, and a wider recognizer is a bigger target for the next round. The fence and the probe domain are two renderings of one boundary — the fence names WHO is out of scope, the domain names WHICH INPUTS are — and every admissibility clause must cite them (contract clause (e) below), because a fence the admissibility clauses do not reference loses to the wider clause every time.

  4. **Score, when the surface is enrolled.** If the subject is a guard surface enrolled in the source-mutation registry (`tests/mutation/source/registry.ts`; spec `docs/superpowers/specs/ci/2026-08-04-source-mutation-guard-gate.md`), the brief states the convergence criterion as **the mutation score plus an empty unaccepted-survivor set** — both machine-computed, neither a matter of opinion. A "the guard does not pin what it claims" finding is then admissible **only with the surviving mutant that demonstrates it**: an operator and a site, both from the declared set. If no declared operator produces a surviving mutant for the claimed gap, the finding is refuted, or it is an operator proposal — a registry change carrying its own before/after numbers — and neither is a round on the current diff. When the subject of a review IS a guard, proof, or equivalence surface the registry can express (a lib module or script whose defect class is "reports OK while the output moved"), enrolment precedes review, and it includes SHAPE: the runner overlays a target only when a Vitest suite imports it, so such a surface is authored as an importable module with a referring suite from the start — not as a terminal CLI script — and is enrolled with `pnpm mutation:guards` run BEFORE the first dispatch, the score plus the unaccepted-survivor set stated in the round-1 brief. Two arcs measured the cost of deciding this late: the classname equivalence scripts were never enrolled and, as shipped, not even enrollable without restructuring (CLI-shaped — no exports, unconditional `process.exit`, no importing suite), drawing fifty false-pass findings across fourteen diff rounds at roughly 25 minutes of dispatch per mutant (that arc's own figure; the step3 filing records no per-mutant duration); the step3-a11y tap-target suite spent six of nine diff rounds the same way before a later probe showed the registry cannot express that Playwright surface at all (its nineteen mutants are bespoke component edits). An enrolled surface runs in roughly 93 seconds (this block's measured first customer). The step3 outcome is the other branch of the same rule: a surface the registry cannot express is re-dispositioned honestly with the probe that shows it (`docs/superpowers/specs/2026-08-09-quick-wins-2-mech.md` §1.1.4), never enrolled symbolically. (`docs/review-rounds/fix/step3-a11y-cluster/61281c23e8ce.md` diff §, `docs/review-rounds/refactor/classname-array-join-cn/9bd0a8456151.md` diff §.)

  That is bullets 1-3 made mechanical, not a fourth rule to remember. "No escaping input exists" ranges over an infinite space and does not terminate; "no surviving mutant" ranges over a closed operator set applied to a finite program, and does. Enrolling a surface costs one registry row and, for the first customer, ~93s per run (`pnpm mutation:guards`) against roughly 50 minutes of dispatch across five whole-diff rounds. That surface scored 82/84 with 18 `equivalent` and 2 `accepted-gap` rows, and the gate found eleven real gaps in a suite that had already cleared five review rounds — including a `findings.sort(...)` that could be deleted outright with the suite still green.

  "The closure set is the convergence criterion" is the **forbidden** form: enumeration over an open class never terminates. **The gate matches that form on USE, not mention** — it strips quoted and backticked spans before scanning, because a good brief quotes the forbidden phrasing in order to reject it, and blocking that is a use-vs-mention error. Found by running the gate against its own author's brief. This is per-copy behavior like the tally below: a copy without the strip flags both the brief that commits the error and the brief that warns against it, and only the second author is confused by it. Install on another machine:
  `printf '#!/bin/sh\nexec bash "$HOME/.claude/hooks/review-convergence-gate.sh"\n'` — the hook itself lives in the per-machine `~/.claude/` tree; this section is the durable contract.

  The hook's advisory finding tally was measured at 48.0% accuracy against 681 real reviewer outputs (`docs/superpowers/specs/ci/probes/2026-08-04-finding-format-probe.md`) because it inferred findings from a numbered-bold pattern. It now reports the reviewer's declared `FINDINGS: <n>` line per round, or says "not declared" — never an inferred count and never a sum. It takes that count from the dispatch's own result.json whenever one carries a `findingCount` key: that is the wrapper's resolved answer and the same value the corpus row holds, and re-deriving it is the only way the two can disagree. Only when no usable result.json survives does it read the message files itself, by the same rule `parseFindingCount` in `scripts/codex-guard.mjs` uses: ONE terminal message per dispatch — the recovered rollout message when the out-dir holds one, else the last attempt message with non-empty content — fenced blocks elided, the pattern end-anchored, and two different declared values treated as "not declared". The two must agree, because an operator sees both; where both exist, the committed corpus row is authoritative and the hook's line is an advisory rendering of it. The hook is per-machine and this machine holds one copy per Claude workspace config dir, so the repair applies to every `$CLAUDE_CONFIG_DIR/hooks/review-convergence-gate.sh` — one under `$HOME/.claude` and one under each `$HOME/.claude-account*` — enumerated from disk, because a config dir added later is invisible to this file. A copy left unrepaired prints the inferred number while this paragraph promises the declared one. This paragraph is the durable contract.

- **Finding-admissibility contract for detector/heuristic and guard surfaces (2026-07-31 round-economy retrospective; full write-up `docs/agents/adversarial-round-economy-2026-07-31.md`).** Review briefs for specs/plans/diffs whose subject is a detector, classifier, text heuristic, or structural/mutation guard MUST state: (a) claims about current behavior or corpus content are settled by probe — the reviewer includes the probe output, and no recognizer/guard tightening is accepted without a probe demonstrating the corruption it prevents; (b) a hypothetical input is a finding only if a probe shows silent corruption or wrong auto-correct — a worst case of conservative-demote-plus-surfaced-warning files to the spec's documented-limits section without a round; (c) for guard/mutation surfaces, a new mutation family requires a live escaping mutant demonstrated against the shipped guard; (d) a forced change later reversed (inline-later-group R21/R27, R53/R55) is a review defect chargeable to the probe-less acceptance — on reversal, fence the decision in both directions in the spec so neither side relitigates it; (e) **every admissibility clause cites the threat fence and the probe domain (2026-08-15)** — a probe input must come from the declared `PROBE DOMAIN:` or be one ordinary edit away from an input in it, and a constructed fixture outside the fence files to documented limits, not to a round. A clause that omits the citation loses to itself: the speclint-prose-count-parity diff brief fenced its threat model to "ordinary authoring mistakes, corpus-shaped input" and then admitted "a concrete document" in the very next section; the reviewer lawfully took the wider clause, and round 20's finding was a thematic-break fixture (`- - -` under a two-item list) that appears nowhere in the corpus.

- **Split tight-scope reviews are the default for large diffs.** Whole-diff `codex exec` reviews died silently (exit 0, no verdict emitted) on four consecutive PRs (#495/#497/#499/#500); the recovery that worked on #500 — two tight file-list reviews — converged APPROVE in 2 rounds. For any diff beyond a handful of files, dispatch scoped reviews per surface (with the file list inlined in each brief) from the start instead of attempting whole-diff first and falling back.

- **Verify every citation in a review brief before dispatch.** A brief citing the wrong path for the invariant-9 registry row (`tests/auth/` instead of `tests/admin/`) produced a false BLOCKING finding and a wasted round on #500. Review briefs are subject to the same live-code citation pass as specs: grep every `file:line` the brief asserts before sending.

- **Log refuted diff-only claims in the triage record.** When a finding is refuted against the mount tree / runtime behavior rather than the diff (Codex reasons from the diff alone and confabulates cross-file state — e.g. the modal-header "stale overlay" MEDIUM refuted by `key={showId}` remount), record the claim AND its refutation in the milestone triage/close-out doc so later rounds and future reviewers do not re-derive or re-raise it. The modal-header close-out §11 pattern ("recorded so a future reviewer does not re-derive it") is the template.

- **REVIEWER ONLY — adversarial review briefs MUST inline the reviewer-never-fixes rule.** Every adversarial-review brief (every round) MUST contain an explicit "Your role: REVIEWER ONLY. Do not fix issues, propose patches as commits, or imply changes you will make. Challenge the implementation approach and surface findings — fixes are the implementer session's job in a separate dispatch." The codex-companion template enforces this structurally, but manual Codex CLI briefs lose that framing unless the orchestrator inlines it. Check: grep every brief for "REVIEWER ONLY" before sending; if absent, the brief is incomplete. (Companion caveat: any brief whose verification commands include `pnpm screenshot:help` MUST also say "After verification, restore committed WebPs via `git restore public/help/screenshots/`" — local capture overwrites the x64-Linux baseline with host-architecture bytes per the byte-comparison discipline above, polluting the tree with bytes that look like proposed changes but aren't.)

## Routing convention

Every milestone has an assigned implementer model+harness, documented in `docs/superpowers/plans/2026-04-30-fxav-crew-pages-v1/ROUTING.md`. When a milestone is delegated across harnesses, the handoff follows `docs/superpowers/plans/2026-04-30-fxav-crew-pages-v1/HANDOFF-TEMPLATE.md`. Read both before starting any milestone.

### Hard rule: UI work is always Opus / Claude Code

Any task whose primary deliverable is UI code is owned by Opus, regardless of which harness owns the rest of the milestone. UI code means:

- Any file under `app/` **except** `app/api/**` (pages, layouts, loading/error/not-found components, route group folders)
- Any file under `components/`
- `app/globals.css`, `tailwind.config.ts`, `postcss.config.mjs`, `DESIGN.md`, design-token / theme files

If you are running under Codex and a task you are about to start lands in any of those locations, **stop**. The task belongs to Opus + the **impeccable v3** skill (`/impeccable` slash command and its setup gates: `context.mjs` context load (PRODUCT.md + DESIGN.md) → register identification). Impeccable v3 superseded the legacy `frontend-design` skill as the canonical UI workflow on this project; do NOT load `frontend-design` for new UI work. Hand back to the orchestrator (Claude Code) for that task. The handoff doc records which tasks split which way.
