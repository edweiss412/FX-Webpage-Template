- **Heavy local phases run under the machine-wide slot semaphore.** `pnpm heavy <cmd>` (equivalently `python3 scripts/with-heavy-slot.py -- <cmd>`) takes one of N flock'd slots in `/tmp/fx-heavy-slots` and then `execvp`s into the command, so the command IS the wrapper process: the caller sees its exit status unchanged, the environment is untouched apart from one reentrancy marker, and a crash — SIGKILL included — releases the slot at process death with zero cleanup code. This exists because roughly nine concurrent arcs, each individually well-behaved and each free to run a full suite, exhausted this machine's memory on 2026-08-10 (12 `vm-compressor-space-shortage` JetsamEvents, hard reset, ~2 h of wall clock lost across every live arc); no other layer imposes admission control ACROSS worktrees. Classification is by INVOCATION SHAPE, never by alias.

  Admission now REAPS FIRST. The `heavy` script is `tsx scripts/heavy-reap.ts --kill --quiet; python3 scripts/with-heavy-slot.py --`, so whenever anyone wants a slot, heavy-phase workers that outlived the harness owning them are cleared before the queue is joined. The semaphore bounds how many phases may START, and nothing bounded how long a worker may LIVE once its parent died, which on 2026-08-16 left eleven orphaned vitest workers burning a core each for over a day. The two commands are sequenced with `;` and never `&&`, so a reaper that errors, hangs to its own bounded timeout, or is absent cannot block admission, and the wrapper then runs with byte-identical argv and its own exit status intact. The wrapper stays the LAST segment because `pnpm` appends the caller's arguments to the END of the script body; a reaper placed after it would capture the caller's command instead. `scripts/with-heavy-slot.py` is untouched by this. Run the tool by hand as `pnpm heavy:reap`: it REPORTS and kills nothing by default, `--kill` is required before it signals anything, `--all` widens the report only and never the kill set, and `FX_REAP_MIN_AGE_S` overrides its 4 h age floor. It is deliberately not itself wrapped — one bulk `ps` read plus at most one more per kill target — since wrapping it would deadlock it against the semaphore it runs in front of. Spec: `docs/superpowers/specs/ci/2026-08-16-heavy-orphan-worker-lifetime-design.md`.

  Trigger 2 is a `Stop` hook, and like the codex-guard shim it is per-machine config this repo cannot install. Trigger 1 above already covers the contended case, so a checkout without the hook is DEGRADED rather than unprotected, which is the difference from the codex reaper whose absence leaves nothing at all. Install one-liner for other machines and checkouts:
  `mkdir -p ~/.claude/hooks && printf '#!/bin/sh\nexec pnpm --dir "$HOME/FX-Webpage-Template" heavy:reap --kill --quiet\n' > ~/.claude/hooks/heavy-reap.sh && chmod +x ~/.claude/hooks/heavy-reap.sh`
  Then register it under the `Stop` key of `$CLAUDE_CONFIG_DIR/settings.json`, the same file and key the codex reaper uses. `pnpm --dir` is load-bearing: the hook runs with an arbitrary cwd, and `tsx` resolves out of the repo's own `node_modules`, so a bare `pnpm heavy:reap` finds neither the script nor the interpreter. This machine has four Claude config dirs (the default plus three per-account siblings, per the cross-account section above), so the registration is repeated per config dir or the hook is live in only one account.

  **MUST wrap** — any full-suite vitest run: `pnpm test`, `pnpm test:fast`, or any `vitest run` not scoped to an explicit file list. Any non-interactive playwright run: `pnpm test:e2e` and its scoped-config aliases, any `playwright test` without an interactive flag, plus the screenshot captures `pnpm screenshot:gallery` and `pnpm screenshot:help` (their config runs an inner 8192 MB build, `playwright.screenshots.config.ts:128`). Any build: `pnpm build`, direct `next build`, or a `next build` run through `scripts/with-admin-dev-flag.mjs` — that script's own build lock is WORKTREE-LOCAL, because `ROOT = process.cwd()` (`scripts/with-admin-dev-flag.mjs:42`) and the lock file lives under that root (`scripts/with-admin-dev-flag.mjs:97-98`), so it bounds nothing across worktrees. The mutation harness wraps through its OWN class: `pnpm heavy:mutation` for `pnpm mutation:guards`, `pnpm mutation:browser` (its gate spawns a real Playwright child per mutant), and any `--project mutation` run, one slot per concurrently-running shard batch. The class is a single-slot admission taken ALONGSIDE an ordinary slot, so at most one score run generates scratch churn at a time while total concurrency is unchanged; `pnpm heavy` alone does not bound score runs against each other. Note `pnpm heavy --class mutation` does NOT work — the `heavy` script already ends in its own `--`, so the flag is swallowed as the command — which is why the class has its own script. A class phase nested under an already-held slot REFUSES with a non-zero exit rather than queueing behind a lock it cannot win; wrap at the outermost entry instead. Spec: `docs/superpowers/specs/ci/2026-08-24-mutation-scratch-fs-event-storm-design.md`. **Transitive shape rule:** a command is classified by what it TRANSITIVELY launches, not by its own surface shape, so an explicitly-scoped or non-suite outer command whose body spawns a heavy phase is wrapped at its own outermost entry. Current known members: `RUN_BUILD_ARTIFACT_GATE_TEST=1 pnpm vitest run tests/admin/build-artifact-gate.test.ts` (scoped vitest, but its helper runs `pnpm build` twice, `tests/admin/build-artifact-gate.test.ts:73`; the env gate is load-bearing — without it the suite is `describe.skipIf(!RUN)` at line 103 and stays unwrapped) and `node scripts/share-link-flash-adversary-matrix.mjs` in full mode (it runs non-interactive playwright, `scripts/share-link-flash-adversary-matrix.mjs:1042`; the mode is load-bearing — `--quick` spawns none and stays unwrapped, line 1243). The derived cover is the sweep `rg -n -U 'execFileSync\("pnpm",\s*\["build"\]|execFileSync\("pnpm",\s*\["test:e2e'` over `tests/` + `scripts/` — rerun it when authoring changes to either tree rather than trusting that member list.

  **MUST NOT wrap** — any INTERACTIVE playwright invocation, identified by shape: `--ui` (including the `pnpm test:e2e:ui` alias), `--debug`, or a `PWDEBUG`-set environment. These are unbounded-lived and a slot held indefinitely starves every other arc; run them unwrapped and sparingly. Scoped vitest runs with an explicit file list, `pnpm typecheck`, `pnpm exec eslint .`, `pnpm format:check`, codex dispatches, CI polling, git/gh operations, and spec/plan authoring all stay unwrapped — wrapping them would put the phases that dominate arc latency behind a queue they never needed. Long-lived servers start OUTSIDE the wrapper: `next dev`, `next start`, and pre-warmed dev servers hold a slot for their whole lifetime, and the suite hitting them is the heavy phase, not the server.

  Wrap the OUTERMOST command only — an inner wrap under a live holder passes through with a surfaced notice instead of self-deadlocking, so it is harmless, not correct. Closeout and CI-stage runs set `FX_HEAVY_PRIORITY=1`, a best-effort bias toward the nearest merge rather than a queue position. NEVER set `FX_HEAVY_SLOT_DIR` in a production session: two dirs are two independent semaphores and the divergence is undetectable by design (tests point it at a per-case tmpdir, which is why the suite is safe to run under the wrapper). Capacity changes go through `python3 scripts/with-heavy-slot.py --recreate --slots <N>` ONLY — editing `config` by hand or `rm -rf`ing a live slot dir hand-builds the recreation races `--recreate` exists to prevent. Spec: `docs/superpowers/specs/2026-08-10-heavy-phase-semaphore-design.md`; guard: `tests/docs/agentsHeavyPhaseRule.test.ts`.
