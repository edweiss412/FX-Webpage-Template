# Why the CrewRowActions §14 pair is not measured in a browser
#
# bl-orch's AC-13 ruling pre-authorised recording a pair that genuinely cannot
# mount, WITH the probe showing why. This is that probe. The other two pairs of
# the trio ARE measured, in tests/e2e/control-outline-contrast.live.spec.ts.

## 1. The gate, read from the shipped source

components/admin/wizard/step3ReviewSections.tsx:4305-4318

      render: (s) =>
        isPublished(s) ? (
          <CrewBreakdown
            dfid={s.driveFileId}
            members={s.crewMembers}
            actions={{
              showId: s.showId,
              slug: s.slug,
              enabled: s.published && !s.archived,
              crewIds: (s.previewRoster ?? []).map((r) => r.id),
            }}
          />
        ) : (
          <CrewBreakdown dfid={s.driveFileId} members={s.crewMembers} />
        ),

`actions` is passed ONLY on the `isPublished(s)` branch, and the trigger mounts
only when `actions?.enabled` (step3ReviewSections.tsx:1675, :1725). The `s` on
that branch is the PUBLISHED-show section shape: it carries `showId`, `slug`,
`published`, `archived` and `previewRoster`.

## 4. Conclusion

`CrewRowActions` is IMPORTED by step3ReviewSections (line 139) but mounts only
on the published-show surface, not in the step-3 wizard review tree. Driving it
in a browser needs the published-show surface, which is a different harness with
a different fixture and is outside this arc's diff.

It is covered by the source pin in tests/styles/controlOutlineDimensions.test.ts,
whose planted defects fire on each of its two ternary arms independently, and by
scripts/ac15-width-parity.mts (767 elements, 0 width differences). Both are
weaker than a rendered measurement and are recorded as weaker.

RE-FILE TRIGGER: a browser harness for the published-show surface existing for
any other reason, at which point this pair should be measured there.
