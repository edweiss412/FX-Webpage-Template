## §2 Design — parse layer and module shape

New helper module `tests/docs/_ledgerMdast.ts` (test-tree infra, walked by no shipped bundle):

- `parseLedger(text: string): Root` — `remark().use(remarkGfm).parse(text)`. One parse per ledger file per run.
- `extractEntries(root, text, opts: { levels: 2|3 mask; requirePrefix: string | null }): LedgerEntry[]` — **top-level headings only** (direct children of `Root`; matches today's `^`-anchored semantics — a heading nested in a blockquote neither opens an entry nor mints an id, §7). Id extraction is REGEX-PARITY (r2 F5 repair — the r1 draft narrowed it): optional bracket prefix with ARBITRARY content (`[P2]`, `[URGENT]` — the live matcher's `\[[^\]]+\]`), optional `~~strikethrough~~` (id-flatten INCLUDES `delete` content — a struck id still occupies the heading for the no-overlap invariant), token = maximal `[A-Za-z0-9/-]` run from there with NO terminator requirement (`## BL-X: open` mints `BL-X`, exactly as the live `shoutyIds` matcher does — the "followed by a dash" prose in its doc comment is not in the regex), rejected if it contains lowercase, `BL-` prefix required where `requirePrefix` says so. **Entry partition is id-heading to id-heading** (r2 F3 repair): an entry's span runs from its id-bearing heading to the NEXT id-bearing top-level heading at ANY accepted depth — NOT to the next same-or-shallower heading. This is exact regex parity: the live walk partitions at every matched BL heading regardless of depth, so the nine H3 entries nested under `BL-NULLCODE-STAMP-BATCH-2` (live today) each own their spans and never leak fields or provenance into the H2 parent; non-id prose headings do not close an entry (also parity).
- `flattenLines(nodes, mode: "claim" | "id"): FlatLine[]` — depth-first over the entry's block nodes with the COMPLETE node-type disposition table below (r2 F2 repair — full inventory, not an ad-hoc drop list). Splits lines at `break` nodes, at literal `\n` inside text values (probed: soft breaks emit no node), and at block boundaries; records `strong` character spans per line.

| mdast type | claim-flatten | id-flatten | rationale |
| --- | --- | --- | --- |
| `text` | text | text | prose |
| `strong` / `emphasis` | descend (strong spans recorded) | descend | rendered emphasis = same words |
| `delete` | **drop** | descend | `~~CLOSED~~` negates (r15); struck id still occupies its heading |
| `inlineCode` | **text** (span recorded as code-contributed) | text | renders visibly — `**Status:** \`RESOLVED\`` is the r15 backticked-value plant, verdict HIT preserved. Both shapes probed at zero live instances; both verdicts verified executable in the committed lane probe (2026-08-01) |

`normalizeSection` and its `__`-fold/comment-strip die: both are structural now.
- `type FlatLine = { text: string; strongSpans: [start, end][]; codeSpans: [start, end][] }` (r3: type completed). A strong span is ONE span per `strong` NODE — its full flattened extent, nested `emphasis`/`inlineCode` descendants included — never per text fragment (`**Resolved *by*:**` is a single label span). `codeSpans` records `inlineCode`-contributed ranges; every label recognizer (line-leading, mid-line field-label, strong-label) rejects a label whose span OVERLAPS any code span (full-range check, not first-character — `**Sta\`tus\`:** CLOSED` has no recognizable label).
- **Probed parser facts** (remark@15.0.1 + remark-gfm@4.0.1, harness `docs/superpowers/specs/2026-08-01-ledger-guard-mdast-rewrite-mdast-probes.mjs`): soft line breaks are literal `\n` INSIDE text-node values — no `break` node — so `flattenLines` splits text values on `\n`, not only at `break` nodes; character references cook in text nodes (`C&#76;OSED` parses as text `CLOSED`); a 3-space-indented ATX heading parses as a heading, 4-space as code; setext headings parse (depth 2 for a `---` underline); GFM autolink literals become `link` nodes (a bare URL containing a terminal word is structurally excluded); a struck heading id is a `delete` node inside `heading`; task-list checkboxes are `listItem.checked`, invisible to flattened text.
- `entryTerminal(entry: LedgerEntry): { hit: boolean; lane: string } | null` — the single evaluator (r40 architecture kept: one function used by the live walk AND exercised directly by every plant, so removing a lane wiring breaks an executable plant).

The test file keeps: registries (`GRADUATED`, `BACKLOG_GRADUATED` with provenance rows), `HEADING_TERMINAL_EXEMPT`, the eight `it()` cases including the origin-gate substance check. `TERMINAL_WORDS` union unchanged: `CLOSED|WITHDRAWN|RESOLVED|SUPERSEDED|SHIPPED|DONE|OBSOLETE|REFUTED`.

## §3 Lane semantics on the AST

Terminal TOKEN rule (all lanes): a maximal run matching `[A-Za-z0-9-]+` in flattened text that case-insensitively EQUALS a `TERMINAL_WORDS` member — hyphen excluded from both boundaries by token maximality (§1.1.5). The veto window runs on the flattened line prefix before the token: `PARTIAL(?:LY)?`, `NOT`, `NEVER`, `NO LONGER`, `PREVIOUSLY`, `FORMERLY`, with one optional intervening non-terminal word (full r29 semantics restored; emphasis marks no longer appear in flattened text, so the veto's tail class shrinks to whitespace/colon/dashes).

| Lane (regex era) | AST rule |
| --- | --- |
| `STATUS_TERMINAL` / `FILED_TERMINAL` + r22 `CONTAINER` + r27 `__`-fold + r29–r30 emphasis-label wrappers + r32 `Resolution` | **Line-leading field lane:** flattened line begins `Status` / `Resolution` / `Filed` (label word, case-insensitive) + optional colon / dash separator; terminal token directly after (through optional `✅`/whitespace) is a claim. Containers and emphasis already dissolved by flattening. |
| `boldFieldTerminalHit` (r13/r17/r27/r35/r36 label rule + particle chains) | **Bold-label lane:** per `strong` span on the line — a span is a LABEL when its text ends with a colon or the text following the span opens with a colon or dash. Label evaluation uses the GLOBAL token rule (r3 repair, replacing r40's `/[^A-Za-z]+/` word-split): tokenize the label into maximal `[A-Za-z0-9-]` runs, strip trailing whole-token particles (`PARTICLE_WORDS` inventory, r38/r39, ported verbatim), and the final remaining token must EQUAL a terminal word — `**Resolved by:** PR #621` hits, while `**Shipped precedent:**`, `**re-CLOSED:**`, `**CLOSED2:**`, `**2CLOSED:**`, and `**CLOSED-by:**` do not (the r40 word-split false-positived on all four of the latter, shown by the r2 review's probe — a §1.1.5 consistency fix, probe-backed). Non-label spans: per-occurrence terminal-token scan. Veto window = line prefix (r27). |
| `FIELD_VALUE_TERMINAL` (r39/r40 bare fields) | **Bare-field lane:** terminal token followed (through optional particle chain) by a colon, an em/en dash, or a whitespace-delimited ASCII dash ⇒ field-value claim. |
| — (new; r2 F1 repair replaces the r1 draft's detection-only widening) | **Mid-line field-label lane (fixes P1):** for each STRONG label span on ANY line whose label word is `Status`/`Resolution`/`Filed`, evaluate the text FOLLOWING that span (to the next label span or end of line) for a leading terminal token — `**Class:** x · **Status:** CLOSED` hits. The label must be a strong span; a bare mid-line `Status:` in prose stays inert (§7). |
| — (r35/r36 label rule, applied line-wide; fixes P2) | **Terminal-label lane:** the bold-label rule (final non-particle word of a colon/dash-labeled strong span is terminal ⇒ claim) runs on EVERY line — `**Effort:** M. **Resolved:** by PR #700.` hits; `**Partial closure (2026-07-27):**` and `**Residuals (still open):**` do not (final words non-terminal). |

**Per-lane input domains (explicit, r2 F1):** the line-leading field lane, the per-occurrence bold NON-label scan, and the bare-field lane run ONLY on lines line-led by `Status`/`Resolution`/`Filed` (r40 scope — this is what keeps narrative `REFUTED` inside a bold segment or before a separator on prose lines inert; the r1 draft's "any bold label makes a field line" widening would have false-positived on live `BL-EXPORT-BLANK-ROW-SEGMENTATION` line 607, caught by the r1 reviewer's probe). The two new lanes above run on every flattened line but are LABEL-STRUCTURE-gated: they evaluate only text adjacent to a recognized strong label span. The heading and opening lanes keep their single-line domains.
| `HEADING_TERMINAL` + r30 `CHECKED_TERMINAL` | **Heading lane:** claim-flattened heading text STRICTLY AFTER the id token's end — anchors (em/en dash, whitespace-delimited ASCII dash, or `✅`) inside an arbitrary bracket prefix or anywhere before the id are NOT the entry's own claim (r3 fix, probe-backed: all four anchor forms false-positived pre-id). When the id is delete-wrapped (struck), it is absent from the claim flatten and the scan starts at offset 0 — a struck id with a terminal suffix stays conservative-loud. Terminal token after the anchor, or `✅`-anchored terminal token (r30 anchored form REPLACES main's bare-`/✅/` heading test predicate; a decorative ✅ in an open title is not a claim). |
| `OPENING_TERMINAL_BOLD` / `_BARE` + r26 `firstContentLine` | **Opening lane:** first non-empty flattened line of the body (container-only lines produce no flattened text, so r26 falls out). Terminal token at line start counts any-case when inside a `strong` span, ALL-CAPS-only when bare. |

Deleted with nothing ported: `normalizeSection`, `CONTAINER`, `CONTAINER_ONLY`, `WRAP`, `AFTER`, the r27 intraword-`__` carve, the r28 comment-deletion bounds — every one is a regex workaround for structure the parser now owns.

## §7 Documented limits (round-0 budget; consequence-bound)

Posture: the guard is a drift TRIPWIRE over first-party ledger prose. Its consequence bound: an honest in-place closure in prose position is caught loudly; everything else is at worst silent-open (an entry stays in the queue — the conservative direction for an archive guard), never a false graduation.

- Terminal words inside **table cells, link text/labels, images, fenced/indented code blocks, HTML comments, and BLOCK-level raw-HTML islands**: invisible by construction (dropped in flatten). r28 obfuscation ratification owns these. (INLINE raw-HTML islands are the exception — the enclosed prose survives the tag drop and is scanned, a gain over the regex era; and inline code spans contribute text, preserving the r15 backticked-value catch — see the §2 disposition table.)
- **Footnote prose** (`[^x]: …`): unscanned — commentary, not the entry's own field. Zero live footnotes across all four ledger files (complete count, r1 review probe).
- **Bare mid-line field labels** (`… Status: CLOSED` with no strong span): inert — the mid-line lane is label-structure-gated; a bold label or a line-lead is what makes a field the entry's own claim.
- **Character references** (`C&#76;OSED`): remark cooks entities into plain text, so this class — regex-invisible, previously ratified-out — is now CAUGHT for free (probed §2; pinned by a §5 plant). Moves out of the limits budget.
- **Soft-break-split field values** (`**Status:**` with `CLOSED` on the next source line, one rendered line): line discipline is preserved — the value line is not the field line, so it stays unscanned. Render-equivalent one-liners are r28's class.
- **Nested headings** (inside blockquotes/lists) neither open entries nor mint ids (§2) — matches today; quoted entry headings in prose stay inert.
- **Bare non-leading fields without bold** (`Closed: 2026` mid-prose, no strong span): unscanned — prose legitimately discusses closure dates; the bold label or the line-lead is what makes it the entry's own field (r39 parity).
- **Compound prepositions** (`as part of`, `in favor of`): interior tokens are open-class nouns; not added to `PARTICLE_WORDS` (r40 ratification carried).
- **DEFERRED.md terminal-claim scanning**: out of scope (parity with today); graduation invariants cover it. Widening is a separate, cheap follow-up if wanted.
- **Postfix reopening semantics** (`CLOSED but reopened`): r30 boundary carried — honest reopenings are written `Status: REOPENED` or narrative, both silent.
