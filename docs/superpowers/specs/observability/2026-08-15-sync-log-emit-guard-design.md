# Sync-log emit guard — a sync never fails because logging failed

**Date:** 2026-08-15 · **Authoring branch:** `docs/sync-log-emit-guard-spec` · **Implementation branch:** `fix/sync-log-emit-guard` · **Status:** DRAFT
**Entry:** `BL-SYNC-LOG-EMIT-UNGUARDED` (BACKLOG.md, filed 2026-08-10) · **Effort:** S · **Plan:** authored beside this spec in the plan directory docs/superpowers/plans/2026-08-15-sync-log-emit-guard/ (same PR)

## §0 Why

`sync_log` emits ride a separate postgres connection (`writeSyncLog` opens its own, `lib/sync/syncLog.ts:65`, `{ max: 1, idle_timeout: 1 }`), so the sink can fail while the sync it observes is healthy. The shared emit chokepoint — `await deps.logSync?.(entry);` inside the exported `logSync` helper (`lib/sync/runScheduledCronSync.ts:2313`; helper defined at line 2287) — has no try/catch, and several of its call sites sit inside the per-show advisory-lock callback (`processOneFile_unlocked`, `lib/sync/runScheduledCronSync.ts:3502`–line 3527, invoked under `deps.withShowLock ?? withPostgresSyncPipelineLock`, line 2893). A transient connection fault at emit time therefore throws out of the lock callback and rolls the sync transaction back: the log write can fail the thing it exists to observe. `fix/sync-log-show-id-duration` widened the blast radius from two entry points to ten — every manual re-sync path installs the sink.

The sibling arc `docs/superpowers/specs/observability/2026-08-14-sync-observability-gaps-design.md` already closed this class for its own surfaces: the catch-emits in `runManualSyncForShow`/`runManualStageForFirstSeen`/the pending-ingestion retry route and the two post-commit emits in `applyStaged` are each wrapped, escalating a sink failure via `log.error` with `code: "SYNC_LOG_EMIT_FAILED"` (e.g. `lib/sync/applyStaged.ts`, both `catch` blocks carrying that code). This arc closes the REMAINDER of the class — the shared helper chokepoint and the two direct-sink surfaces the sweep below names — and graduates the family code into §12.4 as a durable admin-log-only row.

## §1.1 Resolved scope — do not relitigate

1. **Ratified decision (Eric, 2026-08-15, orchestrator session; captured in the orchestrator's G3 scope brief (smalls-g3-signal-arcs.md in the session briefs directory, outside the repo)).** Guard the emit — a sync never fails because logging failed — AND make the swallowed failure itself observable: `log.error` with a durable §12.4 code, full lockstep triple (§2.4). This is the entry's own "middle option ... probably right", ratified.
2. **Code REUSE, row NEW.** `SYNC_LOG_EMIT_FAILED` is already the escalation code at four production surfaces (`lib/sync/applyStaged.ts`, `lib/sync/runManualStageForFirstSeen.ts`, `lib/sync/runManualSyncForShow.ts`, `app/api/admin/pending-ingestions/[id]/retry/route.ts` (grep SYNC_LOG_EMIT_FAILED)), ratified as an "app_events-only forensic code" by the 2026-08-14 spec (its R1 F6/F7). This arc does NOT mint a second code for the same failure class; it adds the §12.4 row that makes the existing code durable and cataloged. The ratified "NEW durable §12.4 code" is satisfied by the ROW being new to §12.4; a second code string would split one failure family across two identifiers for zero discrimination gain. The 2026-08-14 spec's "§12.4 catalog: untouched" was that arc's scope statement, not a fence against cataloging — this row is the graduation it left open.
3. **Admin-log-only row.** The §12.4 row uses the catalog's admin-log-only convention (master spec `docs/superpowers/specs/2026-04-30-fxav-crew-pages-v1.md` §12.4 "Admin-log-only codes" bullet): `—` Doug/Crew cells, no `helpfulContext` YAML key, catalog entry with all-null facing fields (shape precedent: `STALE_WRITE_ABORTED`, `lib/messages/catalog.ts:256`). No UI ever renders it; invariant 5 (no raw codes in UI) is untouched.
4. **Warning-card copy rule: N/A, stated per the brief.** `SYNC_LOG_EMIT_FAILED` is a `log.error` escalation code, not a warn-severity `ParseWarning` — it never enters `parse_warnings` as a warning object and never renders a warning card, so the `WARNING_CARD_COPY_CODES` obligation (`lib/messages/catalog.ts:59`, `docs/superpowers/specs/2026-07-20-warning-card-copy-restore.md` §4.2) does not apply. No `WARNING_CARD_COPY_CODES` row.
5. **Scope fence (ratified): the per-emit dedicated connection stays.** The entry's fold-in — reusing the sync transaction's connection to shorten lock hold — is NOT taken: it changes the sink's isolation semantics (the row would roll back with a failed sync instead of recording the failure). Decided limit, recorded in the archive with the entry's reasoning (§4 limit 3). No follow-up row is filed: the lock-hold cost is one short single-row INSERT on a warm local connection per emit, and this spec makes no measurement claiming otherwise — the brief's "file a follow-up only if measurable" branch is not triggered.
6. **Onboarding `tx.logSync` is out of the class by construction.** The onboarding scan's `tx.logSync` (`lib/sync/runOnboardingScan.ts:659`) writes `sync_log` through the scan's OWN transaction connection — it has no independent failure mode: a fault there means the scan's own DB work is failing on the same connection, and its rows are tx-bound by design. Guarding it would convert designed tx-atomicity into the exact semantics change fenced by item 5. Untouched.
7. **Autonomy: both user review gates WAIVED** (Eric's 2026-08-15 batch grant, kickoff brief). Stop only for a genuinely new question.
8. **All AGENTS.md invariants bind**; the ones this arc exercises: 1 (TDD), 2 (no lock-topology change — no new lock holder, §2.3), 5 (no raw codes in UI — admin-log-only row), 6 (conventional commits), 10 (observability; §2.5), 11 (worktree-only), 12 (claims), §12.4 lockstep triple.

### §2.2 Guard shape (all three GUARD rows, one pattern)

Wrap the awaited sink call; on catch, escalate; then CONTINUE — return/flow as if the emit succeeded. Never rethrow, never alter the operation's result. At the helper chokepoint the guarded region is exactly the `await deps.logSync?.(entry)` statement — entry construction above it stays outside the guard (a construction bug should stay loud; only the SINK write is the fenced fault domain). Escalation mechanics, from the IN-LOCK precedents rather than the post-commit applyStaged ones (spec R1 F1/F2 — both repaired here and swept below):

- **Fire-and-forget, never awaited.** `const escalation = log.error(...); void escalation.catch(() => {});` — the shape at `lib/sync/runManualStageForFirstSeen.ts:379` and `lib/sync/runManualSyncForShow.ts:346`, whose in-code comments carry the invariant-10 rationale: an app_events emit must never extend a held advisory-lock window. R1 F1 probed the awaited form holding the lock for the sink's full latency (a hung persist request would hold it indefinitely). Uniform at all three guard rows — the webhook sites hold no show lock, but one shape for one pattern; the local-const assignment (not a chained call) is load-bearing for prettier + the stripLogEmissionCalls producer scan, per the same precedents' comments.
- **Fields:** `code: "SYNC_LOG_EMIT_FAILED"`, `source:` the surface's existing log source, `driveFileId` (and `showId` where in scope), and `error:` carrying the RAW caught value — NOT `serializeError(...)`. The logger serializes exactly once in `buildRecord` (`lib/log/logger.ts:37`); pre-serializing feeds a plain object back through `serializeError`, whose non-Error branch is `String(value)`, and the record's diagnostic collapses to `"[object Object]"` (R1 F2, probed live).

**Class sweep of R1 F2 (same shape, live tree; repaired in the implementation PR — the AGENTS.md class-sweep default, no deferral exception applies).** `grep -rn "error: serializeError(" lib/ app/` returns 20 sites. Two are OUT of the class: `lib/log/persist.ts` lines 32 and 38 pass the result to `console.error` directly, which never re-serializes. The other 18 sit in a `log.*` fields object and double-serialize today, silently corrupting the diagnostic they exist to carry: the four shipped SYNC_LOG_EMIT_FAILED guards (`lib/sync/applyStaged.ts` both blocks, `lib/sync/runManualStageForFirstSeen.ts:377`, `lib/sync/runManualSyncForShow.ts:344` and line 572), the pending-ingestion retry route's six sites, `lib/sync/emitRoleFlagsNotice.ts` (three), `lib/log/emitLeadRoleApplied.ts:77`, `lib/log/emitIdentityLinkRenameUnlanded.ts:66`, `lib/auth/picker/resolveShowPageAccess.ts:75`, and `lib/auth/picker/resolvePickerSelection.ts:56`. Repair is mechanical (drop the wrapper; the logger serializes), plus updating any test pin asserting the pre-serialized shape. Structural defense lands in the same commit (structural-defense-calibration rule: the class is nameable at first occurrence): a walk-derived meta-test under `tests/log/` asserting no `log.*` fields object passes `serializeError(...)` as its `error` property — file-walked, not an enumerated site list, so a new site fails by default.

Guard condition for the new behavior: with no sink installed (`deps.logSync` undefined), the optional-call emits nothing and the guard is dead code — unchanged from today. A sink that RESOLVES is unchanged. A sink that THROWS is the only behavior delta: swallowed + escalated instead of propagated.

### §2.3 Why the escalation emit is safe inside the lock callback

The brief requires the swallowed-failure emit to be "post-commit-safe per invariant 10 (no emit inside the advisory-lock tx that can itself throw)". The fire-and-forget escalation satisfies this where it stands, without threading state out of the lock callback, because it adds no awaited work to the lock window (§2.2, R1 F1) and because `log.error` cannot throw and cannot touch the tx connection:

- The logger's default sink guards BOTH the dynamic `import("./persist")` and the write, swallowing all persist faults (`lib/log/logger.ts:58` `defaultSink`, its try/catch around `persistAppEvent`); `persistAppEvent` itself swallows and degrades to console (`lib/log/persist.ts:12`, the "best-effort log sink" swallow-and-degrade comment).
- Persistence goes through the Supabase service-role HTTP client (`app_events` insert), never the sync tx's postgres connection — no interaction with the lock or the transaction.
- The console line is synchronous and unconditional (the "ONE intentional console chokepoint", `lib/log/logger.ts` defaultSink), so the signal survives even a total app_events outage.

No new lock holder, no lock-topology change (invariant 2): the guard adds zero lock acquisitions; `tests/auth/advisoryLockRpcDeadlock.test.ts` is unaffected.

### §2.6 Tracker interplay (manual paths)

`runManualSyncForShow`'s tracked sink marks `rowWritten = true` BEFORE awaiting the base sink (`lib/sync/runManualSyncForShow.ts:304`–line 311, line 503–line 510). Today a sink throw propagates, is caught by that surface's catch, dedupes against the already-true `rowWritten`, and the SYNC FAILS carrying the sink error. With the helper guard: the throw is swallowed at the chokepoint, the sync proceeds on its own merits, and the attempt's missing row is signaled by the escalation. `rowWritten` staying true after a swallowed sink failure is correct for its purpose — it prevents a DUPLICATE catch-emit for an attempt whose sink is evidently failing; the escalation, not a second doomed write, is the record. Stated here so the plan's tests pin it and no review round re-derives it.

## §3 Acceptance criteria

- **AC-1 (guard, helper).** With an installed sink that rejects, `processOneFile` / `processOneFile_unlocked` (driven via their runners with injected throwing sinks) complete with the outcome the sync itself earned — the sink rejection does not alter the returned result and does not abort the lock callback. One `SYNC_LOG_EMIT_FAILED` `log.error` fires per swallowed failure, carrying `driveFileId` and a USABLE diagnostic: asserted via an injected log sink (`setLogSink`), the record's `context.error` preserves the thrown sink error's `message` (kills the double-serialize mutant, R1 F2). Assert the CODE, not merely that some error was logged (the 2026-08-14 R1 F7 rule). The escalation is not awaited by the guard (R1 F1): the test's log sink resolving late must not delay the runner's return (assert the runner resolves while the escalation promise is still pending).
- **AC-2 (guard, push).** `logUnlessArchived` with a throwing sink still returns its `result` (fetch-failure and duplicate-skip branches); escalation fires with the code.
- **AC-3 (guard, webhook).** The folder-fallback dispatch with a throwing sink still returns its `dispatched` array (both the listFolder-failure branch and the per-file branch; the per-file branch continues the LOOP — later files still dispatch); escalation fires per swallowed failure.
- **AC-4 (success path unchanged).** With a resolving sink, every guarded site's emitted entries are byte-identical to today's (same entry shapes, same call counts) — the guard is invisible on the happy path.
- **AC-5 (lockstep triple).** §12.4 row + regen + catalog row land in one commit; `pnpm test:audit:x1-catalog-parity` green; the catalog row is all-null-facing (admin-log-only); no `WARNING_CARD_COPY_CODES` change.
- **AC-6 (never silently wrong).** No guarded site swallows without escalating: the catch body's ONLY terminal outcomes are escalation-then-continue. A mutant deleting the `log.error` inside any guard's catch is killed by the AC-1/AC-2/AC-3 code assertions.
- **AC-7 (double-serialize sweep).** All 18 in-class `error: serializeError(...)` sites (§2.2 sweep) pass the raw value instead; the walk-derived meta-test is green and fails when any `log.*` call regains a pre-serialized `error` field; the two `lib/log/persist.ts` console sites are untouched.
- **AC-8 (ledger).** `BL-SYNC-LOG-EMIT-UNGUARDED` archives on the implementation PR's merge with the §1.1 item 5 fence and §4 limits recorded; `BL-SYNC-LOG-ATTRIBUTION-METATEST` gains the §4 limit 6 guard-presence scope line in the same PR; markers strip per invariant 12.

## §4 Documented limits

1. **A lost escalation is possible if the process dies before the fire-and-forget persist lands.** The synchronous console line has already printed (the logger's console write precedes persist); only the app_events row can be lost. Accepted: the awaited alternative is R1 F1's lock-hold hazard, and the in-lock precedents ratified this exact trade (their invariant-10 comments).
2. **A swallowed sink failure loses that attempt's `sync_log` row.** The attempt is signaled (`SYNC_LOG_EMIT_FAILED` in `app_events` + console) but not recorded in `sync_log` — conservative demote plus surfaced signal; never silently wrong. Re-emitting the entry later would need a queue this S-arc does not build.
3. **Per-emit dedicated connection stays; lock hold includes the emit round-trip** (§1.1 item 5, ratified). The entry's fold-in paragraph rides into the archive as the record of the rejected alternative.
4. **The escalation's own persistence is best-effort.** If `app_events` is ALSO down, the durable record degrades to the synchronous console line + `persistHealth` counters (`lib/log/persist.ts`, `recordPersistFailure`) — the logger's designed floor, not this arc's to change.
5. **Onboarding `tx.logSync` rows remain tx-bound** (§1.1 item 6): an onboarding scan that fails still rolls back its own scan-log rows. Designed atomicity, not a gap.
6. **No CI-time completeness recognizer for FUTURE sink sites ships in this arc (R2 F1, ship-and-fence).** A structural walker asserting every sync_log sink invocation is guarded needs the writer-set derivation problem solved — aliases, nested-deps carriers, emission-vs-construction — and that design already exists, six rounds deep, as `BL-SYNC-LOG-ATTRIBUTION-METATEST` (writers derived from `lib/sync/syncLog.ts` exports plus the `logSync`/`insertSyncLog` method and callback forms, with two open definitional questions the shipping arc deliberately did not settle). A second ad-hoc walker here would fork the writer-set definition — the two-copies-drift shape. Instead: (a) the implementation PR adds one scope line to that entry's body recording that the walker, when built, ALSO asserts guard-presence (this finding's dimension) alongside attribution; (b) the regression's failure mode is bounded — an ordinary new UNGUARDED site regresses to today's shipped behavior, a LOUD failure of the observed operation (the throw propagates), never a silent one, so the consequence bound's "never silently wrong" holds even across the regression this limit accepts.
