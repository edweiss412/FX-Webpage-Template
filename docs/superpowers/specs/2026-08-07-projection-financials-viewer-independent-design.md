## 0. Problem — two defects, one mechanism

The crew-page projection alert (`TILE_PROJECTION_FETCH_FAILED`) is driven by the `tileErrors` map of the rendered projection: `_CrewShell` raises when `failedKeys` is non-empty and (S6) resolves the whole `(show_id, code)` row when it is empty (`app/show/[slug]/[shareToken]/_CrewShell.tsx`, `failedKeys` from `data.tileErrors`; `lib/adminAlerts/resolveAdminAlert.ts` stamps `resolved_at` with no `failedKeys` guard).

**The projection is cached per viewer, stale-while-revalidate.** `getShowForViewer` serves the data fan-out — `tileErrors` included — from `unstable_cache` keyed `[version, showId, viewer.kind, crewMemberId]` with `revalidate: 300` as TTL backstop; `revalidateShow` (write paths) is the primary bust (`lib/data/getShowForViewer.ts:896-911` `cachedShowData`, comment at `lib/data/getShowForViewer.ts:888-894`; memoization pinned by `tests/data/getShowForViewer.cache.test.ts:212-222` — a mock cache that deliberately does NOT model expiry, per `tests/data/getShowForViewer.cache.test.ts:4` and its line 38). An infrastructure outage is not a write, so during an outage the TTL is the only refresh. And because both consumers are dynamic routes (the crew route reads cookies/headers via `lib/auth/picker/showPageChainRequest.ts:19`; admin preview is `force-dynamic`), Next 16 `unstable_cache` serves an EXPIRED entry to the first post-expiry request and refills in the background (R2 probe against the installed `next@16.2.10` `unstable_cache` implementation: dynamic requests return the cached response immediately; only static generation awaits fresh data); the background refill runs the fan-out but renders nothing. Alert state therefore moves at **rendered-fill** granularity: a fill's `tileErrors` affects the alert only when a subsequent request renders that fill.

`getShowForViewer` skips the `shows_internal.financials` read unless the viewer is entitled — `financialsEntitled = isLead || derivedFlags.includes("FINANCIALS")` (`lib/data/getShowForViewer.ts:380`, `isLead = isAdmin || LEAD` at `lib/data/getShowForViewer.ts:375`); the fan-out wave passes `financialsEntitled ? readFinancials() : Promise.resolve(undefined)` (`lib/data/getShowForViewer.ts:762`). Two consequences:

1. **Raise delay (the BL entry's premise, accepted at v1).** A financials-only outage with non-entitled-only traffic is unalerted until an entitled viewer's cache FILL (not merely a render) observes it. Ratified as "Accepted v1 limitation (explicit, `financials` only)" in phase-1 spec §4.13 (`docs/superpowers/specs/v1-pre-deployment-amendments/2026-06-15-crew-page-redesign-phase1-design.md`).
2. **Resolve defect (post-entry regression, found this arc).** S6 auto-resolution (`docs/superpowers/specs/alerts/2026-07-03-admin-alert-auto-resolution.md` §S6, ratified 2026-07-03 — AFTER the BL entry, filed 06-17; zero mentions of `financials`/`isLead`) resolves the whole row on any empty-`failedKeys` render. A non-entitled projection can NEVER carry `tileErrors.financials` — so during a financials-only outage, every non-entitled render (from every cache fill, indefinitely) looks healthy and clears the lead-raised alert. The alert flaps for the whole outage: raised at each entitled cache fill, cleared by the next non-entitled render. This is **unbounded** wrong-resolve — it does not decay with the 300s TTL, because fresh non-entitled fills are just as blind as stale ones. It violates the §4.13 R41/R43 intent ("no lower-visibility render can shrink the row"); resolve is stronger than shrink.

**Scope-narrowing fact.** `readRunOfShow` reads the SAME `shows_internal` table unconditionally in every fan-out (`lib/data/getShowForViewer.ts:684-710`), so a table-level outage already alerts viewer-independently under the `run_of_show` key. The residual blind class is failures specific to the financials read. Narrow — but defect 2 bites on ANY financials-visible failure regardless.

## 2. Design

### 2.1 The one code change (`lib/data/getShowForViewer.ts`)

`readFinancials` becomes unconditional in the fan-out wave; the entitlement gate moves inside, at the return boundary:

- The wave slot at `lib/data/getShowForViewer.ts:762` changes from `financialsEntitled ? readFinancials() : Promise.resolve(undefined)` to `readFinancials()` (reads the closure const or gains a parameter — plan's choice; behavior below is the contract).
- `readFinancials` ALWAYS issues the existing `from("shows_internal").select("financials").eq("show_id", showId).maybeSingle()` on the existing service-role client (`lib/data/getShowForViewer.ts:330`). Same query, same client, same wave. Cost: one additional parallel query per non-entitled **cache fill** (not per render — fills are already rate-bounded by the cache), zero added latency (the wave resolves on its slowest member; this table is already hit by the unconditional `run_of_show` read).
- **Failure paths (any viewer):** returned error → `tileErrors["financials"] = internalRes.error.message`; thrown → message — byte-identical to today's entitled-fill behavior, now in every fill.
- **Success path, entitled:** decode + return the row — byte-identical to today.
- **Success path, NOT entitled:** return `undefined` WITHOUT decoding. The fetched value is dropped inside the function; `ShowForViewer.financials` stays `undefined` for non-entitled viewers exactly as today, so nothing new is serialized toward the client and the cached per-viewer entry never contains financials data for a non-entitled key (the per-viewer cache keying is itself a security boundary — `lib/data/getShowForViewer.ts:888-894`).

### 2.2 Defense-in-depth restatement (honest accounting)

Today's comment stack claims three lines of defense: code gate ("the JSONB column isn't even queried", `lib/data/getShowForViewer.ts:713-718`), RLS, physical separation. The middle line is inert on THIS path — the fan-out runs entirely on the service-role client (`lib/data/getShowForViewer.ts:330`), which bypasses RLS. The real lines are the code gate and physical separation (financials not on `shows`). After this change the code gate moves from query-issuance to the return boundary: gated data is fetched server-side and discarded pre-projection for non-entitled viewers. RLS continues to protect every non-service-role path unchanged. The comment blocks stating the old contract are updated in the same commit (AC-7 lists them).

### 2.3 Why both defects close — the bounded-staleness contract

`_CrewShell` branches only on `failedKeys` emptiness of the projection it rendered; projections move at cache-fill granularity (§0). The correct claim is therefore about fills, not renders:

- **Raise:** every fill — any viewer — now observes the financials fetch. A non-entitled fill during an outage carries `tileErrors.financials` → its renders raise with `failedKeys: ["financials", ...]` via the existing union-merge RPC. Defect 1 closes: the first RENDERED fill after outage start alerts, regardless of who triggered it — immediately for a key with no entry (blocking fill), and on the second post-expiry request for a key serving a stale healthy entry (SWR, §0).
- **Resolve:** an empty-`failedKeys` projection now proves financials fetched successfully **as of that projection's fill**. Wrong-resolve shrinks from UNBOUNDED (every non-entitled fill blind, forever) to the pre-existing SWR staleness window every other domain already has. Per viewer key, the convergence sequence during an outage is: pre-outage healthy entry served until TTL expiry (up to 300s); the FIRST post-expiry request still renders the stale healthy entry (and can still wrongly resolve) while triggering the background refill that observes the outage; the NEXT request renders the refilled failure state and raises. So the wrong-resolve window per key is **TTL + the key's next two request arrivals** — wall-clock-bounded only under continued traffic (request cadence T ⇒ ≈300s + 2T worst case), analytical (the cache mock does not model expiry, so no test pins the wall-clock figure). A key with NO entry (new viewer, post-deploy version bust) takes a BLOCKING fill and observes the outage on its first request. Under continued traffic every live key converges to failure state; steady-state alert = raised, and S6 wrong-resolves cease. On recovery the same sequence applies in reverse (lingering raise for one TTL + two arrivals per key, then S6 resolves). Defect 2 closes at exact parity with `hotel`/`rooms`/`contacts`/`transportation`/`run_of_show` — same S6-era semantics, same SWR window.
- **Alert volume/churn:** raise now fires from all-traffic renders during an outage. The RPC already bounds this: `lastCountedAt` 10-minute debounce bounds `occurrence_count`; the `WHERE`-gated `DO UPDATE` makes same-union in-window sightings true no-ops (§4.13 union-merge bullet). `occurrence_count` becomes an all-traffic recurrence signal — strictly more accurate.

**What this deliberately does NOT claim:** per-render observation, zero-staleness alerting, a flat wall-clock convergence bound, or resolve correctness stronger than the cache's SWR freshness contract. Those would require busting or bypassing the cache for observability — fenced out by R8.

## 6. Documented limits

- **SWR staleness window: TTL + request cadence (pre-existing class, all six domains).** A projection cached before an outage start can wrongly resolve (and, post-recovery, wrongly re-raise) until its key's TTL expires AND two further requests arrive (stale-while-revalidate: the first post-expiry request renders stale and refills in background; the second renders the refill — §2.3). Wall-clock-bounded only under continued traffic; a key that stops receiving requests simply stops rendering (its stale alert influence ends with its traffic). Outages are not writes, so `revalidateShow` does not shorten this. This is the S6-era contract for every domain; this arc brings financials INTO that contract from a strictly worse (unbounded — no amount of traffic converged) one. Not a finding; fenced by R8.
- **Decode-level corruption stays silent for financials** (unchanged): a corrupt stored financials JSONB decodes to the null-field fallback without a `tileErrors` entry, unlike `run_of_show` which signals decode corruption. Pre-existing posture; not widened or narrowed here.
- **Entitlement-derivation bugs are invisible to this alert** — it observes fetch health, not whether the right viewers are entitled. Out of scope.
- **No-traffic shows are unobserved** (no fills → no observation). Admins retain the independent infra signals (drive-health, sync alerts) noted in the BL entry.
- **Consequence bound** (for review convergence): every cache fill's financials fetch outcome is handled correctly OR signaled into `tileErrors`/alert state — never silently wrong beyond the SWR staleness window above (TTL + two request arrivals per key), which is surfaced here as a documented limit and converges under continued traffic without intervention. Threat-model fence: this guards against infrastructure fetch failures, not adversarial viewers; viewer-facing exposure is governed by the return-boundary gate (AC-3), the per-viewer cache keying (§2.1), and the unchanged physical separation.
