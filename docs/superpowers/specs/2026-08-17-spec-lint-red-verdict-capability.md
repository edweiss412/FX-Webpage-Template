# spec:lint — red verdict-capability contract (shape + collection)

**Date:** 2026-08-17 · **Backlog:** `BL-SPECLINT-RED-COMMAND-SHAPE` + `BL-PLANLINT-RED-CLAIM-EXECUTION` (both in `BACKLOG.md`) · **Kind:** tooling (no UI, no DB, no runtime surface)

One contract closing both rows: **a `red=` claim must be CAPABLE of expressing a verdict — statically and executably.** The red-then-green task contract requires a task's `red=` command to be OBSERVED failing for the stated reason and later passing; two whole families of commands cannot do either, and today's linter accepts every one of them:

1. **Shape-incapable** (`BL-SPECLINT-RED-COMMAND-SHAPE`): a command the executing shell cannot parse expresses no verdict in either direction (measured: `sh -c` exits 2 on the unquoted-`<>` mutation-site shape, and the shipped `--exec-red` classifier reads any non-zero exit as "red observed" — `lib/specLint/redContract.ts:339`); a `vitest … -t` whose pattern matches nothing exits 0 and reports GREEN from the moment it is written (measured, §2.2).
2. **Collection-incapable** (`BL-PLANLINT-RED-CLAIM-EXECUTION`): the red-contract arm parses the claim but never checks the command can COLLECT the tests it claims to observe. A `red=` whose file filter collects nothing — a typo'd path, a suite living only in a vitest project gated behind an env flag — exits non-zero for a collection reason, reads as "red observed", and the asserted cycle can never complete (probed: five findings across four plan rounds of the originating arc, each found by the reviewer running the declared command by hand).

Extends `pnpm spec:lint` (`scripts/spec-lint.ts`, core under `lib/specLint/`; governing spec `docs/superpowers/specs/2026-07-19-spec-lint.md`; red-contract arm `docs/superpowers/specs/2026-08-15-spec-lint-intent-red-arms.md`, hereafter "the arms spec").

## 1. Scope

### 1.1 Explicitly resolved scope decisions (do not relitigate)

1. **The parse dry-run uses `sh -nc`, not the ledger row's `zsh -nc`.** The row sketched `zsh -nc`; the ratified choice is the SAME shell `--exec-red` executes with (`spawnSync("sh", ["-c", command], …)`, `scripts/spec-lint.ts:311`). A parse check in a different shell than the executor is two recognizers that can disagree — and they measurably do (§2.1: zsh exits 1, sh exits 2 on the same input; their grammars differ in corners the fence does not cover). The row's intent — "catches the quoting class as a whole rather than the `<`/`>` instance" — is preserved exactly: the shell itself is the grammar, and no shell syntax is re-implemented in TypeScript (the speclint-prose-count-parity lexer ratchet is the documented anti-pattern this forbids).
2. **The parse check runs on the DEFAULT invocation, adapter-spawned, outcome-injected.** The payoff moment is review-time linting (`codex-guard --lint-doc` invokes `spec:lint` without `--exec-red`), so gating it behind `--exec-red` would miss every dispatch that needs it. Cost measured ≈2-5 ms per command (§2.1). Purity holds: the core derives the parse plan and synthesizes findings; the adapter alone spawns `sh -nc` and injects outcomes — the same seam shape as `ExecResults` (`lib/specLint/types.ts:51`). Determinism: `sh -n` over fixed text is a pure function of the shell binary; same doc + same shell, same result.
3. **`-t`/`--testNamePattern` in a `red=` is ADVISORY, ratified by measurement — do not re-propose a hard tier.** 10 of 390 corpus `red=` commands carry the flag (§2.2), five of them authored markers in the MERGED, review-approved premisescan plan (`docs/superpowers/plans/2026-08-16-premisescan-import-edge-fidelity.md`) where a new case is added to an existing suite and the name filter is the legitimate red selector. A hard code with known-legitimate corpus instances gets waived reflexively and re-permits the defect (governing spec §1.1 item 1 posture, same argument as the arms spec §1.1 item 1). The advisory says what to check; the executable arm (item 5) catches the no-match case mechanically when execution is opted into.
4. **Collection probes ride `--exec-red`; no new flag.** The arms spec §1.1 item 4 ratified "execution mode is opt-in per invocation"; collection probing is execution-mode work with the same cost profile (one vitest boot per probe, ≈0.8 s scoped, §2.3) and the same opt-in rationale. This spec AMENDS the arms spec's sentence "runs only markers declared `red-state=live`" as follows: `--exec-red` runs the *red commands* of live markers (unchanged) and additionally runs *derived collection probes* — `vitest list` invocations, defined in §5 — for vitest-shaped live and authored markers owned by red-contract regions.
5. **A list-only probe for authored markers does NOT relitigate "never run authored red commands" (arms spec §1.2).** That fence exists because an authored red's *failing case* does not exist at plan time — running the command cannot observe the asserted redness. A collection probe runs `vitest list`, which executes COLLECTION, not tests: it answers "can this command's file selection ever see the named suite", a question that is answerable today and whose negative (§2.3: a tracked file in an env-gated vitest project collects empty) is precisely the originating filing's sharpest case. The red command itself is still never run for authored markers.
6. **Accept-set for the collection arm: simple vitest-shaped commands, by declared token grammar.** A command is vitest-shaped iff it BEGINS with optional `NAME=value` env-assignment tokens, then an optional `pnpm `, `pnpm exec `, or `npx ` runner prefix, then the token pair `vitest run` (grammar normative in §5.1), and it is probe-eligible only when it also contains none of the shell control/substitution tokens `&&`, `||`, `;`, `|`, `$(`, or a backquote, anywhere in its text (quotes deliberately not parsed — a quoted `|` in a pattern over-declines, which is the conservative direction). That admits 282 of 390 corpus `red=` commands, 280 of them operator-free (§2.2). Everything else — `tsx` scripts, `rg`, `sh`, `test`, compound commands, and wrapper forms such as the 3 live `pnpm heavy … vitest run` v2 commands (§2.2) — is OUTSIDE the accept-set: the parse arm (§3) still covers every such command, and the collection arm's silence there is the arms spec §1.1 item 9 out-of-accept-set posture, recorded as documented limit §9 item 5. WITHIN the accept-set there is no silent branch: every probed marker is passed clean, named by a finding, or declined with a surfaced advisory (item 9). A new runner or wrapper spelling files to documented limits with its corpus instance, never to a round.
7. **Decline-to-classify beats grammar growth, always — and a declined probe NEVER executes any part of the command.** Wherever a derived probe cannot be constructed confidently (an unstrippable name filter, §5.1) or safely (a control/substitution token, item 6 — a derived `vitest list` on a compound command would launch the trailing clauses verbatim, which for an authored marker is exactly the "never run authored reds" violation the arms spec §1.2 fences), the arm SKIPS the probe and surfaces `RED_PROBE_UNVERIFIED` (advisory) naming the reason. Repair direction under any same-axis review recurrence is NARROWING — a smaller accept-set plus a surfaced signal — never a wider recognizer. This is this spec's binding instance of the AGENTS.md repair-direction rule.
8. **Threat model: accidental authoring mistakes by an ordinary contributor.** Adversarial obfuscation — a command engineered to parse under `sh -n` but explode at run time, a `vitest` invocation hidden behind an alias or a wrapper script, a name filter constructed to defeat the strip grammar — is out of scope and files to documented limits (§9). Same fence as the arms spec §1.1 item 8; every admissibility clause in review briefs cites it.
9. **Consequence bound (convergence criterion), over a finite domain.** Every `red=` command in the probe domain — the live tracked plan corpus, `git ls-files 'docs/superpowers/plans'`, `.md` only — is either (a) passed clean, (b) named by a specific finding, or (c) declined with a surfaced `RED_PROBE_UNVERIFIED`; never silently misjudged. A conservative decline plus a surfaced advisory is a DOCUMENTED LIMIT, not a finding. Mechanical convergence for the changed module is the mutation score plus an empty unaccepted-survivor set (§8). The whole-corpus calibration (§2.4: zero false fires over the entire probed v2 population — §2.4 owns the numbers) is the zero-false-advisory statement of this bound, settled by a corpus scan, not by argument.
10. **No CI gate, no legacy relint** (governing spec §1.1 items 2, 10, unchanged). Point-in-time pre-dispatch tool. Legacy impact is measured, not hypothesized: exactly one corpus marker draws `RED_UNPARSEABLE` (§2.1), and no gate ever relints that plan.
11. **No new marker fields, no grammar change.** Every input this contract needs — `red=`, `red-state=`, region ownership — is already parsed by `parseMarker` / `taskTopology` (`lib/specLint/taskContract.ts:83` and `lib/specLint/taskContract.ts:309`). `taskContract.ts` is untouched; recognition stays with its one owner (arms spec §5).

### 1.2 Out of scope

- Verifying a red command fails for the STATED reason (arms spec §8 item 8 remains; this spec closes the collection-artifact subset only).
- Running `red-state=authored` red commands (arms spec §1.2, reaffirmed — item 5 above is a list-only probe).
- Collection semantics for non-vitest runners (jest, playwright, bespoke scripts) — outside the accept-set (item 6).
- Shell-syntax modeling in TypeScript, in any form (item 1).
- Auto-fixing; CI wiring; relinting the legacy corpus.
- Gate-command (`<!-- gate: -->`) execution or probing semantics beyond the parse check in §3 (arms spec §4.6 posture unchanged).

### 2.3 Collection discriminators (`vitest list`, vitest 4.1.5)

| input | `vitest run` | `vitest list` |
| --- | --- | --- |
| existing collectible file | red/green per tests | exit 0, one line per collected test |
| nonexistent path | **exit 1** ("include:" / no-files error) — reads as red today | **exit 0, empty output** |
| tracked file in env-gated project (`tests/parser/mutationHarness.shard4.test.ts` without `VITEST_INCLUDE_MUTATION_HARNESS=1`) | **exit 1** — reads as red today | **exit 0, empty output**; with the env prefix: collects |
| `-t` matching nothing | exit 0 (skip) | **exit 0, empty output** (`list` honors `-t`) |

Empty `list` output is therefore ONE discriminator for the whole family — bad path, gated project, no-match name filter — with no stderr parsing and no vitest-version message matching. Cost: 0.79 s for a scoped single-file list on this repo. Collection executes module scope (a documented, measured property of vitest collection on this repo — `tests/mutation/source/surfaceCases.ts:19-21` records that a suite's cost during collection is import-time module-scope execution), so probe cost and side effects are those of collection, not of test execution; the heavy-phase discipline stays the caller's, as ratified for `--exec-red` itself (arms spec §1.1 item 5).

## 3. Static arm — parse capability

New hard codes, `check: "taskContract"`, plan-kind docs only (like every red-contract code; a marker-shaped line in a spec is prose — arms spec §8 items 12-13):

- **`RED_UNPARSEABLE`** (hard) — the `red=` capture of a well-formed marker is non-empty and `sh -nc <command>` exits non-zero. Scope is GLOBAL over well-formed markers in plan-kind docs, v1 and v2 alike, enrolled or not — the same validity-global rationale as `RED_TARGET_INVALID` (arms spec §4.3): a parse-broken command can express no verdict anywhere, and the defect class predates the v2 grammar. Empty `red=` stays `TASK_RED_EMPTY` alone (no parse plan entry — `sh -nc ''` exits 0 and would prove nothing). Detail carries the `sh -n` stderr tail (200 chars, same trim as the arms spec §4.4).
- **`GATE_CMD_UNPARSEABLE`** (hard) — same check over a well-formed gate marker's non-empty `cmd=` capture (`lib/specLint/redContract.ts:30`). The class-sweep peer: a gate command a shell cannot parse is the same verdict-incapable shape, one grammar away. Empty `cmd=` stays `GATE_CMD_EMPTY` alone.
- **`RED_PROBE_UNVERIFIED`** (advisory) — the parse spawn itself failed, timed out, or died on a signal: capability UNVERIFIED, which must never read as either verdict (the arms spec §4.4 error-first posture, reused). One advisory code shared with §5's probe failures; detail names which probe and why.

Population and mechanism: a pure core function derives the parse plan — `{line, command}` for every well-formed marker's non-empty `red=` and every well-formed gate marker's non-empty `cmd=` — the adapter spawns `sh -nc` per entry (repo-root cwd, same per-command ceiling and `SPEC_LINT_EXEC_TIMEOUT_SECS` seam as `--exec-red`; parse checks are ms-scale so the ceiling is a formality), and a pure synthesis function maps outcomes to findings. Runs on EVERY plan-kind invocation, `--exec-red` or not (§1.1 item 2).

Interaction with execution: a marker whose parse check failed is EXCLUDED from the `--exec-red` run population and from §5 collection probes — executing a command the shell cannot parse observes nothing, and the hard finding already stands. (The shipped exec population rule in `planExecutions`, `lib/specLint/redContract.ts:273`, gains this one exclusion.)

## 4. Static arm — name-filter shape

- **`RED_TEST_NAME_FILTER`** (advisory) — the `red=` command of a marker owned by a red-contract region contains a `-t` or `--testNamePattern` token (token match, not substring: ` -t ` delimited, or `--testNamePattern` with space or `=` — a `-t` inside a quoted pattern or a path is not a token). Message: a no-match name filter exits 0, so this red can silently report green; confirm the pattern matches the failing case at red time (or run `--exec-red`). Advisory and region-scoped exactly like `RED_CONJUNCTION` (arms spec §4.5): measured legitimate uses (§2.2), the finding says what to check, the author dispositions it.

## 5. Executable arm — collection probes (`--exec-red`)

### 5.1 Vitest-shape recognition and probe derivation (pure)

A `red=` command is **vitest-shaped** iff it matches the declared grammar: at its start, optional `NAME=value` env-assignment tokens, then an optional runner prefix (`pnpm `, `pnpm exec `, or `npx `), then the token `vitest`, then the token `run` (§1.1 item 6 — `vitest run` appearing only mid-command, e.g. under a `pnpm heavy` wrapper, does not qualify). A vitest-shaped command is **probe-eligible** only if its text contains no `&&`, `||`, `;`, `|`, `$(`, or backquote anywhere (§1.1 items 6-7): the derived probe runs through `sh -c`, so any trailing clause of a compound command would execute verbatim — for an authored marker that is running code the arms spec §1.2 says must never run. An ineligible vitest-shaped command draws `RED_PROBE_UNVERIFIED` naming the offending token; quotes are deliberately not parsed, so a quoted operator over-declines conservatively. The derived probe command is the eligible original with that first `vitest run` token pair rewritten to `vitest list` — env prefixes and every other argument preserved verbatim (so a command that carries its own gating env var probes WITH it, and one that is missing the env var probes without it, which is exactly the discriminating case in §2.3).

For **authored** markers only, the derivation additionally strips name-filter tokens by declared grammar: `-t` or `--testNamePattern` followed by a single-quoted, double-quoted, or bare argument (or `=`-attached value). The authored case's named test is future by declaration, so a name filter must not mask the file-level question "can this command ever collect the suite". If a name-filter token is present but does not match the strip grammar, the probe is SKIPPED and `RED_PROBE_UNVERIFIED` names it (§1.1 item 7) — the strip grammar is never widened in review.

Non-vitest-shaped commands derive no probe and draw nothing (§1.1 item 6).

### 5.2 Probe population and execution

Under `--exec-red` (and only then — §1.1 item 4), for markers OWNED by a red-contract region's task extents (the arms spec §4.4 population), excluding parse-failed markers (§3):

- **`red-state=live`, vitest-shaped:** the red command runs as today. If it exits 0 → `RED_ALREADY_GREEN`, unchanged, no probe. If it exits 126/127, times out, or dies → the shipped advisories, unchanged, no probe. If it exits any other non-zero → the derived probe runs (filters INTACT, `-t` included — live means observable today): **empty collected output → hard `RED_COLLECTS_NOTHING`** — the observed red is a collection artifact (bad path, gated project), not an observation of the asserted failure; non-empty → clean, red genuinely observed.
- **`red-state=authored`, vitest-shaped:** the red command is never run (§1.1 item 5). The derived probe (filters stripped) runs, and every token of the ORIGINAL command that is both a member of the tracked-file set and a test-file path (suffix .test.ts or .test.tsx) (the exact-token-against-tracked-set device `RED_TARGET_RETIRED` already uses, `lib/specLint/redContract.ts:217`) must appear in the collected output: **any missing → hard `RED_SUITE_UNCOLLECTED`**, detail naming each missing file — the command can never collect its declared suite, even after the case is authored (the env-gated-project filing case, §2.3 row 3). A command naming any UNTRACKED test-file token draws **advisory `RED_SUITE_UNVERIFIED`** listing each one (future file or typo — indistinguishable statically, §2.3, and `vitest list` on a nonexistent path is silently empty): the untracked tokens are surfaced by name even when tracked siblings collect fine, so a one-character typo in a multi-file command cannot hide behind its collectible siblings; the tracked ones are still membership-checked (hard on absence). A command with ZERO test-file tokens (directory or glob selectors — a live corpus shape, §2.4) is judged by the probe itself: **non-empty collected output → clean** (the selector demonstrably collects, which is a positive verification, not a silent pass — a new file under that selector will be collected the same way); **empty → `RED_SUITE_UNVERIFIED`** ("selector collects nothing today: future location or typo; confirm the path"), which is exactly the one-character-directory-typo case from the round-1 filing. Measured corpus cost: zero markers today (§2.4). This replaces silence with either positive verification or the surfaced decline §1.1 item 9 requires; whether a named future file is genuinely intended stays judgment (§9 item 3).
- **Any probe that exits non-zero, times out, or fails to spawn** → advisory `RED_PROBE_UNVERIFIED` (detail: exit/signal/reason + stderr tail). A failed probe proves nothing about collection, and reading it as either verdict is the corruption this arm exists to prevent.

Probes run sequentially in doc order after the live-red executions, through the same spawn seam, ceiling, and env seam as red commands. The adapter's spawn seam gains captured stdout for probe invocations (list output IS the observation); red-command executions keep discarding stdout (arms spec §4.4 unchanged).

All `check: "taskContract"`, anchored at the marker line, column 1:

## 6. Architecture & purity

```
scripts/spec-lint.ts        # spawn seam: parse checks (default path) + collection probes (--exec-red); stdout capture for probes
lib/specLint/redContract.ts # pure: parse plan, vitest-shape recognition, probe derivation, tracked-file-arg extraction, synthesis
lib/specLint/run.ts         # carries the new outcome maps core-ward, same pattern as ExecResults
lib/specLint/types.ts       # parse/probe outcome + result types (no runner type crosses the boundary)
```

- **Purity holds** (`tests/specLint/_metaPureCore.test.ts` covers the tree by default): every new core function is a pure map from `(model, tracked, outcome maps)` to plans/findings; the adapter alone spawns. Outcome injection mirrors `ExecResults` exactly — plans derived pure, outcomes injected, findings synthesized pure.
- **One grammar, one owner, unchanged:** `taskContract.ts` is not modified (§1.1 item 11). All new logic consumes `parseMarker`/`taskTopology` exports.
- **Finding plumbing:** all new findings report `check: "taskContract"`; no new check groups, `CHECK_ORDER` (`lib/specLint/run.ts:16`) unchanged.
- **`lib/specLint/redContract.ts` is an enrolled mutation surface** (`tests/mutation/source/registry.ts` id `redContract`, floor 0.95): the diff re-runs `pnpm mutation:guards`, re-anchors shifted accepted rows 1:1 (operator + `from>to` preserved, the documented 2026-08-09 precedent), and lands with the score and an empty unaccepted-survivor set (§8).

## 7. Testing

All under `tests/specLint/`, TDD per task, anti-tautology rules of `docs/agents/writing-plans.md` in force (fixtures plant specific defects; assertions name exact code + line derived from fixture construction; premises via `tests/_shared/premise.ts` where an assertion rests on a fixture property).

- **Parse-plan + synthesis unit suite** (extends `tests/specLint/redContract.test.ts` / `tests/specLint/redExec.test.ts`): plan enumerates non-empty `red=` of well-formed markers (v1 AND v2) and non-empty gate `cmd=`, excludes empty captures, fenced markers, malformed markers, spec-kind docs; synthesis maps non-zero → `RED_UNPARSEABLE`/`GATE_CMD_UNPARSEABLE` (right code per source), zero → silence, timeout/signal/spawn-error → `RED_PROBE_UNVERIFIED`; parse-failed markers are excluded from the exec population (the `planExecutions` exclusion asserted directly).
- **Filter-shape suite:** `RED_TEST_NAME_FILTER` fires on ` -t ` and `--testNamePattern` (space and `=` forms) inside red-contract regions; NOT on a `-t` outside a region, inside a quoted pattern, or as a path substring; NOT on gate commands.

## 9. Documented limits (round 0)

1. **Parse capability ≠ run capability:** `sh -n` accepts commands that fail at run time (missing binary, bad flag, unset env). Those remain covered by the exec-time 126/127 advisories and §8-item-8 of the arms spec. The parse check closes only the parse class — deliberately (§1.1 item 1).
2. **`sh` vs interactive-shell divergence:** an operator pasting a red command into zsh may see different parse behavior in corners where the grammars differ. The contract's shell is the executor's (`sh`), and that is the only self-consistent choice; zsh-only breakage is out of scope.
3. **Authored-new-file collection is unverifiable, and a future file is indistinguishable from a typo:** both are untracked test-file tokens whose `vitest list` is silently empty (§2.3). The arm surfaces the token by name (`RED_SUITE_UNVERIFIED`, advisory — measured corpus cost zero, §2.4) and stops there; whether the named path is intended, spelled right, and will be collectible (right include glob, right project) stays with plan review. (Measured shape behind the class: 10 distinct nonexistent `tests/**` files in `red=` commands, arms spec §2.3 — all in v1 markers today.)
4. **`vitest list` honors the ambient environment:** a probe run in an environment that happens to carry a gating env var will collect what the plan-follower's environment might not. Same ambient-trust posture as `--exec-red` itself (arms spec §1.1 item 5).
5. **Runner shapes outside the declared grammar** (a `make test` wrapper, a shell function, a script that internally invokes vitest, and the 3 live `pnpm heavy … vitest run` wrapper commands cited in §2.2) are not vitest-shaped and draw no collection finding; the parse arm still covers them. Compound vitest-shaped commands are declined WITH a surfaced advisory rather than probed (§5.1) — probing them would execute their trailing clauses. Filing a new runner spelling is a registry-style accept-set change with its own corpus numbers, not a review round (§1.1 items 6-7).
6. **Name filters the strip grammar cannot read** skip the probe with a surfaced advisory (§5.1) — decline, never guess.
7. **Collection executes module scope** (§2.3): a probe's cost and side effects are collection's. A plan whose reds are full-suite commands probes slowly; the flag is opt-in precisely so this cost is chosen (arms spec §8 item 10 posture).
8. **A red command that is red for a non-collection wrong reason** (bad env, wrong cwd, unrelated compile error) still reads as red when collection is non-empty. Narrower than before (the collection subset is closed), otherwise unchanged.
9. **`-t` advisory is disposition-only:** a live marker whose pattern matches a currently-failing test is legitimate and draws the advisory anyway; the author dispositions it or runs `--exec-red`, where the probe settles it mechanically.
10. **Gate commands get the parse check only.** Their collection/probing semantics stay declared-not-verified (arms spec §4.6, §8 item 9).
