# `lib/data` Supabase call-boundary meta-test — design

**Date:** 2026-08-09 · **Ledger:** `BL-LIBDATA-SUPABASE-CALL-BOUNDARY-METATEST` (BACKLOG.md) · **Branch:** `test/libdata-call-boundary-metatest`

## §0 Summary

A registry-style structural meta-test, `tests/data/_metaLibDataCallBoundary.test.ts`, that walks `lib/data/**` from disk and requires every Supabase `.from(...)`/`.rpc(...)` call site to be (a) shape-pinned in an in-file registry, (b) discharged to named behavioral coverage, or (c) explicitly waivered inline. It converts the per-read behavioral fail-soft coverage that already exists for `lib/data` into a class-wide, fails-by-default CI guard — the same conversion `tests/auth/_metaInfraContract.test.ts` performed for the auth domain (invariant 9, AGENTS.md).

Test-only arc. Zero production-code behavior change. One production-comment edit (a stale waiver reason, §3.6).

## §1 Resolved scope — do not relitigate

1. **Extend the `_metaInfraContract` pattern; do not modify `tests/auth/_metaInfraContract.test.ts`.** The auth meta-test stays byte-identical. Sibling domains own their own registry-style meta-tests by design (`tests/auth/_metaInfraContract.test.ts`, comment above the orphan-scan test: "Sibling domains (lib/notify, lib/sync, ...) are owned by their own registry-style meta-tests"). Shared mechanics come from `tests/_shared/stripComments.ts` (`stripCommentsForFile`) and `tests/_shared/premise.ts` (`premise`), both of which already exist — nothing is extracted from the auth test. Ratified: BACKLOG.md entry, "Extend the `_metaInfraContract` pattern, don't write a parallel scanner" — the pattern is the registry+orphan-scan+waiver topology, reused with the shared helpers; the auth file itself is not a library.
2. **No behavioral rewrites of `lib/data` call sites.** Both compliant styles are pinned as-is: destructuring (`const { data, error } = await ...`, `lib/data/listShowsForCrew.ts`) and result-object (`const showRes = await ...; if (showRes.error)`, `lib/data/getShowForViewer.ts`). Invariant 9's text says "destructures `{ data, error }` (not bare `data`)"; the result-object form reads `.data`/`.error` off a named result and distinguishes returned-error from thrown identically — it is the established, review-hardened shape across `getShowForViewer.ts` and is compliant. The meta-test pins current shapes; it does not force a style migration.
3. **Threat-model fence:** the guard defends against accidental authoring mistakes by an ordinary contributor — a new read added without error handling, a registered file gaining an unpinned site, a file added to `lib/data` with Supabase calls and no registration. Adversarial obfuscation (dynamic table names, aliased/re-exported clients, computed member access) is out of scope and files to §6 Documented limits.
4. **Consequence bound:** every `lib/data` Supabase call site is shape-pinned, behaviorally discharged, or waivered by name — a new unregistered site fails CI with a message naming the file and the three discharge paths. The guard's failure mode is a red test naming its subject, never silent acceptance. A conservative miss (a call shape the scanner cannot see) is a DOCUMENTED LIMIT (§6), not a finding.
5. **No source-mutation-registry enrollment** (`tests/mutation/source/registry.ts`). The scanner carries its own planted positive AND negative self-test shapes in the same file (§3.5), which is the executable closure for a text scanner; registry enrollment mutates production modules against a suite, which is the wrong grain for a guard whose subject is test-side scanning. Filed as a documented decision, not deferred work.
6. **Bundling:** this arc ships only the meta-test + the stale-waiver reword. The sibling hardening entries named in the ledger row (`BL-ADMIN-POSTGREST-DML-LOCKDOWN`, `BL-RLS-COVERAGE-CROSSCUTTING`) are NOT in scope.

## §3 Design

### 3.1 File and layering

New file `tests/data/_metaLibDataCallBoundary.test.ts` (name mirrors `_metaInfraContract`; the `tests/data/` directory already runs in the unit suite — sibling tests there are green in CI today). Three layers in one file:

- **Layer 1 — orphan scan** (§3.3): disk walk, fails-by-default for any file with an undischarged call site.
- **Layer 2 — per-site registry reconciliation + shape pins** (§3.4): the scanner's extracted site list is deep-equal-reconciled against ordered registry rows, and every registered row carries its own executable discharge (a shape pin, or a covering-suite citation).
- **Layer 3 — scanner self-tests** (§3.5): planted positive/negative shapes proving the scanner discriminates.

### 3.2 Scanner — the PARSE, not a text pattern

```ts
function extractSites(source: string, file: string): Site[]   // walks ts.SourceFile
```

Sites come from `typescript`'s own parse of the file, not from a regex over its text.

**Why the design changed (whole-diff R1-R4).** Four consecutive review rounds each demonstrated another spelling that a text pattern could not see, every one of them SILENT — the site vanished from the extraction, so Layer 1 saw no call and Layer 2's ordered deep-equal still matched:

| Round | Escaping spellings |
| --- | --- |
| R1 | `.rpc("cost$center")`, `.from("crew's")`, `.rpc('say"hi')`, `` .from(`cost$center`) ``, `.from("")` |
| R2 | `` .rpc(`cost\${center}`) `` (escaped substitution), a backslash line continuation in the name |
| R3 | `.from <Row>("x")`, `` .rpc/* c *\/<Row>("x") ``, `.rpc?.("x")` |
| R4 | `` sb./* c *\/from("x") ``, `sb.rpc?.<T>("x")`, `sb.from!("x")`, `sb.from!<A, B>("x")` |

Each repair widened the pattern; each round found the next spelling. That is the recognizer ratchet the round-economy rules name: **"does this text look like a call?" ranges over an open set of spellings and does not terminate.** The parser answers the question that actually matters — *is this a `CallExpression` whose callee is a member named `from` or `rpc`, with a static string first argument?* — and answers it for every spelling at once, because comments, whitespace, type arguments, optional calls, non-null assertions, parentheses and element access are syntax it has already resolved before this code sees a node.

Three consequences worth stating, because they are visible in the shipped self-tests:

- **The literal is the COOKED value** (`arg.text`) — the name Postgres would actually see. `"say \"hi\""` yields `say "hi"`, and an escaped `\${` inside an otherwise-static template is simply part of the name. The whole class of escape questions disappears rather than being answered.
- **`isStringLiteralLike` draws the static/dynamic line for us**: a string literal or a no-substitution template is a static name; a template WITH substitutions is a genuinely dynamic one and remains §6.1. The limit is now derived from the grammar instead of pattern-matched.
- **Two limits are gone**, not narrowed: generic segments containing parentheses or nested angle brackets were a §6.1 carve-out only because a regex had to bound `<...>` somehow. They are ordinary syntax to the parser and are now planted POSITIVES.

`sb.from(tableVar)` remains a non-site for the reason it always did: no static string name. `sb["from"]("x")` IS a site — element access with a literal name costs three lines here and would otherwise have been the next round's finding.

**The argument has spellings too** (whole-diff R5 F1). Grouping parentheses, the non-null `!`, and the three type-assertion forms all erase at runtime, so `sb.from(("x"))`, `sb.from("x" as const)`, `sb.rpc(<const>"x")`, `sb.rpc("x"!)` and `sb.from("x" satisfies string)` are five spellings of one call with one static name. `unwrap()` strips them, and is applied to the callee and the argument alike — the earlier version unwrapped only the callee, which is how a whole second family of silent misses survived the move to the parse. The lesson generalises: switching to the parse removes the spelling problem only where the code actually asks the parse rather than pattern-matching a node shape.

**Instantiation expressions count too** (whole-diff R6 F1). `(sb.from<Row>)("x")` and `(sb.from)<Row>("x")` supply the type arguments separately and are the same call, so `unwrap()` also strips `ExpressionWithTypeArguments`. Worth recording because the reviewer's fixtures and the shipped self-tests disagree about position: at STATEMENT position `(sb.from<Row>)("x")` is a chain of comparisons, and a leading `await` makes TypeScript read `await (…)` as a call named `await`. Reporting no site in either case is correct, not a miss; the planted positives sit in a declaration initializer, where the instantiation expression is what TypeScript actually parses.

**One predicate for "is this a site".** `siteAt()` answers it once, and the scanner, the orphan scan and the pin-coupling erasure all ask it. Two readers of that question have disagreed twice — the `Array` exclusion lagged the member-name reader (whole-diff R9 F1), then the erasure lagged the exclusion, so a pin naming only an innocent `Array.from("x")` was erased along with the real call and looked coupled to it (R14 F1). Both were LOUD-vs-silent in opposite directions and both are the same defect: an answer computed twice.

**Pins are matched statelessly, and only statelessly.** A pin is the author's `RegExp` and may carry `g` or `y`, which make `.test()` stateful — `lastIndex` survives between calls, so a pin shared by two rows could report dependence for a row it never guarded, purely from where the previous call left off (whole-diff R14 F2). Every match runs on a FRESH copy, which is the whole fix: `lastIndex` starts at 0 and one call behaves exactly as authored. The flags are PRESERVED. Stripping `y` as well was that repair's own next bug (R15 F1) — sticky is not statefulness, it anchors the match at `lastIndex`, so a de-stickied pin matches where the authored one does not and pins that never matched the source were passing both coupling and the source-match rule.

**One extractor, two access forms.** `calleeParts()` returns the receiver and the member name for property access and element access alike, so a rule that reads the member and a rule that reads the receiver cannot disagree about what the call is. They did twice, and both times it was the exclusion below that was left behind — `(Array).from(…)` (whole-diff R6 F2) and `Array["from"](…)` (whole-diff R9 F1), each a LOUD false positive on a receiver the guard explicitly exempts.

**One named collision is excluded.** `Array.from("abc")` is a real call with a static string argument and is not a Supabase boundary; it was a loud FALSE POSITIVE — a red test naming an innocent line (whole-diff R5 F4). `isStandardLibraryFrom()` excludes exactly a receiver identifier of `Array`. That is a named collision in the standard library, not a widening: every other receiver still counts, including `sb.from("abc")`, which is planted as a positive alongside it.

Calibration probe: §4.

### 3.3 Orphan scan (Layer 1)

Walk `lib/data` recursively (same `walk` shape as the auth test, `readdirSync`/`statSync`) accepting `/\.(ts|tsx|mts|cts|js|jsx|mjs|cjs)$/` — the full set of module extensions the toolchain compiles, not only `.ts`/`.tsx` (spec R1 F2: this project's tsconfig includes `**/*.mts`, so a `.mts` module with a Supabase call must not be invisible to the walk; only `.ts` files exist in `lib/data` today, so the widening has zero current-corpus effect). For each file whose comment-stripped source matches `SUPABASE_CALL_RE`, require one of:

1. membership in the Layer 2 registry (every site row reconciled and discharged there),
2. an inline `// not-subject-to-meta: <reason>` waiver whose marker is the whole of a LINE comment, with a non-empty reason. **Which comments those are is decided by the lexer** (`ts.createScanner`, `SingleLineCommentTrivia`), not by anchoring text. Two rounds of textual anchoring could not settle it: comment-stripping erases a block comment exactly as thoroughly as a line comment, so "present in the original, absent after the strip" could not tell a real waiver from documentation ABOUT the convention (`/* // not-subject-to-meta: … *\/`, a JSDoc line, whole-diff R2 F3) — and a line anchor still accepted a block comment whose INNER line began with the marker, in three further spellings (whole-diff R4 F4). Writing about the directive is ordinary authoring; silently exempting a live read because someone documented the convention is not. A context-free LEXER was the first repair and was not enough either: it reads `//` inside a regex character class (`/[// not-subject-to-meta: ]+/`) or inside JSX text (`<div>// not-subject-to-meta: fake</div>`) as a line comment, so a marker that is not a comment at all silently waived a live call site (whole-diff R5 F2). Comment ranges anchored to PARSED token positions end the family, because by then the regex literal and the JSX text are nodes, not a stream of characters that happen to contain two slashes. A waiver written any other way is simply unrecognized, so the file stays undischarged and Layer 1 names it — the signalled direction, pinned by self-tests

(The draft's separate `BEHAVIORAL_CONTRACT_FILES` set is folded INTO the registry: a behavioral discharge is now a per-site registry row whose discharge is a covering-suite citation instead of a shape pin — §3.4. One mechanism, one reconciliation.)

**Registry precedence:** a file with registry rows is reconciled by Layer 2 regardless of any waiver comment it contains. This closes the file-grain-waiver hole for the one file that has both pins and waiver comments (`getShowForViewer.ts`, 10 sites + 2 waiver comments): its sites are individually reconciled; its waiver comments cannot exempt them. Waivers only discharge files with NO registry rows.

Failure message names the file and the three discharge paths (mirrors the auth test's message).

### 3.4 Per-site registry reconciliation (Layer 2)

**Design principle (spec R1 F1):** the reconciliation is DERIVED from the scanner's extraction, never from an authored count. The draft carried a hand-maintained expected-count per file; the R1 probe showed that a new unchecked call plus a count bump passes every layer — the authored number reconciled against itself. So there are no counts. The registry is a per-file ORDERED list of site rows, and the test asserts deep equality between the scanner's extracted `{ kind, literal }` sequence and the registry rows' `{ kind, literal }` sequence, per file, in both directions. A new site changes the extracted sequence and cannot pass without a new registry row — and a registry row cannot exist without a discharge, because the row TYPE requires one:

```ts
type SiteRow = { kind: "from" | "rpc"; literal: string } & (
  | { pin: [RegExp, ...RegExp[]] }                    // shape pin(s), asserted against the file's stripped source
  | { coveredBy: [string, ...string[]]; via: string } // behavioral discharge: covering-suite paths + exported wrapper symbol
);
```

**Row validation (runtime, mirroring `validateSurface` in `tests/mutation/source/registry.ts` — the authoring-time half of the anti-vacuity defence; the non-empty tuple types are the compile-time half, and both exist because a cast defeats either alone):** a `validateRows()` pass runs FIRST in the suite and fails with a named problem list when any row violates:

1. `pin` and `coveredBy` are non-empty (spec R2 F3: an empty array discharges vacuously — `[].every(...)` is `true`);
2. **call coupling, proven by ERASURE** — at least one `pin` must STOP matching once the row's call is erased from the source. Not "does the pattern's text mention the call": that question is unanswerable and four rounds proved it. A bare substring let a `shows` row take a `shows_internal` pin (R3 F1); the literal alone let an `rpc("shared")` row take a `from("shared")` pin (R11 F1); a missing left boundary let `notfrom("x")` take a `from` row (R12 F1); and reading that boundary out of the pattern text still broke on supplementary-plane characters and on `\u{61}from` (R13 F1, F2). A regex source is a pattern, not a program, and lexing it is the same open-set mistake §3.2 and rule 3 both escaped by asking a real question instead. The erasure runs through the PARSE, so every call spelling the scanner understands is erased too, and a pin copied from another site, another call kind, or another function keeps matching and is rejected — whatever its own text looks like.

   The erasure targets the ORDINAL site, not every site sharing a kind and a literal. `getShowForViewer.ts` reads `crew_members` and `shows_internal` twice each, and erasing both at once let the second row carry a copy of the first row's pin and pass — silently (whole-diff R16 F1). Position is the identity Layer 2 already reconciles on, so the two rules now agree on what a row points at, and every registry fixture in the suite registers its file's sites in order.

   **A row makes TWO claims, so it is tested twice.** "The call is here" and "its error is checked" are different assertions, and requiring one pin to depend on the call proved only the first: an exact pin on the row's own call plus an `if (other.error)` pin copied from the neighbouring site passed every layer while the call never inspected its own result (whole-diff R17 F1) — the substantive defect this guard exists to catch. The second claim is tested by OBSCURING the names the site's result is bound to (`const x = await …`, `x = (await …)`, and every name in a destructuring binding) and requiring a pin that **survives the call erasure but fails the binding obscure**. The independence matters: the call pin fails both tests on its own, so "some pin fails each" left the borrowed error pin unexamined. A pin that speaks about the result, and not merely about the call, is exactly what the error claim needs.

   Only the ARGUMENT is erased, never the callee. That was this repair's own first bug and a mutant caught it: with `sb.from` blanked, a pin of `/sb\.from\(/` — which names the member and nothing else, and would discharge any `from` row in the file — stops matching and is ACCEPTED. Leaving the callee in place keeps it matching, so it is rejected, which is what "this pin guards THIS site" has to mean. Pinned by a planted rejection with its passing control.

3. for `coveredBy` rows: each cited path must BE a test suite (`tests/**/*.test.ts` or `.tsx`) — any readable file satisfied the citation before, so a row could cite the production module it is registered against, which trivially supplies both the `via` and the table literal and discharges the row with no test at all (whole-diff R16 F2). `via` must EXACTLY match an exported identifier of the scanned source file, **read from the parse** — the module's own export declarations, including `export { addAdminEmail }`. A line-anchored regex counted text that merely LOOKED like an export: a line inside a multiline template, or after a backslash continuation, made a bogus `via` pass (whole-diff R4 F5); it also could not see a re-export list, which is a real export, so that limit went away with the recognizer. Destructuring exports bind real callable names, so `export const { addAdminEmail } = impl` and its renamed, array, nested and rest spellings all count (whole-diff R16 F3 — omitting them rejected an honest `via`, loud but wrong). Only RUNTIME, NAMED bindings count: `export declare …` and every type-only spelling (`export type { X }`, `export { type X }`) parse as exports and export nothing callable, and a DEFAULT export binds the name `default` whatever its declaration is called — `export default function addAdminEmail` does not export `addAdminEmail` (whole-diff R12 F2), nor do the list spellings `export { f as default }` and `export { default } from "./other"`, which bind the same non-named export (whole-diff R15 F2). A NAMED re-export is a real callable binding and is accepted, so none can discharge a behavioral citation (whole-diff R5 F3). An empty `via` and a strict-prefix typo (`addAdmin` for `addAdminEmail`) both fail, since a containment predicate would pass both (spec R3 F2); and EACH cited suite must MENTION the row's `literal` OR its `via` — where the names a suite mentions are read from ITS parse: every identifier it writes and every static string it contains. Text containment cannot answer this, and three rounds proved it one spelling at a time: ASCII `\b` let `x$get` satisfy `$get` (whole-diff R7 F1), a letter/digit approximation of IdentifierPart let `get\u0301x` satisfy `get` (R8 F1), and raw `#` and `\` still let `#get`, `get\u0301x` and `admin_emails\u005Fv2` satisfy their tokens (R10 F1). Source text is not identifier text — `\u005F` IS an underscore and `#get` is not `get` — and only the lexer knows. Same move as §3.2's, for the same reason. String literals count alongside identifiers because a table name is cited as a string, and because a mention in a test title is §6.5's ratified limit; comments contribute nothing, which is where R2 F4's comment-only rejection now comes from rather than a separate strip. The OR is there because a suite that mocks at the client boundary never mentions the table literal (spec R2 F1: `tests/data/adminEmails.test.ts` contains `listAdminEmails` 7 times but `admin_emails` zero times; the literal-only check could never be green there).

Registry contents (all 17 sites; the plan enumerates the exact pin regexes, typechecked):

- `lib/data/listShowsForCrew.ts` — 2 pin rows: `/const\s+\{\s*data:\s*tokens,\s*error:\s*tokenErr\s*\}\s*=\s*await\s+supabase\.rpc\("my_share_tokens_for_email"\)/` plus the `if (tokenErr)` throw pin; the matching `{ data: shows, error: showErr }` + `if (showErr)` pins for the `.from("shows")` read.
- `lib/data/loadShowShareToken.ts` — 1 pin row: the try/catch wrap around `supabase.rpc("admin_read_share_token"` and the `const { data, error } = result` + `if (error)` pins.
- `lib/data/getShowForViewer.ts` — 10 pin rows: per-site result-object pins — `.from("hotel_reservations")` read into `hotelRes` with `hotelRes.error` checked; same shape for `showRes`, `roomRes`, `contactsRes`, the two `crew_members` reads, the two `shows_internal` reads, `transportation`, and the `viewer_version_token` RPC (`versionRpc`).
- `lib/data/adminEmails.ts` — 4 `coveredBy` rows: the `admin_emails` read cites `tests/data/adminEmails.test.ts` with `via: "listAdminEmails"` (exported at `lib/data/adminEmails.ts`, `export async function listAdminEmails`; the suite mentions the symbol 7 times but never the table literal — spec R2 F1); the `upsert_admin_email_rpc` / `revoke_admin_email_rpc` sites cite `tests/data/adminEmails.test.ts` (literal present there), `via` `addAdminEmail` / `revokeAdminEmail` (spec R3 F1: the live export wrapping the upsert RPC is `addAdminEmail`, `export async function addAdminEmail` — there is no `upsertAdminEmail` symbol); the `set_admin_developer_rpc` site cites `tests/data/setAdminDeveloper.test.ts` (spec R1 F3), `via: "setAdminDeveloper"`.

**Authoring bar for a `coveredBy` row (human-reviewed, per limit 7):** the cited suite must exercise BOTH arms of the boundary through the named `via` — the RETURNED error and the THROWN/rejected call — because invariant 9 requires them to be distinguished and both to surface as a typed infra fault. The machine proves the citation is live (§3.4); it does not prove the suite reaches both arms, and attempting to recognize that textually would be the scope ratchet §1.3 forbids. All four shipped rows were audited against this bar and two gaps were repaired in-branch: `revokeAdminEmail` had no thrown-call test (whole-diff R2), and `listAdminEmails` could not have one, because the suite's `.from()` mock had no way to throw or reject (whole-diff R4). Both suites now cover both arms, verified by a `wrapInfra` mutant that reds them.

**`coveredBy` rows are themselves executable, not prose:** the §3.4 validation asserts suite existence plus literal-or-`via` containment, so a behavioral citation to a suite that never mentions either fails, and a suite deletion or rename fails. This is what makes the behavioral discharge as falsifiable as a pin. (A suite that mentions the symbol without meaningfully exercising the boundary is a documented limit — §6.5.)

The gate-count-reconciliation lesson still holds — produced must equal classified — but the classification is now the registry itself, and the "produced" side is always the live extraction.

### 3.5 Scanner self-tests (Layer 3)

Planted string fixtures (the `plant()` pattern from `tests/docs/_metaLedgerInProgress.test.ts`), asserting the scanner:

- matches `.from("x")`, `.rpc("x")`, single-quote variants, no-substitution template literals `` .from(`x`) `` (positive — spec R2 F2), AND explicit-type-argument forms `.rpc<T>("x")` / `.from<A, B>("x")` including a multi-line generic segment (positives — spec R4 F1);
- matches a literal containing the OTHER quote characters, a bare `$`, an escaped quote, or nothing at all — `.rpc("cost$center")`, `.from("crew's")`, `.rpc('say"hi')`, `` .from(`cost$center`) ``, `.from("say \"hi\"")`, `.from("")` (positives, one per shape — whole-diff R1, F13);
- matches every non-adjacent spelling of the call — a space or a comment before the generic segment, and optional-call `?.` in both positions — while `Array.from (iterable)` and `Array.from?.(iterable)` stay negative (whole-diff R3 F2, F3);
- rejects a row whose pin embeds its literal only as a SUBSTRING (`shows` inside `shows_internal`) and one whose literal is empty, each paired with a passing honestly-coupled control so the rejection is the rule and not an unsatisfiable fixture (whole-diff R3 F1);
- matches an ESCAPED `\${` as the static name it is (`` .rpc(`cost\${center}`) ``) while still dropping a live `${t}` and one behind a literal backslash; matches a backslash LINE CONTINUATION in every JavaScript terminator (LF, CR, CRLF, U+2028, U+2029) — whole-diff R2 F1, F2;
- rejects a `coveredBy` citation whose only mention of the literal or `via` is in the cited suite's COMMENTS (whole-diff R2 F4);
- asserts registry PRECEDENCE on the reconciliation itself, not on orphan status: a waivered file carrying rows still reports a per-site mismatch when it gains an unpinned call. Asserting precedence through `undischargedFiles` alone is vacuous, because "not an orphan" cannot distinguish discharged-by-rows from discharged-by-waiver, and chained filters are a conjunction whose order cannot change the result (whole-diff R2 F5);
- fails LOUDLY rather than quietly on near-miss waiver spellings (`//not-subject-to-meta:`, a doubled space, a space before the colon, the `/* */` block form): each is unrecognized AND leaves the file undischarged, so Layer 1 reds and names it. The same posture is pinned for a `via` exported only through a re-export list (`export { addAdminEmail }`), which `validateRows()` rejects by name rather than accepting. These pin the SIGNALLED half of §1.4 so the guard's conservative directions stay decisions rather than accidents;
- does NOT match `Array.from(iterable)`, `Array.from({ length: n })` (negative);
- does NOT match `.from("x")` inside `//` or `/* */` comments (negative — proves the strip is load-bearing);
- does NOT match `.from(tableVar)` or a substitution template `` .from(`${t}`) `` (negatives — the §6.1 documented limit, asserted deliberately so the limit is executable, not prose);
- `validateRows()` self-tests: an empty `pin`/`coveredBy` array is rejected (R2 F3); a row whose pins all lack the literal is rejected (R2 F4); a `coveredBy` row whose suites mention neither literal nor `via` is rejected (R2 F1); an empty `via` and a strict-prefix-typo `via` (`addAdmin`) are rejected by the exact-export check (R3 F2);
- waiver self-tests (R3 F3): a blank-reason marker (`// not-subject-to-meta:` with nothing after) does NOT waive; the marker inside a string literal does NOT waive; a well-formed commented marker DOES waive.

## §6 Documented limits (accepted, not findings)

1. **Dynamic call arguments are invisible.** `.from(tableVar)`, `.rpc(fnVar)`, `.from(TABLE.shows)` and substitution templates (`` .from(`${t}`) ``, `` .from(`a${t}b`) ``) name a table the source does not state, so the parse cannot report one. No-substitution templates ARE matched, including ones containing a bare or escaped `$` — the grammar, not a character ban, separates the two. No such dynamic site exists in `lib/data` (§4) and the repo convention is literal table names. Worst case: a dynamically-named read escapes the guard — a conservative miss, no silent corruption of anything the guard already covers. Pinned executable by Layer 3 negatives. (The former carve-out for generic segments containing parentheses or nested angle brackets is RETIRED: it was an artifact of bounding `<...>` in a regex, and both forms are now planted positives — §3.2.)

2. **File-grain waivers on unregistered files.** A waiver anywhere in an unregistered file discharges all its sites (inherited from the auth test's semantics; registry precedence in §3.3 closes this for every currently-multi-site file). Worst case: a contributor waivers one site and a second site rides along — the per-site reconciliation does not apply to waiver-discharged files. Accepted: zero waiver-discharged files exist today, and promoting one to the registry is the documented response if one appears.
3. **Shape pins are text pins.** A pin proves the source text contains the compliant shape near the call, not that control flow reaches it. The behavioral suites in §2's table carry the runtime half; this guard is the structural half. Same division as the auth meta-test.
4. **`supabase.auth.*` and storage calls are out of scan scope** — the scanner keys on `.from(`/`.rpc(` only, matching the ledger entry's scope. No such call exists in `lib/data` today; if one lands it is invisible to Layer 1. Files to the same response as limit 2: register or extend the regex when the first site appears.
5. **`coveredBy` proves mention, not exercise.** The executable check on a behavioral row (§3.4) asserts the cited suite exists and contains the site's literal or `via` symbol in LIVE code (comments are stripped first, whole-diff R2 F4) — it cannot prove the suite meaningfully exercises the boundary, and an import, a test title, or an unrelated string still counts as a mention. The runtime half stays with the behavioral suites themselves (same division as limit 3). Worst case: a hollow citation passes the structural check — conservative, and visible to any reader following the citation.
6. **Duplicate literals are distinguished by position, and that is now enforced rather than merely noted.** The two `.from("shows_internal")` and two `.from("crew_members")` sites in `getShowForViewer.ts` share a kind and a literal, so sequence order is their only identity. This limit previously accepted that a row could carry its twin's pin; whole-diff R16 F1 showed that outcome is SILENT, so it was repaired rather than kept: the coupling erasure targets the ordinal site (§3.4 rule 2), and a row pinned to its twin is rejected. What remains is the ordering itself — reordering two same-literal sites AND their rows together still reconciles, which is a faithful description of a file whose reads were reordered.
8. **Other built-in `from` receivers are reported, loudly.** `Buffer.from("abc")`, `Readable.from("abc")`, `Uint8Array.from("abc")` and `globalThis.Array.from("abc")` are calls to a member named `from` with a static string argument, so the scanner reports them; only `Array.from` is excluded, because it is the one such collision present in this corpus (`lib/data/normalizeDateRestriction.ts`). Deliberately not generalised (whole-diff R6 F2): enumerating built-in receivers is an open set, and this arc has already paid five rounds for a recognizer whose convergence criterion was enumeration. Worst case is a LOUD false positive — a red test naming the line, answered by one waiver comment — which §1.4 admits. The heuristics that would close it (excluding capitalized receivers, say) trade this for a SILENT miss on a client held in a capitalized binding, and that trade is the one the consequence bound forbids. Pinned executable: a planted test asserts these ARE reported, so the limit is a stated behavior rather than an accident.

7. **Pin strength beyond literal-coupling is human territory.** `validateRows()` proves a pin is non-empty, matches the source, and embeds its own literal (§3.4); it cannot prove the pin asserts a MEANINGFUL error-handling shape — a contributor could author `pin: [/from\("new_table"\)/]`, which matches the call itself and nothing else. That is deliberate weak authoring, outside the §1.3 fence (accidental mistakes), and lands in PR review where the pin text is visible. Same division as limits 3 and 5: the machine proves presence and coupling; humans review strength.
