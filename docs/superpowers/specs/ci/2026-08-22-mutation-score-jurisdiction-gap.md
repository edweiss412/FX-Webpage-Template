## §0 Problem

`psqlStartupScan` (`tests/mutation/source/registry.ts`, row `id: "psqlStartupScan"`) is enrolled with a SCOPED operator subset, `relational-boundary` + `regex-quantifier-bound`, ratified by the 2026-08-16 enrolment spec §1.1 because the full six-operator set is hours of per-mutant children. Diff round 3 of `fix/shell-attached-redirection-target` found a regression that arc had introduced: `$((...))` arithmetic lexed as a `$()` command substitution, yielding a resolved psql site for a command bash never runs. Four earlier review rounds and a `49/49` score with zero unaccepted survivors had passed over it. The score could not see the branch: both declared operators enumerate ZERO sites over it, and the branch's own tests are equality checks and a `Math.max`, which no declared operator rewrites.

The row's severity line is exact and is the whole defect: **the number is honest and its jurisdiction is not stated.** A reviewer handed `49/49, 0 unaccepted survivors` as the convergence criterion had no way to read, from that line, that the score ranged over 2 of 6 operators and reached none of the code the diff added. Worse, the admissibility rule in `AGENTS.md` convergence bullet 4 says a "does not pin X" finding without a surviving mutant from the declared set is REFUTED or an operator proposal. Read literally on that arc, a reviewer's correct finding about the arithmetic branch was refutable by a score that structurally could not see it. The finding survived only because the reviewer probed bash, which is the probe-domain half of the convergence criterion doing the work the score cannot.

The general shape outranks the instance, and the row says so: a mutation score answers "does the suite pin what is WRITTEN". It cannot answer "is what is written the whole domain", because a construct the code never distinguished generates no mutant of that code. Before the fix the `$((` branch did not exist, and no operator over any registry configuration could have generated a mutant of code that was absent. After the fix the branch exists, and its terminal verifier is a bash-oracle matrix that derives every expectation from whether the shell executed the command, a stronger instrument than any mutant of the branch (`tests/cross-cutting/psqlStartupFileSuppression.test.ts`, test "the scanner agrees with BASH on every arithmetic-versus-substitution spelling").

### §1.2 Outcome (a), a per-region enrolment mechanism: DECLINED

**What it would be.** A registry field scoping extra operators to a region of a file rather than the whole file: `regions: [{ anchor: <unique source text>, extent: "statement", operators: [...] }]`, with `enumerateSites` filtering region operators to the anchor's enclosing statement. The anchor-uniqueness check would reuse the `control.from` mechanism (`tests/mutation/source/registry.ts`, symbol `validateSurface`, the "occurs exactly once" branch), and the two `$((` arms have unique anchors today (§1.0).

**What it would buy on this instance.** Mutants from the four undeclared operators inside the two arms. Read against the oracle matrix: flipping the guard's `&&` or `===` makes the arithmetic arm fire on ordinary `$(` text, which the matrix's control row and the suite's existing substitution cases kill; removing the `lexShellWords(...)` call inside the arm is killed by the matrix's nested-substitution row; the `i + 3` offsets and the `Math.max` bound move a nested entry's `offset` or drop a delimiter, which no consumer of a nested arithmetic entry observes today and which would therefore arrive as `equivalent` ledger rows. So the region buys kills the matrix already proves, plus ledger rows, plus possibly one narrow gap (the `line +=` newline count across a multi-line `$((` span) that is a single deciding-suite case, not a mechanism.

**Why it is declined, three failure modes.**

1. **It is the ratchet, made declarable.** A region is a second grain of enrolment that a reviewer can demand for every branch a diff adds to a scoped surface ("why is the new arm not region-enrolled?"). That converts every diff on the seven scoped surfaces (7 of 42 rows declare a strict subset at HEAD: `premiseScan` 3, `paneCompactionCore` 5, `psqlStartupScan` 2, `serializeErrorStructure` 5, `mutationSurfaceEnumerate` 3, `mutationSurfaceTotality` 3, `spawnBounded` 4) into a region-enrolment decision taken under review pressure, which is the exact posture R1 exists to refuse. The region grammar itself (anchor forms, extent kinds: statement, block, function) is a recognizer that grows one shape per round.
2. **It touches the seam this spec is fenced from.** A region changes the surface's mutant count, so it changes `weightOf` and can repartition shards (§1.3 measures a widening moving 20 surfaces). R5 puts that seam with `BL-MUTATION-WEIGHT-MODEL-BOOT-COUNT-ONLY`, and a mechanism that cannot land without coordinating a repartition is not an L-effort close.
3. **It does not address the general shape.** The incident's regression was in code that did NOT EXIST before the fix. No region over absent code generates a mutant. A region mechanism closes the scoped-subset sub-case of the jurisdiction gap and leaves the general case exactly where it is: `executionMethodsDerivation` sat at 1.00 with zero unaccepted survivors while a `Set` member was missing, "because mutation testing perturbs code that EXISTS and a missing member of a `Set` literal is not a mutation of existing code" (`BACKLOG-archive.md`, entry `BL-EXECUTION-METHODS-DERIVED-FROM-DRIVER-TYPES`). Shipping a mechanism whose spec must say "this still cannot see absent code" buys registry complexity for a sub-case the oracle already covers.

### §1.4 Outcome (c), documented limit plus required disclosure: RATIFIED

The jurisdiction gap is a PROPERTY of mutation scoring, not a defect of this registry row. The close is therefore to (i) state the property where the harness states its limits, (ii) make every quoted score carry its jurisdiction, mechanically, at the one boundary every score passes through, and (iii) stop the admissibility rule from letting a score refute a finding about code it cannot see.

**What (c) answers.** After this spec, a round-1 diff brief cannot carry a `MUTATION SCORE:` arm, on a plain or heading-form declaration line, without naming the operator set that score ranges over (§2.2); `AGENTS.md` bullet 4 says the surviving-mutant requirement binds only where a declared operator reaches the code, and that a finding on unreached code is settled by a domain probe and repaired by a test (§2.3); the harness spec carries the limit with this instance's numbers (§2.4); the row graduates with its measured close (§2.5).

**What (c) still cannot do, stated so it is not re-derived.** It does not make any score see the `$((` branch; the branch's coverage remains the oracle matrix (R3). It does not detect a construct the code never distinguished; nothing can, and the disclosure is what keeps a reviewer from reading a perfect score as evidence about it. It does not verify the disclosed operator set against the registry (§4 L-A); a wrong `OPERATORS:` tail is loud in the brief the reviewer reads, the same posture as a below-floor score.

**Why this is the L-effort close the brief budgets for.** The plan is the ledger edit, the limits record, and the disclosure-line rule with its gate test. No enrolled source, deciding suite, or registry row is edited, so no score is retired and no shard moves.

## §2 Design

### §2.1 The jurisdiction statement (definition, cited by everything below)

> A mutation score is complete over its DECLARED OPERATORS applied to CODE THAT EXISTS in the enrolled source. Its jurisdiction is that product and nothing more. Code no declared operator reaches is outside it; code that does not exist is outside every possible configuration of it. A score quoted without its operator set is a number without its jurisdiction.

### §2.2 The disclosure arm (the mechanical half)

The GUARD SURFACE dispatch gate (`scripts/codex-guard.mjs`, symbol `checkGuardSurfaceDeclarations`; contract `docs/superpowers/specs/ci/2026-08-15-round-economy-enforcement-pair.md` §2.1 item 4) gains one requirement on the SCORE ARM only:

- A line whose remainder satisfies the score arm (`MUTATION_SCORE_ARM`) must ALSO, on that same line, contain `OPERATORS:` followed by a non-empty tail: regex `/\bOPERATORS:\s*\S/` over the remainder. The tail is the author's: the comma-separated declared operator names (`tests/mutation/source/operators.ts`, `OPERATOR_NAMES`), or the literal `all` for a full-set row. Presence is checked; membership is not (§4 L-A, the same posture as the cannot-express arm's citation quality and the score arm's floor).
- **The trigger recognizes the CommonMark ATX heading form (spec review round 1, BLOCKING, repaired here).** The shipped trigger `/^\s*GUARD SURFACE:(.*)$/` (`scripts/codex-guard.mjs`, symbol `checkGuardSurfaceDeclarations`) never matched a declaration written as a Markdown heading, and the corpus writes it that way. **INCIDENT, measured 2026-08-22** (the fact that licenses touching the trigger at all under a documented-limit close): swept over every brief in `/Users/ericweiss/FX-worktrees/_briefs/`, the 77 declaration-shaped lines are 53 plain-form and 24 ATX-heading-form (`## GUARD SURFACE: …`), with ZERO list-item, blockquote, or bold forms (the other 47 of 124 hits are prose mentions inside code spans or sentences, not declarations). The commands, re-runnable:

grep -n "GUARD SURFACE:" /Users/ericweiss/FX-worktrees/_briefs/*.md        # 124 hits: 53 plain, 24 heading, 0 list/quote/bold, 47 prose

 Of the 25 round-1 diff briefs that contain the marker, the shipped trigger recognizes 14 files and a heading-aware trigger recognizes 24; the 25th mentions it only in prose. So ten declaring round-1 briefs were dark to the gate, among them the filing arc's own round-1 brief (arc-shell, dated 2026-08-20, in the briefs directory the probe domain names; its line reads `## GUARD SURFACE: psqlStartupScan — MUTATION SCORE: 42/42 plus 0 unaccepted survivors`, which the canonical score arm also rejects on its `plus` separator, so it dispatched only because the heading hid it). The trigger becomes `/^\s*(?:#{1,6}\s+)?GUARD SURFACE:(.*)$/`: one CommonMark structure (one to six `#` then whitespace), keyed on structure rather than spelling. Everything else stays a non-declaration (§4 L-E). This is the measured, in-domain, accidental-author input the repair-direction rule widens for; the sweep is the finite cover, and the 24 heading-form lines are replayed as gate fixtures (§5 AC-9).
- **Marker precedence: the `MUTATION SCORE:` marker selects the arm, and nothing rescues a score-shaped line (spec review round 2, BLOCKING, repaired here; family swept at the orchestrator's instruction before round 3).** The shipped control flow falls from an unsatisfied score branch through to the cannot-express check, so a line carrying a `MUTATION SCORE:` without `OPERATORS:` AND a `CANNOT-EXPRESS:` tail dispatched on the second arm: a quoted score passing without its jurisdiction, the exact thing the consequence bound forbids. One real corpus instance exists (a two-half surface declared on one heading line, arc-H, 2026-08-17; the reviewer's probe over every declaration in the briefs directory and the committed dispatch history: `{total:77, scoreOnly:50, cannotOnly:15, both:1, neither:11}`). Round 1 found the trigger form, round 2 found a rescue arm outranking the disclosure; both are arm-precedence gaps in one grammar, so the rule is stated once, over every combination, derived from the shipped control flow rather than from the two instances:

  | `MUTATION SCORE:` on the line | canonical score with safe operands | `OPERATORS:` tail | `CANNOT-EXPRESS:` tail | verdict                           | deciding arm                  |
  | ----------------------------- | ---------------------------------- | ----------------- | ---------------------- | --------------------------------- | ----------------------------- |
  | absent                        | n/a                                | any               | non-empty              | dispatch                          | cannot-express                |
  | absent                        | n/a                                | any               | absent or empty        | reject (bare)                     | none                          |
  | present                       | no (non-canonical, `0/0`, `2/1`, unsafe integers) | any | any                  | reject (non-canonical score)      | score marker, never rescued   |
  | present                       | yes                                | absent or empty   | any                    | reject (no `OPERATORS:`)          | score marker, never rescued   |
  | present                       | yes                                | non-empty         | any                    | dispatch                          | score                         |

  So the marker `MUTATION SCORE:`, wherever it sits in the remainder, makes the line a score declaration: it is decided by the canonical score arm plus the `OPERATORS:` check and is never consulted against the cannot-express arm, whether its score is valid or not. The cannot-express arm decides only lines with no `MUTATION SCORE:` marker. An `OPERATORS:` tail on a line with no score marker is inert (it neither rescues nor rejects). A line that wants to declare a scored half and a cannot-express half declares them on two lines, which is what the per-line contract already says (enforcement-pair §2.1 item 4, one surface per line). Every existing gate fixture keeps its verdict under this table (the non-canonical, `0/0`, `2/1`, unsafe-integer, floating-fraction and fenced cases all still reject or still stay inert for the reason they did), which the plan's gate run proves; the table adds exactly two rejections the shipped code did not make: a score-shaped line rescued by a cannot-express tail, valid or not.
- The cannot-express arm is otherwise unchanged: a surface the registry cannot express has no operator set to disclose.
- The trigger point (round-1 diff only), per-line discipline, fence stripping (`stripCodeBlocks`, so a heading inside a fence is stripped like any other line), exit code and no-dispatch-on-rejection behaviour are unchanged. The rejection message names the third element: `each GUARD SURFACE: line in a round-1 diff brief must carry its own MUTATION SCORE (<killed>/<total> plus "0 unaccepted survivors" plus OPERATORS: <declared names, or all>) or CANNOT-EXPRESS: <probe citation> — see AGENTS.md convergence-criterion bullet 4`.

Canonical conforming line, which the plan's gate test uses verbatim:

```text

```

Why the gate and not a prose rule: the orchestrator's lessons record already said "state, when quoting a score, WHICH operator families it ranges over" when the filing arc quoted `49/49` without them. "Adding a 123rd rule to a set whose measured failure is that 122 are not applied buys nothing" (`docs/agents/spec-self-review.md`, accept-set discipline paragraph); the enforcement is the dispatch boundary, where the same paragraph puts the convergence gate. The gate is round-1-only and the repair for a rejected brief is one clause.

Why presence and not membership: validating the tail against the registry means importing a TypeScript module, or a second copy of `OPERATOR_NAMES`, into a plain-node CLI wrapper, which is the recognizer-growth shape the enforcement-pair spec fenced at its §5 item 8 for the floor. The threat fence is accidental omission, not evasion; an author who writes `OPERATORS: all` on a scoped row has stated something checkable by the next reader, which is the whole point.

**Fleet effect, stated.** Every round-1 diff brief that carries a score arm and no `OPERATORS:` tail exits 2 at dispatch with the message above, from the moment this merges, and that now includes the heading-form briefs the gate previously never read: a heading-form line is held to the whole canonical grammar, separator included, so a `plus 0 unaccepted survivors` heading is rejected on the separator as a plain-form line always was. The gate is round-1 only, so in-flight arcs past round 1 are unaffected; an arc dispatching round 1 after this merges adds one clause or fixes one separator. The orchestrator is told in the readiness report.

### §2.3 The admissibility correction (the contract half)

`AGENTS.md`, convergence-criterion bullet 4 ("Score, when the surface is enrolled"), is rewritten in place, the superseded sentences deleted rather than left beside the new ones, so that it says, in this order:

1. the convergence criterion is the score plus the empty unaccepted set, **stated with the operator set it ranges over** (the `OPERATORS:` arm of the `GUARD SURFACE:` line), because the score's jurisdiction is its declared operators applied to code that exists (§2.1);
2. a "does not pin X" finding is admissible only with a surviving mutant from the declared set **where at least one declared operator reaches X**;
3. where no declared operator reaches X (an excluded operator of a scoped subset, or a construct the code does not yet distinguish), the score says nothing and cannot refute: the finding is admissible with a domain probe drawn from the brief's `PROBE DOMAIN:`, and its repair is a deciding-suite case (the `psqlStartupScan` arithmetic-branch precedent: a bash-oracle matrix), never a registry widening under review pressure;
4. a score is never offered as guard completeness; the existing "operator proposal" disposition remains for gaps a declared operator COULD reach with a different operator set.

The bullet carries no numbers; the numbers live here (§1.0, §1.3) and in the harness spec's limit (§2.4). The `AGENTS.md` line under "Codex dispatch guard" that describes the GUARD SURFACE grammar ("Guard-surface briefs (round-1 diff only)") gains the `OPERATORS:` element in the same edit.

The harness spec's §6.1 keeps its dated quotation of the original bullet and gains one sentence naming `AGENTS.md` as the live text and §7 L-11 as the jurisdiction amendment, so a reader of §6.1 is not sent to a superseded bullet.
