**Status:** Ready for adversarial review
**Date:** 2026-08-15
**Branch:** `feat/mutation-section-order` (continues `BL-MUTATION-SECTION-ORDER`; supersedes wave-plan branch-5 Tasks 3–4)

## 1. Problem

`UNKNOWN_FIELD` is emitted today from two sites: 386 of the corpus's 394 emissions come from the positional sweep inside `parseVenue` — a scope window opening at the first recognized venue field and closing at the first `VENUE_BLOCK_TERMINATORS` row (`lib/parser/blocks/venue.ts`, `inVenueFieldScope`; emission via `emitUnknownField`, `lib/parser/warnings.ts:351`) — and 8 from `parseEventDetails`'s block-local unknown-label fallback (`event.ts:225`), the 8 including all four Stage/Storage audited true positives (review probe docs/superpowers/specs/parser/probes/2026-08-15-rev-probe-kinds.ts; the narrowing audit's per-fixture table attributes all 394 to the window — its drop conclusion survives, since none of the 8 sit in the venue block either, but the attribution is corrected here). The parity probe proved the window is a positional artifact: spec §7.2(a) (emission parity) and §7.2(b) (swap invariance) are jointly unsatisfiable, and the honest position-free sweep costs +4,291 emissions (12×).

The 394-emission audit settled what the signal actually is:

- **0 of 394** emissions sit in the venue block proper — every fixture's venue block is clean.
- **~380 of 394** are junk swept from neighbor blocks: crew rosters, gear pull-sheets, agenda tables, a Google-Forms echo, xlsx artifacts.
- **~14 of 394** are genuine near-misses of KNOWN field labels — none of them venue fields: the 8-row colon-suffixed client-contact group (`Phone:`, `E-mail:`, `Cell Phone:`, `Address:`, …), `Stage`/`Storage` vs `event.stage_size`/`event.equipment_storage`, and the 2-row `ADDITIONAL ROOM` header (later resolved as already-recognized and deliberately stub-gated - §2.3).

The product that was accidentally being delivered is therefore a **label-similarity near-miss detector**, and position was never the right key. This spec replaces the positional sweep with that detector, keyed on content alone.

## 1.1 Resolved scope — do not relitigate

1. **Coverage-audit product is dead.** Telling Doug which sheet sections are intentionally ignored reports the system working as designed and reads as a broken parser. User-ratified 2026-08-15 (session record; probe: dark blocks are office-side working data). No whole-document "unrecognized section" widening ships.
2. **Quieting is ratified.** Corpus emissions go 394 → the calibrated baseline (§3.2; 65 rows after the r4 recalibration — the ratified 72 lost 7 rows to the resolution-site consumption repair, which removed a false-positive class where a correctly named curated field with an empty value warned as a near-miss of itself; the quieting decision itself is unchanged in kind). The wave spec's §7.2(a) parity constraint is superseded by this spec: the new baseline is the calibrated multiset, regenerated deliberately. User-ratified 2026-08-15 after reviewing the audit.
3. **The `UNKNOWN_FIELD` code is kept**, not replaced: same §12.4 row identity, same gap class (`lib/parser/dataGaps.ts:38`), same actionable-anchor membership (`dataGaps.ts:414`), same help-family routing (prefix `"UNKNOWN"`, `app/help/errors/_families.ts:82`). Copy updates to near-miss framing (§5). No new warn code, no enum churn, warning-fingerprint continuity preserved.
4. **No edit-distance fuzzing in v1.** The corpus contains zero letter-typo instances (audit judgment table). Deterministic normalization + token-subset only; edit distance is a documented extension (§9), admissible later only with a live instance.
5. **Wave-plan branch-5 Tasks 3–4 are superseded** by this spec's task set; Tasks 1–2 (parity pin, swap-invariance RED tests) are kept and repurposed (§8). Recorded as a ratified amendment in the wave overview (`docs/superpowers/plans/2026-08-08-parser-mutation-wave/00-overview.md`).
6. **`UNKNOWN_SECTION_HEADER` is out of scope.** The section-level near-miss gate (`lib/parser/index.ts:731-759`, `emitUnknownSection` at `index.ts:758`) ships unchanged. Its strictness is correct under the near-miss framing: blocks that don't look like sections ("Pending", "Timestamp") SHOULD evade it.
7. **Threat model.** The detector defends against accidental authoring mistakes by sheet editors (typos, punctuation variants, encoding artifacts). Adversarial obfuscation is out of scope and files to documented limits.
8. **Consequence bound.** Every input row is either parsed by a block parser, flagged as a near-miss, or silently ignored as not-field-shaped — and "silently ignored" is the DESIGNED outcome for office-side content, not a defect. A hypothetical escaping input is a finding only with a probe showing a near-miss of a real field going silent; conservative silence on junk is the intent.

## 2. Mechanism

### 2.1 What is removed

- `parseVenue`'s scope window: the `inVenueFieldScope` flag, the `VENUE_BLOCK_TERMINATORS` scope-close behavior for unknown-field purposes, and the `emitUnknownField` call inside `parseVenue` — all in `lib/parser/blocks/venue.ts`, anchored by those three symbols (line locators rot; the symbols are unique in the file). `parseVenue` keeps parsing venue FIELDS exactly as today; the venue suite's PAYLOAD assertions (`tests/parser/blocks/venue.test.ts`) stay green unchanged. **Direct block-parser emission tests are updated in the same commit as the removals (r5 finding 3 — four sites, verified by static probe):** the two `parseVenue` UNKNOWN_FIELD/raw-unrecognized cases (`tests/parser/warnings.test.ts:213` and `tests/parser/warnings.test.ts:233` region, drafting-time locators), the out-of-scope-alias UNKNOWN_FIELD assertion (`tests/parser/blocks/venue.test.ts:301`), and the direct `parseEventDetails` unknown-label emission case (`tests/parser/blocks/event.test.ts:403`). Each flips to the new contract — the block parser emits NO `UNKNOWN_FIELD` and pushes NO `raw_unrecognized` entry (the detector at the document seam owns both) — with replacement positive coverage living in the detector suite and the corpus baseline. `emitUnknownField` couples the warning and the `raw_unrecognized` push (`lib/parser/warnings.ts:365`), so the persisted `raw_unrecognized` array follows the emission set (394 → 65) — part of the same ratified quieting delta; it is storage-only surface, deliberately never selected by observe (`lib/observe/query/warnings.ts:10`).
- `parseEventDetails`'s fallback emission: the `emitUnknownField` call in `lib/parser/blocks/event.ts` (unknown-label fallback branch, drafting-time locator `event.ts:225`). The fallback's self-slug STORAGE behavior (`toCanonicalKey` write, `event.ts:407-412`) is UNCHANGED — payload compatibility — but its warning emission moves to the detector, which is the sole `UNKNOWN_FIELD` emitter after this change. These are the only two `emitUnknownField` call sites in `lib/parser/` (verified by grep 2026-08-15); a structural assertion in the detector suite pins "exactly one call site" going forward.
- **`TYPO_NORMALIZED` is re-gated, not orphaned.** The scope flag §2.1 removes has a second reader: the `TYPO_NORMALIZED` info emission at `venue.ts:135`, deliberately scope-gated by a prior review decision (`venue.ts:149-155`). NOT the store event: the r2 re-review proved a store-conjunct unsatisfiable — the only `venue.*` typo alias is `Hotal Contact Info` → `venue.contact_info` (`lib/parser/aliases.ts:27`, TYPO_ALIASES at aliases.ts:142-147), a field `parseVenue` never writes, so a store-gated emission is dead code. Under block membership the emission is REACHABLE (a constructed fixture places a typo-alias row inside the venue block) while every corpus instance stays silent — the 10 fixtures carrying the `Hotal Contact Info` row all carry it in hotel blocks, and the corpus census is 0 today (review probe docs/superpowers/specs/parser/probes/2026-08-15-rev-probe-typo.ts) and 0 after (venue blocks are clean, audit table), pinned alongside the baseline (AC-N8). `FIELD_LABEL_AUTOCORRECTED` (the emission immediately following, venue.ts:156) is already row-local-proven and ungated — untouched.
- **Downstream comment + rationale refresh:** `lib/drive/unknownFieldAnchors.ts:16` ("The two blocks whose parsers call `emitUnknownField`") documents the `BLOCKS` array's rationale and goes stale with the call-site moves — updated in the same commit to name the detector as the emitter and §2.2's kind mapping as the anchor-namespace contract.

### 2.2 What is added

A new module `fieldNearMiss` under `lib/parser/` (created by this work): a document-level pass invoked from `lib/parser/index.ts` where block parsers finish (aggregator in hand, same seam family as the branch-4 `normalizeLeadingColumn` call):

- **Candidate rows (consumption-keyed accept-set):** a row is a candidate iff the actual parse left it unresolved — it is not a recognized section/alias row (`resolveAlias` at `lib/parser/aliases.ts:166`, `resolveAliasFull` at `lib/parser/aliases.ts:177`, `isKnownSectionHeader` at `lib/parser/knownSections.ts:202`, `canonicalSectionKind` at `lib/parser/sectionKind.ts:82`) and no block parser resolved it to a CURATED key. Consumption is reported by the parse itself (a consumption ledger on the aggregator, populated where block parsers resolve rows), NOT re-derived from a static exclusion list — the calibration probe proved static vocab exclusion misclassifies rows resolved by block-internal maps (`event.ts` `CANONICAL_KEY_MAP` "room diagram"; `transport.ts` resolution of "Load In:"). **Curated-key RESOLUTION excludes a row — whether or not a payload value was written; self-slug fallback storage does NOT** — `parseEventDetails`'s unknown-label fallback stores under a generic self-slug (`toCanonicalKey`, `event.ts:407-412`) without resolving to any real field, and those rows (including the corpus's most-confirmed true positives, Stage/Storage) remain candidates. §3.3 is the normative ledger semantics (resolution-site, r4-recalibrated). Position never enters — consumption is content/section-keyed, so the detector stays swap-invariant by construction.
- **Vocabulary (derived, never hand-listed):** all alias label strings from `FIELD_ALIASES` (`lib/parser/aliases.ts:19`) + all `SECTION_HEADER_TOKENS` + `LABEL_TO_KIND` keys. A later alias addition is covered automatically. `TYPO_ALIASES` (`aliases.ts:142`) members already resolve and are therefore never candidates.
- **Normalization (both sides):** the v3 rule as defined normatively in §3.1 (single source; an earlier v0 wording here was a defect the cross-model r3 review caught).
- **Match rule + guards:** §3 (calibrated form is normative; the executable single source is the calibration test baseline).
- **Emission:** one `UNKNOWN_FIELD` warning per matching row via `emitUnknownField`, message naming both the row label and the matched candidate (§5). No autocorrect field — the detector suggests, never rewrites.
- **`block`/`blockRef.kind` contract (normative — three consumers depend on it).** The detector emits kind (and `opts.block`) by an anchor-namespace mapping: `"venue"` when the row's physical block is the venue block — decided since 2026-08-27 by the shared `isVenueBlockOpener` predicate (`docs/superpowers/specs/parser/2026-08-27-venue-block-predicate-design.md` §2), so this mapping and the `TYPO_NORMALIZED` gate cannot drift apart and both corpus venue shapes are covered; `"details"` when it is a DETAILS-family block; otherwise the row's normalized physical block-opener label.

## 3. Calibration (normative)

Full measurement record: `docs/superpowers/specs/parser/probes/2026-08-15-near-miss-calibration.md` (probe scripts alongside; every number below is from its §7–10, measured stable across 3 independent runs). The committed baseline JSON (AC-N1) is the executable single source for expected emissions; the numbers here are the at-authoring-time record of that measurement.

### 3.1 Final rule (normative definition)

- **Normalization (both sides, "v3"):** decode HTML entities → casefold → collapse every run of non-alphanumeric characters to one space → trim. Additionally compute a **fused form**: delete hyphens sitting directly between two alphanumerics BEFORE the punctuation collapse (`E-mail:` → `email`); free-standing hyphens are untouched.
- **Match:** (a) normalized-string equality against a vocabulary entry, or (b) token subset-or-equal: the candidate's token set (plain or fused form) is a non-empty subset of, or equal to, some vocabulary entry's token set.
- **Guards (all three, deterministic, applied to EVERY match — type (a) and type (b) alike, exactly as the calibration executable does; guarding only type (b) lets `Details?` through as a type-(a) equality and inflates the firing count by one — cross-model r3 probe):** minimum normalized length 5; reject ALL-CAPS single-token candidates; require at least one candidate token whose vocabulary document-frequency is ≤ 4 (threshold = the frequency of "address", the least-distinctive required true-positive token — corpus-derived, not arbitrary).
- **Vocabulary:** derived per §2.2; 132 distinct v3-normalized entries at authoring time (174 raw strings).
- **Tie-break + candidate provenance (normative — r4 finding 4):** the vocabulary is built in DERIVATION ORDER (`FIELD_ALIASES` values flattened in declaration order, then the section-header token barrels, then the `LABEL_TO_KIND` keys); the first raw string producing a given normalized entry is that entry's stored RAW spelling, and later duplicates never overwrite it. Matching iterates the vocabulary in that same insertion order and the FIRST matching entry wins — deterministic by construction. The reported `candidate` is the winning entry's stored raw spelling, verbatim (e.g. `Address:` reports `VENUE ADDRESS`, `E-mail:` reports `Client Email`, `Diagrams?` reports the alias table's literal `DIagrams` spelling — raw provenance, never a lowercased normalized form). The baseline pins the candidate per row (AC-N1), so any tie-break drift fails the pin rather than self-blessing.

### 3.2 Measured corpus outcome (17 fixtures, 5,736 candidate rows)

- 77 rule firings, minus 12 rows the consumption ledger excludes (curated-key resolutions, §3.3: 5 with written values — 3× "Room Diagram" in DETAILS blocks, 1× "Notes" via `event.ts`'s curated map, 1× "Load In:" via `transport.ts` — plus 7 resolved-but-EMPTY curated rows found by the r4 recalibration: 6× "Room Diagram" in DETAILS-family blocks incl. `GS DETAILS (FOR BOTH)`, 1× roundtable "Notes") = **65 expected emissions**, the committed baseline (followup probe Part D; `SUMMARY-D … new_total=65`).

All residuals conservative and surfaced, pinned in the baseline JSON.
- **Confirmed non-catches** (each with its verified reason, probe §8): `ALT. E-mail:` (extra token), `Cell Phone:` (tokens span two aliases), `Fax:`/`Event Name:` (no vocabulary counterpart), `Other` (contextual). Dispositions in §9 Documented limits.
- Guard variants tried and REJECTED with measured TP loss (probe §4): multi-token-only subset matching (TP→0), distinctiveness ≤1 (drops `Address:`), block-opener-recognized gating (drops the fused-opener block's TPs). These are fenced: re-proposing any of them requires a probe showing zero TP loss on this corpus.

### 3.3 Consumption ledger semantics (measured, §7 of the probe)

The naive "payload changed ⇒ consumed" rule would have dropped Stage/Storage — `parseEventDetails`'s fallback stores them under self-slug keys while today also emitting `UNKNOWN_FIELD`. The normative definition is RESOLUTION-SITE (r4 recalibration — this supersedes the earlier write-site/deletion-diff wording): **a row is consumed iff a block parser resolves its label to a curated canonical key (exact map hit, alias hit, regex path, or gated fuzzy correction — `gatedVocabCorrect`, `lib/parser/blocks/event.ts:200-212` and event.ts:292-298), regardless of whether a payload value is then written.** The ledger mark sits AT the resolution decision, before any `presence()`/sentinel write filter. Why: deletion-diff semantics cannot see "resolved but empty" — the r4 review's corpus probe showed 6 `Room Diagram` rows and 1 `Notes` row that are exact curated fields with EMPTY values sitting in their own blocks; under write-site marking the detector reported each correctly named field as a near-miss of ITSELF and the copy told Doug to rename a correctly named row. Resolution-site marking removes that false-positive class with zero true-positive loss (Stage/Storage never pass through curated resolution — fallback self-slug writes via `toCanonicalKey` are not curated and never mark; probe Part D retains all 7 audited TPs). Verified against the real `CANONICAL_KEY_MAP` including the coincidence case (a curated slug equal to the self-slug: "room diagram", "notes" — curated wins, row excluded). An empty recognized field is deliberately SILENT: surfacing empty curated fields is a different product (a completeness audit), not a near-miss warning. **Ledger key (occurrence identity - plan-r1 finding 1):** entries are keyed by the NUL-joined triple of the resolving block's OPENER first-cell text, the row label, and the row value - not label+value alone. Three fixtures carry byte-identical empty-value `Room Diagram` rows in both a DETAILS-family block (consumed) and the Timestamp block (must warn); a label+value key suppresses both or assigns consumption by document order, which is position-keyed - the defect class this spec exists to remove. The opener text moves with its rows under swaps, so the triple stays swap-invariant; the detector checks membership using the candidate row's own physical block opener (probe record `docs/superpowers/specs/parser/probes/2026-08-15-plan-r1-sweeps.md` section 4).

**Derived cover for ledger call sites (plan-time walk, not a two-item list):** every module under `lib/parser/blocks/` that accepts a `ParseAggregator` (11 files) is audited for internal resolution vocabularies at plan execution; the known members at spec time are `event.ts` (`CANONICAL_KEY_MAP` + `gatedVocabCorrect`), `contacts.ts` (regex resolution), `transport.ts` (lib/parser/blocks/transport.ts:217 label regex). The arbiter is executable, not the list: the committed 65-row baseline equals the resolution-site measurement (followup probe Part D), so a missed ledger site surfaces as a baseline mismatch, not silence.
