## 1. Why

`buildInlineReservations` (`lib/parser/blocks/hotels.ts:717`) splits a multi-`Check In` inline cell into per-group reservations, then assigns group 0's `baseName` to every row (`lib/parser/blocks/hotels.ts:766-769`). A later group that carries its OWN hotel is silently clobbered. Probe-verified on branch base `233742abd` (2026-07-27):

```
| Hotel Stays | Hyatt Regency 100 Main St John Smith - 1001 Check In: 3/1 Check Out: 3/2 Marriott Downtown 200 Oak Ave Jane Doe - 1002 Check In: 3/3 Check Out: 3/4 |

row 0: hotel "Hyatt Regency 100"  names ["Main St John Smith"]  3/1–3/2
row 1: hotel "Hyatt Regency 100"  names ["Oak Ave Jane Doe"]    3/3–3/4
```

`Marriott Downtown 200 Oak Ave` vanishes; Jane's crew page shows the wrong hotel with no operator signal beyond the cell-level `HOTEL_GUEST_SPLIT_AMBIGUOUS` on reservation 0. The backlog disposition (ratified 2026-07-26) requires the fix signal to come from the raw FRAGMENT (`splitInlineReservationGroups` output, `lib/parser/blocks/hotels.ts:863`) BEFORE parsed output exists — three output-derived carve-outs were each probe-refuted (parent spec §3.1 row 7 rationale, `lib/parser/blocks/hotels.ts:756-767` comment block).

This spec ships a three-tier fragment-level detector, per the design approved in conversation on 2026-07-27 (option "auto-correct and raise a flag"):

- **Tier 1 (postal-complete auto-correct):** the fragment's pre-guest prefix contains a street-address-shaped phrase that ends in a postal anchor (ZIP, ZIP+4, or Canadian postal code) → the group is parsed standalone and keeps its own hotel; new warning `HOTEL_INLINE_GROUP_OWN_HOTEL` fires so the operator confirms. A postal terminator is required because it is the only marker that PROVES where the address ends and the guest begins (S8); an address without one demotes to tier 2.
- **Tier 2 (suspicion, inherit):** hotel-like evidence too weak to act on → inheritance unchanged; new warning `HOTEL_INLINE_GROUP_HOTEL_SUSPECTED` fires, and its copy states the fix lives in the sheet and what edit makes the parser read it as intended.
- **Tier 3 (silence):** divider + guest only (the `consultants` shape) → inheritance unchanged, no warning. Corpus card counts do not move.

## 3. The detector (normative)

A pure function over one raw segment, run per later group inside `buildInlineReservations`, and EXPORTED from `lib/parser/blocks/hotels.ts` so the §8.1 D6-abort oracle can unit-test it directly (R11 finding 4). Pinned API (R15 finding 1):

```ts
export type LaterSegmentOutcome =
  | { tier: 1; hotelText: string; build: InlineBuild } // build = buildInlineHotel(rest, ordinal, contextYear); D7 reads build.judgedGuestBoundary
  | { tier: 2 } // caller stashes HOTEL_INLINE_GROUP_HOTEL_SUSPECTED
  | { tier: 3 };

export function classifyLaterSegment(
  rawSegment: string, // pre-D1 segment as returned by splitInlineReservationGroups
  ordinal: number,
  contextYear: string | null,
): LaterSegmentOutcome;
```

`InlineBuild` is the existing `buildInlineHotel` return type (`lib/parser/blocks/hotels.ts` — the `{ row, judgedGuestBoundary, addressAmbiguity? }` shape read at `lib/parser/blocks/hotels.ts:724`). `ordinal` carries a PRECONDITION, not a runtime check: callers pass the group's positive integer ordinal (the same value `buildInlineHotel` receives today); behavior for zero, negative, or non-integer ordinals is unspecified (R16 finding 5). The detector never runs on group 0 and never on single-group cells (`checkInCount < 2`, `lib/parser/blocks/hotels.ts:718`); the scope-A/B degraded scans are the CALLER's (they need cross-segment context the pure function does not have).

**Ordering vs the all-names fallback + degraded segmentation (Codex R7 finding 1; widened R9 finding 1).** Detection is computed for every later segment BEFORE the all-names guard (`lib/parser/blocks/hotels.ts:735-753`) decides whether the cell collapses to a single reservation. Two degraded paths can still reach the single-reservation fallback: (i) a provisional build had `names: []` (e.g. a non-ASCII guest `José Núñez - 1002` defeats the ASCII matchers, parent spec §3.1 row-6 note); (ii) **segmentation itself fails** — `splitInlineReservationGroups` cuts only at `Check Out` markers (`lib/parser/blocks/hotels.ts:863`), so a multi-`Check In` cell whose group 0 lacks its checkout comes back as ONE segment and there are no later segments to classify at all (R9; probe-confirmed: `… John Smith - 1001 Check In: 3/1 Marriott Downtown 200 Oak Ave, Chicago, IL 60601 Jane Doe - 1002 Check In: 3/3 Check Out: 3/4` collapses to a single Hyatt reservation and the Marriott vanishes). **Entity-split markers are a pre-existing ROUTING limit, out of scope (R24 finding 2):** the multi-group gate counts markers on the RAW cell (`checkInCount`, `lib/parser/blocks/hotels.ts:718`, `/check\s+in/gi` — `\s` does not match the literal `&#10;` entity), so a cell whose second marker is written `Check&#10;In` routes to the SINGLE-group path (probe 2026-07-30: one glued reservation, Jane inside group 0's names) and neither the detector nor any scope runs. This spec changes nothing on the single-group path (S1/S5 boundary: re-routing shipped cells is a separate feature); the cell stays byte-identical to today with zero new codes, pinned by the §8.1 entity-split-marker negative. The limit is EXACTLY the raw gate (R26 finding 1): entity-split shapes that leave the raw count at two or more stay fully in scope — an entity-split first checkout collapses segmentation into one degraded segment whose scope-A scan (D1-normalized) warns; an entity-split final checkout leaves the later segment classifiable and keepable (both pinned in §8.1).

Degradation is handled at TWO scopes, and neither auto-corrects. Auto-correct (tier 1) exists only for a segment whose ENTIRE text is accounted for by the structural partition (the tier-1 completeness gate, S9 — Codex R11 finding 1, closed structurally after R12 findings 1-2):

- `[0, addressEnd)` — the kept hotel text (D4 match, postal-terminated per S8; its pre-address name region bounded by guard (d), R31);
- `[addressEnd, prefixEnd)` — the pre-guest residual, bounded by the residual-tail guard's three arms;
- `[prefixEnd, end)` — everything after the prefix (delimiter, conf, dates, and any GLUED later material), which must scan NEGATIVE for hotel evidence. The post-prefix scan has TWO arms (R12 finding 2; R13 finding 2): (i) street/postal, TWO reads per regex (R29 finding 1): the padded raw region (`" " + s2.slice(prefixEnd)`) AND the padded DASH-NEUTRALIZED region (dash runs `[-–—]+` replaced by a single space) each match neither `STREET_ADDRESS_RE` nor `STREET_ADDRESS_ZIP_RE`, and the region (both reads) lacks the postal-evidence regex. The neutralized read closes the seam where a dash glued to a street number (`-1515 Madison Ave`) defeats the street regex's leading-whitespace anchor while the conf arm's street-start suppression discards the same candidate — leaving a recognizable glued address invisible to BOTH arms (probe 2026-07-30: raw read null, neutralized read matches ` 1515 Madison Ave`). Neutralization is scan-input-only (never D3, never persisted text) and can only REVEAL street/postal shapes: a split ZIP+4 (`99999 1234`) matches no street or postal regex, so the ratified ZIP+4 keeps are unaffected; (ii) post-marker conf token, ANY live family (widened R17 finding 1) — the region AFTER the segment's first `Check In` match's end contains no confirmation token per the recognizer family the live guest-evidence gate uses (`hasGuestEvidence`, `lib/parser/blocks/hotels.ts:908-915`), with ONE normative delta (R18 finding 2): the dash family carries D3's ZIP+4 exclusion (the `stripConfTokens` `isZip4` predicate, `lib/parser/blocks/hotelConfTokens.ts:64-74`; citation corrected R19 finding 2). Live `hasGuestEvidence` LACKS that exclusion — its dash arm reads `99999-1234`'s `-1234` as a conf token — so reusing it verbatim falsely demotes a segment whose post-marker text carries a ZIP+4; arm (ii) must not. Families: dash-delimited (`[-–—]{1,3}\s*#?\s*\d{4,}\b` with `looksLikeStreetStart` false and NOT a ZIP+4 hyphen per the predicate above), hash-only (`#\s*\d{4,}`), or a bare six-plus-digit run (`\b\d{6,}\b` — longer than any ZIP, and ZIP+4 carries a hyphen, so postal text never trips it; date digits are slash-separated and never reach six). Arm (ii) is post-marker ONLY: a clean multi-guest booking legitimately carries several conf delimiters BEFORE its marker (probe B4, and the two-guest own-hotel keep pinned in §8.1), but after `Check In` comes only date/checkout material, so a conf delimiter there proves a glued later booking even when it carries no address (probe 2026-07-28: `… Jane Doe - 1002 Check In: 3/3/26 Hilton Midtown Bob Roe - 1003 Check Out: 3/6/26` parses today to names `["Jane Doe","Hilton Midtown Bob Roe"]`). For a zero-marker tail the post-marker region is empty and arm (ii) is vacuously negative;
- and the segment contains **at most one `Check In` match** — zero (a tail segment) or one; two or more means an intermediate checkout is missing and the segment glues bookings the detector cannot attribute.

Any evidence outside the partition demotes an otherwise-qualifying segment to tier 2's SUSPECTED — never tier 3 silence, and never a tier-1 keep that would attribute the guests and dates of a glued booking CARRYING RECOGNIZABLE EVIDENCE to the kept hotel. The scan's reach is exactly its recognizers (R20 finding 2): street/postal shapes and the three conf-token families. **Casing precondition (R30 finding 1, ratified; scoped precisely R31 finding 2):** the two-letter STATE/PROVINCE token is UPPERCASE-ONLY (`[A-Z]{2}`) in every context (D4 ZIP arm, D4b arms 2/3, the S8 terminator shape, guard (b), and both scan arms), while the CANADIAN POSTAL CODE alternation is CASE-INSENSITIVE (`[A-Za-z]\d[A-Za-z]\s?\d[A-Za-z]\d`) — both exactly as the live regex writes them, so `Toronto ON m5v 2t6` keeps (state token uppercase; postal chars case-free) and `Toronto on M5V 2T6` demotes (state token lowercase, no recognized anchor), each pinned — the live `STREET_ADDRESS_ZIP_RE` uses `[A-Z]{2}` with `/u` and no `/i` deliberately, and the spec's postal-anchored regexes mirror it, because lowercase two-letter tokens collide with English words (`in 60601`, `on 12345` would counterfeit postal evidence and fire spurious guard-(b)/scan demotes on legitimate keeps). Text whose STATE TOKEN is lowercase (`71 chicago, il 60601`) is therefore OUTSIDE the recognizer set — exactly the visibility the live splitters have today — and every consequence is the conservative one: a lowercase-state own hotel never auto-corrects (guard (a)/S8 demote it to SUSPECTED), and SUFFIXLESS lowercase-state glued material is invisible to the scans (R32 finding 2 scoped this: a SUFFIXED street inside lowercase-state text stays scan-VISIBLE — live `STREET_ADDRESS_RE` is `/iu` and consults no state token, so `1515 Madison Ave, chicago, il 60601` post-marker demotes via arm (i), pinned), so an otherwise-qualifying segment whose glued material is suffixless keeps at tier 1 under this same recognizable-evidence scoping with OWN's check-your-dates copy as the operator surface (today's parse absorbs the identical material SILENTLY — probes 2026-07-30). Case-widening the recognizers is a separate live-parser feature with its own false-positive analysis, not a detector decision; pinned by four §8.1 casing oracles. Post-marker material carrying NONE of these — a bare hotel name and bare guest with no conf, e.g. `… Jane Doe - 1002 Check In: 3/3 Hilton Midtown Bob Roe Check Out: 3/6` — is indistinguishable from note text at the raw-fragment level (the same S1 fact behind §11's guest-first bare-name limit), so the segment keeps at tier 1 and the glued booking's trailing checkout lands on the kept row. That keep is NOT silent: the row carries `HOTEL_INLINE_GROUP_OWN_HOTEL`, whose copy says to double-check the reservation's hotel, guests, AND dates — and today's parse already misattributes the same checkout to the INHERITED hotel with no warning on that row at all (probe 2026-07-30), so the tier-1 keep strictly improves both the hotel and the operator signal. Documented detection limit, pinned by the §8.1 bare-glue negative so a future recognizer widening flips a test deliberately. This closes the whole bypass class rather than enumerating degradation shapes: R11's `>= 2`-marker demotion, R12 finding 1 (a zero-marker tail with fully-qualifying evidence fell to tier 3 under an "exactly one" reading), and R12 finding 2 (a single-marker segment gluing a later booking whose own `Check In` is missing reached tier 1 and swallowed its guests) are all instances the partition covers by construction.

**(A) Per-segment degraded scan (R9 finding 1; widened R10 finding 1 — partial degradation; tier-1 gate R11 finding 1).** A segment containing **two or more `Check In` matches** glued multiple bookings together (an intermediate checkout is missing), and the detector cannot classify what it cannot segment — segment 0 included. Such a segment is DEGRADED, and tier 1 is unreachable for it: a degraded LATER segment still runs D3-D6 evidence evaluation, but any outcome that would otherwise qualify for tier 1 (D4 match, postal terminator, guards, successful D6) DEMOTES to tier 2's `HOTEL_INLINE_GROUP_HOTEL_SUSPECTED` — its prefix may be a second hotel, but the segment also glues a THIRD booking after its first marker, and keeping the prefix hotel would silently attribute that third booking's guests and dates to it. No OWN stash can exist on a degraded segment's row, so the OWN+SUSPECTED stash-order question does not arise (max one SUSPECTED per row, below). Additionally, for EVERY degraded segment (segment 0 included, fallback or not): run the **evidence scan** (street/postal regexes OR the post-marker conf-token arm ii, any family, S9/R13/R17) on the **D1-NORMALIZED** segment text after its FIRST `Check In` match's end. **Scan-input normalization (R21 finding 2):** although scope A/B are caller-side, the scan input is the segment text passed through the SAME D1 normalization the detector applies (`&#10;`/`\r` to spaces, whitespace collapsed, trimmed — `lib/parser/blocks/hotels.ts:896` shape), with the first-marker position located in that normalized text; only the scan INPUT is normalized — the stashed `rawSnippet` stays the RAW text. Raw-byte scanning misses evidence an exporter entity splits (`200&#10;Oak Ave` matches `STREET_ADDRESS_RE` only after normalization; pinned by the §8.1 entity-split-evidence row) — that region can only contain later bookings' material, since the segment's own hotel text precedes its first marker. If it matches `STREET_ADDRESS_RE` or `STREET_ADDRESS_ZIP_RE` (padded read — raw AND dash-neutralized, R29) or the postal-evidence regex, OR contains a conf token of any live family (arm ii — R13/R14/R17: dash with the ZIP+4 exclusion per the R18 delta above, hash, or bare six-plus-digit conf after the first marker is a glued later booking even without an address; the family definition, exclusion included, is IDENTICAL in every scan context), stash ONE `HOTEL_INLINE_GROUP_HOTEL_SUSPECTED` on that segment's surviving row. Probe-verified (2026-07-27): the 3-booking cell `Hyatt … Check In: 3/1 Marriott Downtown 200 Oak Ave, Chicago, IL 60601 Jane Doe - 1002 Check In: 3/3 Check Out: 3/4 Bob Roe - 1003 Check In: 3/5 Check Out: 3/6` survives as TWO rows (no fallback) with the Marriott vanished into row 0 — segment 0 has 2 `Check In` matches and positive evidence, so row 0 warns; the 2-booking missing-checkout collapse (whole cell = one segment with 2 markers) is the same rule at the fallback scope. The scan's true negative is the CONF-LESS glued guest `Hyatt Regency John Smith - 1001 Check In: 3/1 Jane Doe Check In: 3/3 Check Out: 3/4` (probe 2026-07-28: one fallback row, names `["Hyatt Regency John Smith"]`) — its scan region `Jane Doe Check In: …` has no street/postal shape and no conf delimiter. The conf-CARRYING variant (`… Jane Doe - 1002 Check In: 3/3 …`) scans POSITIVE via arm (ii) and warns — R14 finding 1 flipped the pre-R13 oracle: `- 1002` after the first marker proves Jane's glued booking, exactly the loss the scan exists to surface.

**(B) Fallback attribution (R7 finding 1).** When the all-names guard collapses the cell to one reservation (a provisional build had `names: []` — e.g. a non-ASCII guest `José Núñez - 1002` defeats the ASCII matchers, parent spec §3.1 row-6 note), the per-group rows are discarded as today, but if any computed later-segment outcome was tier 1 or tier 2 (including a D6 abort), exactly ONE `HOTEL_INLINE_GROUP_HOTEL_SUSPECTED` is stashed on the surviving reservation. (A)'s per-segment scan also applies to the survivor via the whole-cell "segment".

At most one SUSPECTED stash per row regardless of how many arms fire. Envelope for scope-(A)/(B) stashes: `blockRef.index` = the surviving row's final index, `blockRef.name` = its resolved hotel name, `rawSnippet` = the row's raw, PRE-normalization (its raw segment on the multi-row path; the whole cell for the fallback survivor, matching the existing single-path `rawCells`) — the D1-normalized `s` never leaves the detector (R11 finding 3). The operator learns the cell may book another hotel even though the parser could not split it.

**D1 — normalize.** `s` = the segment with `&#10;`/`\r` replaced by spaces, whitespace collapsed, trimmed — the same normalization `buildInlineHotel` applies (`lib/parser/blocks/hotels.ts:896`).

**D2 — divider strip.** `s2` = `s` with any leading run of whitespace and dash characters removed (`/^[\s\-–—]+/`). Later groups in the shared-hotel shape begin with a divider; a hotel name never does.

**D3 — prefix.** Scan `s2` for the first **confirmation delimiter** ("non-street" dropped R27 — there is no street exemption): `[-–—]{1,3}\s*#?\s*(\d{4,})` — NO trailing `\b` (R25 finding 1): the dash class mirrors the `stripConfTokens` dash MATCHER (`/(\s*)([-–—]{1,3})(\s*#?\s*)(\d{4,})/g`, `lib/parser/blocks/hotelConfTokens.ts:54-56` region), because D3's job is to keep the prefix free of anything the row-level strip pass would later delete from crew-visible `hotelText`. A trailing-`\b` D3 skips `99999-1234A` while the stripper still mangles it (probe 2026-07-30: the kept row's split becomes `hotel_name "Marriott Jane Doe 99999 A"` — Jane buried plus junk). **There is NO street exemption in D3 (R27 finding 1, REVERSING R21 — ratified in both directions, the same treatment as the R16/R17 comma):** EVERY dash-run candidate is a delimiter, street-shaped or not, hashed or not, subject only to the ZIP+4 exclusion below. ### 8.2 Anti-tautology notes

Every expected value above is a string/array literal in the test derived from the input cell, never read back from the parser, and every input is fully specified in this document — no test input or public/helper-boundary choice is deferred to plan time (Codex R11 finding 4; the only spec-to-test transformation is §8.1's deterministic year-suffix materialization). Any oracle that distinguishes RAW from NORMALIZED text uses an input where the two actually differ (the envelope cells embed `&#10;` and a doubled space) — asserting raw-equality on an input D1 leaves unchanged proves nothing (Codex R12 finding 3). The byte-parity tests capture today's output as literals in the test file (from a fresh pre-change probe of the YEAR-SUFFIXED cell, with a comment saying so — the §2 yearless transcripts are shape references, not parity sources), so a behavior drift in ANY tier fails loudly. The tier-2 abort test and the tier-3 consultants test remain key discriminators — the first catches an implementation that keeps whenever D4 matches and the rebuild is not consulted, the second catches one that warns on every later group — but neither claim is exclusive (R24 finding 7): the suffix-only, residual-guard, provenance, and post-prefix demotes also fail a keep-happy implementation, and the below-threshold, fallback-no-evidence, and bare-name negatives also fail a warn-happy one. The matrix discriminates in aggregate; no single oracle carries an exclusivity guarantee.
