## 1. Why

`buildInlineReservations` (`lib/parser/blocks/hotels.ts:717`) splits a multi-`Check In` inline cell into per-group reservations, then assigns group 0's `baseName` to every row (`lib/parser/blocks/hotels.ts:766-769`). A later group that carries its OWN hotel is silently clobbered. Probe-verified on branch base `233742abd` (2026-07-27):

```
| Hotel Stays | Hyatt Regency 100 Main St John Smith - 1001 Check In: 3/1 Check Out: 3/2 Marriott Downtown 200 Oak Ave Jane Doe - 1002 Check In: 3/3 Check Out: 3/4 |

row 0: hotel "Hyatt Regency 100"  names ["Main St John Smith"]  3/1–3/2
row 1: hotel "Hyatt Regency 100"  names ["Oak Ave Jane Doe"]    3/3–3/4
```

`Marriott Downtown 200 Oak Ave` vanishes; Jane's crew page shows the wrong hotel with no operator signal beyond the cell-level `HOTEL_GUEST_SPLIT_AMBIGUOUS` on reservation 0. The backlog disposition (ratified 2026-07-26) requires the fix signal to come from the raw FRAGMENT (`splitInlineReservationGroups` output, `lib/parser/blocks/hotels.ts:863`) BEFORE parsed output exists — three output-derived carve-outs were each probe-refuted (parent spec §3.1 row 7 rationale, `lib/parser/blocks/hotels.ts:756-767` comment block).

This spec ships a three-tier fragment-level detector, per the design approved in conversation on 2026-07-27 (option "auto-correct and raise a flag"):

- **Tier 1 (postal-complete auto-correct):** the fragment's pre-guest prefix contains a street-address-shaped phrase that ends in a postal anchor (ZIP, ZIP+4, or Canadian postal code) → the group is parsed standalone and keeps its own hotel; new warning `HOTEL_INLINE_GROUP_OWN_HOTEL` fires so the operator confirms. A postal terminator is required because it is the only marker that PROVES where the address ends and the guest begins (S8); an address without one demotes to tier 2.
- **Tier 2 (suspicion, inherit):** hotel-like evidence too weak to act on → inheritance unchanged; new warning `HOTEL_INLINE_GROUP_HOTEL_SUSPECTED` fires, and its copy states the fix lives in the sheet and what edit makes the parser read it as intended.
- **Tier 3 (silence):** divider + guest only (the `consultants` shape) → inheritance unchanged, no warning. Corpus card counts do not move.

## 3. The detector (normative)

A pure function over one raw segment, run per later group inside `buildInlineReservations`, and EXPORTED from `lib/parser/blocks/hotels.ts` so the §8.1 D6-abort oracle can unit-test it directly (R11 finding 4). Pinned API (R15 finding 1):

```ts
export type LaterSegmentOutcome =
  | { tier: 1; hotelText: string; build: InlineBuild } // build = buildInlineHotel(rest, ordinal, contextYear); D7 reads build.judgedGuestBoundary
  | { tier: 2 } // caller stashes HOTEL_INLINE_GROUP_HOTEL_SUSPECTED
  | { tier: 3 };

export function classifyLaterSegment(
  rawSegment: string, // pre-D1 segment as returned by splitInlineReservationGroups
  ordinal: number,
  contextYear: string | null,
): LaterSegmentOutcome;
```

`InlineBuild` is the existing `buildInlineHotel` return type (`lib/parser/blocks/hotels.ts` — the `{ row, judgedGuestBoundary, addressAmbiguity? }` shape read at `lib/parser/blocks/hotels.ts:724`). `ordinal` carries a PRECONDITION, not a runtime check: callers pass the group's positive integer ordinal (the same value `buildInlineHotel` receives today); behavior for zero, negative, or non-integer ordinals is unspecified (R16 finding 5). The detector never runs on group 0 and never on single-group cells (`checkInCount < 2`, `lib/parser/blocks/hotels.ts:718`); the scope-A/B degraded scans are the CALLER's (they need cross-segment context the pure function does not have).

**Ordering vs the all-names fallback + degraded segmentation (Codex R7 finding 1; widened R9 finding 1).** Detection is computed for every later segment BEFORE the all-names guard (`lib/parser/blocks/hotels.ts:735-753`) decides whether the cell collapses to a single reservation. Two degraded paths can still reach the single-reservation fallback: (i) a provisional build had `names: []` (e.g. a non-ASCII guest `José Núñez - 1002` defeats the ASCII matchers, parent spec §3.1 row-6 note); (ii) **segmentation itself fails** — `splitInlineReservationGroups` cuts only at `Check Out` markers (`lib/parser/blocks/hotels.ts:863`), so a multi-`Check In` cell whose group 0 lacks its checkout comes back as ONE segment and there are no later segments to classify at all (R9; probe-confirmed: `… John Smith - 1001 Check In: 3/1 Marriott Downtown 200 Oak Ave, Chicago, IL 60601 Jane Doe - 1002 Check In: 3/3 Check Out: 3/4` collapses to a single Hyatt reservation and the Marriott vanishes). **Entity-split markers are a pre-existing ROUTING limit, out of scope (R24 finding 2):** the multi-group gate counts markers on the RAW cell (`checkInCount`, `lib/parser/blocks/hotels.ts:718`, `/check\s+in/gi` — `\s` does not match the literal `&#10;` entity), so a cell whose second marker is written `Check&#10;In` routes to the SINGLE-group path (probe 2026-07-30: one glued reservation, Jane inside group 0's names) and neither the detector nor any scope runs. **The same raw-gate fact covers QUOTE-split markers (R50 finding 2):** a second marker written `Check"In` (or with a smart quote, U+201C/U+201D, in the quote position) routes single-group identically, because quote characters are not `\s`, survive `clean()` (which strips only zero-width/backslashes), and only D1, which never runs on the single-group path, would read them as spaces (probes 2026-07-30, all three quote forms: ONE glued reservation `{"Hyatt Regency", "100 Main St John Smith", names ["Main St John Smith","Jane Doe"], group-0 dates}`, zero new codes). Pinned by the §8.1 quote-split-marker negative. Zero-width marker splits are NOT a discrepancy: `clean()` deletes the character before the gate and D1 would too, so both layers agree `CheckIn` is no marker. This spec changes nothing on the single-group path (S1/S5 boundary: re-routing shipped cells is a separate feature); the cell stays byte-identical to today with zero new codes, pinned by the §8.1 entity-split-marker negative. The limit is EXACTLY the raw gate (R26 finding 1): entity-split shapes that leave the raw count at two or more stay fully in scope — an entity-split first checkout collapses segmentation into one degraded segment whose scope-A scan (D1-normalized) warns; an entity-split final checkout leaves the later segment classifiable and keepable (both pinned in §8.1).

Degradation is handled at TWO scopes, and neither auto-corrects. Auto-correct (tier 1) exists only for a segment whose ENTIRE text is accounted for by the structural partition (the tier-1 completeness gate, S9 — Codex R11 finding 1, closed structurally after R12 findings 1-2):

- `[0, addressEnd)` — the kept hotel text (D4 match, postal-terminated per S8; its pre-address name region bounded by guard (d), R31; every free word run inside the consumed span bounded by the R36 interior caps);
- `[addressEnd, prefixEnd)` — the pre-guest residual, bounded by the residual-tail guard's FOUR arms (a0/a/b/c, R39);
- `[prefixEnd, end)` — everything after the prefix (delimiter, conf, dates, and any GLUED later material), which must scan NEGATIVE for hotel evidence. The post-prefix scan has TWO arms (R12 finding 2; R13 finding 2): (i) street/postal, TWO reads per regex (R29 finding 1): the padded raw region (`" " + s2.slice(prefixEnd)`) AND the padded RESTRICTED-dash-neutralized region each match neither `STREET_ADDRESS_RE` nor `STREET_ADDRESS_ZIP_RE`, and the region (both reads) lacks the postal-evidence regex. **The neutralized read is RESTRICTED (R52 finding 1; R53's extra clause REVERSED by R55 finding 1 — ratified in both directions):** only dash runs immediately followed by a digit (`[-–—]+(?=\d)`) and NOT a true ZIP+4 hyphen (the `isZip4` predicate, all five clauses) are replaced by a single space. The digit-after clause is safe: a dash before letters is never a glued street number (`Note 2026-Drive kickoff` stays intact). The isZip4 clause is safe: a true ZIP+4 hyphen is ratified postal bytes (`Note 99999-1234 Way` stays intact). R53 added a no-word-char-before clause to stop `Note FY-2026 Drive kickoff` fabricating — but the premise was FALSE: a glued street number CAN follow a word character (`Hilton-1515 Madison Ave` — the raw regex misses, arm (ii) street-start-suppresses the dash candidate, and an un-neutralized read leaves the glued booking invisible to BOTH arms, so an otherwise-qualifying segment keeps OWN and absorbs Hilton's checkout — probes 2026-07-30, all three dash forms, both contexts). That trades a safe false demote for a CORRUPTION hole; corruption beats a missed keep. Do not relitigate in either direction: R53 proposed the clause, R55 proved it corrupting (the R21/R27 treatment). **Dash-glued digit-run prose (R54 finding 1; widened to word-char-led forms by the R55 reversal — DOCUMENTED LIMIT, the residual ambiguous core):** within the restricted class, prose whose dash run leads 1-5 digits with a downstream suffix word — whatever precedes the dash (`Note: -2026 Drive kickoff`, `Ref (-404 Path migration)`, `Note FY-2026 Drive kickoff`) — is byte-indistinguishable from a dash-glued street address (`-1515 Madison Ave` and `Hilton-1515 Madison Ave` are the SAME shape — S1); the neutralized read reveals the digit run and the street regex cannot tell prose from address, so the segment demotes CONSERVATIVELY (rows byte-equal to today's parse plus a SUSPECTED, never silence, never corruption; same at scope A, where the spurious stash is a warning on an already-degraded cell). No further structural discriminator exists — the digit-after and isZip4 clauses remove every shape that is provably not a glued street, and what remains IS the glued-street shape (R55: the word-char-before clause over-removed and was reversed). Pinned by the §8.1 digit-run-prose demotes; fenced both directions (reopening requires a discriminator this parser does not have — the R27/R33/R52 posture). The neutralized read closes the seam where a dash glued to a street number (`-1515 Madison Ave`) defeats the street regex's leading-whitespace anchor while the conf arm's street-start suppression discards the same candidate — leaving a recognizable glued address invisible to BOTH arms (probe 2026-07-30: raw read null, neutralized read matches ` 1515 Madison Ave`). Neutralization is scan-input-only (never D3, never persisted text); it reveals dash-glued digit runs, and the street regex then decides — which it cannot do for digit-lead prose (the dash-glued digit-run-prose limit above, punctuation-led AND word-char-led per R55). A split ZIP+4 (`99999 1234`) matches no street or postal regex, so the ratified ZIP+4 keeps are unaffected. **Suffix-surname collision (R52 finding 1, DOCUMENTED LIMIT):** the pre-marker span of `postGuest` legitimately holds conf delimiters and FURTHER GUESTS, and a 4-5-digit conf value followed by a guest whose surname is a street-suffix word is byte-indistinguishable from a dash-glued street address — ` 1002 Adam Lane` and ` 1515 Madison Ave` are the SAME shape (S1): the spaced form (`Jane Doe - 1002 Adam Lane - 1003 Check In: …`) matches `STREET_ADDRESS_RE` on the RAW read, the glued form (em-dash `1002` run) on the restricted neutralized read. No raw-level discriminator exists; the scan demotes CONSERVATIVELY — rows stay byte-equal to today's parse plus a SUSPECTED, never silence, never corruption — so an arm-(i) match is treated as evidence, not proof. Pinned by the §8.1 suffix-surname demote; fenced both directions (reopening the demote requires a discriminator this parser does not have — same posture as R27/R33). The ratified two-guest keep's 7-digit conf values are structurally immune: `\d{1,5}` cannot consume them; (ii) post-marker conf token, ANY live family (widened R17 finding 1) — the region AFTER the segment's first `Check In` match's end contains no confirmation token per the recognizer family the live guest-evidence gate uses (`hasGuestEvidence`, `lib/parser/blocks/hotels.ts:908-915`), with ONE normative delta (R18 finding 2): the dash family carries D3's ZIP+4 exclusion (the `stripConfTokens` `isZip4` predicate, `lib/parser/blocks/hotelConfTokens.ts:64-74`; citation corrected R19 finding 2). Live `hasGuestEvidence` LACKS that exclusion — its dash arm reads `99999-1234`'s `-1234` as a conf token — so reusing it verbatim falsely demotes a segment whose post-marker text carries a ZIP+4; arm (ii) must not. Families: dash-delimited (`[-–—]{1,3}\s*#?\s*\d{4,}\b` with `looksLikeStreetStart` false and NOT a ZIP+4 hyphen per the predicate above), hash-only (`#\s*\d{4,}`), or a bare six-plus-digit run (`\b\d{6,}\b` — longer than any ZIP, and ZIP+4 carries a hyphen, so postal text never trips it; date digits are slash-separated and never reach six). Arm (ii) is post-marker ONLY: a clean multi-guest booking legitimately carries several conf delimiters BEFORE its marker (probe B4, and the two-guest own-hotel keep pinned in §8.1), but after `Check In` comes only date/checkout material, so a conf delimiter there proves a glued later booking even when it carries no address (probe 2026-07-28: `… Jane Doe - 1002 Check In: 3/3/26 Hilton Midtown Bob Roe - 1003 Check Out: 3/6/26` parses today to names `["Jane Doe","Hilton Midtown Bob Roe"]`). For a zero-marker tail the post-marker region is empty and arm (ii) is vacuously negative;
- and the segment contains **at most one `Check In` match** — zero (a tail segment) or one; two or more means an intermediate checkout is missing and the segment glues bookings the detector cannot attribute.

Any evidence outside the partition demotes an otherwise-qualifying segment to tier 2's SUSPECTED — never tier 3 silence, and never a tier-1 keep that would attribute the guests and dates of a glued booking CARRYING RECOGNIZABLE EVIDENCE to the kept hotel. The scan's reach is exactly its recognizers (R20 finding 2): street/postal shapes and the three conf-token families. **Casing precondition (R30 finding 1, ratified; scoped precisely R31 finding 2):** the two-letter STATE/PROVINCE token is UPPERCASE-ONLY (`[A-Z]{2}`) in every context (D4 ZIP arm, D4b arms 2/3, the S8 terminator shape, guard (b), and both scan arms), while the CANADIAN POSTAL CODE alternation is CASE-INSENSITIVE (`[A-Za-z]\d[A-Za-z]\s?\d[A-Za-z]\d`) — both exactly as the live regex writes them, so `Toronto ON m5v 2t6` keeps (state token uppercase; postal chars case-free) and `Toronto on M5V 2T6` demotes (state token lowercase, no recognized anchor), each pinned — the live `STREET_ADDRESS_ZIP_RE` uses `[A-Z]{2}` with `/u` and no `/i` deliberately, and the spec's postal-anchored regexes mirror it, because lowercase two-letter tokens collide with English words (`in 60601`, `on 12345` would counterfeit postal evidence and fire spurious guard-(b)/scan demotes on legitimate keeps). Text whose STATE TOKEN is lowercase (`71 chicago, il 60601`) is therefore OUTSIDE the recognizer set — exactly the visibility the live splitters have today — and every consequence is the conservative one: a lowercase-state own hotel never auto-corrects (guard (a)/S8 demote it to SUSPECTED), and SUFFIXLESS lowercase-state glued material is invisible to the scans (R32 finding 2 scoped this: a SUFFIXED street inside lowercase-state text stays scan-VISIBLE — live `STREET_ADDRESS_RE` is `/iu` and consults no state token, so `1515 Madison Ave, chicago, il 60601` post-marker demotes via arm (i), pinned), so an otherwise-qualifying segment whose glued material is suffixless keeps at tier 1 under this same recognizable-evidence scoping with OWN's check-your-dates copy as the operator surface (today's parse absorbs the identical material SILENTLY — probes 2026-07-30). Case-widening the recognizers is a separate live-parser feature with its own false-positive analysis, not a detector decision; pinned by four §8.1 casing oracles. Post-marker material carrying NONE of these — a bare hotel name and bare guest with no conf, e.g. `… Jane Doe - 1002 Check In: 3/3 Hilton Midtown Bob Roe Check Out: 3/6` — is indistinguishable from note text at the raw-fragment level (the same S1 fact behind §11's guest-first bare-name limit), so the segment keeps at tier 1 and the glued booking's trailing checkout lands on the kept row. That keep is NOT silent: the row carries `HOTEL_INLINE_GROUP_OWN_HOTEL`, whose copy says to double-check the reservation's hotel, guests, AND dates — and today's parse already misattributes the same checkout to the INHERITED hotel with no warning on that row at all (probe 2026-07-30), so the tier-1 keep strictly improves both the hotel and the operator signal. Documented detection limit, pinned by the §8.1 bare-glue negative so a future recognizer widening flips a test deliberately. This closes the whole bypass class rather than enumerating degradation shapes: R11's `>= 2`-marker demotion, R12 finding 1 (a zero-marker tail with fully-qualifying evidence fell to tier 3 under an "exactly one" reading), and R12 finding 2 (a single-marker segment gluing a later booking whose own `Check In` is missing reached tier 1 and swallowed its guests) are all instances the partition covers by construction.

**(A) Per-segment degraded scan (R9 finding 1; widened R10 finding 1 — partial degradation; tier-1 gate R11 finding 1).** A segment containing **two or more `Check In` matches** glued multiple bookings together (an intermediate checkout is missing), and the detector cannot classify what it cannot segment — segment 0 included. Such a segment is DEGRADED, and tier 1 is unreachable for it: a degraded LATER segment still runs D3-D6 evidence evaluation, but any outcome that would otherwise qualify for tier 1 (D4 match, postal terminator, guards, successful D6) DEMOTES to tier 2's `HOTEL_INLINE_GROUP_HOTEL_SUSPECTED` — its prefix may be a second hotel, but the segment also glues a THIRD booking after its first marker, and keeping the prefix hotel would silently attribute that third booking's guests and dates to it. No OWN stash can exist on a degraded segment's row, so the OWN+SUSPECTED stash-order question does not arise (max one SUSPECTED per row, below).
