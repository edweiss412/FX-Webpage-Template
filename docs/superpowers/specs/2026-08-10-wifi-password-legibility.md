### 4.1 `FactRows` API (mirrors the existing `KeyValueRows` flag pattern)

`FactRow` (`components/crew/primitives/FactRows.tsx:42` region) gains two optional flags:

- `code?: boolean` — value span additionally carries `code-value` (the class is self-contained per its own comment: it binds the family, so it works on the span as-is).
- `copyLabel?: string` — when present AND non-empty, the row renders a copy control after the value; the string is the accessible name material (e.g. `"Copy the Wi-Fi password"`). Absent/empty → no control, no layout change. **Row keying (R10 F1): `FactRows` keys a row by `testId` when present, falling back to today's label+index — the password row's key is therefore STABLE across sibling-row churn (optional loading-dock/parking/room rows precede it, `VenueSection.tsx:238` region), so a realtime update cannot remount the island and orphan its in-flight write. Belt (redesigned R11 F2 — a module counter alone leaves a pending write's resolution targeting a dead island): the module keeps a write LEDGER (latest seq + value) and an ACTIVE-OWNER registration — each island registers in a LAYOUT effect — synchronous with commit, not a passive effect, so no microtask window exists between the new island's commit and its ownership claim (R12 F1: a passive-effect registration leaves a commit-to-setup gap in which an old promise resolution still sees the dead island as current — the DEFERRED.md:153 act()-flush blind spot would hide exactly that trace) — registration re-points handler ROUTING to the new owner and deregistration mirrors it in the layout cleanup — prior pending writes stay live and deliver their §4.2 value-based outcomes through whichever owner is registered at resolution time (R15 F2: no write is invalidated; the earlier invalidation phrasing is withdrawn); resolution truth follows §4.2's ONE rule (value-only; sequence/ownership route handlers — R14 F1 removed this paragraph's duplicate phrasing): two rapid same-value taps each append their keyed entry with no false corrective; a different-value inversion takes the corrective path. The overlapping-writes tests cover both inversions. A remount/sibling-churn test drives exactly the unmount-pending-resolve-after-new-mount trace, PLUS the empirical race spike the lifecycle rules require — EXECUTED AT SPEC TIME (R13 F1): `docs/superpowers/specs/probes/2026-08-10-wifi-ownership-spike.test.tsx` (strengthened R14 F2; rerun 2026-08-10, 1 passed) performs a REAL keyed remount (unmount A, mount B) and releases the pending write via a microtask queued from B's commit-phase layout effect. **Claim corrected to what is measured (R15 F1): the guarantee is LEDGER CORRECTNESS FROM COMMIT — registration happens in the layout phase, so any later resolution, whether it lands before or after passive effects (this environment flushes passive first, recorded in the probe), observes the new owner. Resolution-vs-passive ordering is environment-dependent and irrelevant to truth; no window-emptiness claim is made.** The implementation task re-runs this form as its regression.** This is the whole lifecycle of both flags: set at exactly one site today (§4.3), read in `FactRows`, no storage.

**AMENDED AT IMPLEMENTATION — the belt paragraph above is SUPERSEDED by what shipped (whole-diff review rounds 10-17); §4.2's normative rule is unchanged and was never in question.** The belt as specified routes a late resolution by NAME: the module holds an active-owner registration keyed by the row's identity, and a resolution is delivered to whichever owner is registered for that identity at resolution time. Review demonstrated, with a probe per ordering, that a name cannot answer the question it is being asked — identity is caller-supplied, so a name lookup also matches a different row sharing it (two `FactRows` lists reusing a testid) or a later row reusing it, and a confirmation lands on a row nobody tapped. What shipped instead, and what a maintainer must NOT "restore" the specified form over:

- **The affirmative routes by PROOF, not by name.** An island vacating in a commit offers itself as a predecessor for exactly that commit's window (cleared on the next microtask, per identity, consumed once and never when two islands vacate under one identity), and the incoming island claims it. A late resolution walks that successor chain and nothing else. An unlinked write's affirmative lands nowhere, which is correct: the value is on screen and the clipboard already holds it.
- **The retraction broadcasts by VALUE across every mounted island** (round 17), because a resolution is a fact about the CLIPBOARD — one resource every row writes to — while a confirmation is per island. An island whose current value differs from what the clipboard now holds is making a claim that is false whichever row it belongs to; matching values are left alone, which is §4.2's value-only truth from the other side.
- **The write ledger is a per-row COUNTER only** (rounds 14/16). It never decides truth, and it no longer decides "is this the newest write dispatched" either: which resolution owns the reset window is decided per island against the seq that ARMED the window now running, so a newer write still in flight — or one dispatched by a different row sharing the identity — cannot shorten the confirmation on screen.

The spec-time spike at `docs/superpowers/specs/probes/2026-08-10-wifi-ownership-spike.test.tsx` remains valid evidence for the claim it was run to settle (a layout-effect registration is live from commit); it predates the routing redesign and is not a description of the shipped mechanism. `components/crew/primitives/CopyFactValue.tsx`'s header carries the shipped rules with the ordering each one was found by.


Guard conditions: `v` empty/whitespace → the push site guards it (`VenueSection.tsx:262` pushes the row only when a parsed password exists, and the parser rejects empty recognized values in its label-scan around `lib/crew/wifiDisplay.ts:165`); `copyLabel` set while `v` is empty cannot occur at the only call site, and `FactRows` renders no control when `v` is empty regardless (belt). `code` on a non-string node: flags apply only to string `v` rows; the type stays `string` for `v` at this site.
