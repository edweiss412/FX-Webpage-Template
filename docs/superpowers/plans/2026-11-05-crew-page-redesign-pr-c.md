## Decisions this plan makes

Each is the plan's reading of the spec where the spec leaves a choice; none amends it.

1. **`packlist` is an entitlement gate, not a content rule.** A gate false day withholds the pack list, so `crewSectionEntitled("packlist", ...)` is `isPackListVisibleToday` (`lib/visibility/packList.ts:122`), a new row in `SECTION_GATES` (`lib/crew/crewSections.ts:112-127`): no body is built, `?s=packlist` resolves home, `popstate` replaces it away, and a refresh that crosses into a Show day closes the sheet through the lost-entitlement path (`components/crew/CrewSections.tsx:382-386`, spec line 258). `isPackListVisibleToday` needs the stage restriction and today, so `CrewSectionsViewer` (`lib/crew/crewSections.ts:47`) grows to `SectionPeekViewer`'s shape (`lib/crew/sectionPeek.ts:47`) and the shell computes `today` (`app/show/[slug]/[shareToken]/_CrewShell.tsx:299`) before the entitled set (`app/show/[slug]/[shareToken]/_CrewShell.tsx:284-287`). There is no content rule: spec line 240 states the gate only, so a member with no pull sheet lists the section and shows "No pack list on file yet." The gate is today's, unchanged: `gearRows.ts` applies it to every viewer, a plain admin included (`components/crew/sections/gearRows.ts:222-225`). The pull sheet arrives on the show row (`lib/data/getShowForViewer.ts:836-837`), so line 241's fetch rule has nothing to act on here. `CREW_ALWAYS_SECTION_IDS` (`lib/crew/crewSections.ts:145`) drops `packlist` by construction, so the loading skeleton never shows it.
2. **Nav order is the registry order.** `CREW_SECTION_IDS` (`lib/crew/resolveActiveSection.ts:15-25`) ends as `venue`, `event`, `crew`, `contacts`, `schedule`, `agenda`, `hotels`, `transport`, `rooms`, `packlist`, `billing`, the order of `SECTIONS` (`lib/showSections/registry.ts:49-61`). It stays a literal: `lib/auth/validateNextParam.ts:7` imports this module and the registry pulls in `lucide-react`, so the id list carries `satisfies readonly ShowSectionId[]` (a type import, erased) and Task 9 pins equality with the registry, proven by one planted mutant on each side (PR B's rule for equality claims).
3. **Where each retired card's id goes.** A card id is stored in a report's `fieldRef` (`components/shared/CardReportTrigger.tsx:62`), so a card that survives keeps its id (spec line 328). A card that stops existing retires its id.

4. **Field cards.** Spec line 328 keeps every card's actions, and the walker in `tests/components/crew/sourceLinkCoverage.test.tsx:310-322` fails on a region no card references, so dropping `today-dress` would leave `dress` a zombie. The Event body takes `fieldCards`: per key, a `cardId` and an `actions` node. A row with one renders inside a `data-card-id` wrapper with the actions in a `data-slot="section-card-action"` cell, which is what the walker and the parity harness read (`tests/search/_parity.ts:130`, region is the nearest `data-card-id`). Absent, the markup is the admin's. The panel and a field card now each own an action slot, and `gear-keynote` and `gear-opening-reel` share `gear-tech-specs`'s region, so a descendant search cannot tell them apart: with the panel's `actions` omitted, `tests/components/crew/sourceLinkCoverage.test.tsx:372` and `tests/components/crew/sourceLinkCoverage.test.tsx:425` would find a nested field card's slot and pass. Task 5 scopes every per-card read in that walker to the card's own elements: an element counts only when its nearest `[data-card-id]` is that card. Each such row's search `group` is its own label, because a group must be in its region's text (`tests/search/_parity.ts:225-232`); `searchLine` then folds an equal label to null (`components/crew/sections/gearRows.ts:76-79`).
5. **Tile ids are kept where a successor exists** (PR B decision 6). `crew:gear:scope` moves with the scope rows to Rooms, `crew:venue:diagrams` moves with the Diagrams block, and `crew:today:notes` stays on the home. Event details gets `crew:event:details`, Pack list `crew:packlist:cases`.
6. **Rooms on the crew page.** Rooms render in `compareRooms` order (`lib/crew/resolveKeyTimes.ts:38`), as `roomDetailBlocks` did (`components/crew/sections/gearRows.ts:314-315`). The crew passes `cap: null`: `ROOM_DETAIL_CAP` (`components/crew/sections/gearRows.ts:49`) capped the detail blocks only, and the scope cards listed every room (`components/crew/sections/gearRows.ts:161-168`), so a cap would remove a line crew see today (spec line 309, "every discipline stays visible"). The boundary is the sheet's room count; the corpus maximum is read by the probe in Task 7. `dropEmpty` drops a discipline when either existing predicate calls it empty: the crew's `shouldHideGenericOptional` (`components/crew/sections/gearRows.ts:163`: blank, TBD, N/A, TBA, the dashes) or the admin's `isEmptyScopeValue` (`components/admin/wizard/step3ReviewSections.tsx:251-254`: null, N/A, NA and "Not specified", any case, any spacing). Neither alone is enough: the first misses a parsed "Not specified" (`lib/visibility/emptyState.ts:56`), which spec line 309 rules out, and the second misses TBD and the dashes. Both predicates exist, so this adds no text rule, and one function in components/show-panels/roomScope.ts (new) holds the pair, read by the body and by the crew's row helper, so the index and the render agree. Every other crew filter this plan names keeps its own existing predicate, checked against the spec's stated empty values: event rows `shouldHideGenericOptional` and the reel `shouldHideOpeningReel` (spec lines 293, 302), room header fields `shouldHideGenericOptional` (line 293), pack item taxonomy `shouldHideGenericOptional` (`components/crew/sections/gearRows.ts:183-184`), the dress code the same (line 216), Diagrams `shouldHideDiagrams`. A room time such as "10/20 @ TBD" renders as written, as it does today (line 415); line 467's `isAbsentTime` is the pass's anchors. A room with no scope and no detail still renders its name and kind pill: its name is sheet data, the corpus holds no such room (Task 7's probe), and the section's empty state needs zero rooms. The viewer's own disciplines sort first inside each room, a stable partition after the admin's sort, because that is the existing emphasis contract (`components/crew/sections/gearRows.ts:172-176`, pinned by `tests/components/crew/sections/GearSection.test.tsx:12`, spec line 501). Non-string values are coerced in the crew's row helper before the body sees them (`tests/components/crew/gearRoomDetails.test.tsx:108`), which leaves the admin's `hasContent` reads alone. Room times stay visible under date suppression: `lib/crew/dateSuppression.ts:16-48` does not list them and today's Gear shows them, so AC-6 is unchanged.
7. **Copy on the crew side of the shared bodies.** Panel titles are the registry labels (PR B decision 4): "Event details", "Rooms & scope", "Pack list". Section empty states follow PR B's sentence: "No event details on file yet.", "No rooms on file yet.", "No pack list on file yet." The Event body takes `groupTitle`, default identity; the crew maps "Wardrobe & key moments" (`components/admin/wizard/step3ReviewSections.tsx:376`) to "Dress code & key moments", because spec line 406 retires "Wardrobe" on the crew page and line 505 forbids changing it on the admin.
8. **Headings.** The admin's room name and group title are spans (`components/admin/wizard/step3ReviewSections.tsx:1807`, `components/admin/wizard/step3ReviewSections.tsx:1986`). The crew's room name is an `h4` today (`components/crew/sections/GearSection.tsx:410`, an audit fix) and its four cards are `h3`s, so both bodies take a heading-element prop defaulting to `"span"`, and the crew passes `"h4"`. The same classes apply, so the admin output is unchanged and heading navigation keeps its landmarks.
9. **`packItemLabel` becomes the one item label.** `packListItemLabel` (`components/crew/sections/gearRows.ts:182`) and `packItemLabel` (`components/admin/wizard/step3ReviewSections.tsx:2118`) are two copies of one rule, the anti-goal at spec line 31. `packItemLabel` moves to the body module, re-exported from its old home; the crew's copy retires. Its only difference is the "(unnamed item)" fallback, which reaches crew too.
10. **The body is the case list.** Spec line 310's shared piece is `PackListBreakdown`'s "case list". The archived-tab affordances stay in the admin wrapper, which holds the `useRef` focus target (`components/admin/wizard/step3ReviewSections.tsx:2208`) and the state machine (`components/admin/wizard/step3ReviewSections.tsx:2188`), as siblings after the body inside that wrapper. A slot prop would have one caller that places it last in the same container, so the body has none.
11. **Group headings are the nav's only.** Spec line 239 puts the groups in the nav; line 227 keeps "All sections" a single card, so the list stays flat. The nav draws contiguous runs of a group in entry order, never a filter over `SHOW_SECTION_GROUPS`: a run starts when an item's group differs from the one before it, so a group with no member renders no heading (a non-lead sees no "Money", the admin's rule, `components/admin/review/ShowReviewSurface.tsx:937`) and no item can fall out of the nav. Entry order is registry order (decision 2), and `tests/showSections/registry.test.ts` gains the one fact that needs: each group's sections are contiguous in `SHOW_SECTIONS`. The heading is a plain label, the admin's `div` (`components/admin/review/ShowReviewSurface.tsx:941-942`), never an `h*`, so the page outline does not move. `CrewWideNavItem` gains an optional `group`: an item without one (Today, and every test that mounts the nav directly) draws no label. `CrewSection` does not change, so the literal entry fixtures (`tests/crew/sectionIdConsumption.test.ts:126`, `tests/components/crew/runOfShowCard.test.tsx:393`) stay as they are: the controller's `navItems` adds the group through `showSection`. The nav's content now runs past the viewport on a short window, and spec line 513 says the nav tracks the section in view, so the measure effect in `components/crew/CrewWideNav.tsx:62-85` also scrolls the nav itself, instantly, to keep the active item inside it. It does so only when `nav.scrollHeight > nav.clientHeight`, which is false in jsdom, so a mocked rect never feeds `scrollTop`.
12. **Saved copies.** `showRenderedSectionInUrl` (`components/offline/SavedCopyBar.tsx:261-274`) copies `data-active-section`, which holds canonical ids only. A copy saved before this PR ran its own build's script, and its `?s=gear` opens Rooms through the alias on reload. Nothing changes there.
