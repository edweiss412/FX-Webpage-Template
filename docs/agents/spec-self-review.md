# Spec self-review additions (project-scoped)

Extracted from `AGENTS.md` so it loads on demand instead of in every session. This file is canonical for its subject and carries the same authority as `AGENTS.md`; `AGENTS.md` links here. Applies to every agent harness working in this repo.

Run these checks during the self-review step in `superpowers:brainstorming` (or its Codex equivalent). They are derived from past adversarial-review findings on this project.

- **Guard conditions for every prop.** For each prop/input, specify what happens when it's null, empty, zero, or NaN. React components receive partial data during editing — the spec must say what renders.
- **Mode boundaries.** When a component has multiple modes or layouts, explicitly state which visual elements belong to which mode. "Shared elements" must name which modes share them.
- **Cap/truncation behavior.** Whenever a list could grow unbounded (schedule entries, zones, segments), state the max count and what happens at the boundary (ellipsis, note, truncation).
- **Rendered vs conceptual.** If something should be a rendered component element (not just a markdown description), say so with exact placement, styling, and text content.
- **Dimensional invariants.** Any component with a fixed-height or fixed-width parent containing flex/grid children MUST have a "Dimensional Invariants" section listing every parent→child dimension relationship and the exact class/style that guarantees it (`items-stretch`, `h-full`, `self-stretch`, explicit `style={{height:...}}`). **This project's Tailwind v4 does not default `.flex` to `align-items: stretch`** — every such relationship must be stated explicitly in the spec and verified in the plan with a real-browser Playwright assertion (jsdom is not sufficient).
- **Transition inventory.** Any component with multiple visual states MUST have a "Transition Inventory" table listing every state-transition pair and its animation treatment. For N states, enumerate all N\*(N-1)/2 pairs. Each pair gets either an explicit animation or an explicit "instant — no animation needed" declaration. Also enumerate compound transitions (state A changes while state B is mid-transition or in a non-default value).
- **Existing-code citations + live-code citation pass (mandatory).** Every factual claim about current code — function signatures, parameter/field names, CHECK constraint names, enum values, component APIs, URLs, DOM roles/shapes, test-fixture shapes, JWT claims, env-var names, schema PK/FK columns — MUST cite `file:line`. **Run a dedicated citation-grep pass BEFORE drafting** (not just during self-review): for every concept the spec is about to name, grep the live codebase and verify it exists with the claimed shape. Budget 30-60 min per spec. This is the #1 source of adversarial-review rounds across every milestone (e.g. M12 spec R19–R22 burned ~12 findings on invented columns/claims/URLs). The discipline is "look it up; don't invent the API." **Anchor durably by file + symbol/searchable token; the line number is a drafting-time locator that rots at every merge** (the inline-later-group arc needed a dedicated post-merge "citation refresh" commit solely to re-verify line anchors). A drifted line number on an otherwise-correct claim is not a review finding, and post-merge refresh commits are not required — re-verify an anchor only when the CLAIM it supports is in question. **Render-path enumeration is part of this pass:** for every component the spec claims emits — or must not emit — a protected data class, enumerate every render path of that component that can emit it, not only the lines the spec cites. The arc-A citation pass read the named sites, verified them correctly, and missed a raw fallback path that emitted the same class; that filing estimates this one step would have cut R1 from 9 findings to about 3 (`docs/review-rounds/docs/arc-a-spec/a0e41551c059.md`, spec §).
- **Numeric sweep (discrete pass).** Separately from the broader "self-consistency sweep" below, grep the spec for every literal number (counts, durations, env-var/table-row/alias-map counts) and cross-check against the body it describes. Stale counts after a later round edits the underlying list are a recurring finding (M12 spec R5/R10/R16/R18/R19/R24/R25). Structural fix: single-source-of-truth (one canonical section + cross-references); the numeric sweep is the per-round check that catches drift. Where a count exists in BOTH an executable declaration and prose, the executable one (a single named declaration — the `EXPECTED_SITE_TOTAL` pattern, a module-local `const` at `scripts/verify-cn-operand-parity.mjs:80`) is the single source: prose either references the constant by name or carries a dated at-authoring-time qualifier, and a present-tense prose cardinality that repeats the literal is a defect even while the values are equal — the next re-derivation updates the executable declarations (they gate) and strands the prose. Dated historical records (probe transcripts, execution records) are never corrected and never compared. The classname delta arc spent four review rounds plus one CI cycle clearing exactly this class instance-by-instance; the wedge-remeasure arc filed the sibling-list and cross-template variants against `NUMERIC_NOUN_MISMATCH` (`lib/specLint/numerics.ts:88`). Mechanical arm filed as `BL-SPECLINT-PROSE-COUNT-PARITY`. (`docs/review-rounds/refactor/classname-array-join-cn/b2aca7b02547.md` diff §, `docs/review-rounds/chore/next-1630-wedge-remeasure/9bec2e11ab11.md` spec § and diff §.)
- **Tier × domain completeness matrix.** For any DB-touching change, include an explicit matrix covering every affected tier × domain × layer (table DDL, inline CHECK, RPC read path, RPC write path, propagation trigger function, cleanup function, frontend form, audit page, tests). Every cell gets a concrete action or "N/A — reason."
- **CHECK/enum migration matrix.** Whenever a CHECK or enum changes, enumerate (a) every method enum value × what the CHECK must accept, (b) NULL/disabled-method rows, (c) the transitional window where tables/ files run BEFORE migrations/ on every apply (so inline CHECKs must accept both old and new values), (d) apply-twice idempotency (`DROP ... IF EXISTS` + `ADD`), (e) one-shot migration lifecycle.
- **Flag lifecycle table.** For every boolean config field or toggle, state its **storage** | **write path(s)** | **read path(s)** | **actual effect on output**. If any column is empty (zombie flag), decide explicitly whether to wire it through or hide it.
- **Self-consistency sweep — after drafting AND after every repair round.** Grep the spec for every numeric literal, default value, and "out of scope" claim. Same value contradicted across Resolved Decisions / body / test section is the most common round-2 finding. The sweep is NOT draft-time-only: re-run it (with the numeric sweep) across the whole document after each round's repair commit — round-N edits stale-ify wording elsewhere, and that class clusters late (R13/R18-era findings in the 2026-07 retrospective) where rounds are most expensive.
- **Disagreement-loop preempt — a §1.1 "Resolved scope — do not relitigate" section is mandatory in EVERY spec,** not just when relitigation seems likely. List resolved decisions, intentional placeholders/stubs, scope deferrals, fail-open vs fail-closed postures, and "won't ship until M<n+1>" exemptions, each with its ratification at `file:line`, so the reviewer verifies contracts instead of re-deriving them. (M4 burned three rounds re-litigating realtime fail-open before the spec citation closed it. 2026-07 retrospective: published-show-alerts shipped the §1.1 section and converged at R3; the modal-header spec omitted it and burned 22 rounds on one contested class.)
- **Build-vs-runtime gate explicitness.** For every env-gated feature, state the gate's evaluation moment (build-time artifact decision / runtime check / both) and the test shape that proves the gate works at that moment (artifact built with flag UNSET vs SET, or runtime probe). M3 R1–R2 spent two rounds discovering this distinction wasn't pre-specified and that the canonical `pnpm build` bypassed the wrapper.
- **Empirical spike before speccing stateful/race/framework surfaces (mandatory; 2026-07-19 round-burn retrospective, PRs #470–#500).** If the spec's subject involves component lifecycle, close/navigation races, optimistic state, cross-surface concurrency, or undocumented framework behavior (e.g., Next router internals), build an empirical probe harness / prototype / measurement BEFORE drafting and cite its findings as data in the spec. Never design a race state machine in prose from first principles. Undocumented framework contracts are verified (probe or framework source read) or explicitly marked UNRATIFIED at draft time. Evidence: modal-close-exit-anim (#488) burned 28 spec rounds speculating close/nav race semantics — every convergence step was a probe, a measurement, a descope, or a spike, never another prose patch; show-modal-prefetch (#497) ran Next-16 segment-cache probes first and its spec converged in 4 rounds; modal-header burned 22 rounds asserting a `w-full` invariant that one `getBoundingClientRect` measurement refuted.
- **Three-round prose cap on design-correctness vectors.** If a stateful/race design vector survives 3 adversarial rounds, stop patching prose: build the probe/prototype, descope the vector, or mark it UNRATIFIED pending a spike. Measured across #488 and role-mappings-freshness, prose rounds past that point had negative marginal value — each round's patch introduced the next round's defect (R20 reintroduced R10's bug). This is the spec-side twin of the writing-plans "same-vector recurrence" rule, with a harder stop: for design-correctness vectors the comprehensive re-analysis IS the spike, not another document audit.
- **Probe-before-argue for detector/heuristic surfaces (2026-07-31 round-economy retrospective, `docs/agents/adversarial-round-economy-2026-07-31.md`).** The empirical-spike rule above extends to any detector/classifier/heuristic over external data (sheet text, filenames, third-party payloads). Before drafting: run the candidate rules against the full fixture corpus AND the live sheets (gsheets MCP) and put the hit/miss table in the spec — corpus-calibrated bounds are draft-time inputs, not a round-47 discovery. During review: any claim about current parser behavior or corpus content is settled by probe, not argument, and NO tightening of a recognizer/guard is accepted without a probe demonstrating the corruption it prevents. Both documented reversals on the inline-later-group spec (R21/R27, R53/R55) were probe-less analytical tightenings later refuted by probes; every probe-backed decision in that 57-round train survived. **Probe scripts get their own mini-review.** A probe whose output feeds a spec's calibration table is itself a spec input, so it is reviewed — iteration bounds, truncation, declared-versus-imported counts — before its output is quoted as fact. Arc B shipped a declared-versus-imported iteration bug and a truncation inside a probe the spec then cited, which put both defects into the spec as measurements (`docs/review-rounds/docs/arc-b-spec/a0e41551c059.md`, spec §).
- **Documented-limits budget + consequence-bound convergence (detector/heuristic specs).** The draft carries a "Documented limits" section from round 0, and the acceptance criterion is the preparedness-audit posture — every input is "parsed correctly or signaled, never silently wrong" (`docs/audits/edge-case-preparedness-audit-2026-07-04.md:92`) — NOT "no imaginable defeating input": the input space is open by declaration (the corpus is a non-exhaustive sample), so adversarial enumeration does not terminate. A hypothetical input needs no corpus instance to be admissible, but it is a FINDING only if a probe shows silent corruption or wrong auto-correct; when the worst case is a conservative demote plus a surfaced warning, it files into the documented-limits section by default, without a review round. The inline-later-group spec ended at exactly this posture ("never silence, never corruption"; limits "fenced both directions") but reached it retail — one ratification round per edge family (R24/R26/R30/R33/R52/R54).
- **Run the mandated passes and attach the transcript.** R1–R3 spec findings are dominated by NON-COMPLIANCE with passes this file already mandates (live-code citation, numeric sweep, anti-tautology) — not by rule gaps. Before dispatching any spec or plan review, actually run the citation-grep and numeric sweep and attach the transcript (commands + output summary) to the review dispatch so the orchestrator can verify the pass happened. Run `pnpm spec:lint <doc>` and attach its report to the review dispatch — every finding it emitted, plus the `summary:` line. The numeric `INVENTORY` block may be omitted; findings may not. If the report is abridged for size, the dispatch says so explicitly and says how much was dropped. `codex-guard --lint-doc <doc>` does all of this automatically and records `lintArm` in result.json, so prefer it to pasting; the hand-run citation-grep/numeric-sweep transcript remains required only for the non-mechanized residue (semantic claim-vs-line verification). A dispatch without the lint output is incomplete.

- **Declared task contract for plans (machine-checked, not remembered).** A plan opts in by delimiting its task region and marking each task:

  ```
  <!-- tasks: depth=2 -->
  ## Task 1
  <!-- task: red=`pnpm vitest run tests/x.test.ts` ac=AC-3,AC-4 -->
  <!-- tasks: end -->
  ```

  `spec:lint` then reports a task with no marker, a marker outside every task, a malformed one, an empty `red=`, and an `ac=` id that appears nowhere else in the plan. Opt-in: a plan with no enrollment line is untouched, so the legacy corpus stays out of scope. The grain is **declared**, never inferred from heading text — a recognizer over `Task 3` / `T2b` prose is the exact shape these rules exist to prevent, and the corpus shows why: the most obvious canonical spelling of a RED step covers 32 lines against 2935 task headings. A plan may declare several sequential regions, each with its own depth — close one region and open the next; headings between regions are unchecked (multi-region design, `docs/superpowers/specs/2026-08-09-task-enrollment-multi-region-design.md`). A region may also carry the optional red-contract region attribute (`<!-- tasks: depth=N red-contract -->`), which turns on the v2 marker fields `red-state=`, `red-target=` and `why=` for every marker it owns and makes those markers eligible for `spec:lint --exec-red` (`docs/superpowers/specs/2026-08-15-spec-lint-intent-red-arms.md`).

- **Accept-set discipline for detector and guard specs — enforced at dispatch, not by memory.** Any spec introducing a surface that decides whether an input is "an instance of X" states what it ACCEPTS, keyed on type or structure rather than spelling, and states that everything outside the accept-set is rejected or reported by name. A spec enumerating *rejected* forms has authored a denylist, and a denylist accepts whatever it did not model.

  This was drafted as another prose rule here and deliberately is not one. Measured 2026-08-04 across 16 concurrent sessions: 474 review rounds, arcs at 41 / 40 / 38 / 33 / 30 / 28, and every arc diagnosed cited a rule that already existed in this corpus and went unapplied — including the three-round cap two lines above. Adding a 123rd rule to a set whose measured failure is that 122 are not applied buys nothing. So the enforcement is `~/.claude/hooks/review-convergence-gate.sh`, which blocks a guard/detector dispatch whose brief states no consequence bound and no threat-model fence, at round 1 where it is cheap. See AGENTS.md for the contract; the numbers are there too.
