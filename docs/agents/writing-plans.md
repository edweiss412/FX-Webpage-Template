# Writing-plans additions (project-scoped)

Extracted from `AGENTS.md` so it loads on demand instead of in every session. This file is canonical for its subject and carries the same authority as `AGENTS.md`; `AGENTS.md` links here. Applies to every agent harness working in this repo.

Run these when writing or revising any milestone plan in this repo.

- **Pre-draft code-verification pass (mandatory).** Before writing any task step that names a specific file, function, field, constraint, component prop, DOM role, URL, or test fixture, verify each against the live codebase with grep. Round-1 adversarial findings are dominated by plans that name APIs or fixtures that don't match reality. Budget ~10 min of verification up front — saves multiple review rounds.
- **Layout-dimensions task (mandatory for fixed-dimension parents).** Add a TDD task that writes a real-browser-rendered assertion (Playwright, or chrome-devtools `evaluate_script`) calling `getBoundingClientRect()` on every documented `data-testid` inside a fixed-dimension parent and asserting `child.height === parent.height` (and/or width) within 0.5px tolerance. Jest + jsdom is not sufficient. Body must include the spec's exact "Dimensional Invariants" list.
- **Transition-audit task (mandatory for components with Transition Inventory).** TDD task that lists every `AnimatePresence`, ternary render, and conditional block; asserts each has appropriate `exit`/`initial`/`animate` props (or is deliberately instant); tests compound transitions (toggle state A while state B is active/mid-animation). Body must include the spec's transition inventory table.
- **Anti-tautology rule for tests.**
  - When asserting a graphic matches a calc result, assert against the data source (e.g., `markdownVariables.shifts[-1].surchargedBuckets`), NOT the container that renders both.
  - When scanning rendered DOM for a label, first clone the tree and remove sibling elements that independently render that label.
  - Derive expected values from fixture dimensions, never hardcode. A 2-hour shift fixture cannot reach a 3.0× top-tier assertion regardless of configuration.
  - For every new test task, state the concrete failure mode it catches. If the only thing it proves is "the function is called," strengthen it.
  - **RED validity.** For every planned RED step, name the production line whose absence or defect makes it fail. A RED whose failure derives from a test-local fixture — a helper the test itself has not written yet, an import that does not resolve, a value the test controls end to end — is invalid by construction: it goes green when the test file changes, not when the implementation lands (`docs/review-rounds/docs/arc-a-spec/a0e41551c059.md`, plan §).
  - **Four pre-dispatch mutants for string-presence guards.** Any test asserting "this string appears in this output" gets all four run before the review dispatch: (a) the value emptied; (b) the expected content plus an appended suffix; (c) the content present but not live — commented out, escaped, in an attribute, or behind a false condition — so it exists somewhere but not where the assertion claims; (d) each discriminating parameter of the function under test varied in turn. Record each result in the commit. All four rounds on `feat/l-wave-push` were test-side escapes these four mutants find in minutes (`docs/review-rounds/feat/l-wave-push/a0e41551c059.md`).
  - **State every guard's premise executably.** An assertion has discriminating power only under some condition: a fixture large enough to cross the boundary, an environment rich enough to differ from empty. Say that condition in code, immediately above the assertion that rests on it, with `premise` / `premiseHolds` from `tests/_shared/premise.ts`. Five shapes, all measured on PR #701 rather than imagined: a fixture that cannot reach the boundary it names (13 claims against a cap of 100); an expected value read from the same degenerate source as the actual (`truth` and `size` both 0 where CI has no refs); an absent event encoded as a sentinel that satisfies the comparison (`indexOf` returns -1, and -1 is less than every real index, so an ordering guard held when the first event never happened); a premise for a mechanism since refactored away; and a premise that never executes at all (`test.each([])` registers no case, so a premise in the callback is unreachable in exactly the degenerate case it exists for). A premise must therefore execute **unconditionally relative to what it guards** — never inside a `.each` callback, whose case count can be zero. **The trap is the repair, not the original:** a guard that goes red in CI is most naturally "fixed" by deriving its expected value from the environment, which is precisely what makes it vacuous there. Where the environment can be constructed, construct it — a throwaway repository, a 101-row fixture — rather than interrogating the ambient one. **A premise that validates something ADJACENT to the case is not a premise:** the condition must be proven on the case's OWN inputs. M-wave's freshness probe suite asserted once, up front, that a venue edit paints, then ran six cases whose own mutations were never checked — a mis-pathed pair produced identical renders and reported PASS. Each case proves that its own inputs differ in the adapted data, not that some other case's did (`docs/review-rounds/feat/m-wave-ui/fc4902004b78.md`, rule 2). Suites enrolled in the mutation registry have this enforced by `tests/mutation/_metaPremiseContract.test.ts`; elsewhere it is convention. Full rationale and the taxonomy: `docs/superpowers/specs/2026-08-04-guard-premise-reachability-design.md`. **A premise stated inside a plan's embedded test block can now be CHECKED rather than trusted:** mark the block with ``<!-- fixture: why=`…` -->`` on the line immediately above its opening fence and `pnpm spec:lint --exec-red` splices it into `tests/`, runs it once against the live tree, and reports `FIXTURE_UNSATISFIABLE` when a stated premise did not hold — the defect where a constructed fixture never reaches the assertion it was built for (`docs/superpowers/specs/2026-08-18-planlint-fixture-satisfiability.md`). Enrolment is declared and never inferred, so an unmarked block is checked by nothing, and silence from the arm is not a certificate.
- **Every acceptance criterion a plan declares is CLAIMED or DISPOSED, on its own declaring line.** `spec:lint` reads a plan's body for its criteria: a list item or ATX heading whose content begins with an id, the id a standalone token at the head. An id no task marker's `ac=` cites draws `TASK_AC_UNCLAIMED` unless that same line ends with a disposition, and a marker citing an id the plan never declares draws `TASK_AC_UNDECLARED` — but only in a plan that declares at least one, since 55 of the 117 enrolled plans keep their criteria in the sibling spec and carry a coverage map here. The disposition is an **accept-set** with a closed grammar (spec `docs/superpowers/specs/2026-08-26-speclint-dispatch-gates-design.md` §4.3), parenthesised and end-anchored, `RETIRED` case-sensitive, the owner a token list of `Task N` forms plus `closeout`, `the closeout` and `the PR's last commit`: `(discharged by Task 10)`, `(RETIRED: superseded by the closeout)`. **A reason must not name another `AC-` id:** the reason sits on the declaring line, so the line would then carry two ids and the count cut declines it — the criterion is exempted by the decline rather than by the disposition, which is not what you wrote. A near miss REPORTS rather than exempting, because to a plan author silence and clean are indistinguishable, and a sentence that merely ends in "Task 10." disposes nothing. **A disposition may only say what the plan already says** — never a reinterpretation and never an inference from task structure; where the plan's prose settles nothing, or names an owner the closed set cannot express, the pair goes on the committed residue at `tests/specLint/acUnclaimedResidue.ts` with its evidence (12 rows today) and stays flagged. **The arm declines rather than guesses on a line carrying more than one id**, and every such line is asserted against `tests/specLint/acAmbiguousRecord.ts` (14 lines today) so declining is never silent. **That decline is silent by design everywhere else, and the number is why:** recording each declined line would commit 1224 rows across 105 plans, because most plans state their criteria in tables and coverage maps, and an exact-equality record that size reds on any routine plan edit anywhere in the corpus. The loudness sits instead on the corpus assertion that the live `TASK_AC_UNDECLARED` set is empty.

- **Adversarial review (cross-model) is mandatory.** When creating the task checklist, add an "Adversarial review (cross-model)" task between "Self-review" and "Execution handoff." After plan self-review completes, invoke the cross-CLI review (Codex if implementer is Claude, Claude if implementer is Codex). Models iterate until convergence; only escalate genuine ambiguity to the user. Do not proceed to execution handoff without this step.
- **Meta-test inventory (mandatory).** Before drafting tasks, declare in the plan body which structural meta-tests this milestone CREATES or EXTENDS. Candidate registries: Supabase call boundaries (`tests/auth/_metaInfraContract.test.ts`); sentinel hiding in optional text (`tests/components/tiles/_metaSentinelHidingContract.test.ts`); `admin_alerts.upsert` catalog completeness (`tests/messages/_metaAdminAlertCatalog.test.ts`); advisory-lock topology (`tests/auth/advisoryLockRpcDeadlock.test.ts`); no-inline-email-normalization (`tests/admin/no-inline-email-normalization.test.ts`). Most milestones touching auth, DB writes, admin alerts, or tile rendering will have at least one entry. "None applies because <reason>" is acceptable but must be declared explicitly. (M4 §8.3 and M5 R14–R18 both became cheap only once the meta-test landed; pre-declaring saves the rounds.)
- **Advisory-lock holder topology (mandatory if the plan touches `pg_advisory*`).** Enumerate every existing lock holder for each hashkey the plan touches (JS-side wrapper, in-RPC, nested SECURITY DEFINER) and state which layer is the new code's holder. If multiple layers acquire the same key, the plan MUST resolve to a single layer or extend `tests/auth/advisoryLockRpcDeadlock.test.ts` to pin the topology. M5 R20 was a CRITICAL deadlock from this class; this rule catches it at plan time.
- **Fix-round regression budget.** When a fix in a review round patches surface S for class C, the next-round preparation must include: (a) re-grep class C across S after the patch, (b) confirm the relevant meta-test (if any) still passes, (c) note both in the round closure. M5 R19→R20 introduced a CRITICAL deadlock by patching an advisory-lock hole on a surface that already had a JS-side wrapper; this rule catches that class. **The repair's own tidy-up is a defect site**, so (a)'s re-grep covers the repair commit's incidental edits, not only the patched class: two of m-wave's sharpest findings were in repairs rather than originals — an `empty:hidden` that re-hid the region the fix had just exposed, and a channel migration that left the old speaker in place and duplicated speech (`docs/review-rounds/feat/m-wave-ui/fc4902004b78.md`).
- **Same-vector recurrence triggers comprehensive re-analysis (mandatory).** If three adversarial-review rounds in a row identify findings on the same vector (HTTP semantics, advisory-lock topology, Supabase call-boundary, etc. — same conceptual surface, even if different files), the next round's preparation MUST include a comprehensive re-analysis of that vector: read the governing spec / RFC / contract end-to-end, enumerate every requirement as a checklist, and audit the diff against the full checklist BEFORE the next review fires. If the round after the comprehensive re-analysis STILL surfaces a finding on the same vector, the analysis was incomplete — stop patching, declare the vector unresolved, and deep-dive the spec + diff together until convergence is structural (not per-instance). Codified after M7 Task 7.9 R14→R22 (9 rounds on incremental RFC 7233 / HTTP-semantics edge cases that a single up-front spec audit would have one-shotted). The class-sweep rule above catches "found one, find peers"; this rule catches "implementing a documented spec, audit the full surface."
- **Structural-defense calibration (M12 plan R5 amendment; tightened 2026-07-19).** When the round AFTER comprehensive re-analysis still surfaces same-vector findings, ship structural defenses (meta-tests, registry entries, CI-time grep guards) **in that round's repair commit** — do NOT wait for another adversarial round to confirm the analysis was incomplete. The structural defenses close the class at CI time; further adversarial rounds on the same vector are no longer the convergence path. (M12 plan R5: 5 rounds on live-code-fidelity; converged only when R5 declared the vector unresolved AND shipped a validation-tz-pin meta-test + extended `email-canonicalization.test.ts` scope in the same commit. The M12 spec ran 25 rounds without this calibration and never formally APPROVE'd.) **Tightening: if the class is already nameable at FIRST occurrence, ship the structural defense in the FIRST repair commit** — the 3-round same-vector threshold is a ceiling, not a waiting period. Every long train audited in the 2026-07 retrospective converged only when the structural defense (or probe) landed; waiting for recurrence just delayed that landing.
- **Repair economy for recognizer/guard surfaces.** The function-grain companion to the same-vector-recurrence and structural-defense-calibration bullets above — it applies alongside them and restates neither. (1) A recognizer bounded by a NUMBER — a cap, a position, a backreference count — will be found by the next reviewer; derive the bound from the input instead. (2) A key that can ALIAS is not a clock: recency wants a monotonic ordinal, never a session or attempt id. (3) When consecutive rounds keep landing on ONE function (the filing measured four), the mechanism is answering the wrong question — the comprehensive re-analysis the same-vector rule already mandates should ask "what question does this function actually need to answer?" and prefer deleting or deriving the mechanism over widening it. The codex-guard emphasis parser was deleted, −71 lines, and all four rounds' shapes became unreachable. (4) A scanner's claims are planted as executable self-test shapes, positive AND negative, in the same commit as any widening; the widenings shipped without self-tests are the ones that came back. Site-list derivation is not restated here — it lands once, in the `AGENTS.md` class-sweep bullet. (`docs/review-rounds/feat/review-round-economy/48b280b949cc.md`, `docs/review-rounds/feat/m-wave-ui/fc4902004b78.md`.)
- **Typecheck pasted snippets + verify CI wiring (mandatory pre-draft; 2026-07-19 retrospective).** Every test/implementation snippet embedded in a task body gets typechecked against the repo's strict tsconfig (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`) before the plan is dispatched for review — paste-time compile errors (`@vitest-environment` pragma missing, unsafe index access, `.includes` narrowing) cost one round each across every audited feature. In the same pass, confirm every new test file the plan creates has its `testMatch` entry and workflow path-filter wiring named in the plan, and that the named entries exist or are created by an explicit task step.
- **Every `red=` and gate command is validated executably at plan time (round-economy followups-2, 2026-08-09).** The task-marker contract is red-then-green ON THE SAME COMMAND: a `red=` is valid only if the task has a point where the command is OBSERVED failing for the stated reason and a later point where the SAME command passes. Before dispatching a plan for review: a `red=` asserting the current tree already fails (its failing case exists at plan time) is RUN — one that exits 0 is a plan defect. A `red=` whose failing case the task itself writes — a NEW test file OR a new case added to an EXISTING suite — is the ordinary invariant-1 shape: it is not run at plan time (the pre-change suite may legitimately be green, or the file absent); instead the task names the production line whose absence or defect will make the new case fail (the RED-validity bullet above — cross-reference, do not restate), verified absent or defective on the live tree, with observed-red landing in the task's RED step. Rejected statically in either branch is any marker whose cycle cannot complete: a guard test that passes the moment it is authored; a command whose target the GREEN step deletes or renames (the SAME command never passes); a conjunct behind `&&` where an earlier expected failure short-circuits it (asserted red, never observed — the conjunction is the GREEN criterion); and a task body with no one-line "what is red and why" statement. Declared gate commands (merge gates, closeout checks, CI probes) get the mutant-red treatment: probe each against a CONSTRUCTED failing input and confirm non-zero exit — a bare `gh run list`, an unresolvable sha that empties a diff into a passing `test -z`, and a fail-open shell chain all exit 0 on the exact failure they name. The mechanical arm has landed: a plan region opened `<!-- tasks: depth=N red-contract -->` requires `red-state=live|authored`, a `why=`, and — for `authored` — a `red-target=` naming the production surface, all checked statically, with `pnpm spec:lint --exec-red` running the `red-state=live` commands of that region and reporting any that already exit 0 (`docs/superpowers/specs/2026-08-15-spec-lint-intent-red-arms.md`). The VERDICT-CAPABILITY arms have landed on top of it (`docs/superpowers/specs/2026-08-17-spec-lint-red-verdict-capability.md`): every `red=` and gate `cmd=` is parse-checked with `sh -nc` on the DEFAULT invocation, because a command the executing shell cannot parse expresses no verdict in either direction and today's classifier reads its non-zero exit as red observed; and under `--exec-red` a derived `vitest list` probe settles whether a vitest-shaped command can COLLECT the tests it claims to observe, so a red that exits non-zero for a collection reason (a mistyped path, env-gated project) is named rather than believed. A `-t` name filter draws an advisory, since one that matches nothing exits 0 and reports green from the moment it is written. (`docs/review-rounds/refactor/classname-array-join-cn/61281c23e8ce.md` spec §, `docs/review-rounds/docs/quick-wins-2-specs/97e179d831aa.md` plan §, `docs/review-rounds/test/resurrect-mobile-safari-e2e/9bd0a8456151.md` plan §.) **DOCUMENTED LIMIT of `RED_TARGET_INVALID`, so it is not re-derived: it checks that a tracked path has an IN-RANGE line, and never what is AT that line.** A line-form `red-target=` that drifts onto unrelated code stays green by design, and the drift is caused by the task's OWN implementation more often than by anyone else's. Measured 2026-08-20 on `feat/speclint-claim-sweep-after-repair`: Task 7 cited `scripts/spec-lint.ts:397` for a `why=` naming the flag loop's final else-if, that task then inserted an eleven-line `--also` branch above it, and the citation resolved green while pointing at `const key = (`. The closeout re-verification is therefore by READING each cited line and matching it to the symbol its `why=` names -- confirming the citation RESOLVES establishes nothing. Line-form citations are as exposed as path-only ones; they are merely exposed silently rather than loudly.
- **Reconciliation/closeout sweeps are authored AND RUN at plan time.** Any plan step of the form "grep for X and reconcile the hits" must include the exact command, its current output, and a per-hit disposition in the plan body — not a description of a grep to be run later. Authoring the sweep without running it cost the financials plan 6 consecutive rounds (R5–R10) on sweep syntax alone (case-sensitivity, missed prose lines, wrong counts); the R9 fix — a grep-DRIVEN comprehensive sweep — belongs at plan-authoring time, not round 9. **Registry count reconciliation** takes the same authored-AND-run posture: when a plan adds or removes rows in a registry-bearing meta-suite, the plan body carries the mechanical diff of the registry arrays against the tasks' stated additions and removals, run at plan time and pasted, not described as a check to perform later (`docs/review-rounds/docs/arc-a-spec/a0e41551c059.md`, plan §). **A sweep for a claim a repair CHANGED is mechanical and belongs here rather than in a reviewer's attention:** after superseding a value or re-classifying a named site, run `pnpm spec:lint --repair <rev> --superseded <N> --replacement <M>` (or `--claim-about <identifier>`, or both) with `--also <path>` for every peer document the arc writes, and it reports the occurrences elsewhere in the corpus that still assert the old claim. It is ADVISORY by construction -- it cannot know whether a surviving occurrence is stale or deliberate -- and it REFUSES rather than reporting a clean when the declaration is incoherent or absent, because silence from an undeclared invocation is not a certificate.

- **Three one-line lint shapes over HANDOFF/plan text.** All three were caught only by review across the arc-A/B/C batch — final-diff ordering independently in two arcs, the other two once each, with gate-grep precision arriving as arc B's second distinct HANDOFF-text defect class. (i) *Review covers what merges*: the diff the final review round examined must be the diff that merges, so a handoff whose last commit lands after its final round has reviewed something else. (ii) *Handoff gate checks read anchored state from origin*, never from bounded log output — `git log -N` can truncate past the very fact being asserted, and the check then passes by not seeing it. (iii) *Gate-grep precision*: a handoff's "this grep proves the gate ran" command must match only the gate's own output shape, or it succeeds on unrelated text and proves nothing. (`docs/review-rounds/docs/arc-c-spec/a0e41551c059.md` plan §, `docs/review-rounds/docs/arc-b-spec/a0e41551c059.md` plan §.)
- **e2e harness-readiness checklist (mandatory for any plan attaching Playwright).** The plan states: (a) the server boot mechanism (dev vs prod build, port, config), (b) the readiness/hydration gate awaited before the first assertion (`waitForRowHydration`-class, never `networkidle` alone), and (c) detach-safety for any sampler/`locator.evaluate` call that can outlive its element (auto-wait hangs on unmounted nodes). All three were repeat LATE-round plan findings across #497/#499; none is currently covered by any other rule.
- **Mutation-family closure for guard/meta-test work (2026-07-31 round-economy retrospective, `docs/agents/adversarial-round-economy-2026-07-31.md`).** Any plan shipping mutation checks or structural guards enumerates its mutation-operator families up front — that enumeration is the closure set the review converges against. A reviewer-proposed NEW family is admissible only with a live escaping mutant demonstrated against the shipped guard, not hypothesized. Guard surfaces otherwise have unbounded attack space ("three more mutation families" was still landing at ci-dark impl R13); "the reviewer imagines no further mutant" is not a fixed point and is not the convergence criterion.
- **`echo >>` discipline.** Never use `echo "X" >> .gitignore` (or any append-to-file shell idiom that doesn't guarantee a trailing newline on the previous line). M0 R1 + M4 R7 both shipped malformed gitignore entries this way. Use `printf '\n%s\n'` and verify with `git check-ignore -v <path>`.
