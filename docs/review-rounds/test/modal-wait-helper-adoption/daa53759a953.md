**Judgment:** every finding was correct. Not one was refuted, and that is the honest headline —
this was not a reviewer relitigating a fenced decision, it was a guard that genuinely did not pin
what it claimed, four times over.

Rounds 1-2 were structural and worth their cost. The census had silently lost 31 of 51 members
(a Shape-G call carries no route text, so adopting REMOVED a site from its own census), and the
member rules were count-free on a rationale — "recognizing the adopted shape is self-evidencing" —
that a probe refuted in one edit. Those are design defects, found by exactly the mechanism reviews
exist for.

**Rounds 3-5 are the arc's own same-axis recurrence, and the AGENTS.md rule applies to me.**
Each landed one comment-or-activation corner: whole-line comments (round 3, via CI rather than the
reviewer), split activations (round 4), inline comments beside live code (round 5). Three
consecutive rounds each widening the same recognizer by one input family is precisely the shape the
repair-direction rule names, and I was the one widening it.

What broke the pattern was changing the KIND of repair rather than adding a fourth corner. Round
5's fix is not "handle inline comments too"; it is a statement of what each scan is asking —
"does this NAVIGATE / has this ADOPTED" is about CODE and reads the STRIPPED line, "does it declare
an EXEMPTION" is about a COMMENT and reads the RAW line. That subsumes every comment spelling at
once, including ones nobody probed, and it is smaller than what it replaced. Had I reached for it
at round 3 instead of `startsWith("//")`, rounds 4 and 5 would not have existed.

**Round 6 is a different vector, and it is the one worth naming.** It found the mutation ledger
stale at HEAD: a siteId is `operator:LINE:column:from>to`, so my own previous commit relocated the
accepted id and the gate would report a stale-ledger-row for an id no generated site has. That is
the SECOND time the same shape landed — round 2's finding was the same ledger disagreeing a
different way — and it is the same class as the exemption inventory I had already repaired earlier
in the arc by re-pinning it on FILE + CLASS instead of `file:line`. Line-keyed pins churn under
edits to the file they describe. The siteId format is the harness's, so the repair here is not a
re-key but a stated discipline recorded beside the rows: the ledger is a measurement OF A REVISION,
re-run in the same commit as any source change.

**Counted rounds 7-9 are the tail, and the tail is where the round cap actually bit.** Round 7
(corpus 8) found that the adopted-site counts are aggregate rather than site-associated: moving a
wait between two member sites keeps `f/member-shape-N` at 12 while orphaning one. Correct, probed
on live corpus lines — and **declined**, because site-associating a wait is control-flow analysis,
because the surface had already spent three rounds on one-grammar-corner-per-round, and because the
finding carried no surviving mutant from the declared operator set. It is recorded in the guard's
header, this closeout, and an OPEN `BL-MODAL-WAIT-SITE-ASSOCIATED-COUNTS`. That is the
ship-and-fence branch of the repair-direction rule taken deliberately rather than by exhaustion.

Round 8 (corpus 9) is the one that vindicates the fence by contrast: `d/reference-not-activation`
was a genuine catch-all — "not a `.click()`, not prose" — and ONE ordinary corpus edit
(`page.getByTestId(...).press("Enter")` replacing an existing assertion) walked straight through it
with `undisposed=0`. That is a probe from the declared domain showing a rule asserting something
false, so it was admissible where round 7's was fenced, and the repair was a NARROWING: an
allowlist of the six reference-only forms the corpus contains, with any unrecognized activation
shape now failing as undisposed. **Narrowing re-exposed a defect the catch-all had been hiding** —
the split-activation binding satisfies the allowlist's `binding` form, so two rules claimed the same
two lines and the census's disjointness assertion went red. That is the argument for narrowing in
one observation: the wide rule was not merely over-permissive, it was masking an overlap.

Round 9 (corpus 10) is the second fence, and it is the more interesting of the two because it
proves the round-8 decline was not laziness. It found that the round-8 narrowing is still LINE
granular: reformat its own probe as the multiline chain the corpus already uses eleven lines away —
`await page` / `.getByTestId(...)` / `.press("Enter")` — and the candidate is the middle line, so
the verb sits where the classifier cannot see it. A sibling probe run in the same session found the
second member (an in-page `click()` inside a `page.evaluate` body, testid on the argument line).

One defect, stated as a class: **the unit of classification is the physical line.** Filed with both
probes as `BL-MODAL-WAIT-LINE-GRANULARITY-ACTIVATION`. Declined, because both available repairs are
the ones the rule forbids here — a "check the next line" arm is the third grammar corner on the axis
that already consumed counted rounds 3-5, and the honest repair is a change of UNIT (classify the
STATEMENT) which is a redesign with its own spec. One free narrowing was taken: the rule's separate
`continuation` arm was DEAD, both live instances also satisfying the `dataOnly` arm, so it was
deleted rather than defended.

**The lesson this arc paid ten rounds for: a recognizer's limit is a property of its UNIT, and
naming the unit ends the sequence that enumerating spellings never does.** Rounds 3-5 each added a
comment spelling until round 5 changed WHAT was asked (of the stripped line) and subsumed them all.
Rounds 8-9 are the same story one level up, and this time the change of unit was too large to make
here — so it is filed as the unit change rather than paid down one spelling per round.

**Mechanizable:** two, and both were already available.

- **The single-source comment rule is enforced, and I broke it anyway.**
  `tests/cross-cutting/_metaStripCommentsSingleSource.test.ts` exists to stop exactly the
