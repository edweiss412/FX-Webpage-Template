## spec — 4 rounds

**Examined:** four rounds at this base, all BLOCKING, 14 findings declared (5 / 3 / 3 / 3). Every one was accepted; none was argued down. The subject is a one-file planner, `lib/sync/holds/holdAwareApply.ts`, and its five `retainRows.set` sites.

**Judgment:** the rounds did not converge because each one refuted a general CLAIM about the surface rather than a line of it, and each repair replaced the refuted claim with a new general claim. The sequence is legible in one list:

- R1 refuted "a live row exists at some sites and not others" — the `crew_identity` restore branch runs with one, because `undo_change` re-inserts the crew row.
- R2 refuted its replacement, "the restore branch carries an undo's payload" — `mi11_reject_hold` writes the identical persisted shape and never touches `crew_members`, and `readOpenHolds` cannot tell the producers apart.
- R3 refuted the next one, "the retain is never consulted while the sheet lists the member" — false for a rename baseline, where the hold survives precisely because a parse row carries the suppressed email.
- R4 refuted the enumeration that replaced the claims, on two rows, and found a mixed-liveness state in the mechanism R3's repair had introduced.

Four rounds, four claims, and the finding rate flat at 3 per round from R2 on. The diagnosis is not that the reviewer widened its scope; the probe domain and the threat fence were stated identically in all four briefs and every finding was drawn from inside them. It is that the arc kept arguing about WHEN a code path runs, over a state space nobody had bounded, when the answer it needed was about WHO CAN WRITE the row — a set with two members.

The orchestrator's ruling at the cap is that argument: a held `entity_key`'s live `crew_members` row is written only by the retain output itself and by operator edits, because the sync's own upsert for that key IS the plan's row for that key, and a rejected rename's replacement is suppressed by both name and canonical email so it never reaches `plan.crewMembers`. Meanwhile `held_value` is a copy of a prior live row (`writeMi11Holds` reads `liveCrewByName`, the pre-apply snapshot). Therefore live is never older than the snapshot, in any state, and live-wins is correct without any claim about when the retain is consulted. It settles every finding R1 through R4 raised, and it would have settled them at R1.

The same ruling drops the mechanism R3's repair added, which is where R4's blocking finding was: a rename-restore `nonIdentityOverride` whose guard tested the STORED replacement name for prior liveness while the release check matches by email under ANY name, so a truly-added stored name whose current email-match is a different pre-existing member would have adopted that member's fields. Removing the mechanism removes the finding. What it preferred over live-wins was the suppressed replacement's sheet fields, which is now a documented limit — and one that was true before this arc.

**Mechanizable:** declined: this arc files no ledger row of any facing, by the 2026-08-27 arc-batch directive, and the observation below is a named shape rather than a proposed gate. Recorded here so a later arc that hits the shape a sixth time has the count.

The R3-to-R4 pair is mechanizable in principle. R3's repair introduced a guard on one key (`suppressed_added.name`) protecting a lookup keyed on another (canonical email under any name); the release check twenty lines away already demonstrates the two are not interchangeable. A guard whose predicate is keyed differently from the lookup it protects is a shape a linter could see, and it is the second time on this arc that a `previousCrewNames.has(...)` test has been the load-bearing guard for something it does not fully cover — WM-F4's own comment records the first as having "recurred 3x". Nothing here proposes a new gate; the observation is that the recurrence is now at five and the shape is stable enough to name.

## plan — 4 rounds
