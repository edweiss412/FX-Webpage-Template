Arc subject: the `screenshots-drift` byte gate, which failed on captures that changed no render input.

## spec — 7 rounds

**Examined:** every finding raised across spec r1 (5), r2 (3), r3 (3), r4 (1), r5 (0), r6 (1) and r7 (0), plus plan
r1 (7) and plan r2 (7), classified by whether a mechanical check could have caught it before dispatch. Counts are the reviewers'

**Mechanizable:** one arm, proven by an incident on this arc and executed before filing rather than
proposed.

`spec:lint` checks marker→AC but not AC→marker. `TASK_AC_UNRESOLVED`
(`lib/specLint/taskContract.ts:376`) fires when a marker's `ac=` id appears nowhere in the plan's text.
Nothing fires when a plan DECLARES an acceptance criterion that no task marker claims. On this arc the plan
declared AC-2, no marker referenced it, `spec:lint` reported **0 hard**, and plan r1 raised it as BLOCKING.
An unowned acceptance criterion is an assertion nobody is scheduled to write.

Filed as `BL-SPECLINT-AC-UNCLAIMED`. The check is the existing traversal read in the other direction and
was run against this arc's own plan before filing — it reproduces the finding on the pre-repair document
and reports clean on the repaired one.

**r6 is a scoped round past the cap, and its single finding is the cheapest kind.** A measurement landed
after the r5 APPROVE — both failures are `pull_request` runs while all nine non-reproducing probes are
`workflow_dispatch` — so the 0/9 account, the `eventName` field it forces, and the discrimination row that
protects it went back for coverage rather than self-certification. The reviewer returned one finding: a
timestamp bucket said seven runs at `11:32Z` when one of the seven is stamped `11:33:01Z`. The count, the
trigger classification, the sha and the conclusion all held.

Worth recording because it is not mechanizable and not a design defect either — it is an authoring slip in
a hand-written measurement, the class that only a reviewer re-running the producing command catches. The
implementer had independently caught the same slip while the round was in flight and deliberately held the
repair rather than editing a tree under review; the finding and the held note agree exactly. That is the
round working as intended, and it is the argument for scoping a post-approval measurement back through
review rather than trusting the author who just wrote it.

r7 confirmed the repair and returned zero findings. A confirmation round after a single factual repair is
worth its cost precisely once — the repaired claim is this arc's only load-bearing new measurement, and an
author confirming their own correction to a measurement a reviewer had just corrected them on is the
weakest form of proof available. It is not a precedent for confirming every repair.

**Judgment:** the other eighteen findings are design defects no lint reaches. Three shapes, each invisible
from inside the design:

1. **The observer inside the observed** (spec r2). Fault branches replace the very selector the capture
   waits on, so the fault class the gate exists for arrives in the one form that unmounts every instrument
   the gate adds. The consequence bound had been written two rounds earlier and was false the whole time.
2. **A denylist wearing an accept-set's name** (spec r2, r3; plan r1). The recognizer was keyed on
   comparison spellings, so a `catch`, a `switch` case, and an IMPORTED type-guard predicate were invisible
   by construction. Repair: key the accept-set on the rendering construct, resolve predicates through their
   declaration rather than their name, and assert that unknown forms are REPORTED — the only assertion that
   separates an accept-set from a denylist.
3. **Assertions that cannot fail** (spec r2, r3, r4; plan r1). A route mutant that could not distinguish
   the parser defect it targeted; an AC with no owning task; a "proven on a real dispatched run" naming no
   command; and AC-2, which took **four rounds and three repairs** to actually assert anything.

   AC-2 is the one worth recording in full, because each repair looked sufficient and the next round showed
   it was not. A directory count passes because the fourteen baselines are already on disk. Completion
   events emitted when the capture function returns pass, because deleting the single `writeFile` leaves it
   returning normally. Reading the file back after writing ALSO passes, because a healthy capture
   reproduces the committed baseline byte-for-byte — the criterion's own premise — so the pre-existing file
   satisfies both the length and the hash check.

   The lesson generalises past this arc: **no assertion over an output path can prove a run produced it
   when the correct output is byte-identical to what is already there.** Three rounds were spent looking
   for a better assertion when the defect was structural. The repair is structural too — capture into a
   directory created empty at the start of the run, so file existence means this run wrote it.

**Infra:** none. Every dispatch returned a verdict — no `no_verdict`, no reaped run, no wrapper fault.

### Why the rounds were not a ratchet

The finding rate DID decay on spec — 5, 3, 3, 1, and BLOCKING to NEEDS-ATTENTION at r4 — and the residue
at the cap is a single finding on one acceptance criterion rather than a spread. The distinction from a
ratchet is worth recording because a raw count alone cannot show it:

- **No vector repeated.** Each round found a different class, and none was "the guard does not pin what it
  claims" against the arc's own suite — the ratchet's signature.
- **The deliverable changed shape twice** on the strength of findings (layer 0 for the replacement class;
  the accept-set inverted from comparisons to rendering constructs). Those are design discoveries, not
  guard growth.
- **No recognizer widened per round.** The accept-set gained forms, but by moving to a structural key that
  subsumes them, not by accreting one grammar corner per round.
- **The arc's own derivations corrected reviewer enumerations twice**, in the direction that reduces
  rounds: a replacement branch (`admin-checkpoint-infra-error`) that an enumeration missed, and a mutant
  proven vacuous because all seven live manifest routes share the `/admin` first segment, so a quote-only
  parser and a complete one derive identical roots.

The honest reading: the subject's failure mode was genuinely unknown at draft time — both ledger rows named
two candidate mechanisms and the replay refuted all of them — so rounds 1-4 were the discovery, which is
where the convergence criterion says genuine design gaps live.

### Disposition at the cap, and the fifth round

Round 4 returned NEEDS-ATTENTION with one finding, on AC-2, repaired structurally rather than by a fourth
assertion. The arc reached the cap with a converging rate and a single open axis, not a widening one.

**A fifth round was authorized and spent, scoped to that one criterion.** The reason is a rule this
session applied twice already: a design change made AFTER a verdict does not inherit that verdict, because
the approval attaches to a document that no longer exists. Self-certifying the structural repair would have
been the artifact-moving-under-a-claim shape, and it was the criterion three prior rounds had each failed
to get right — the last thing worth self-certifying.

The round was bounded to §5's structural-provability paragraph and §9's AC-2, declared terminal, and
instructed to approve plainly on nothing admissible. It returned **APPROVE with 0 findings**, confirming
the criterion directly: deleting the live `writeFile` leaves the fresh directory with zero or thirteen
identities, so the fourteen-identity equality fails, and any passing run must populate all expected
identities in a directory that began empty.

**Cost accounting.** One extra round bought the difference between a shipped self-certification and a
verified one, on the arc's most-repaired assertion. That is the round the cap exists to make deliberate
rather than to forbid.

## plan — 6 rounds

**r5's single finding was minted by a post-approval spec edit, which is the round-economy lesson here.**

reviewer stating what it could not re-run is the behavior the probe-settles-claims rule is asking for, and

**Mechanizable:** two arms. One is already filed, one is new — and a third candidate was DISCARDED after
being executed, which is recorded because the discard is the more useful result.

1. **An acceptance criterion no task claims** — filed as `BL-SPECLINT-AC-UNCLAIMED` in the spec section
   above. Raised as BLOCKING by plan r1 against a plan `spec:lint` had passed at 0 hard.

2. **A `red-target=` that resolves to a blank line.** `spec:lint` validates that a marker's `red-target`
   cites a tracked file and a line within range; it does not check that the line has content. This plan
   shipped `scripts/help-screenshots.ts:116` — a blank line between two functions — and linted clean. An
   authored red names the defective production line, and a blank line cannot be one. The check is one
   predicate on a value the linter has already read.

### The third arm was proposed, executed, and DISCARDED

The obvious third arm is "a prose `Task N` reference that resolves to no task heading" — the r2 reorder
left eight in-prose references on the old numbering, including the whole anti-tautology block, which then
described the wrong tasks while reading perfectly.

**Run against the pre-repair revision, that check finds ZERO.** Measured:

```
e3b8d3780^: task headings=[1..9]  dangling Task-N refs=0   blank red-targets=[help-screenshots.ts:116]
HEAD:       task headings=[1..9]  dangling Task-N refs=0   blank red-targets=[]
```

The reorder renumbered the HEADINGS as well, so tasks 1 through 9 existed before and after. Every stale
reference pointed at a task that still exists and now means something else. An existence check cannot see
that; distinguishing it needs to know what each task DOES, which is the semantic judgment a lint does not
have.

So the arm is discarded rather than filed. Recording the discard matters more than the arm would have: a
mechanizable-arm proposal that nobody executes is a claim wider than its evidence, and this one read as
obviously correct right up until it was run. The same execution pass confirmed arm 2 reproduces exactly —
one arm proven, one refuted, from the same ten lines.

**Judgment:** the remainder are design defects no lint reaches. Four shapes:

1. **A contract wrong in BOTH directions at once** (r3, Task 7's evidence parser). A null-heavy record
   satisfied its checks, so the obvious repair is to demand a complete record — but the capture aborts on
   the first refusal, so a legitimate refusal produces a short record BY DESIGN, and that repair would have
   failed every genuine refusal. Only branching on outcome respects both. A finding that names one
   direction invites a repair that installs the other, which rule 297 already records as its own class.

2. **A red that cannot fail for its stated reason** (r2, r3). Task 2's test would have failed on module
   resolution rather than on detector scope; Task 8's red was a command green on BOTH sides of the change,
   because mutation enrolment is opt-in and an absent surface is untouched by the harness. Both look like
   reds and neither discriminates.

3. **The appended repair, twice, in this arc's own plan** (r3). Task 1 introduced completion events in one
   revision and replaced them with fresh-directory artifacts in a later one, and both survived — the
   document contradicted itself inside one body. One line further down, AC-2's statement still named the
   literal count while the task body derived it from the manifest. The generalization worth keeping: **a
   number stated in an acceptance criterion IS an assertion**, however correct it is on the day it is
   written, and the second half of every repair is deleting what it replaces.

4. **A verification step that could not verify, in this arc's own subject matter** (r4). AC-2's local
   byte-equality command ran `pnpm screenshot:help` on the host and diffed the committed WebPs — on Darwin
   arm64, while CI captures in the pinned linux/amd64 image. Occurrence B of this very arc is the proof
   that those two environments rasterize differently, so the plan specified a local check whose failures
   would have meant nothing, against baselines it would also have left dirty. Writing a rule down does not
   stop you applying it everywhere except your own verification block.

**Infra:** one, and it shaped the round. Plan r3 consumed three wrapper attempts: attempts 1 and 2
produced messages with no parseable verdict line, and attempt 3 returned a verdict with no `FINDINGS:`
line. The round is recorded with `findingCount: null` — "not declared", never "none found".

### The freeze window, corrected by this arc and adopted fleet-wide

The rule "never move a document under a live reviewer" was being applied from dispatch to FIRST MESSAGE.
That is wrong, and this arc broke it: on reading attempt 1's findings I committed fixes while attempt 2 was
still running against the live tree. **The freeze runs from dispatch to `result.json`**, because a wrapper
retry is a new attempt reading the current tree, not a continuation of the one that produced the message
you read. Adopted as fleet doctrine by the orchestrator 2026-08-22.

The slip was recoverable only by luck of scope — the edits addressed attempt 1's own findings verbatim and
nothing else — which is the reason to write the rule down rather than to rely on the same luck twice.

**Examined:** rounds 1, 2, 4, 5 and 6 by counted verdicts, across eight dispatches. Round 3 returned

What round 6 did settle is worth more than a decay would have been: the answer to its question was NO. The

or polarity conclusion without passing through the funnel that was supposed to be the sole authority.

**Mechanizable:** most of it, and the pattern is one shape rather than twenty-five. Seventeen of the twenty-five
were a guard or validator that did not hold what it claimed, and TWELVE of those were defects in a repair made
by an EARLIER round of this same review — the fix-the-named-instance failure the class-sweep rule exists to
prevent, committed repeatedly while repairing exactly that class.

The three that generalise beyond this arc:

1. **Clauses cannot be complete; tables can — but a table is only total if something READS the field set.**
   The evidence validator was patched with clauses in rounds 1, 2 and 4a, and rounds 2, 4a and 5a each found
   more cases. Nothing enumerates what a clause misses. Round 5a replaced them with an outcome-by-field
   table and declared it "total by construction" in a comment.

   Round 6a then found three declared fields — `absentSelector`, `geometry`, `geometrySkippedReason` — that
   the table omitted, so malformed values rode through on the outcome that never emits them. The paragraph
   claiming totality was the only thing holding it, and a comment reads nothing. This entry previously
   asserted the round-5a table WAS total; that assertion was wrong, and it is corrected here rather than
   quietly renumbered, because the filing making the same unenforced claim as the code is the more
   interesting half of the finding.

   The repair is not the three rows. It is a test that derives the field set from the `CapturedEntry`
   declaration with ts-morph and compares it two-directionally against the table's keys, so field N+1 fails
   by default. Adding the three rows alone would have left the identical defect wearing a later date. The
   same derived-cover shape was already in use one file over, in the residue registry — which is why the
   sweep for peer sites came back clean.
2. **A negation silently acquires every new case and gets it wrong by default.** "Require faultHits on
   every refusal that is not selector-absent" was wrong for three of the five shapes the capture actually
   emits, and it made the always-run CI verifier REJECT VALID RECORDS. Replaced with an enumerated
   obligation per reason. This was the second "everything except X" rule on this branch to be wrong.
3. **A guard scoped to a FILE cannot protect the SITES in it.** The hand-marking assertion checked that a
   marker appeared anywhere in a declared file; with two declared residues in one file and four marker
   occurrences, deleting one still passed. Per-site now, and each of four sites verified by removing its
   own marker and watching the case fail.

4. **A funnel is only a funnel if every caller goes through it, and only a test can say they do.** Round 5
   replaced multiple marker and polarity paths with single authorities and called the class closed. Round 6b
   found four callers still deciding for themselves: a text regex over subtree source paired with a
   vacuously-true unconditionality check, so a marker in a COMMENT certified a component; only the first
   `return` inspected, so a later unmarked one was invisible; an embedded-local hop that re-implemented
   "root or any marked descendant" and dropped the conditional-ancestry rule in the copy; and a hand
   registry matching the marker's SPELLING, which the omitted-value form `data-render-fault={undefined}`
   satisfies while React renders no attribute at all.

   The live tree could not have caught any of it. No shipped fault branch renders a marking component
   without passing the prop, so the census stays green whether the predicate works or not — the suite's own
   comment says so. Round 5's sabotage tested marker DELETION, which the regex did catch, and never tested
   DEGRADATION, which is the case that mattered. Each repair now fails on its own mutant, verified by
   applying six of them.

   One correction to the finding as filed: it prescribed `attributeAlwaysPresent` for the hand registry, and
   that fails correct code — `TelemetryOverviewStrip.tsx:252` is `{isInfra ? "telemetry-events" : undefined}`,
   conditional by design, because a hand-marked site must not mark a healthy render. The probe's real content
   is narrower, that a marker which can NEVER render passed, so the repair adds `attributeCanRender` beside
   the existing predicate and pins the two apart. Taking the prescription instead of the defect would have
   traded a false negative for a false positive on a live component.

declined: all four are already ENCODED in this arc's own repairs rather than pending work — the total
outcome-by-field table, the enumerated obligation-per-reason, and the per-site marking assertion each ship in
this branch and each is pinned by a test that fails on the mutant it was written for. Generalising them into
lints that police OTHER surfaces would be process-facing ledger rows, and the process-facing mint bar wants a
measured incident on the surface a guard would defend, not an extrapolation from this one. The incidents here
bought the repairs here.

**Judgment:** three, and they are genuinely judgment rather than mechanism. Whether the invariant-8 gate
