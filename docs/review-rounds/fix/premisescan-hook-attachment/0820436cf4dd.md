**Judgment:** three of five rounds were spent on ONE question a static scanner cannot answer — does
this function ever get invoked — and each repair answered it a different wrong way before the design
settled on declining to answer it at all. Every suppression is a trade: accept one failure direction
to avoid another. Wrong attribution is noisy and PERMITTED by the bound; false certification is
silent and FORBIDDEN. Intuition prefers quiet output, so the unsound direction is the one that feels
like an improvement, and it was chosen twice.

Two structural causes, both chargeable, neither mechanizable:

1. **A sweep that spares a site must justify everything that site DOES, not the aspect that raised
   the question.** At r3 the suppression in producer B was deleted and the twin in producer A was
   spared, because the exemption was checked against the `.each` datum case that raised it. The
   exemption was scoped to a CASE while the code was scoped to a CONSTRUCT. r4 cost one full round.
2. **A suppression's comment is a checkable claim.** The r3 flag carried "an unfollowable
   registration that DOES invoke the enclosing function is itself reported" — false, since nothing
   syntactic connects a body to a call site. An unexplained suppression invites scrutiny; one with a
   confident false rationale deflects it, which is why it survived two rounds.

### The measurement that agreed with itself

Round 6's finding is the arc's sharpest and it is not about the deliverable. A line-keyed ledger row
had been re-keyed sixteen times, and every key restated a supporting fact — that
`premiseIsAssociated` has two callers — derived each time from the same `grep -c` over the name,
which counts the function DECLARATION alongside the single call site. It has ONE caller. The premise
survives (what it needs is that the caller set did not CHANGE), but the diligence did not: sixteen
re-validations through one instrument agreed with themselves every time, because a stable wrong
number never contradicts anything. **Re-running a measurement is not re-deriving it. Only a different
route can disagree with you.**

### Review and mutation answer different questions

Five adversarial rounds did not find the slot-0 defect and the closeout mutation audit did — a clause
whose deletion broke none of 374 tests. Review asks whether the code says what it should, reading
intent, structure and argument, and a plausible clause with a plausible justification passes. Mutation
asks whether any of it is LOAD-BEARING and cannot be fooled by a rationale. Neither substitutes: the
converse is already on record, that a perfect score with an empty survivor set can coexist with a
live defect class. Stated with this arc's numbers: after round 1, review found nothing in the
deliverable's behaviour that the deliverable's own tests could not have caught — every later finding
was against a repair, a comment, a doc or a guard — while the audit found a real inconsistency at the
end.
