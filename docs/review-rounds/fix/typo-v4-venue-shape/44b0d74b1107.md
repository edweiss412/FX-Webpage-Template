## plan — 4 rounds

**Examined:** the four plan dispatches at this base (`44b0d74b1107.jsonl`, `--stage plan`), their briefs, and the repair commit each produced. Findings by round: 6, 4, 3, 2. All four were BLOCKING. Every finding was admitted; none was refuted. The count declines monotonically, and the §0 measurements reproduced under review three rounds running — so the residual risk moved out of the plan's factual claims and into its task mechanics, which is where the findings actually landed.

**The distribution inverted from the spec stage, and that is the useful comparison.** The spec's eight findings were seven parts operator copy and one part everything else. The plan's were almost entirely about **whether a stated red is a real red** — five of the first ten, across both BLOCKING verdicts:

| round | finding | why it was not a red |
| --- | --- | --- |
| 1 | Task 2 had no valid RED | its command went green by editing test expectations, not by an implementation |
| 2 | the anchor task's premise WAS the behaviour under test | on the RED the premise is false, so the case stops at "premise not met" before its real assertion |
| 2 | the `.each` list was inline, its guard in a separate test | the guard bound to a duplicate, so it could pass over zero executed cases |
| 1 | mutant (b) was tautological | expected and actual both derive from the catalog object under mutation, so the suffix moves both |
| 1 | Task 3's RED could not collect | two missing imports turn a behavioural red into a collection failure wearing the same exit code |
| 3 | the anchor task had no coherent fixture | a two-row workbook described against a two-anchor/`A3` expectation; two rows give one anchor at `A2` |
| 4 | the AC-V7 case hardcoded `"venue"` instead of joining on the warning's kind | the detector could regress to the venue-only arm and the case would stay green while the operator's link vanished |
| 4 | the false-early guard tested ordering, not exactness | the exact regex and a prefix mutant both select row 0 in that fixture, so it would survive the recognizer being broadened |

Each is the same underlying error in a different costume: **a check that fails, or passes, for a reason other than the one it claims.** `spec:lint --exec-red` catches exactly one shape of that (a `red-state=live` command already exiting 0 — it did catch mine, and I fixed it before dispatch). It cannot see a premise that restates the goal, a guard bound to a duplicate list, or a mutant whose two operands move together, because all three are green-and-well-formed to a static reader.

**Mechanizable:**

- declined: the "premise restates the behaviour under test" shape is checkable in principle — a premise whose expression reads the same module the assertion does is suspect — but only heuristically, and a heuristic here fails in the expensive direction: it would flag legitimate premises that read a neighbouring surface, and an author who silences it once silences it always. It files to `docs/agents/writing-plans.md` under the anti-tautology rule as a named shape with this arc's worked example, not as a lint arm. Process-mint freeze applies: the done condition would be a property of the checker.
- declined: the "guard bound to a duplicate rather than to the `.each` binding" shape is real and recurring, and the existing rule already names it ("a premise that validates something ADJACENT to the case is not a premise"). The rule was written down and not applied. Adding a second rule does not repair a first rule that went unapplied — that is the measured lesson of the 2026-08-04 corpus, and it is why the accept-set discipline was made a dispatch gate rather than a 123rd bullet.
- The one thing worth mechanizing is already mechanized and did its job: `--exec-red` caught a `red-state=live` that was already green, at plan time, before a reviewer spent a round on it.

**Judgment:** two findings could not have been mechanized at any price. The post-archive repair path was internally impossible — it prescribed re-doing a marker removal that no longer exists, against archives that categorically reject in-progress entries — and seeing that required holding invariant 12, the archive semantics and the repair flow in mind together. The AC-V9-not-at-the-shipping-head finding required noticing that a criterion's wording and a task's position disagreed by one commit, on a measurement that would not in fact have changed. Both are what a reviewer is for.

**Infra:** none. No dispatch reaped, no `no_verdict`, no wrapper fault across four plan rounds.

**Two of the fifteen findings were damage the arc did to itself with scripted edits**, and they are worth separating from the rest because their cause is different. The r1 fold left ten cross-references pointing at the pre-fold world; the r2 task swap cut at line boundaries that fell inside a fenced block, so the archive template's fence swallowed the whole of Task 5 and a fence-state probe read `heading fence=true` for it. Neither is a reasoning error — both are the cost of moving blocks by script and not re-reading the seam. The repair was to rebuild by hand and to check fence balance programmatically rather than by eye. A structural edit is not finished when the blocks are in the right order; it is finished when every delimiter and every reference to what moved has been re-checked.

**The procedural lesson, and it is not the same one the spec stage taught.** The spec's lesson was an ordering rule about evidence (probe first, write second). The plan's is about **self-consistency after restructuring**: the r1 fold moved a task and left ten cross-references pointing at the world before the move, four of which I found by re-reading and six of which the reviewer found. A structural edit to a plan is not finished when the edit is correct; it is finished when every reference to what moved has been re-read. The writing-plans corpus already calls this the most common round-2 finding, and it was, twice.
