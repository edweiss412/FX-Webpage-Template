## spec — 4 rounds

**Examined:** R1-R4, 11 declared findings (3, 4, 1-with-5-instances, 3).

The design was ratified before round 1 and no round contested it. Every finding in this stage was about the spec's account of how the design would be PROVEN, and every one sorts into two classes.

**Mechanizable:**

- **An oracle that cannot discriminate the property it names** (R1.1; R2.1; R2.3; R3 instances 1 and 5; R4.1; R4.3), already named by 3 arcs. This arc extends its shape from a written fixture to a SPECIFIED oracle, which is the same mistake one stage earlier. Seven instances, six spellings: a control set that included the panel's own rows, so "intersects an interactive control" was positive by construction while "elementFromPoint returns the panel" was negative by construction, and the real defect (interception by a ROW) was invisible to both; a repair that then refused to run unless the panel was open, which is the exact inverse of the sibling probe's claim; viewport cells at 375 and 1280 that `(max-width: 400px)` satisfies as well as the specified query; a hydration claim assigned to a client-only `render` that emits no server markup; three named wizard assertions that discriminate none of the five ways the predicate can be built wrong; and a 44px band measured rather than hit-tested, which a `pointer-events: none` pseudo-element satisfies while taking no taps. The repair each time was the same question, asked earlier: what would a WRONG implementation do, and can this oracle see it?

- **A load-bearing claim with no assertion anywhere** (R2.4; R3 instances 2, 3, 4; R4.2), a class this corpus has not named before. Distinct from the class above, where an assertion exists and is too weak: here the document states a property, calls it load-bearing, and the test plan does not mention it at all. Cancelled-frame non-consumption, the operator-opened resize in both directions, the whole post-repair wizard branch, and the panel's vertical anchor each arrived this way. The last is the one worth remembering: the spec said in as many words that the probe must not "fix" the occlusion by re-anchoring to the pill, the source records that exact attempt and its measured result, and nothing asserted it, so the arc's own defect was reachable by a second route through a green suite. Not mechanizable as stated, and deliberately not attempted: deciding which sentences of a spec are load-bearing claims is an open grammar, and this repo's measured lesson is that a recognizer over prose grows one corner per round. The repair that held is structural instead — §9.3, a table mapping every claim to the assertion that settles it, so the next gap is a visibly missing row rather than a paid round.

declined: LIM-NONDISCRIMINATING-FIXTURE for the first class and LIM-CLAIM-WITHOUT-ORACLE for the second, both parked rather than filed. The first slug already exists and this arc cites it rather than coining a twin; its shape extends from a written fixture to a specified oracle, which is the same mistake one stage earlier. The second is coined here. Neither becomes a ledger row: both are process-facing, the 2026-08-25 mint freeze admits a process row only under `invariant` or `product-blocked`, and neither applies — no product arc was blocked, and no plan-wide invariant is defended. The repair that actually held for both is structural and already shipped in this spec (§9.3), not a detector; a detector over "which sentences are load-bearing claims" ranges over an open grammar, which is the shape this repo has measured growing one corner per round.

**Judgment:** R1.3, whether a peer sharing the code shape but not the bug shape owes a ledger row (it does not; class-sweep's exception (a) explains a deferred instance rather than inventing one). R2.2, how many viewport cells settle a negative probe (three, matching the sibling row's declared domain).

**Infra:** none. Four dispatches, four verdicts, no reap, no `no_verdict`.

**What would have cut this stage in half, and it is an ordering rather than a rule.** §9.3 was the repair for round 2, and it retroactively explains rounds 1, 3 and 4 as well: every finding here is a row that could not discriminate or a row that was missing. Writing that table BEFORE specifying any probe would have surfaced R3's instances 2-4 and R4's finding 2 at draft time, and it forces the "what would a wrong implementation do" question that kills the other class. Nothing new had to be invented to know this; the table just had to come first.

**Standing observation about this stage's shape, recorded for the orchestrator rather than actioned here.** Eleven findings, zero on the design, all on the test plan. The obligations table is plan-grade content living in a spec, so it drew plan-grade review under the spec stage's round budget. Moving it to the plan document is a re-scope decision and belongs to the orchestrator, not to a review brief or to this filing.

## plan — 4 rounds

**Examined:** R1-R4, 18 declared findings (3, 5, 6, 4). One `no_verdict` on the round-2
dispatch (usage limit, not a reap), re-dispatched at the same round number.

Every finding in this stage was about EXECUTION rather than design, which is the split the
spec stage's filing predicted when the obligations table moved here. Three classes.

**Mechanizable:**

- **Red validity, five findings across three consecutive rounds (R1.F1; R2.F1, R2.F2;
  R3.F1, R3.F6), and the guard for it already existed in this repo.** Five spellings of one
  question, "can this command actually be observed failing, for the reason claimed": a task
  that changed production before the test that proved it; three tasks that ENDED red and
  relied on a later task to green them; two tasks claiming ids their marked vehicle could
  not exercise; a compound red joined by `&&`, where the first command's expected failure
  short-circuits the second so the browser vehicle never ran at all; and a red that depended
  on WINNING a race, filtered by `-g` into the isolation under which the defect had never
  reproduced.

  **The measured cost is an adoption gap, not a missing mechanism, and that is the part
  worth recording.** `lib/specLint/redContract.ts:259` already reports `RED_CONJUNCTION` on
  exactly the `&&` shape that cost round 3, and `docs/agents/writing-plans.md` rejects it in
  prose. Neither reached me, for two independent reasons that compound:

  1. **The arm is region-gated.** `redContract.ts:256-257` looks up a `contractExtents`
     entry and `continue`s when there is none, so a plan whose tasks region is opened
     `<!-- tasks: depth=3 -->` rather than `<!-- tasks: depth=3 red-contract -->` gets
     silence. Opting in is one word, and nothing asks for it.
  2. **Inside the region it is ADVISORY, and this plan carried 22 advisories at dispatch.**
     My own dispatch note told the reviewer the advisory list is a density heuristic firing
     on section numbers and viewport dimensions. An advisory that lands in a list its author
     has been told to discount is not a signal, whatever its text says.

  So the repair that held was opting in — every marker now carries `red-state`, `why=` and
  `red-target=`, statically checked — and the class closed the moment it did. Three rounds
  were paid for a flag.

- **Section-2-against-section-4 closure, one finding in every single round (R1.F2, R2.F4,
  R3.F5).** Rows without an acceptance id, then ids without rows. Each repair extended a
  LIST of exceptions, and each list went stale on the next addition: round 3's finding was
  that my "the exception is these two ids" sentence was wrong by three, on a document I had
  just swept. The list form cannot converge, because the artifact it describes keeps
  growing. What held was a rule with LOCAL declarations — every id names its own non-spec
  source in its own bullet — plus a mechanical reconciliation run at authoring time rather
  than described, which reports 25 and 25 with an empty difference both ways.

- **A red that a wrong implementation still passes (R3.F6, R4.F1, R4.F2), the class that outlived the structural defense.** Opting into `red-contract` closed the SHAPE questions and the very next round found three findings the arm cannot see, all in the same task. Its red depended on winning a race; the replacement depended on an unresolved import, which `docs/agents/writing-plans.md:15` rejects because writing the test helper makes it green; and the deterministic contract that replaced THAT lagged only the viewport, so an implementation returning before the `ResizeObserver` fit settled passed every assertion in the task. Three attempts, three ways of not pinning the thing.

  The root cause is worth recording plainly: **that task is a TEST-ONLY repair, so a production-defect red does not exist for it.** Invariant 1's cycle assumes a production surface to be defective, and there is none — the defect IS the suite. Two of the three attempts were manufacturing a red where the invariant does not reach, and the third was the honest answer: the structural cover, which is red on the current tree for a text-scan reason and cannot pass on a schedule, carries the marker, and the other two assertions are labelled REGRESSION.

- **Enumeration claimed over an incomplete population (R2.F3, R3.F3, R3.F4, R4.F4).** A blast-radius
  table that said "enumerated rather than sampled" while missing a suite THIS ARC had added
  two commits earlier, and a CI gate (`standalone-baseline.json`) that no task mentioned at
  all. The second was live rather than hypothetical: the temporary P-1 probe has been
  registered in `standalone.config.ts` but absent from the baseline since `787acdef3`, so
  that gate is red on this branch today, and no review round found it until the third. Round
  4 added the fourth instance: the plan said `standalone.config.ts` boots a server, and it
  has no `webServer` at all — each member boots its own, which is real work two new specs
  owed and the plan never named.

declined: LIM-ADVISORY-UNDISPOSITIONED covers part of the first class and is cited rather
than twinned. The adoption-gap half is coined here as LIM-OPTIN-GUARD-DORMANT. Neither
becomes a ledger row: both are process-facing, the 2026-08-25 mint freeze admits a process
row only under `invariant` or `product-blocked`, and neither applies — no product arc was
blocked, and the plan-wide invariant the red contract serves (invariant 1) is defended by
the arm that already exists, once opted into.

**Judgment:** whether a test-only repair can carry an invariant-1 red at all (it cannot; the
honest form is a live structural red plus regression assertions). Whether the wizard-occlusion obligation deserves a manufactured acceptance id
or a stated no-AC disposition (disposition — a measurement already taken cannot be given a
red). Whether the wizard's Escape ownership is one obligation or a mechanism (an obligation,
asserted on the Escape target rather than the prop).

**Infra:** one `no_verdict` on plan R2, a usage limit rather than a reap, confirmed by the
verbatim error and by the reaper log showing live trees and no orphans. Re-dispatched at the
same round number once credits were restored; it counts toward no cap.

**What would have cut this stage in half, and like the spec stage's lesson it is an
ordering.** Opening the tasks region as `red-contract` at draft time. The spec stage
concluded that its obligations table should have come first; this stage's equivalent is that
the mechanical red arm should have been switched on first. Both are the same shape: the
artifact that catches the class already existed, and writing it earlier costs nothing.

**And one thing that would NOT have helped, recorded so it is not tried.** The structural
defense landed in round 3 and round 4 still returned four findings, two of them on red
validity. The arm checks that a marker DECLARES the right fields and parses; it cannot check
whether the declared failure is the one that will occur, which is `LIM-AUTHORED-RED`'s parked
territory and is measured-and-refuted there. So "mechanize it harder" is not this stage's
lesson. The lesson is narrower and about scope: an in-arc repair of a TEST defect was folded
into a product arc mid-stream, and it accounts for R2.F3, R3.F3, R3.F6, R4.F1 and R4.F2 —
five of eighteen findings, and every finding in the final round but one. Folding it in was a
reasonable call on locality; what it cost was a task the plan's own red contract does not fit,
argued three times.

**Disposition, 2026-08-29:** bl-orch ruled the split. The repair moved to `fix/popover-clip-fit-stale-viewport` with its full diagnosis, and this arc's plan lost the task and its three acceptance ids. What did NOT move is the P-1 probe deletion: that probe asserts an arrival state this arc's own suppression makes false, so it must die on the product branch or the branch breaks its own `standalone-e2e` gate. The split is `AGENTS.md`'s documented repair direction under same-axis recurrence, taken on the fifth round rather than after a sixth.
