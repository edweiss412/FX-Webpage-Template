## spec — 4 rounds

**Examined:** R1-R4, 11 declared findings (3, 4, 1-with-5-instances, 3).

The design was ratified before round 1 and no round contested it. Every finding in this stage was about the spec's account of how the design would be PROVEN, and every one sorts into two classes.

**Mechanizable:**

- **An oracle that cannot discriminate the property it names** (R1.1; R2.1; R2.3; R3 instances 1 and 5; R4.1; R4.3), already named by 3 arcs. This arc extends its shape from a written fixture to a SPECIFIED oracle, which is the same mistake one stage earlier. Seven instances, six spellings: a control set that included the panel's own rows, so "intersects an interactive control" was positive by construction while "elementFromPoint returns the panel" was negative by construction, and the real defect (interception by a ROW) was invisible to both; a repair that then refused to run unless the panel was open, which is the exact inverse of the sibling probe's claim; viewport cells at 375 and 1280 that `(max-width: 400px)` satisfies as well as the specified query; a hydration claim assigned to a client-only `render` that emits no server markup; three named wizard assertions that discriminate none of the five ways the predicate can be built wrong; and a 44px band measured rather than hit-tested, which a `pointer-events: none` pseudo-element satisfies while taking no taps. The repair each time was the same question, asked earlier: what would a WRONG implementation do, and can this oracle see it?

- **A load-bearing claim with no assertion anywhere** (R2.4; R3 instances 2, 3, 4; R4.2), a class this corpus has not named before. Distinct from the class above, where an assertion exists and is too weak: here the document states a property, calls it load-bearing, and the test plan does not mention it at all. Cancelled-frame non-consumption, the operator-opened resize in both directions, the whole post-repair wizard branch, and the panel's vertical anchor each arrived this way. The last is the one worth remembering: the spec said in as many words that the probe must not "fix" the occlusion by re-anchoring to the pill, the source records that exact attempt and its measured result, and nothing asserted it, so the arc's own defect was reachable by a second route through a green suite. Not mechanizable as stated, and deliberately not attempted: deciding which sentences of a spec are load-bearing claims is an open grammar, and this repo's measured lesson is that a recognizer over prose grows one corner per round. The repair that held is structural instead — §9.3, a table mapping every claim to the assertion that settles it, so the next gap is a visibly missing row rather than a paid round.

declined: LIM-NONDISCRIMINATING-FIXTURE for the first class and LIM-CLAIM-WITHOUT-ORACLE for the second, both parked rather than filed. The first slug already exists and this arc cites it rather than coining a twin; its shape extends from a written fixture to a specified oracle, which is the same mistake one stage earlier. The second is coined here. Neither becomes a ledger row: both are process-facing, the 2026-08-25 mint freeze admits a process row only under `invariant` or `product-blocked`, and neither applies — no product arc was blocked, and no plan-wide invariant is defended. The repair that actually held for both is structural and already shipped in this spec (§9.3), not a detector; a detector over "which sentences are load-bearing claims" ranges over an open grammar, which is the shape this repo has measured growing one corner per round.

**Judgment:** R1.3, whether a peer sharing the code shape but not the bug shape owes a ledger row (it does not; class-sweep's exception (a) explains a deferred instance rather than inventing one). R2.2, how many viewport cells settle a negative probe (three, matching the sibling row's declared domain).

**Infra:** none. Four dispatches, four verdicts, no reap, no `no_verdict`.

**What would have cut this stage in half, and it is an ordering rather than a rule.** §9.3 was the repair for round 2, and it retroactively explains rounds 1, 3 and 4 as well: every finding here is a row that could not discriminate or a row that was missing. Writing that table BEFORE specifying any probe would have surfaced R3's instances 2-4 and R4's finding 2 at draft time, and it forces the "what would a wrong implementation do" question that kills the other class. Nothing new had to be invented to know this; the table just had to come first.

**Standing observation about this stage's shape, recorded for the orchestrator rather than actioned here.** Eleven findings, zero on the design, all on the test plan. The obligations table is plan-grade content living in a spec, so it drew plan-grade review under the spec stage's round budget. Moving it to the plan document is a re-scope decision and belongs to the orchestrator, not to a review brief or to this filing.
