**R13 — the accept-set had no stopping condition.** BLOCKING/2.

F1 is the sharpest finding of the late rounds. "An export is an entry point iff it transitively reaches any derived writer" is recursive: `unarchiveShow` reaches a writer, so it becomes an entry point, so its caller at `unarchive.ts:34` owes a sink, and so on up the call graph without termination. And no disposition there is truthful — the show is known, the attempt is real, and once the sink is wired into `unarchiveShow` itself the attempt IS emitted. The guard was unsatisfiable against a correct production call.

The repair keys the accept-set on the **sink parameter**: an export is an entry point iff its own signature accepts a deps object carrying `logSync`. That terminates by construction and is decidable from the callee alone. `unarchiveShow` is then correctly a caller, not an entry point, and its callers inherit nothing.

Worth noting what this says about the arc's favourite move. Six rounds of replacing hand-lists with derivations were right, and this is the counter-case: a derivation can be *too* general, and "transitively reaches" was general enough to swallow the whole call graph. Deriving is not automatically safer than enumerating; the derivation has to be over the right relation. Signature-acceptance is the right one because it names the property the rule cares about — can this call install a sink? — rather than a property that merely correlates with it.

F2 forced the marker vocabulary to be honest: `run-level-sync-log` had acquired two incompatible meanings. R1 found the manual first-seen path never captured an attempt start, so its applied rows persisted `duration_ms = NULL`; R4 found the pending-ingestion retry path had the identical gap. Both bypass `processOneFile`, which is where the cron path captures its start — so "install a sink" and "own an attempt boundary" are separate obligations, and I had conflated them. The second instance is the one that stings: R1's finding should have triggered a sweep for every path that bypasses `processOneFile`, and it did not.

**Infra:** None. All four dispatches returned a verdict on the first attempt.

### The analyzer, and what finally stopped it

`analyseDestructiveFile` drew a finding in every single round: a commented-out guard, a reassigned binding, a second unguarded client (R1); a parameter shadow, array and object destructuring rebinds (R2); cross-function, cross-block, and parameter-collision scope confusion (R3); `&&=`, `for…of`, `for…in`, and switch-case declarations (R4). Four rewrites — regex, then AST name-matching, then AST lexical scope resolution — each closing the named escapes and each inviting the next. That is precisely the ratchet this repo's round-economy rule warns about, and I was three rounds into it before naming it.

What stopped it was giving up on describing what is forbidden. The rule now states what must be true:

> every declaration of the connected name in the file is a `const` initialized directly from a trusted guard call.

`const` is the whole mechanism, not a style preference: the language guarantees such a binding is never reassigned — by `=`, `&&=`, destructuring, a loop head, or any syntax not yet invented — so there is no rebinding check left to leak. Requiring it of *every* same-named declaration dissolves the scope question too, because it no longer matters which declaration a use resolves to. The analyzer got smaller at the round where it stopped growing.

It is deliberately conservative: a file reusing the name for something unguarded is rejected even when the connected binding is fine. That false positive is loud, local, and fixed by renaming a variable — the right direction for a guard whose failure mode is silently pruning a shared project.

**R5 found one more, and it confirmed the lesson rather than denting it.** A local function named `postgres`, wrapping a differently-imported driver, discarding its validated argument. The escape was on the OTHER participant: I had resolved the guard by import and still trusted the driver by spelling. The repair was not a new kind of check, it was applying the same provenance rule symmetrically — the driver is now an import-resolved identifier too. One rule, both sides, and the analyzer did not grow a new mechanism.

**R6 was the same again, one level out:** `const connect = postgres; connect(remote)`. The alias was never inspected, so "every connection is checked" was false while a safe first connection satisfied the count. The repair took the same exit a third time — the driver name may now appear ONLY in call position, so no alias can exist. That covers passing it as a callback and reaching through a property too, without naming either.

Three rounds, three escapes, one move each time: replace a recognizer with a condition that makes the escape unrepresentable. `const` for rebinding, import-resolution for provenance, call-position-only for aliasing. Each shrank the analyzer.

**The lesson worth carrying:** when a guard draws the same class of finding in three consecutive rounds, the next move is not a better recognizer. It is to find an invariant something else already enforces — the type system, the language, an existing meta-test — and assert that instead.
