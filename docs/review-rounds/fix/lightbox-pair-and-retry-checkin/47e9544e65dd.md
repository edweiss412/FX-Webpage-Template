## spec — 4 rounds

**Examined:** R1-R4, 17 findings (5, 4, 5, 3), every round BLOCKING. The rate did not decay, and
the last round refuted the structural repair written for the vector that produced most of it.

**Stage outcome: CAPPED-NARROWED.** No APPROVE. The orchestrator ruled on 2026-08-31, after the cap,
that the spec NARROWS rather than runs a fifth round: the reader inventory is deleted entirely,
because an inventory over an open set IS the refutable surface, and it is replaced by a consequence
bound (any out-of-render reader may observe a stale snapshot; the mechanism must make that
harmless). The mechanism became two named candidates rather than one ratified in prose, decided by a
deciding suite, on the ground that prose had been wrong about it twice. **Standing fence for every
later brief on this arc: a reader-census finding files to `LIM-OUT-OF-RENDER-SNAPSHOT-READ`, never
to a round. The bound is the contract.**

**Mechanizable:**

- **Out-of-render snapshot reads of React state.** R1 finding 3, R3 findings 1 and 2, R4 findings 1
  and 3. Five of seventeen, in three of four rounds, and it is the axis the stage ended on. Code
  scheduled during render (a `setTimeout` callback, a passive effect, a subscriber registered once)
  reads the state of the render that scheduled it, so any rule this spec evaluates during render
  cannot govern it. Two repairs were written and both were refuted:

  1. An intersection making stale writes "inert by construction" (R1-R2). True of rendering, false
     of everything else; R3 showed a queued callback outliving the reconciler and poisoning the next
     retry, and an announcement effect holding a pre-`onLoad` snapshot.
  2. A ref mirroring `retrying`, synced in a passive effect, consulted by every out-of-render reader
     (R3 repair). R4 refuted it on ordering: React flushes pending passive effects before the next
     render, so the announcement effect and the ref-sync effect are both pending from the same
     commit and the ref has not learned about a removal that has been queued but not rendered. A ref
     helps only if it already knows, and this one does not.

  The inventory is what the narrowing deleted. R4 showed it fails open: it named five readers and
  missed the Embla subscriber (`GalleryLightbox.tsx:559`, cited in the very next paragraph as the pattern), both
  components' `<Image>` `onLoad`/`onError` (`Gallery.tsx:749`, `GalleryLightbox.tsx:1319`), and the
  Restart handler. AC-17 was scoped to "readers named in §3.2a", so the omissions were invisible to
  the criterion written to catch them.

declined: LIM-OUT-OF-RENDER-SNAPSHOT-READ, a new slug for this shape. A lint would have to decide,
for every function reachable from an effect, a timer or a subscriber, whether a value it reads is a
render snapshot and whether acting on a stale one is observable. That is dataflow over an open input
space, and the process mint freeze admits a process row only under `invariant`, `product-blocked` or
`recurrence`: none applies, since this blocked no product arc and both hits are inside this one arc,
which the recurrence exception excludes by name. The freeze's admission test also asks for a done
condition that is a number outside the process, and this has none. What the corpus should carry
instead is the shape of the two refutations, because both were plausible and both were wrong in the
same way: a mechanism that learns about a removal on the same schedule as the reader it is meant to
protect protects nothing. The candidate the rounds did not test is the writer-side twin, where every
`setRetrying` call site updates the mirror synchronously rather than an effect mirroring the state
afterwards; that set is CLOSED and greppable, unlike the reader set. No round proposed it, and the
orchestrator ADOPTED it after the cap as the PRIMARY candidate, to be pinned by a structural walker
over the writer call sites and judged by planted-race tests, with fire-time re-read as the fallback.
State the writer set, never the consultation schedule. Re-file trigger: a second independent arc measuring this class as its
non-decaying one.

- **A spec citing a mechanism or symbol that does not exist.** R1 findings 4 and 5, R3 finding 5.
  A connectedness guard credited to shipped code that ships on neither success path; a claim that the
  timing scanner cannot parse a numeric separator when `tests/docs/interactionTimingScan.test.ts:69`
  asserts it can; `nameOf` claimed as a shared helper when it exists only in `Gallery.tsx:401`, with
  zero occurrences in the lightbox. R4 added a softer instance: the ref citation overstated
  equivalence, since the shipped `retryingStateRef` mirrors raw `retrying` while the proposed one
  mirrored `sweptRetrying`.
declined: LIM-CITATION-WELLFORMED-BUT-WRONG, the existing slug, which covers this shape exactly. Its
stated mitigation is the one that would have worked here: verify from the CODE side, open the cited
line and ask whether the sentence is true of it, rather than reading the sentence and looking for
confirmation. This arc's instances decayed after R3, so this is a naming rather than a trigger fire,
and it mints nothing.

- **Normative text contradicting a rule stated in the same document.** R3 findings 3 and 4, R4
  finding 2. An invariant written as a universal over every write, which would have obliged two
  shipped handlers to remove from a set that cannot contain the id; a state table reading `checkedIn`
  raw two paragraphs above the rule saying it is read only through its intersection; and, in R4, two
  paragraphs of §3.2a giving the timer callback mutually exclusive instructions, because the round-3
  repair added the new rule without deleting the sentence it replaced.
declined: LIM-INDEX-RESTATEMENT-DRIFT, the existing slug, at document scale rather than index scale.
That entry's own finding applies here: the class lives in the derivation step rather than in a
location, so sweeping the sites a round names does not close it. R4's instance is the sharpest
evidence in this arc, because it was created BY a repair rather than surviving one.

**Judgment:** R1 finding 1 and R2 findings 1 and 4 were design work and are why the rounds were
worth their cost. R1F1 killed a Restart that bounced through `failed` and exposed a control saying
the diagram could not be loaded while the request was pending, with focus moved onto it. R2F1 caught
that the repair for R1F1 added to `restarting` without leaving `retrying`, so the replacement request
would have carried no deadline: the defect this arc exists to close, reintroduced by its own fix.
R2F4 was a criterion rather than a design, and AC-10 was restated as three observable facts.

**Infra:** none. Four dispatches, four verdicts, no reaped runs and no `no_verdict`.

**What the rounds bought, and the transferable part.** Criteria grew 13 to 20, and six of the seven
added exist because a real finding was invisible to the criteria as written. Two were invisible to a
criterion that COUNTS rather than observes: AC-1 counts live timers and cannot see a window being
restarted, and nothing could see a stale `checkedIn` write until AC-16 asserted it on the NEXT retry,
which is the only place it surfaces. That generalises past React: **a criterion that counts instances
of the right thing passes on an implementation doing the wrong thing at the right cardinality.**

## plan — 4 rounds

**Examined:** R1-R4, 26 findings (8, 5, 9, 4), every round BLOCKING. Like the spec stage, this one
reached the cap without an APPROVE and stopped there by the orchestrator's standing terms.

**Stage outcome: CAPPED.** The mechanism changed mid-stage, at round 2, and that is the single fact
that explains the shape of the rest.

**Mechanizable:**

- **A derivation with a hole, presented as a derived cover.** R3 finding 1 and R4 finding 1, and the
  second is the sharper because of what preceded it. R3 caught that the plan claimed the availability
  sweeps were unedited when a Map cannot pass through them. The repair ran three greps
  (`retryingStateRef`, `sweepSet(|= sweep(`, `of retrying|retrying.has|...retrying`), published the
  five sites they found as a table, and called it derived rather than listed. R4 then found the
  greps had never included `new Set(`. The live count is SEVENTEEN such sites across the two
  components, and every one that writes the phase map returns a `Set` into Map-valued state.

  declined: LIM-HAND-LISTED-POPULATION-SET, the existing slug. The failure here is not that a list
  was used; it is that a list was *called* a derivation and therefore stopped being questioned. Three
  greps chosen by the author cover exactly what the author already suspected, which is an enumeration
  wearing a derivation's clothes. The repair that would have worked is mechanical and cheap: derive
  the population from the TYPE rather than from grep patterns, by making the change and letting
  `tsc` enumerate the breakages. A type error list is a real cover; a grep list is a guess with a
  command attached. Re-file trigger: a second arc publishing a grep-derived site table that a
  compiler could have produced.

- **An oracle that cannot observe its own subject.** R2 finding 3, R3 findings 5 and 6, R4 findings
  2 and 3. Five findings, three rounds, one shape: a test whose instrument is incapable of seeing the
  thing asserted. A `MutationObserver` reading live node references rather than per-commit values; a
  focus check sampling before and after, which passes when one commit moves focus and the next
  restores it; a writer pin accepting any functional update when the guard is the whole point; a
  `&&` chain whose second command never runs because the first is expected to fail; and an unmount
  case resting on React throwing, when React silently ignores post-unmount state updates (the
  reviewer probed this against the installed stack rather than asserting it).

  declined: LIM-NONDISCRIMINATING-FIXTURE, the existing slug, whose arc count this raises. What this
  arc adds to the shape is that four of the five were introduced BY REPAIRS to earlier findings, not
  by the original draft. Each repair replaced a weak oracle with a different weak oracle, because the
  question asked was "what could observe this?" and never "what can this instrument physically
  record?" The mitigation is one question at authoring time, before the oracle is chosen: name the
  observable the instrument actually captures, then check the assertion is a property of THAT.

**Judgment:** R2 finding 2 is the round that mattered and it was correct. It refuted the chosen
mechanism on implementability rather than taste: the writer-side twin required every `setRetrying`
call site to pair with a synchronous mirror write, and both components call `setRetrying` in the
RENDER body where `react-hooks/refs` forbids one, a rule this repo states in its own registry. The
switch to a single per-item phase map came from that finding and is a smaller design than either
candidate the spec named, because it DELETES the disjointness invariant, the intersection rule and
two sets rather than defending them.

**Infra:** none. Four dispatches, four verdicts, no reaped runs and no `no_verdict`.

**What this stage cost, and the one transferable thing.** Rounds 1 and 2 were the plan being wrong.
Round 3 was largely the plan being STALE: the mechanism had changed and the task list was patched
rather than rewritten, so four of its nine findings were residue of a design that no longer shipped.
The comprehensive rewrite landed before the cap rather than after it, which is the same-vector rule
working, and round 4's count fell to four. But it did not reach zero, and the reason is the first
class above: the rewrite's central claim to completeness was a grep table, and a grep table is only
ever as complete as the patterns someone thought to type.

**The generalisable rule, stated because this arc paid for it twice:** when a change is a TYPE
change, the compiler is the cover. Any site list a `tsc` run could have produced should be produced
that way, and a plan that publishes a hand-chosen grep table for a type-driven population has
substituted the author's imagination for an oracle that already exists.
