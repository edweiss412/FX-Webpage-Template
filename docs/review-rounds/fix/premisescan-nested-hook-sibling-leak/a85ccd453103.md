# Review-round economy — `fix/premisescan-nested-hook-sibling-leak` @ `a85ccd453103`

Arc: `BL-PREMISESCAN-NESTED-HOOK-SIBLING-LEAK`. Subject is `tests/mutation/source/premiseScan.ts`, a
recognizer, plus the spec and plan describing a three-line narrowing of it.

## spec — 6 rounds

**Examined:** all twelve findings of rounds 1-6 (1, 3, 5, 1, 1 and 1), sorted by what each was a
defect IN, and by whether a mechanism could have caught it before a reviewer was paid to.

The composition is lopsided and worth recording plainly. **Zero findings touched the repair.** The
narrowing itself — three lines in `hookBodies`, with verdict-neutrality measured against the shipped
classifier before a line was written — was never contested in six rounds. Every finding was about
the documents: an enumerated acceptance criterion, an inert task-marker region, a false `red-state`
claim, an over-stated census denominator, a stale lint count, an unswept inventory, an off-by-one
citation, and a TDD ordering violation.

That is not a complaint about the reviewer; each finding was correct and three were materially
important. The inert markers meant the plan's own contract was checking nothing. The false
authored-red meant a task claimed a discrimination its command could not make. The round-4 ordering
finding meant two tasks would have changed production before the test that reds without it — the
`export` authored ahead of its consumer can only ever be observed green — and round 5 found the
same class surviving in one more place after that repair: the matcher DEDUP still preceded the only
test able to exercise it, because the behavioural family provably cannot. But it does say where this
arc's review cost went, and most of it is mechanizable.

**Mechanizable:**

1. **The inert task-marker region is the expensive one, and it is already detectable from data the
   linter computes.** A plan carrying `<!-- task: … -->` markers and NO
   `<!-- tasks: depth=N red-contract -->` region parses to zero enrolled markers, and `spec:lint`
   then reports `0 hard` — a report about nothing, which its author reads as a pass. `taskTopology`
   (`lib/specLint/taskContract.ts`) already computes both the marker count and the region extent;
   nothing compares them. `taskMarkers > 0 && taskRegionLines === 0` is an advisory the arm could
   emit today, and it would have removed one full round here. Filed as
   `BL-SPECLINT-ORPHANED-TASK-MARKERS`.
2. **A restated lint count goes stale by construction.** §7 quoted `0 hard, 1 advisory`; two repair
   rounds later the true figure was `0 hard, 3 advisory`, and round 3 spent a finding on it. The
   repair was to stop quoting a count and declare the advisories by CLASS. That generalizes to any
   document restating a tool's output, and it is a `docs/agents/spec-self-review.md` rule rather
   than a tool change.
3. **Production-before-red survived its own repair TWICE**, which is the argument for mechanizing it
   rather than trusting a re-read. Round 4's resequencing fixed two tasks and left a third standing;
   round 5 fixed that one by introducing reds that round 6 showed were invalid by the project's own
   RED-validity rule. Three dispatches, one axis, each repair adding surface — which is precisely the
   same-axis-recurrence shape AGENTS.md says to answer by NARROWING. The eventual repair does exactly
   that: **the two exports are deleted from the design entirely**, the derived covers read the
   scanner's source through the AST instead, and the production surface drops back to two edits with
   every red naming a scanner line. Both halves are statically checkable — a production edit ordered
   before the red it answers, and a `red=` whose failure is an unresolved import — and the
   red-contract arm already parses the marker and its owned steps.
4. **The root-file red-target constraint is ALREADY FILED**, as
   `BL-SPECLINT-RED-TARGET-CANNOT-NAME-A-REPO-ROOT-SURFACE` (filed 2026-08-18 by a different arc).
   Round 3's finding here is a second incident on that row rather than a new one: Task 6's
   `red-target` cannot name `BACKLOG.md`, so it names the guard predicate instead. Recorded here so
   the row accumulates evidence instead of the class being re-minted.


**Judgment:** the derived-versus-enumerated class (r1 finding 1, r3 finding 4) is real review value
and is not mechanizable. Deciding that a criterion's population must be READ from the matcher rather
than typed beside it is a design judgment, and it generalized twice in this arc — the sweep that
repaired AC-5 carried AC-6 in the same round, and round 3 still found the meta-test inventory
unswept, which is the same class one level up. Round 3's census-bounding finding is also judgment:
the harness was correct, its denominator was not what the prose claimed, and only a reader comparing
the two would see it.

**Infra:** none. All six dispatches returned a verdict — no `no_verdict`, no reap, no wedge, and
the wrapper's native-binary path resolved on every attempt.
