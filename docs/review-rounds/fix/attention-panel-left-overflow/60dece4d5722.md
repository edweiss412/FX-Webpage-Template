## spec — 4 rounds

**Examined:** 4 spec rounds at this base, 15 declared findings (6, 4, 3, 2),
verdicts BLOCKING, BLOCKING, BLOCKING, NEEDS-ATTENTION. Every finding was
accepted; none was argued down and none was refuted. Repairs at `e0b4d1cd5`,
`be3a78795`, `251b0071d`, and this commit.

The finding rate decayed monotonically and the KIND of finding changed with it,
which is the part worth recording. Rounds 1-3 found design defects that would
have shipped: a height cap assigned to the wrong element, a re-measure mechanism
that does not exist, acceptance criteria that did not exclude the alternative the
spec rejected. Round 4 found a stale cardinality and two mis-cited class-sweep
rows. That is a review converging, not a review ratcheting, and it is the reason
the arc proceeds to the plan rather than buying a fifth round.

**Mechanizable:**

1. **A MECHANISM claim needs a repo search for prior verifications before it
   enters a spec.** The costliest finding of the arc (round 3, finding 1) was that
   Tailwind v4 compiles `scale-*` to the individual `scale` property, so
   `transform` is permanently `none` on this panel — which killed the settle
   oracle used in three sections, killed a `transitionend` design that had already
   survived two rounds, and had been endorsed by the orchestrator on the same
   wrong premise. **The repository had already verified this and written it down**
   (`tests/e2e/helpers/phantomGap.ts:306-310`, whose comment says "verified" in as
   many words). The codebase remembers what individual drafts forget. The
   mechanizable arm is a lint that flags a spec asserting a CSS or DOM mechanism
   (`transform`, `transitionend`, computed-style names) without a citation, the
   way `CITATION_MALFORMED` already flags an uncited file claim.
   **Disposition.** Process-facing under the 2026-08-25 mint freeze. Its done
   condition is a property of the lint — whether it catches every uncited
   mechanism claim — which is the open-input-space shape the freeze names as
   unfinishable, and no product arc was blocked. Parked as a documented limit;
   the re-file trigger is a second arc losing a round to an unverified mechanism
   claim, which with this one would be the two independent arcs
   `Mint-exception: recurrence` requires.

2. **`spec:lint` advisories are not all noise, and this arc treated them as
   noise.** Round 4's first finding was `SIBLING_LIST_CARDINALITY 511:18 claim of
   3 conditions over an adjacent list of 4 items` — emitted by the lint the arc
   ran every round, sitting inside a batch of 39-42 advisories the arc filtered to
   `FAIL|summary:` and never read. A reviewer spent a round of the cap reporting
   what the tooling had already printed. The arm is separating the advisories with
   a real defect rate (`SIBLING_LIST_CARDINALITY`, `CITATION_SYMBOL_ABSENT`) from
   the ones whose false-positive rate makes them unreadable (`NUMERIC_NOUN_MISMATCH`
   firing on "and", "the", "with", "does"), so the first group can be read at the
   same cost as `FAIL`.
   **Disposition.** Process-facing under the 2026-08-25 mint freeze. The done
   condition is guard fidelity, whether the advisory partition is the right one,
   which the freeze's admission test excludes. The cheap half needs no row and is
   adopted by this arc directly: read `SIBLING_LIST_CARDINALITY` and
   `CITATION_SYMBOL_ABSENT` alongside `FAIL` in every future lint invocation.

3. **A static disposition that excuses itself from verification is where a wrong
   exclusion survives.** §5's class sweep scheduled two of four peers for runtime
   confirmation, and the two it left unscheduled are exactly the two whose stated
   facts were wrong (round 4, finding 2): a portal cited for the wrong element,
   and an anchored popover described as a centered dialog. The arm is a rule that
   every row of a class-sweep table is either repaired or scheduled for the same
   verification the defect row gets — no row excluded on a reading alone.
   **Disposition.** Adopted in-arc rather than filed. §5 now schedules every
   non-defect row for Task 1 runtime confirmation, so the repair ships in this PR
   and there is nothing left to schedule. Generalizing it to a checked rule across

## plan — 4 rounds

**Examined:** 4 plan rounds at this base, 19 declared findings (4, 5, 4, 6),
verdicts BLOCKING throughout. Every finding accepted; none argued down. Repairs at
`d36f46449`, `b983d454f`, `31fca6c0b`, `9397d89f9`. Combined with the spec stage,
this arc has run 8 rounds and accepted 34 findings at this base.

**Unlike the spec stage, the plan's finding rate did NOT decay: 4, 5, 4, 6.** The
reason is worth recording, because it is not "the reviewer got pickier". Rounds 1
through 4 kept landing on ONE axis — the task decomposition — and each repair
moved the defect rather than removing it:

| Round | Shape | What the repair did |
| --- | --- | --- |
| 1 | Task 1 deleted its own probe in its GREEN, so its command could never pass | Made the probe persist as a new matrix suite |
| 2 | Tasks 1-3 authored reds only Task 4 cleared: three commits red at their own boundary | Merged those four into one task, still deferring five obligations |

Four rounds, one axis, and the arc converged only when it stopped trying to
decompose an indivisible change. **The production edit falsifies seven suites and
two baselines simultaneously**, so every decomposition that put the repairs in
different tasks produced a commit that was red at its own boundary. That is the
same-vector recurrence rule's trigger, and the comprehensive re-analysis it
mandates should have happened after round 2, not after round 4.

**Mechanizable:**

1. **A task's `red=` command must cover every contract the task's GREEN edits.**
   Round 4's third P0: Task 1 edited five Vitest suites and two baselines while its
   marker ran only two Playwright suites, so a literal execution could have
   committed with five suites red and never looked. The marker grammar already
   carries the command; nothing checks it against the task's declared file set.
   An arm comparing a task's `red=` invocation to the suites covering the files it
   says it edits is mechanical and would have caught this at round 1.
   **declined: process-facing under the 2026-08-25 mint freeze.** Its done
   condition is a property of the lint, not a number a product arc would notice
   moving. Parked as a documented limit; the re-file trigger is a second arc
   losing a round to a marker whose command under-covers its own edits.

2. **A new standalone e2e spec is invisible unless `testMatch` is edited, and
   nothing says so at plan time.** Round 3's second P0. The config's own docblock
   warns that "a spec file that merely exists runs nowhere and silently proves
   nothing" (`tests/e2e/standalone.config.ts:39-41`) — the warning is present, well
   written, and was not read by the plan that added a spec. Worse, the task's
   command also named two REGISTERED suites, so the invocation would have gone
   green while the new file ran zero times. A lint arm reading a plan's `red=`
   for `standalone.config.ts` spec paths and checking each against the allowlist

   **declined: process-facing under the freeze**, same reasoning as arm 1. The
   re-file trigger is a second arc shipping an uncollected standalone spec.

declined: neither arm is filed, and neither may be under the 2026-08-25 process

**Judgment:**

- **The atomicity should have been recognised at plan time, and the signal was

- **Accepting all 19 was correct.** Every one was probe-backed or source-verifiable,

## diff — 4 rounds

**Examined:** 4 whole-diff rounds at this base, 13 declared findings (4, 4, 4, 1),
verdicts NEEDS-ATTENTION throughout. Every finding accepted; none argued down.
Repairs at `fd8e143a9`, `2a5207e88`, `645d179db`, `9c6342ad5`. Across all three
stages this arc ran 12 rounds and accepted 47 findings at this base.

**The rate was flat at 4 for three rounds and then collapsed to 1.** That shape is
the opposite of the plan stage's, and the reason is worth recording: the diff
rounds were NOT circling one axis. They walked a chain, each round landing on the
layer the previous repair had just created.

| Round | What it found | What the repair created for the next round |
| --- | --- | --- |
| 1 | The migration's behavioral gaps — scroll clamping, missing signals, a weakened width contract | Four behavioral repairs, shipped with no tests |
| 2 | Those four repairs had NO regression coverage | Three new tests, and one probed absence |
| 3 | Two of those three new tests did not discriminate | Stronger assertions, proved by mutant |
| 4 | One stale CI path filter | — |

That is a converging chain, not a ratchet: each round's subject was strictly
smaller than the last, and round 4's single P2 is a class no earlier round could
have reached because it lives outside the diff's own files.

**Mechanizable:**

1. **Retiring a file has the same CI-wiring obligation as adding one, and nothing
   says so.** Round 4's only finding: `.github/workflows/step3-live-bundle.yml`
   listed `components/admin/useFitWithinClip.ts` in its path filter, and this arc
   deleted that file. A filter naming a deleted path matches nothing, so the
   desktop-Chromium job it gates would have skipped a `lib/popover` change
   silently. The writing-plans rule already requires confirming path-filter wiring
   when a plan ADDS a test file; the reverse direction is unwritten. A lint over
   `.github/workflows/**` path entries against the worktree is a `test -e` loop —
   I ran exactly that as the class sweep and it found this instance and no other
   real one.
   **declined: process-facing under the 2026-08-25 mint freeze.** Its done
   condition is a property of the lint, not a number a product arc would notice
   moving. Parked as a documented limit; the re-file trigger is a second arc
   shipping a stale filter, which with this one would be the two independent arcs
   `Mint-exception: recurrence` requires.

2. **A registry that proves a mechanism by MODULE can be satisfied by a type
   import.** Round 3's finding, and it reached all seven `placement-module` rows,
   six of which predate this arc. The check required an import from
   `lib/popover/position.ts`; every consumer imports only `Rect` from there — a
   TYPE — and gets real placement from `place.ts`. Every row could have stopped
   placing anything, kept the type import, and passed. Keying on
   `placeWithinVisibleViewport` by name fixes it by construction, because a named
   function cannot arrive through a type import. The generalizable arm is that any
   import-presence guard over a TS codebase must key on a value, never a module
   path, or `import type` satisfies it.
   **declined: process-facing under the freeze.** Repaired in-arc, which is always
   allowed; the general rule is guard fidelity, whose done condition is a property
   of the guard. Re-file trigger: a second guard found satisfiable by a type
   import.

declined: neither arm is filed. Both have done conditions that are properties of
tooling rather than numbers a product arc or a human would notice moving, which is
what the 2026-08-25 freeze's admission test excludes. Both are parked with re-file
triggers requiring a second independent arc to pay the same cost.

**Judgment:**

- **Coverage written to close a coverage gap needs the same proof of
  discrimination as any other test, and mine did not have it.** Round 2 found four
  behavioral repairs shipped with no tests. I added three. Round 3 found that two
  of the three could not fail: both scroll events were dispatched with
  `bubbles: true`, and native element scroll does not bubble — so the events
  reached the listener whether or not it was registered in the capture phase,
  which is the entire mechanism under test. The visualViewport case asserted event
  NAMES, which a no-op handler or a teardown passing a different callback both
  satisfy. The fix was not just stronger assertions but PROVING them by mutant:
  removing the self-origin filter from production now fails the case. A test
  written under the pressure of a coverage finding is written to exist, and that
  is exactly when it needs the mutant.
- **A test NAME is a public contract, because the standalone baseline records
  names.** Round 3 caught an e2e title claiming to verify keyboard order over a
  body that checks DOM descendancy only. Renaming it was trivial; the reason it
  mattered is that `tests/e2e/standalone-baseline.json` commits test identities, so
  the overstatement would have shipped as the suite's declared contract and been
  quoted by the next reader as coverage that exists.
- **Three of the four rounds found something I had already been told about.** The
  measurement helper's own docblock names the self-origin hazard and says the two
  scroll-listening surfaces must carry the filter. The writing-plans rule names
  path-filter wiring. The premise contract names the vacuous-guard shape. Each was
  in the corpus before the round that found it. The arc's recurring failure was
  not reasoning badly; it was not reading the thing that was already written.

**Infra:**

- **The Codex sandbox executed no test command in ANY of the twelve rounds across
  all three stages** — `EPERM` on Playwright's reporter writes, on Vitest's
  transform cache, and on the heavy-slot lock. All 47 findings came from source
  reading and arithmetic. Every brief from spec round 3 onward told the reviewer to
  state unverifiable claims with their command and mark them unverified rather than
  withhold them, and that instruction is what surfaced the `scale`-property
  finding, the `testMatch` finding, the type-import hole and the stale path filter
  — four of the arc's most consequential findings, none of which a
  run-or-stay-silent reviewer would have reported.
