# Review-round economy — `fix/premisescan-registrar-accept-sets` @ `c80f844278bd`

## spec — 4 rounds

**Examined:** whether `premiseScan`'s three hand-maintained accept-sets (`REGISTRARS`, `MODIFIERS`,
`HOOK_REGISTRARS`) can be replaced by sets derived from Vitest's installed surface, and whether that
replacement must ship together with the repair to `registrarRoot`'s callee peel. Seven findings
across four rounds, all accepted, none disputed.

**Mechanizable:** three of the seven, and all three are one class — **an accept-set widened without
every CONSUMER of it agreeing**.

- r1 F2: widening `REGISTRARS` adopted nothing, because the walk dispatches on the root BY NAME
  (`if (root_ === "describe")`, `if (root_ === "it" || root_ === "test")`), so `suite` was recognized
  and then dropped.
- r2 F2: `HOOK_REGISTRARS` has THREE consumers — the file-scope seed, `hookBodies`, `loadTimePremises`
  — each requiring a bare identifier callee, so `test.beforeEach(…)` was invisible to all three and
  left a test `environment-free` that the bare form makes `environment-touching`.
- r3 F1: once the interleaved peel made deeper chains RESOLVE, `eachProducers` still read only the
  immediate curried call's arguments, so `describe.skipIf(process.env.CI).each([1])(…)` classified
  its children while the earlier modifier argument went unattributed.

A checkable form exists: for each accept-set, enumerate its consumers and assert each ranges over the
set rather than over its own copy of some members. That is a structural test, not a review round, and
it would have caught all three before the first dispatch. Filed as `BL-ACCEPTSET-CONSUMER-COVERAGE`,
with these three measured differentials as its incident evidence.

**Judgment:** three of the seven, and none of them mechanizable.

- r1 F1 and r2 F1 are both **which derivation** questions. Enumerating callable own properties
  over-accepts (it admits BUILDERS — `extend`, `override`, `scoped` — whose call returns a new API
  rather than registering); reading `ChainableSuiteAPI` alone under-accepts (`fails` is declared on
  `ChainableTestAPI`). The resolution is that the DECLARATION is the authority and authority is
  PLURAL — a judgement about which declarations constitute the authority, which no lint can make.
- r4 F1 extends the same axis to a suite-factory parameter alias, where the object peels to a name
  that is in no accept-set because it is a local binding.

**Infra:** none. No dispatch was reaped, no verdict was recovered from a rollout, and no round was
discarded.

### What the rounds cost and what would have cut them

The dominant cost was **stating a class rule and not running it against the neighbouring instance**.
§3.3's rule — an accept-set is only adopted where every consumer agrees — was written in round 1 about
`REGISTRARS`, and round 2 found the identical defect in `HOOK_REGISTRARS`, one section away in the
same document. Writing the general statement felt like discharging it. The cheap check is to grep the
document for the class the moment the rule is stated, because the nearest peers are the ones you were
looking at while forming it and therefore the ones least likely to be re-read.

The second cost was a **repair widening what the scanner can SEE without widening what it must
ACCOUNT FOR**: the interleaved peel made deeper chains resolve, and resolving them is what exposed
the single-level argument collector in round 3. A repair that extends a recognizer's reach extends
its obligations in the same edit.
