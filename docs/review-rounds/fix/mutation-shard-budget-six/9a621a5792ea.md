# Review rounds — `fix/mutation-shard-budget-six`, base `9a621a5792ea`

## spec — 3 rounds

**Examined:** 4 spec rounds across 2 bases (1 at `94de73ef6e53`, 3 here; the branch merged
`origin/main` mid-arc, which moved the merge base and opened this file). 19 findings, all 19
accepted and repaired, none argued down. Per round: 6, 6, 4, 3. The decision under review, N = 8,
never moved after round 1 and was explicitly upheld by rounds 2 and 4; every finding was about the
evidence for it rather than about it.

**Judgment:** Two root causes account for 8 of the 19, and both are the same mistake in different
clothes: writing down what a tool does instead of running it.

The first cost three findings on ONE acceptance criterion across two rounds. AC-7 asserts that
shard files below the count are not ignored and the next one up is. Round 2 found it fail-open
because `git check-ignore` suppresses its answer for a TRACKED path, so the assertion could not
fail for exactly the files it protects. Round 3 found the REPAIRED version fail-open a second way,
because `-v` exits 0 whenever it has a rule to report and a negating `!` rule is a rule, so an
exit-code-only implementation passing `-v` reads "ignored" for a path that is not. Neither is
inferable from the criterion's text; both took a probe in a scratch repository. The same shape
produced round 2's finding that a planned task duplicated `records.test.ts:413` and rested on a
vitest behaviour (`passWithNoTests`) that is not configured the way the justification assumed.

The second is narrower and sharper. Round 4 found the spec claiming that every measured surface
observes at or above its declared rate. The drift report sorts descending; the claim was written
from the first forty lines of its output; the counter-example (`acCoverage`, 0.9936) is near the
bottom. An instrument was truncated and the visible part was generalised into a universal. The
aggregate figure the argument actually rests on, 1.1952x, was correct throughout.

**Mechanizable:** Two of the 19, and one of them nearly was already.

- The reproducibility gap is mechanizable. Round 2's highest-value finding was that §1.3's table
  came from a scratch instrument while the document's header claimed every figure was printed by
  a command. A spec that states a numeric table and carries no command producing it is statically
  detectable, and `spec:lint` already models both halves (it parses numerics, and it parses fenced
  commands) without relating them.
- The class-count contradiction ("the two classes that derive from it", followed by Class A, Class
  B and Class C) is the shape `NUMERIC_NOUN_MISMATCH` exists for. It did not fire because the
  count and the enumeration are a heading and three sub-headings rather than a claim and an
  adjacent list, which is the `SIBLING_LIST_CARDINALITY` shape one rule over.

declined: no ledger row, for either candidate, and the decline is a decision rather than an
omission. This arc files no `BL-`/`DEF-` row of any facing under a binding directive, and the
2026-08-25 process mint freeze independently refuses both: each is process-facing, each cites
review rounds burned on a process arc reviewing a process surface, which the freeze names as
exactly the evidence that no longer admits a row, and neither has a done condition that names a
number outside the tooling. Both candidates are also about `spec:lint`, which is not this diff's
surface, so mechanizing either here would be a second arc wearing this one's branch name. What
happens instead is what the freeze prescribes: the observation lives in this filing, which is the
record the next person to touch `spec:lint`'s numeric rules will read, and the re-file trigger is
a spec whose stated table cannot be reproduced from its own commands reaching a review round
again. The cost is measured and small: one finding per candidate across four rounds, both caught
by review, neither reaching code.

What is NOT mechanizable, stated because the tempting conclusion is wrong: the incomplete prose
inventory looks like a lint and is not. Its sweep command's raw output on this tree is about thirty
lines, most of them "four" in an unrelated sense (four required checks, four registries, four
review rounds), so any rule strict enough to catch the two missed members flags a dozen false ones.
The spec states the command as a candidate generator with a triaged table and the N/A rows written
down, which is the honest form rather than a rule nobody would keep green.

**Infra:** None. All four dispatches completed with a verdict; no reaped run, no `no_verdict`, no
retry, no wrapper fault.

## plan — 4 rounds

**Examined:** 4 plan rounds, all at this base, 4 cross-base. 19 findings, all 19 accepted, none
argued down. Per round: 5, 3, 4, 3. All four rounds returned BLOCKING. The task count went 2, then 1, and the restructure that produced is
itself the subject of the largest finding class below.

**Mechanizable:** One candidate, and it is the strongest this arc produced because it accounts for
ten of the sixteen findings across three consecutive rounds.

Every restructure of this plan left the OLD structure described somewhere else inside it. Round 1
found four passages still assigning work to a Task 3 that had been deleted. Round 2 found three
still assigning work to a Task 2 that no longer existed after the merge to one task, plus a
checklist item requiring the observation of a `red-state=live` marker the plan does not contain.
Round 3 found three still directing the guard to a file a later section had moved it out of. Same
defect, three rounds, ten instances, and each round's repair created the next round's instances.

It is statically detectable and the parser already exists. `spec:lint` reads task topology today
(`lib/specLint/redContract.ts` imports `taskTopology` rather than re-implementing it), so "every
`Task <n>` mention in a plan resolves to a `## Task <n>` heading in that plan" is a comparison
between two things the linter already has. The marker half is the same shape: a checklist line
naming `red-state=live` when no marker in the document declares it.

declined: no ledger row. This arc files no `BL-`/`DEF-` row of any facing under a binding
directive, and the 2026-08-25 process mint freeze refuses this one independently: it is
process-facing, its evidence is review rounds burned on a plan document, and its done condition is
a property of `spec:lint` rather than a number a product arc or a human would notice moving. The
freeze names that combination as exactly what no longer admits a row. It is recorded here instead,
which is the record the next person to touch `spec:lint`'s plan rules will read, and the re-file
trigger is a fourth arc losing a round to a stale intra-document task reference. The cost so far is
measured and bounded: ten instances, all caught by review, none reaching code.

**Judgment:** The other nine divide in three, and neither half was available from reading the
plan.

The first half is the contracts of NEIGHBOURING guards. `_metaSpawnDisposition` classifies whole
files, so its rows compose rather than displace, and the file this plan first chose to host a git
call already carried a blanket "no spawns here" row with a pinned count and digest; the row this
plan planned could not have been written. `shardBalance.test.ts` passes the live shard count into
a held-out comparison whose committed fixtures are four-leg data by construction, so raising the
count breaks three ratified measurements from another arc. Neither is visible from the changed
files. Both took reading the guard that would break.

The second half is a guard that cannot fail, which is the same family the spec stage burned three
findings on. Round 1's blocking finding was that a two-task split gave the shard-range guard no
task-local RED: it asserts something true today, so it passes when authored and only fails once the
other task moves the constant. Round 1 also found the guard's third fail-open, ambient exclude
sources, after the spec had already closed two. Across both stages this one guard produced five
findings, and every one of them was "it would have passed for the wrong reason".

The third group is one mistake made twice, in both stages, and it is the one worth carrying
forward. Round 4 of the spec stage found a universal claim ("every measured surface observes at or
above its declared rate") that a single surface disproves; it was written from the first forty
lines of a report that sorts descending. Round 4 of the plan stage found the prose sweep described
as returning "about thirty lines" when it returns 129; that number was the size of a `head -30`
view. Both times an instrument was truncated for reading and the visible part was generalised into
a claim about the whole. Neither was caught by re-reading the document, because the document was a
faithful record of what had been looked at.

**Infra:** None. All four dispatches completed with a verdict. Round 2 could not collect a vitest
command in its sandbox (`EPERM` on Vitest's temporary SSR directory) and correctly declined to read
that as observed RED rather than reporting it as a finding.
