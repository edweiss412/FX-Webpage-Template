## diff — 3 rounds

**Examined:** R1 (1 MEDIUM: all three capture/restore scopes initialized their snapshot to a
destructive empty sentinel, and vitest runs `afterAll` even when `beforeAll` threw, so one transient
capture failure would delete every watch channel, the global orphan alert and the settings row and
put nothing back), R2 (1 LOW: the WATCH_CHANNEL_ORPHANED producer row's `contextKeys` had been
widened to the UNION of its three callers, against this file's stated intersection contract, so
`guaranteedKeys` promised six keys no branch guarantees), R3 (1 LOW: that guard's failure message
still opened "expected 66 files" while its assertion said 67 — two baselines from one failure), A fourth
dispatch (1 LOW: graduation left the spec's `Closes:` pointer aimed at a `BACKLOG.md` heading the
same commit removes) belongs to the POST-MERGE arc and is counted there — see the corpus note
below.

**Judgment:** every diff-stage finding was in the scaffolding around the change — test harness,
registry rows, doc pointers — and NONE in the shipped mechanism. The activation guard, the
`folder_changed` outcome and all four consumer branches drew zero findings across four rounds. That
is the spec (4 rounds) and plan (7 rounds) having done their job: the design arrived settled and
what remained was the harness. The two substantive ones were both two-fact compositions no pattern
would catch — R1 required knowing vitest runs `afterAll` past a thrown `beforeAll` AND that the
initializer was destructive; R2 required reading a contract sentence in one file against three call
sites in another.

Worth recording plainly: R2's first repair was ALSO wrong, in the opposite direction. Narrowing to
the bare intersection broke `allowedKeys`, because that aggregation is `contextKeys` +
`optionalContextKeys` and the row had no optional set. A finding that names a direction ("this is a
union, the contract says intersection") invites over-correction; the registry wanted both halves.

**Mechanizable:** the R1 shape. "A capture/restore scope whose snapshot variable has a destructive
initializer" is statically detectable — a restore called from `afterAll` whose argument was
initialized to an empty collection rather than left `undefined`. Not built here: one arc, three
instances, and the structural repair (guard inside the restore function, not at the call sites)
removes the shape for these files by construction. File it if a second arc grows the same thing.
R3's shape — a guard whose diagnostic states a different baseline than its assertion — is also
mechanizable in principle (compare integer literals in the message against the asserted one) but is
narrow enough that the enumeration cost exceeds the recurrence.

**Infra:** no reaps, no `no_verdict`, no rollout recovery across four dispatches. One dispatch was
blocked pre-flight by `review-convergence-gate.sh` because the round-3 brief's convergence wording
had drifted from the prescribed closable form; the brief was rewritten to carry an explicit
consequence bound and threat fence rather than overridden with `CONVERGENCE_ACK=1`. Recorded as the
gate working, not as a fault.

**The round count was set by CI and by the arc's own tail, not by reviewer imagination.** Real CI
caught three failures every local run passed, all the same shape — a guard that enumerates a surface
failing by default on a new or moved one (`file:line` producer registry, exact-count
`LOCAL_TEST_DATABASE_URL` scan set, 30s DB timeout floor). Those repairs are what R2, R3 and R4 then
had to review. This is the "local-passes-CI-fails is its own bug class" rule landing exactly as
AGENTS.md describes it, and the honest lesson is that the three enumerating guards should have been
run locally BEFORE the first dispatch: `vitest run --project=parallel --shard=2/3` plus the two db
meta-tests would have folded rounds 2-4 into round 1.

**Corpus note (2026-08-09):** `origin/main` was merged into the branch between the third and fourth
dispatch, so `git merge-base origin/main HEAD` moved from `d8cc5c96839b` to `f237624360d0` and the
fourth dispatch's row was written into a new arc file. That is the corpus working as designed — it
is keyed by (branch, base) and round numbers are contiguous WITHIN an arc — so the row stays in
`f237624360d0.jsonl` and is numbered round 1 there, being the first dispatch against that base. Only
the round index was adjusted; verdict, findings and timestamps are the wrapper's.

The consequence worth knowing for any arc that merges main mid-review: **the review thread is longer
than any single arc file shows.** Four dispatches happened here; the files declare 3 and 1. A reader
counting rounds per file will under-read the cost, and `pnpm review:economy` will list two arcs for
one thread. That is a real limitation of base-sha keying, not a defect in these rows — recorded here
rather than worked around, because moving the row to make one file read "4" would break the
row-declares-its-own-base identity check that stops rows being shuffled between arcs.
