## spec — 4 rounds

**Examined:** R1-R4 at base `60dece4d5722`, the only base this arc has. Declared findings per round, read off the JSONL rather than
retyped: R1 5, R2 1, R3 5, R4 1, 12 in total. Every finding was confirmed against the live tree before repair; none was refuted. Two of R3's
five were regressions of my own earlier repairs, which is the fact that shaped the repairs below.

R4's single finding is the shape worth carrying forward: the compound transition §8 had enumerated one
route to the failed branch (a runtime image error, via the failure handler) when the tree has two. The
second is render-phase reconciliation at `components/admin/wizard/step3ReviewSections.tsx:3859-3867`,
which calls `setFailed` directly and never invokes `onFailure`, and it has its own committed test. The
lesson is narrow and reusable: when a spec names a state transition by the HANDLER that causes it, it has
described one route and implied there is only one. Enumerate the writes to the state, not the callers.

**Mechanizable:** declined: `LIM-PLAYWRIGHT-RED-TESTMATCH`, fourth naming, and this one cost nothing: the plan's
real-browser `red=` named `tests/e2e/step3-review-modal.layout.spec.ts` under `pnpm test:e2e`, and that
file appears in NO project's `testMatch` in `playwright.config.ts` — only `.interactions` and `.agenda`
do. It runs under `tests/e2e/standalone.config.ts`, whose allow-list does name it. Caught at
plan-authoring time by deriving the command from `package.json` rather than from the argv shape, so it
never reached a dispatch. The slug's trigger fired at three arcs already and one of those three is
`perf/admin-diagram-next-image`, the arc that filed this row; the freeze's admission test still governs,
and a defect caught before dispatch blocks no product arc, so nothing is minted.

A second, narrower gap, also declined: parked without a slug, because one naming is not a class. The
shipped prose-count parity arm did not fire on `### 4.1 The two live consumers…` above a body naming three. The arm relates
numeric literals to executable declarations; a HEADING CARDINAL against the count of enumerated children
beneath it is a different relation. The structural repair taken here needs no arm at all — §4.1 became a
table, so its count is read off the rows and can no longer be asserted beside them.

**Judgment:** R2's finding is the one no static arm predicts, and it is the reason a wrapper-move is not
the trivial refactor it looks like. Moving chrome onto a focusable element subjects that chrome to
`:focus-visible`, and this repo's rule for it is UNLAYERED, so it beats every Tailwind utility whatever
the specificity: the tile's radius goes 12px to 6px when focused, and a `focus-visible:rounded-md`
utility would not fix it. Nothing in the diff, the class names, or the scanner population says this. It
is found by asking what states the NEW owner has that the old one did not, which is a question about
element kinds rather than about classes.

R3's compound-transition finding is the same question asked once more: before the move the branch axis
and the focus axis were independent, because focus could not reach an image. After it, one event moves
both. The project transition-inventory rule already demands compound cases; what it cannot tell you is
that a placement change CREATES one.

Also judgment, and the cheapest lesson here: two of R3's findings were miscounts of my own. L3 said
"roughly eleven focusable elements" from `rg -c`, which counts matching LINES per file, not elements;
review re-derived eighteen. The repair was to DROP the number rather than correct it, because the claim
L3 rests on needs one verified exemplar and not a population size. A count a claim does not use is pure
liability, and stating one invites a round per restatement.

**Infra:** the reviewer could not execute Vitest in ANY of the four rounds — the read-only sandbox denied
its temporary SSR directory every time — so all four verdicts are static reads plus direct scanner
execution. That is worth knowing when weighting them: the scanner claims were probed twice and are
strong, while nothing in this arc's spec stage was settled by a test run on the reviewer's side.

Separately, `tests/docs/_metaReviewRoundEconomy.test.ts` red once locally on an `afterAll` `rmSync`
cleanup timing out at 30s under fleet load, with all 135 tests passing. `--testTimeout` does not raise
hook timeouts; with `--hookTimeout` raised the file is green. Not a corpus defect, and recorded so the
next reader of that red does not chase it as one.

## plan — 4 rounds

**Examined:** R1-R4 at base `60dece4d5722`. Declared findings per round, read off the JSONL rather than retyped: R1 8, R2 7, R3 3, R4 3, 21 in total. Four consecutive BLOCKING verdicts on a two-className change is the number worth
explaining, and the explanation is not that the change is hard.

**Judgment:** every one of those 21 findings was about the PLAN's own machinery — task topology,
whether a RED could be observed, whether an acceptance criterion had a command behind it — and none was
about the product change, which R1 already agreed was correct and which no later round revisited. The
plan stage cost three times the spec stage on a diff the spec stage had already settled.

One shape produced most of it, and it is worth naming precisely because it is invisible from inside:
**a check that cannot fail reads exactly like a check that passes.** Four separate instances, each found
by a different round or by self-audit:

- a RED command whose two halves were joined by `&&`, so the half expected to fail suppressed the half
  that was supposed to be observed failing (R2 raised the unobserved browser RED; R3 found the `&&`
  still doing it after the repair);
- `git diff --name-only`, which exits 0 whether or not the file is listed;
- a `grep 'lives on the'` that matched the stale sentence as happily as the repaired one;
- an acceptance criterion declared in the coverage table and claimed by no task at all, which no linter
  reports in that direction.

The last one is the instructive one. It was found by DERIVING the declared and claimed id sets and
diffing them, and it had been introduced by the previous round's own repair. Reading the plan would
never have surfaced it, because reading is exactly the faculty that a check-that-cannot-fail defeats.

**Mechanizable:** declined: the same two directions each need a different arm, and neither is minted
under the 2026-08-25 process freeze — a plan defect that costs review rounds is a process cost, and the
freeze's admission test asks for a number a product arc or a human would notice moving.

The first is `LIM-AC-DECLARED-UNCLAIMED`, and it already has a home: `spec:lint` ships an opt-in
`ac-declared` region that reports exactly this direction, and this plan simply did not enrol. That is a
documented limit of the plan, not a gap in the tool — the arm exists and was not switched on. Recorded
here so the next arc knows the switch is there.

The second has no arm and is not obviously mechanizable: deciding whether a shell command can fail on
the tree where it should fail is a question about semantics, not syntax, and a recognizer over shell
that answered it would be exactly the open-grammar recognizer this corpus keeps warning about. The
honest countermeasure is the one this arc ended up using by hand — for every acceptance command, name
the tree on which it FAILS, not only the tree on which it passes. That is a review question, and R3
asked it well.

**Infra:** the reviewer could not execute Vitest or `spec:lint` in any plan round — the sandbox's
read-only temp filesystem failed them before collection with `EPERM` — so every plan verdict is a static
read plus targeted probes it could run, such as the ESLint invocation that exited 0 and disproved a RED
claim. Four plan rounds and four spec rounds, and not one of them ran the suite the plan is about. That
is the single largest thing separating these verdicts from certainty, and it is a property of the
dispatch environment rather than of the reviewer.

## diff — 4 rounds

**Examined:** R1-R4 at base `60dece4d5722`. Declared findings per round, read off the JSONL rather than retyped: R1 3, R2 2, R3 1, R4 1, 7 in total. The only
stage of this arc that decayed. Every finding was confirmed against the live tree before repair and none was refuted.

**Judgment:** the production change was correct at round 1 and no later round revisited it. All 7
findings were about the ARTEFACTS AROUND the change: a regex in the new suite, and prose in the spec,
plan, closeout, test comments and index row. That is worth stating because it is the same distribution
the plan stage showed, and it says something about where the risk in a small diff actually lives.

One shape produced most of them, and it is the sharpest thing this arc learned:

> **A repair falsifies the documents that describe what it repaired.**

Not a claim that was never true. A claim that STOPS being true the moment you fix something, which is
precisely when nobody re-reads it. Every round found exactly one instance and each was mine:

- R1's regex fix left the plan SPECIFYING the defective pattern and naming a symbol that no longer
  existed.
- R2 found that the fix's own test comment made a FALSE STATEMENT — it claimed all three middle-token
  inputs had failed under the old regex, when `bg-` carried no end anchor and was never missed. I had
  asserted that rather than measured it, in the same commit where I was congratulating myself for
  reproducing the bug by execution.
- The repairs then reintroduced the bare-`:NNN` citation class for a FOURTH time, eleven hard lint
  failures across three documents that had been clean, because every repair writes new prose and the
  sweep had been run against the old prose.
- R3 found the specs index row describing the defect in PRESENT tense after the fix had landed.

**Mechanizable:** declined: `spec:lint` already catches the citation instance and did, immediately, on
every occasion — the failure was never detection, it was that I swept before the last edit rather than
after it. Ordering discipline is not a lint rule. The present-tense-claim instance is not mechanizable at
all without a tense-aware model of what the diff changed, which is a recognizer over an open grammar and
exactly the shape this corpus keeps warning against. Nothing is minted under the 2026-08-25 process
freeze: both are process-facing, and their done condition is a property of the tooling rather than a
number a product arc would notice moving.

The countermeasure that actually worked is procedural and free: **sweep after the last edit, not after
the first**, and run the lint over every document in the branch diff rather than the ones you happen to
have touched. That is what turned up the fourth citation recurrence, and it is what a fifth round would
otherwise have found.

**Infra:** Vitest could not collect in the reviewer's sandbox in ANY of the four rounds — temporary
directory creation returns `EPERM` — so every diff verdict is a static read plus targeted probes the
reviewer could run, and it ran many. Separately, the local full suite was deliberately killed by the
fleet orchestrator at swap-critical, 19.2GB, and full suites stayed banned on the machine for the rest of
the arc. Neither is offered as evidence anywhere in this branch; CI's required checks are the
authoritative full-suite signal, which is the correct division of labour but worth recording as the
reason no local full-suite number appears in this arc's record.

One process error, recorded because the outcome was luck rather than method: R3 was dispatched at
`d5c074277` and I committed `71f7a0cf3` while it was running, having deliberately frozen the tree during
R2 for exactly that reason. R3 happened to read the later head, so nothing was torn. R4 was dispatched
against a frozen tree and nothing was edited until its verdict.
