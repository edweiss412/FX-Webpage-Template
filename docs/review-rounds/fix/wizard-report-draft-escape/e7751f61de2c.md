# fix/wizard-report-draft-escape — review-round filing

## diff — 5 rounds

**Examined:** 5 counted diff rounds at this base (rounds 1-5; a sixth dispatch, numbered 3, died `no_verdict` on a Codex usage limit and is recorded but uncounted). 17 findings across the five: 3 NEEDS-ATTENTION, 3 NEEDS-ATTENTION, 5 BLOCKING, 3 NEEDS-ATTENTION, then 0 and APPROVE on the fifth. All 17 accepted; none refuted, none relitigated a fenced decision. Round 5 was authorized past the four-round cap by bl-orch on the explicit condition that it be the LAST, and it converged because the open axis had been closed mechanically first — see below. The product defect itself — a typed report draft destroyed when the wizard review modal closes — was found, fixed and pinned in the FIRST commit of the arc, before round 1.

**Mechanizable:** The dominant class is not a defect class at all, it is a TEST-STRENGTH class: an assertion that reads as a pin while being satisfiable without the behaviour it names. Seven of the 17 findings are that shape, all of them in rounds 1-4.

- R2 F2: an `"x".repeat(n)` fixture that cannot distinguish prefix truncation from a suffix, from filler, or from boundary corruption, because every candidate answer is the same string.
- R2 F3, R3 F4, R4 F2: a test whose prose promises a behaviour (submission survives throwing storage) while the body stops before exercising it.
- R3 F2, R3 F3: fixtures with no discriminating property — a 500 standing in for a 410, an unpadded string standing in for the trimmed-versus-untrimmed distinction.
- R4 F1: assertions all true in the pre-action state, so deleting the action under test leaves them green.

There is a mechanical test for six of the seven, and it is cheap: **delete the action under test and confirm the assertions go red.** R4 F1 is exactly that check applied by a reviewer to a test I had written, in the same round, to close R3's instance of the same class. The one that mechanisation would miss is R2 F2, where the fixture is wrong rather than the sequence — that needs a fixture whose characters differ, which no runner can infer.

This is a candidate for the anti-tautology rule in `docs/agents/writing-plans.md` to state as a PROCEDURE rather than a principle: for every new test, delete its action and re-run before committing.

declined: the process-facing mint freeze (AGENTS.md, 2026-08-25) admits a process row only under `invariant` or `product-blocked`, and this is neither. No product arc was blocked; the rounds were burned by a product arc reviewing its own tests, which is precisely the evidence the freeze says does not qualify. The class is recorded here instead, which is where the freeze sends it.

**What actually converged it.** Not a sixth round of argument. The class above is an assertion about an OPEN space — "could a test be weaker than it reads" — and four rounds showed it does not close by review: findings ran 3, 3, 5, 3 with no decay, and round 4's instance landed in a test written in round 3 to close round 3's instance. bl-orch ruled it closed mechanically instead: extract the surface to an importable module, enrol it in the source-mutation registry, drive to zero unaccepted survivors. The first score was **11/17 = 0.647 with six survivors**, on a suite written to be mutation-proof and already cleared by four review rounds; five were real gaps (the cap constant pinned by nothing because every expectation derived from it, and the surrogate range boundaries pinned by nothing because the fixture sat comfortably inside the range), and the sixth was a true equivalent that is ledgered rather than chased. Repaired, the surface scores **16/16 with zero unaccepted survivors**, and round 5 returned APPROVE with zero findings against that criterion. One mechanical run found five instances of the class that five review rounds had been finding one at a time.

**Judgment:** Two findings were genuine design calls the reviewer was right to raise and that no guard could have caught. R1 F1 (a detached submit's success clearing a shared key) and R2 F1 (the compare-and-clear reading raw storage against capped state) are both consequences of the repair rather than the original defect — the arc's own fixes creating the next round's finding, twice. R3 F1 is a third kind again: a plan-wide invariant (invariant 8's `DEFERRED.md` requirement) that I applied to the wrong ledger, which is a rule-reading error, not a test gap.

**Infra:** One dispatch (round 3, first attempt) died `no_verdict` / `attempts_exhausted` on an OpenAI usage limit, with the reset date in its stderr; the arc held for roughly two hours until credits were purchased and bl-orch broadcast a resume. Its row is kept in the corpus deliberately. A second dispatch's first attempt 401'd immediately after the purchase landed — an auth propagation race — and the wrapper's own retry recovered it without intervention. Every reviewer round ran under a sandbox that could not start Vitest, could not write `tsconfig.tsbuildinfo`, and in later rounds could not open spec-lint's IPC socket; every finding therefore came from reading. That is worth noting precisely because the dominant finding class above is one that reading catches and a green test run hides.
