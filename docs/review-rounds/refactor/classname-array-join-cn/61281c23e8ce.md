The spec converged early and stayed converged. Its design findings ran 2 → 1 → 1 → 0 → 1 → 1 → 0,
and the two late ones were accuracy defects in it rather than design faults (a mis-transcribed data-join

**The plan is where the rounds went, and it was authored without the discipline the spec got.**
Eighteen of twenty-four findings were plan mechanics: false TDD markers, a RED/GREEN split across two
tasks, a dimensional baseline captured after the change it measured, a Playwright spec matching no
project allow-list, a workflow invocation without its `paths:` filter, a ledger marker removed before
the final CI run. None of these is a judgment call and none needed a reviewer to find in principle —
each is checkable against a file that was already in the repo. I wrote the plan in a single pass
while the spec was out for R1 review, and skipped the plan-side equivalent of the citation pass.

**Mechanizable** — three of the eighteen plan findings are checkable by a rule, and all three recurred:

1. **A task marker whose `red=` command does not go red-then-green.** Three separate rounds, three
   different spots: R3-F5 (procedural tasks carrying markers at all), R4-F1 (a guard task whose test
   passes the moment it is authored), R5-F1 (a command naming the very file its GREEN deletes, so
   `vitest run` exits 1 with `No test files found` both before and after). Each repair was correct
   and the next round found the class somewhere else, which is the signature of a class that wants a
   rule rather than another careful pass. `spec:lint` already parses the declared task contract and
   knows each task's `red=` command; it cannot run them, but it can flag the shapes that are
   never-red by construction — a `red=` naming a file the same task creates from scratch with no
   pre-existing failing counterpart, or a task whose body contains no "fails because" clause. The
   stronger version: require each task to state, in one line, *what is red and why*, and lint for its
   presence. R4-F1 is the proof this is worth mechanizing — I "fixed" the TDD markers in R3 and still
   shipped a false one into R4.
2. **A Playwright spec that matches no project's `testMatch`.** `playwright.config.ts` uses explicit
   allow-list regexes and its own header warns that "a spec absent from this regex runs NOWHERE and
   silently proves nothing." A meta-test walking `tests/e2e/*.spec.ts` and asserting each matches at
   least one project would have caught R3-F3 at authoring time, and would catch the next one. This
   repo has already paid for this class twice by that comment's own account (#479, and the
   `admin-layout-e2e` job itself).
3. **A workflow-invoked spec absent from that workflow's `paths:` filter.** R4-F2. Mechanizable in
   the same meta-test: for each spec named in a workflow `run:` line, assert the workflow's `paths:`
   covers the spec, its fixtures, and — harder, so possibly advisory — the components it asserts on.

Filed as candidates rather than done here: all three are guard surfaces of their own, and building
them inside a lint-coverage migration is the scope blowout that class-sweep exception (c) exists to
prevent. They belong to whoever next touches `tests/e2e` wiring.

**Judgment** — the remaining findings were genuine calls, not oversights, and I do not think a rule
would have helped:

- **The accept-set vs ratified R6 (R3-F4).** Stating the guard's accept-set positively is the right
  discipline, and stating it *too* broadly contradicted a ratified scope decision in the same
  document. The repair — scope the accept-set to array joins and add an explicit "what this guard
  does not decide" paragraph — is a judgment about where a guard's subject ends.
- **Ledger marker vs CI-green ordering (R4-F3).** Invariant 12 wants the marker to survive to the
  last commit; the merge wants CI green on the merged head. Both are satisfiable, but only by an
  ordering neither rule states, and the failure mode (a CI repair after the graduation commit) is
  invisible until you walk the unhappy path.
- **The parity check's lifecycle (R1-F2, R3-F2).** The reviewer's insight — that a differential test
  against a frozen base has no viable life as a tracked test, because CI checks out at depth 1 and
  because its allowlist would freeze 18 files forever — reframed the mechanism rather than correcting
  it. That is the round budget working as intended.

**Infra:** none. All seven spec dispatches returned a verdict; no `no_verdict`, no silent death, no
retries. The convergence gate blocked the R1 dispatch once, correctly: the brief stated a consequence
bound in its own words ("never silently left dark") rather than the recognized form. Adopting the
canonical phrasing was the right fix and took one edit — the gate cost nothing and the phrasing is
now uniform with the rest of the corpus.

**What I would do differently, stated concretely rather than as a resolution:** run the plan through
the same pre-draft verification pass the spec got, against the four files a plan makes claims about
here — `playwright.config.ts`, the workflow that will run the new spec, `vitest.projects.ts`, and
`AGENTS.md`'s invariant list. Ten minutes against those four would have pre-empted R3-F3, R4-F1,
R4-F2, and R4-F3: four findings, two rounds.

**One process defect worth recording separately, because it cost a round on its own.** R6-F4: the
round-5 brief carried the round-1 `spec:lint` transcript and no plan transcript at all, while both
artifacts had moved. `docs/agents/spec-self-review.md` already requires a fresh report per dispatch;
I regenerated the artifacts every round and the attachment only once. `codex-guard --lint-doc`
mechanizes exactly this and records `lintArm` in `result.json` — using it, rather than pasting, is
the fix, and it is available today.
