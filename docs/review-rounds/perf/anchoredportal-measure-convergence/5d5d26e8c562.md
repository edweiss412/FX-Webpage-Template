**And a fourth time, in this document.** Sweeping this filing's own numbers
against their sources before committing it turned up three claims taken from
memory rather than measured: the dispatch count (eight, actually seven), the
lines moved (about 105, actually 94 moved and 80 net), and a superseded appendix
number left pointing at a section that had since been renumbered. Every one is
the class this section is about, committed in the prose describing it. That is
not irony worth enjoying, it is the measurement. The class is not "artifacts I
wrote carelessly", it is **any sentence carrying a number I did not re-read off
its source at the moment of writing** — which is why the sweep has to be
mechanical, grep each numeric literal and open its source, rather than a
resolution to be careful.

The fix that actually closes this class is to WRITE LESS. Every sentence
asserting what the guard does is a standing obligation to keep true, and eleven
of thirteen findings this stage were that obligation going unmet. A ledger row
saying "stop overclaiming" is not falsifiable and would sit open forever.

So the arc cut instead. Four blocks totalling 94 lines were MOVED into this
filing, none deleted; the spec went from 646 lines to 566, a net 80, because the
largest cut left a 14-line replacement stating the same boundary in general
terms. Every line moved was HISTORY rather than a claim
about the code: how a probe instrument was debugged, three superseded versions of
it, two withdrawn arguments, and an enumeration of four ways past the workflow
check. The dividing rule was one line: **the spec keeps what is true about the
CODE, the filing keeps how we LEARNED it.** A spec sentence is a maintenance
obligation; a filing sentence is a historical record and carries none. Moving is
therefore strictly better than deleting, since nothing is lost and the upkeep
stops.

The four-defeat enumeration is worth naming separately. It was accurate, and it
was still wrong to keep in a spec: a document that lists four ways past its own
guard publishes an attack menu, and rounds 2 and 3 each arrived with the next
item on it. The spec now states the threat fence in general terms and points
here.

Two things the cut itself broke, both caught before commit and both the same
shape. Removing appendix A.3 left a numbering hole, so A.4 was renumbered to
A.3 — which silently invalidated two citations in the PLAN, and made the moved
block's own label point at a DIFFERENT section than the one it names. That is
citation rot with the polarity flipped: the anchor never moved, the target was
renamed underneath it. A sweep across every arc-touched file caught all three;
grepping only the file being edited would have caught none of them.

**Infra:** none. Seven dispatches carry a row across the two stages — three
spec, four diff — and every one of the seven has `status: "verdict"`. No
`no_verdict`, no exit 3, no reaped run. The count is read off the corpus rather
than from memory, which is the point: an earlier draft of this line said eight,
and it was the same defect the Mechanizable section above is about, committed
in the sentence describing it.

**One monitoring error of the author's, recorded because its DETECTION generalises.**
Progress on the pre-closeout suite was read with a bare `pgrep -f 'with-heavy-slot'`,
which matched four sibling arcs' shells as well as this one, so some reported
elapsed times belonged to another arc's process. It surfaced because the elapsed
time jumped BACKWARDS, from 14:26 to 00:12.

That reversal is the reusable part: **any monotonic quantity that goes backwards
proves the identifier is matching more than one object.** Uptime, byte counts,
line counts, run duration — a reading that can only increase cannot decrease
unless the subject changed underneath you, so a reversal is an identity check
obtained for free.

The correct method is to ENUMERATE broadly and ATTRIBUTE narrowly: `pgrep` to
find candidates, then the process's own cwd to decide which arc owns it.
Attributing by pattern is what produced the wrong reading, and it is the same
defect as the repo's unscoped-kill guard, pointed at reading rather than killing.

**And a PID is not a durable identity either** — it can be recycled, in which
case a death arm keyed to `kill -0` never fires and the watcher silently follows
a stranger. That is the identical defect one level down: an identifier whose
referent can change underneath it. The watcher used here carries the process's
START TIME alongside its PID and stops if the pair disagrees, which a recycled
PID cannot satisfy.

**And silence is not a result.** The pre-closeout suite's watcher reported
`completed (exit code 0)` with an empty result section, and that was read as the
suite finishing clean. It had not finished: the log file's mtime was two minutes
LATER than the watcher's own exit, and `ps` showed the suite alive at 21:52
elapsed. The exit 0 belonged to the WATCHER.

Two constructions caused it and they are one mistake in two places. The loop
never distinguished "the process is gone" from "my iteration budget ran out", so
a timeout and a finish printed the same thing. And the failure check was
`grep FAIL || echo "(none above = clean)"`, which fires its reassuring branch
loudest exactly when the log is empty, which is when it knows least.

The repair is a POSITIVE completion predicate: nothing is called clean unless the
summary line the tool emits on completion is actually PRESENT (`Test Files ...`
for vitest). An absent summary is UNKNOWN and is printed as such. Under that
predicate the suite really was green, and the number is now sourced from the run
rather than from the watcher's silence: 2091 files and 30541 tests passed, 72
skipped, zero failures, `EXIT=0`.

Read together, the three errors in this section are one lesson at three depths.
A pattern can match more objects than you meant (`pgrep -f`). A PID can be
recycled and name a different object than it did (`kill -0`). And an observer can
report nothing at all, which resembles success more closely than either. The
first two are wrong answers; the third is no answer wearing the costume of a
right one, and it is the most dangerous because nothing about it looks like an
error.

### The sharpest instance of this stage's own finding, caught by CI after the filing was written

The Mechanizable section above names the class: **an artifact asserting something
the shipped code does not do.** Every instance across four rounds asserted it to a
HUMAN, and every repair was prose. Then a required check went red on the closeout
head and produced the same defect asserted to a MACHINE.

`fix-citations.py` refreshed sixteen rot-prone anchors, rewriting each to carry
both a derived line number and the symbol it points at. One of the sixteen landed
inside `<!-- task: ... -->`, the plan's task marker, which is not prose: it is a
parsed field list, and `red-target=` is one of its fields. The inserted
parenthetical broke the parse, `ac=AC-1,AC-2,AC-3,AC-4` stopped being read, and
all four criteria became unclaimed. `tests/specLint/acUnclaimedCorpus.test.ts`
failed with `expected [ …(16) ] to deeply equal [ …(12) ]`.

Isolated rather than guessed: running `acAnalysis` over the plan as committed at
`852771a8e` returns `unclaimed = []`, and over the same plan after the citation
commit returns all four ids. One edit, one cause.

**What makes it the sharpest instance is where the temptation pointed.** The red
names a residue registry, and adding four rows to it turns the check green in
under a minute. That registry's own header forbids exactly this: *"it may never
grow to make a red go away."* The honest repair was the opposite direction and
one line long, restoring the marker field, and the arc took it.

Two rules follow, and the second is the general one:

- **A sweep must know which lines a parser owns.** Prose and machine-parsed
  fields are different targets, and a formatting improvement that is right for
  one corrupts the other silently. The sweep here was correct sixteen times and
  wrong once, which is the ratio that makes this class hard: fifteen successes
  are not evidence.
- **A guard's registry is not a place to record that the guard is inconvenient.**
  Where a red points at a list you may edit, check whether that list forbids the
  edit before making it. This one said so in its first paragraph.

**And a third false-green, in the tooling watching all this.** The combined
waiter armed over the three verification arms reported `FAIL files: 0` for a
suite that had been KILLED, because it counted failures without first requiring
the summary line that only a completed run emits. That is the identical defect
the section above records and repairs in the individual watchers, left
unrepaired in the one that aggregated them. Fixing an instance is not fixing the
class, even when you believe you have just fixed the class.
