**R4 and R5 are worth recording as failures of MINE, not of the diff, and they are the SAME
failure twice.** R4's findings 2 and 3 were bookkeeping asserting things that had not happened: plan checkboxes ticked through
"final review", "CI green on the final HEAD", "merge" and "teardown" before any of them occurred,
and this filing's own opening claiming every finding repaired while a typecheck error sat on the
committed HEAD. A durable audit trail that runs ahead of the events is worse than none, because
the next reader cannot tell which parts were observed. The rule taken from it: **a checkbox is
ticked by the event, never by the intention** — and a filing written at the threshold says what
has happened so far, not what is expected to.

R5 then found the same class still alive after I had "fixed" it, and R6 found it a THIRD time.
That third recurrence is the useful datum, and it says something narrower than "sweep harder": my
derivation was itself wrong. R5's completion-claim scan only looked at lines containing an
arc token (`app-e2e`, `batch 1`, the ledger id), so three `As shipped` claims on lines without one
were invisible to it — and in the same edit I introduced two NEW drifting claims, a closeout
saying "R5 pending" and "four counted rounds", both falsified by the corpus row the round itself
wrote.

**The fix is not a better scan, it is deleting the claims.** A hand-maintained restatement of a
machine-known fact drifts by construction: every round makes the round tally wrong, every restart
makes the restart count wrong, and the document has no way to notice. So the closeout no longer
restates round counts or outcomes at all — it names the corpus as the authority and stops. The
corpus is written by the wrapper at dispatch, and `tests/docs/_metaReviewRoundEconomy.test.ts`
asserts the filing's declared count against it, so the one count that survives is the one a test
can fail on.

R7 then found the last instance, and named the mechanism that let it survive three passes: ONE
checkbox conflated two things — an early partial PR-body edit and the final population of the
five run links its own command carries — so satisfying the first made the box look satisfied. The
repair is not a better checkbox but a causal one: the step that populates the links now ticks that
box in the same action, so the tick is CAUSED by the evidence rather than by an intention to
produce it.

Four rounds went to this class (R4, R5, R6, R7). Two rules worth carrying forward:

1. **Prose must not restate a fact a machine already holds** — cite the machine-held source and
   let the guard that watches it do the watching. The one count that survives in this arc is this
   heading's, and `tests/docs/_metaReviewRoundEconomy.test.ts` failed on it during the R7 repair,
   which is precisely the difference between a maintained count and a checked one.
2. **A checkbox is ticked by the event, and ideally by the code that performs it.** Where a step
   produces evidence, the same action should record both; a box a human ticks from memory is a
   claim, not a record.

The mechanism, stated so the next arc can avoid it: **a plan step is a snapshot, and a repair to
the machine source silently invalidates every snapshot of it.** Ticking the box freezes the
snapshot without freezing the source. Four separate repairs (concurrency shape, the retry pin, the
seven-spec list, the date sweep) each landed in the workflow or the spec and left a checked step
describing the pre-repair world. The cheap defence is to make a step cite the source rather than
copy it; the expensive defence is a guard binding each tick to a re-run of its own probe, which is
real work and is NOT undertaken here.

**Mechanizable:** yes, and the mechanization landed in-branch.

Rounds 1 and 3 are the same defect class seen twice: **a guard whose assertion is true without
being discriminating.** Round 1 found that the oracle's `REQUIRED` table was checked against
nothing (a spec could join the workflow with no floor at all) and that its floors were untrusted
literals (a spec that gains cases keeps a stale floor). Round 3 found the residue of that same
class in the repair itself — floor parity is satisfied by `0 === 0`, so a spec resolving nothing
passed every assertion. Both are now machine-checked rather than reasoned about:
`tests/cross-cutting/app-e2e-ci-wiring.test.ts` derives the expected floors from live Playwright
resolution by replaying the workflow's own argv, pins key-set parity in both directions, asserts
the positive premise before the equality, and refuses any command flag outside a reviewed
allowlist. The oracle refuses a non-positive floor outright.

The cost of NOT having it was measured directly: the plan's meta-test inventory had declared this
guard unnecessary — "the coverage scan + oracle + five-green bar cover the same surface" — and
that claim, unprobed, is what rounds 1 and 3 spent themselves disproving. The crew-e2e sibling had
already closed the identical class for its own job (its R14 finding is round 1's finding 2
verbatim). **A new CI job that clones an existing job's shape should clone its wiring guard in the
same commit**; declining the guard cost two BLOCKING rounds to re-derive what an existing file
already knew.

Round 1's finding 3 is mechanizable in a second sense: the oracle's `spec.id` counting was
inherited from the crew script along with a comment asserting it made a repeat count once. The
probe showed the comment was false (seven cases repeated twice produce fourteen distinct ids). A
copied invariant carried its copied justification across without either being re-probed.

**Judgment:** the two AC-4 drops. `help-pages.spec.ts` came out pre-flight because `/help/tour`
throws a hydration mismatch — an app defect on a UI surface, which would have pulled invariant 8's
impeccable dual gate into a CI-wiring arc. `admin-changes-feed-layout.spec.ts` came out during
acceptance because CI reproduced a batch flake. Neither is mechanizable: both are scope calls
about what a batch may admit, and AC-4 exists precisely so they are cheap to make.

**Infra:** the local signal was actively misleading and cost real time. This machine's local
Supabase is shared across concurrent agent sessions, and `signInAs` deletes and recreates fixture
`auth.users` rows, so a concurrent session breaks another's auth mid-run. Two specs' local reds
were correctly diagnosed as that collision — and for `admin-changes-feed-layout` the correct
diagnosis then MASKED a real, CI-reproducible flake underneath it. The rule that came out of it,
now recorded in the ledger entry: **only CI settles a flake question**, and a correct local
diagnosis is not evidence that there is only one cause.
