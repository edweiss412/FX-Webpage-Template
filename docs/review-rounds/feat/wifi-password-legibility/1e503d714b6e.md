## diff — 10 rounds

**Examined:** all ten diff rounds' briefs and verdicts (`docs/review-rounds/feat/wifi-password-legibility/1e503d714b6e.jsonl`), the nineteen findings they raised, and the repairs at `8e6b6fd07`, `8bf417c12`, `6ba387dcc`, `04ff22630`, and round 5's.

Findings by round: 3, 2, 2, 1, 2, 1, 2, 2, 2, 2. Every one was probe-backed, and every one was accepted — no round spent on a refuted claim, and none re-raised a fenced decision. Seven of the nineteen were the same subject: **the lifetime of one boolean and the timer behind it**; six more were a second class, **where a resolution is routed when more than one island exists**; and three were the timing scanner's own totality.

**Mechanizable:** none, and the reason is worth stating rather than filing a tool. Five of the six copy-window findings are the SAME invariant seen from five directions — *a reset timer exists if and only if a confirmation is standing, and it belongs to the confirmation that armed it.* Rounds 1-3 each repaired the vector in front of them (guard on a lagging ref; only the newest write arms; a timer left running after a corrective) and each repair left the invariant true for one more case rather than true outright. The round that ended the sequence is the one where the repair was structural: one exit from `copied` that kills the timer with the state, one rule that every success arms, and a generation so a deferred cancel names its own window. No detector would have found these; what would have shortened the arc is stating the invariant BEFORE the first repair and asking which orderings violate it — the same discipline the class-sweep rule applies to instances, applied to orderings.

**Judgment:** two findings were judgment the reviewer was better placed to make than the implementer. The batched-resolution defect (round 1) turns on React's commit semantics — a ref written in a layout effect lags inside one batch — which reads as correct code until someone builds the batch. The passive-effect window (round 4) is narrower still, and its repair is the only one on this arc NOT covered by a test: `act` flushes passive effects at the end of its scope, which is exactly the gap the scenario needs, and three constructions failed to reproduce the order. That limit is recorded at the call site instead of being papered over with a test that would pass either way.

**Round 5 is the shape a healthy tail looks like**, and worth separating from the six above. Neither finding was the copy window: one was a factual error in a graduation record — the archived probe description had been copied from the entry's ORIGINAL filing ("10 fixture shows, 4 live sheets") rather than from this arc's actual sweep (23 fixture files, the validation DB, the local seed, and NO direct live-sheet read), which would have preserved false evidence in the permanent record. The other enumerated the spellings the round-3 recognizer widening still missed (JSX prop, quoted class field, computed key) and drew the threat-model line through them: two are ordinary and now covered, the computed key is a documented limit with a test pinning it as a decision rather than a hole. Round 5 also independently verified the round-4 repair, which is the only verification that repair has — see Judgment.

**Rounds 6 and 7 each found a real defect the earlier rounds could not have**, because each depended on a boundary the arc had just moved. Round 6 held the diff to the consequence bound the brief itself declared — the corrective retracted a standing GLYPH, but the ANNOUNCEMENT outlives it, so a value change after the window left "Copied." as the log's last word with the clipboard stale; the repair is bounded by the channel's own TTL, so a page that refreshes all day does not narrate an hour-old copy. Round 7 found that the module's owner registration was a single global while `FactRows` permits one island per opted-in row: production renders one today, but an ordinary second `copyLabel` would have left the tapped row idle while an untouched row lit up and announced. The registration is now keyed by row identity. Neither is a variant of the copy-window class; both are the review doing what a review is for.

**The routing class (rounds 7-9) is the same story as the copy window, one level up**, and it is worth reading as a warning rather than a summary. Round 7 found the registration was a single global; keying it by row identity fixed two rows in ONE list. Round 8 found two LISTS sharing a testid; routing to the dispatching island by INSTANCE fixed that. Round 9 found the compound — duplicate identity, plus a remount, plus an unmount — where the identity fallback still delivers to a live wrong island; a duplicate now switches the fallback off and says so in dev. Round 10 found two more orderings — a later row REUSING an identity, and collision bookkeeping that forgets a still-mounted earlier owner — and that is where the patching stopped. Four rounds, four repairs, each correct and each incomplete, because the question was never asked in its general form: *what is the complete set of (islands, mounts, resolutions) orderings, and which of them can deliver a write to a row that did not ask for it?*

The answer, once asked, is that a NAME cannot answer it at all. Identity is caller-supplied, so any name lookup also matches a different row sharing it or a later row reusing it, and every ordering the reviewer found is an instance of that one fact. The repair is therefore not a fifth patch but a different mechanism: the replacement link is established at the only moment it is PROVABLE — React runs an outgoing island's cleanup and the incoming island's setup back to back inside one commit, so an island offered as a predecessor for exactly that window, and cleared on the next microtask, really is the one being replaced. A late resolution walks that chain and nothing else; anything unlinked lands nowhere. The identity map and the collision set are deleted, which is the tell that the mechanism was wrong rather than incomplete: the general form is SMALLER than the four patches it replaces. Asking the general question at round 7 would have produced it three rounds earlier — the same lesson as the copy window, and the second time this arc paid for it.

**Filed rather than fixed (two):** round 7's second finding — a timing-named PROPERTY whose value is not a numeric literal is dropped rather than reported `unclassified`, unlike a timer delay, with five pre-existing sites invisible today. Pre-dates the widening that surfaced it, and closing it means dispositioning five sites on surfaces this arc does not otherwise touch, so `BL-TIMING-SCAN-PROPERTY-TOTALITY` carries it with the probe attached (class-sweep exception (c)). Round 9 added its sibling: an identifier delay resolves by NAME rather than by binding, so a local shadow of a covered constant is suppressed — `BL-TIMING-SCAN-NAME-VS-BINDING`, constructed-probe, no live instance. Both limits are stated in the scanner header too, since a guarantee that is only true of half the forms should not read as if it covers both.
