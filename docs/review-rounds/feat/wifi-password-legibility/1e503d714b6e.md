## diff — 20 rounds

**Examined:** all twenty diff rounds' briefs and verdicts (`docs/review-rounds/feat/wifi-password-legibility/1e503d714b6e.jsonl`), the twenty-nine findings they raised, and the repairs at `8e6b6fd07`, `8bf417c12`, `6ba387dcc`, `04ff22630`, and round 5's.

Findings by round: 3, 2, 2, 1, 2, 1, 2, 2, 2, 2, 1, 1, 1, 1, 1, 2, 1, 1, 1, 0. Every one was probe-backed. Twenty-eight were accepted; ONE was refuted, at round 12, and it is recorded below so a later reader does not re-derive it. Ten of the twenty-eight were the same subject: **the lifetime of one boolean and the timer behind it**; nine more were a second class, **where a resolution is routed when more than one island exists**; and three were the timing scanner's own totality.

**Mechanizable: one, and it took three occurrences to admit it.** A mutation siteId is keyed by LINE, so any edit to an enrolled source — including a comment — shifts every accepted row below it and the gate reports the whole set stale. Rounds 3, 8 and 15 each caught all eight rows of one surface stale, and each was repaired by hand: 161/287/347/362 -> 188/333/393/408 -> 206/392/452/467 -> 208/394/454/469, same columns, same operators, same reasons every time. The first two were treated as incidents and the registry gained a comment saying "re-derive before pushing", which is a habit, not a mechanism, and the third recurrence is what a habit failing looks like. `pnpm mutation:sites` (`scripts/print-mutation-sites.ts`) now prints the live ids for every enrolled surface, flags the stale rows, and names each one's successor by matching operator + column + replacement; it exits non-zero so it can gate a push. Reading the registry from disk means a newly enrolled surface is covered the day it lands.

**Not mechanizable — the rest, and the reason is worth stating rather than filing a tool.** Five of the six copy-window findings are the SAME invariant seen from five directions — *a reset timer exists if and only if a confirmation is standing, and it belongs to the confirmation that armed it.* Rounds 1-3 each repaired the vector in front of them (guard on a lagging ref; only the newest write arms; a timer left running after a corrective) and each repair left the invariant true for one more case rather than true outright. The round that ended the sequence is the one where the repair was structural: one exit from `copied` that kills the timer with the state, one rule that every success arms, and a generation so a deferred cancel names its own window. No detector would have found these; what would have shortened the arc is stating the invariant BEFORE the first repair and asking which orderings violate it — the same discipline the class-sweep rule applies to instances, applied to orderings.

**Judgment:** two findings were judgment the reviewer was better placed to make than the implementer. The batched-resolution defect (round 1) turns on React's commit semantics — a ref written in a layout effect lags inside one batch — which reads as correct code until someone builds the batch. The passive-effect window (round 4) is narrower still, and its repair is the only one on this arc NOT covered by a test: `act` flushes passive effects at the end of its scope, which is exactly the gap the scenario needs, and three constructions failed to reproduce the order. That limit is recorded at the call site instead of being papered over with a test that would pass either way.

**Round 5 is the shape a healthy tail looks like**, and worth separating from the six above. Neither finding was the copy window: one was a factual error in a graduation record — the archived probe description had been copied from the entry's ORIGINAL filing ("10 fixture shows, 4 live sheets") rather than from this arc's actual sweep (23 fixture files, the validation DB, the local seed, and NO direct live-sheet read), which would have preserved false evidence in the permanent record. The other enumerated the spellings the round-3 recognizer widening still missed (JSX prop, quoted class field, computed key) and drew the threat-model line through them: two are ordinary and now covered, the computed key is a documented limit with a test pinning it as a decision rather than a hole. Round 5 also independently verified the round-4 repair, which is the only verification that repair has — see Judgment.

**Rounds 6 and 7 each found a real defect the earlier rounds could not have**, because each depended on a boundary the arc had just moved. Round 6 held the diff to the consequence bound the brief itself declared — the corrective retracted a standing GLYPH, but the ANNOUNCEMENT outlives it, so a value change after the window left "Copied." as the log's last word with the clipboard stale; the repair is bounded by the channel's own TTL, so a page that refreshes all day does not narrate an hour-old copy. Round 7 found that the module's owner registration was a single global while `FactRows` permits one island per opted-in row: production renders one today, but an ordinary second `copyLabel` would have left the tapped row idle while an untouched row lit up and announced. The registration is now keyed by row identity. Neither is a variant of the copy-window class; both are the review doing what a review is for.

**The routing class (rounds 7-9) is the same story as the copy window, one level up**, and it is worth reading as a warning rather than a summary. Round 7 found the registration was a single global; keying it by row identity fixed two rows in ONE list. Round 8 found two LISTS sharing a testid; routing to the dispatching island by INSTANCE fixed that. Round 9 found the compound — duplicate identity, plus a remount, plus an unmount — where the identity fallback still delivers to a live wrong island; a duplicate now switches the fallback off and says so in dev. Round 10 found two more orderings — a later row REUSING an identity, and collision bookkeeping that forgets a still-mounted earlier owner — and that is where the patching stopped. Four rounds, four repairs, each correct and each incomplete, because the question was never asked in its general form: *what is the complete set of (islands, mounts, resolutions) orderings, and which of them can deliver a write to a row that did not ask for it?*

The answer, once asked, is that a NAME cannot answer it at all. Identity is caller-supplied, so any name lookup also matches a different row sharing it or a later row reusing it, and every ordering the reviewer found is an instance of that one fact. The repair is therefore not a fifth patch but a different mechanism: the replacement link is established at the only moment it is PROVABLE — React runs an outgoing island's cleanup and the incoming island's setup back to back inside one commit, so an island offered as a predecessor for exactly that window, and cleared on the next microtask, really is the one being replaced. A late resolution walks that chain and nothing else; anything unlinked lands nowhere. The identity map and the collision set are deleted, which is the tell that the mechanism was wrong rather than incomplete: the general form is SMALLER than the four patches it replaces.

Round 11 then found the first draft of that mechanism resting on an unchecked assumption of its own — a single vacancy slot, when React batches cleanups AHEAD of setups for a group remount (`cleanup A, cleanup B, setup A, setup B`), so the slot holds B by the time A's setup runs. With distinct identities that only LOSES a link; with a shared one it hands A the wrong predecessor. The proof now has three parts, each of which was a defect before it was a rule: within the commit, per identity, and consumed once (never when ambiguous). Every part is pinned by a test that fails when that part alone is reverted — three mutants, three failures — and the one residual is stated as a documented limit rather than claimed: a DIFFERENT row reusing a just-vacated identity in a second commit inside the same synchronous task is indistinguishable from the replacement, which needs an identity both duplicated and reused within one task. Asking the general question at round 7 would have produced it three rounds earlier — the same lesson as the copy window, and the second time this arc paid for it.

**Round 13 closed the copy-window class the way round 11 closed the routing one** — by moving what a mechanism is keyed on rather than adding a case. The generation existed so a deferred corrective could name the window it meant, and it advanced when a timer was ARMED. But a non-latest success can keep a window already running, arming nothing, so the corrective still matched and cancelled the window now backing a NEW confirmation. Entering `copied` advances the generation now, because the generation names the CONFIRMATION, not the timer. That ordering shares the round-4 environment limit — it needs a resolution inside React's passive-effect window — so it is fixed and recorded rather than tested, with the reviewer's probe as its evidence.

**Round 14 is the counterexample to this filing's own headline**, and it belongs here for that reason. After two classes were closed at the mechanism, the next finding was neither an ordering nor a keying question: a write that REJECTED stayed the ledger's newest, so the success after it was treated as stale, kept a nearly-spent timer, and showed its confirmation for 250ms of two seconds. One predicate — is this the newest write that could still fill a window — and it is reachable with fake timers, so unlike rounds 4 and 13 it is pinned by a test. Not every tail finding is a design flaw; some are just a missing case, and the way to tell is whether the repair fits in a predicate.

**Round 16 reopened both closed classes at once, and the lesson is about what "closed at the mechanism" is worth.** Rounds 11 and 13 each replaced a patch with a rule, and this filing said so before round 16 raised one more instance of each. Both were real, and both repairs again DELETED code rather than adding a case — which is the evidence that the rule was right and its EXPRESSION was still carrying a compensator.

- *Routing.* A claimed vacancy was consumed by marking it ambiguous. But "ambiguous" is also what a second live vacancy sets, so the mark conflated two different facts and the next offer in the same window was refused — an ordinary event, since an island that just claimed can be replaced again before the sweep (a layout effect commits synchronously, ahead of any microtask). The chain ended at a dead island, the late resolution landed nowhere, and the standing "Copied." it should have retracted stayed the log's last word with the clipboard already stale. Consuming by DELETION keeps the claim-once rule and stops spending the window's ambiguity on a vacancy that is already spoken for.
- *The copy window.* Round 14 taught that a REJECTED write must stop counting as the newest, and the repair was a `failed` set. The general fact is larger and was visible in that sentence: only a RESOLUTION has a confirmation to protect, so a newer write still in flight should not shorten the one on screen either — nor should a write dispatched by a DIFFERENT row sharing the identity, because the counter is per row while confirmations are per island. Comparing per island against the seq that ARMED the running window retires all three cases, and the `failed` set with them. The bookkeeping existed only to patch the comparison.

The reviewer found both instances of the second class in one round and named them as a class, which is the reviewer-side sweep rule working; both were repaired together in-branch, with no peer left filed — the mechanism exists in exactly one file (`rg 'vacanc|successor'` over the tree outside `docs/`).

**Round 17 asked the routing question from the other end, and that is what finally sized it.** Rounds 7-11 all asked *who should receive this resolution*, and the answer — only a provably-linked island — is right for the AFFIRMATIVE, which claims something about one row. Round 17's finding is that the same routing was applied to the RETRACTION, which claims something about the CLIPBOARD, and the clipboard is one resource shared by every row on the page. Two producers, both probed and both repaired here: an island unmounted and restored across two refreshes is unlinked by construction, so its late write said nothing while the restored row stood a confirmation the write had just falsified; and a second opted-in row needs no unmount at all, since its copy silently invalidates the first row's standing claim. The retraction is now broadcast BY VALUE — no name lookup, and no false positive available, because an island whose value differs from what the clipboard now holds is making a false claim whichever row it is. Matching values are left alone, which is §4.2's value-only truth doing the same work from the other side. The island decides in its own render phase, reusing the corrective machinery whole, because "is a claim standing" read from a layout-effect ref lags inside a batch — round 1's defect, and the reason this is a push rather than a poll.

The arc's own lesson, third statement: each of these three classes ended when someone asked what the mechanism is KEYED ON rather than which case it missed. Routing was keyed on a name (round 11: key it on a proof), the window on the newest write dispatched (round 16: key it on the write that armed the window), and the retraction on the row (round 17: key it on the clipboard). Every one of those repairs deleted more than it added.

**Round 18 is the round every mechanism-replacing arc owes and almost never pays.** The finding raised no defect in the code: it observed that the canonical spec §4.1, the plan, the graduation entry, the component header, the `identity` prop's own doc comment, `FactRows`, the standalone harness entry, and three test comments all still described the mechanism rounds 10-17 deleted — a name-keyed active-owner registration that routes a resolution to whoever is registered for that identity. Under invariant 7 the spec is canonical, so that is not a stale comment; it is an instruction to restore the thing five rounds were spent removing. All eight sites were repaired together (the sweep is `rg -n "active-owner|owner registration|registered at resolution|write ledger"`, which is how the three the reviewer had not cited were found), the spec carries a dated amendment recording what was superseded and why rather than a silent rewrite, and the round-11 header sentence that now holds only for the AFFIRMATIVE says so.

The general lesson, since this arc produced three mechanism replacements: **a repair that deletes a mechanism is not finished when the tests pass.** Every artifact that described the old one is a live instruction to rebuild it, and the review round that catches it is cheap only because someone else is reading. The cost of not paying it is a future arc "fixing" the code back to its spec.

**Round 19 charged the round-17 repair for an exclusion that read as an optimisation.** The broadcast skipped the island the write had just been delivered to — it already knows — so with two rows resolving in ONE batch, the last writer processed only the PREVIOUS writer's message, retracted a claim that was true, and both rows ended corrected. The repair is to tell every island, the delivered one included, which makes each island's decision a pure function of the clipboard's FINAL content and its own value: the order the messages arrive in stops mattering. That is the property the first draft was missing, not a case it had not covered, and the difference is worth naming because the two look identical from the finding. `deliverWrite` now carries the affirmative only; the single retraction path is the render-phase one both triggers already shared, so the log cannot end on two correctives and `clearCopied` is deleted. Both orderings are pinned by a `test.each`.

**Refuted (one), recorded so it is not re-raised.** Round 12 probed a different row taking over an identity in the SAME commit with the same value, and read the resulting "Copied." as misattribution. It is not: identity is the CALLER'S declaration that this is the same row, so reusing it in the swap is the caller saying so, and resolution truth is VALUE-ONLY (spec §4.2, ratified at spec round 17 and on this arc's do-not-relitigate list) — the entry claims the clipboard holds the string this row is showing, which is true of the row now displaying it. The same probe with a DIFFERENT value produced the corrective, which is that rule from the other side and is exactly right. The reasoning now sits in the component header beside the mechanism, because it reads like a defect until both rules are in view.
