**Judgment:**

The finding rate did not decay — 5, 3, 6 — and presenting that as convergence would be a lie.
What changed is the KIND, and that distinction is this filing's whole content.

Rounds 1-3 contain ONE recurring class, and it is the implementer's, not the reviewer's:
**every guard asserted a PROXY for its property instead of the property.**

| round | what the guard asserted | what it could not see |
| --- | --- | --- |
| 1 | the members were read, once each | the read happened at the wrong TIME (before the pass) |
| 2 | resolution preceded the roster, once each | the read happened outside the SCOPE (before the pass existed) |
| 3 | every member was read FRESHLY per invocation | the fresh answer was DISCARDED (a cached report) |

Each time the cover was satisfied by a build that had lost the property it named, and each time
the reviewer demonstrated it with a weakened build rather than arguing it. Counting calls cannot
see when a read happened, where it happened, or whether its answer was used. The repairs are
correspondingly structural rather than additional cases: an ordering pin; a pass-construction
trap (`readOnce` ENUMERATES its surface, so enumeration is an observable moment a Proxy can
timestamp); and a value-sensitivity case that changes the world between invocations and asserts
the decision changes with it.

Round 3 broke the pattern in a way worth naming. Its four core findings were PRODUCT
correctness — `String.replace` interpreting `$&` inside a valid git branch name, refusals citing
conditions that had not fired, infra faults exiting 1 where the taxonomy reserves 1 for
refusals. The detector did not widen; the product got more correct. That is the opposite of the
recognizer-growth trap the round-economy rules warn about, and it is why the flat rate is not
by itself an argument for stopping.

The one genuinely expensive mistake was mine and was licensed by a document. Round 2 reused the
existing `nonce-mismatch` refusal for a failed consume, reasoning it was "the same condition",
and cited spec §3.2's "the refusal catalog rows are unchanged" as support. It was not the same
condition — the gate compares marker against record at DECISION time, the consume compares at
SPEND time — so the shipped message was false about both halves, and round 3 spent a P1 on it.
The repair corrected the licensing SENTENCE as well as the code, because a sentence that
rewards keeping a catalog short over naming what fired will license the same defect again.

**Mechanizable:**

- The lying-refusal class now has a durable form here: one message per condition, plus a

**Infra:**

- The heavy semaphore is a RACE, not a FIFO queue: a waiter can lose turnovers indefinitely. One
  16-minute wait here bought nothing because the command could only error, and the error was
  invisible because the run was piped through `tail` — a pipeline reports the LAST stage's exit,
  so a dead-on-arrival gate is indistinguishable from a queued one.
- Per-shard CI artifacts are downloadable at JOB completion, while run LOGS wait for the slowest
  job in the run. Resolving which shard a surface partitions into (`surfacesForShard`) makes the
  number takeable well before the run ends.
- Pushing a new head CANCELS in-flight shards of the superseded run. A number captured before
  cancellation stays valid for the head it measured, and only for that head.
- A guard that enumerates via `git ls-files` sees a CONFLICTED path once per stage, so an
  unresolved merge produces phantom duplicate findings that read exactly like content defects.
  `tests/docs/retiredIdentifierReferences.test.ts` reported ten unaccounted references here; the
  count went to zero on `git add` alone, with no content change.
