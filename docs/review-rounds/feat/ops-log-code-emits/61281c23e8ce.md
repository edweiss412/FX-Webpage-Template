# Review-round filing — `feat/ops-log-code-emits` @ `61281c23e8ce`

Cluster E telemetry: durable `code:` emits at six failure sites (`BL-OPS-LOG-OAUTH-EMITS`, `BL-OPS-LOG-ONBOARDING-EMIT`).

## spec — 9 rounds

**Examined:** R1-R9, spec + plan reviewed together from R3 on. Findings by round: 4, 4, 3, 2, 3, 2, 2, 2, 0 — twenty-two total, all accepted, none refuted, APPROVE at R9. No round relitigated a settled decision, so the §1.1 do-not-relitigate block and the per-round "what changed" section did their job; the round count came from real defects, not scope ratchet. **The arc's design did not change after R1** — every subsequent round tightened test coverage or corrected a claim about code.

**Judgment:** Two genuine design forks, both settled once and never reopened. (1) Whether to persist the user-facing `OAUTH_REDIRECT_INVALID` or a distinct forensic code — the adjacent shipped `OAUTH_EXCHANGE_REJECTED` precedent pointed the other way, and the resolution turned on whether the internal event and the user-facing code assert the *same* proposition (here yes, there no). (2) Whether `reason` should discriminate the validator's internal cause or the call site — resolved to call site, with the validator and `verifyPickerIntent` both deliberately left opaque as documented limits §5.1 and §5.6. Both were argued in the draft rather than discovered by review, and neither cost a round.

**Mechanizable:** none.

The honest reading of R2-R4 is that **eight of the nine findings after R1 were incompleteness in the previous round's repair, not new defects** — the fix-round regression class that `docs/agents/writing-plans.md` already names. The progression is one class, repaired three times at widening scope:

- R2 broke a **denylist** ("no `error` key, no sentinel, no `private_key`") with a parse message relocated into `message` and with a partial key fragment. Neither was hypothetical; both came with probes.
- R3 broke the **context-only accept-set** that replaced it, by placing a fragment in `source` — which `buildRecord` promotes out of `context` and `persistAppEvent` writes as its own column. R3 also caught that Tasks 1-2 still carried the superseded wording: a real miss in my R2 sweep.
- R4 broke the **third copy** of the assertion list, still sitting in Task 4's body and still contradicting the shared shape, plus a guard whose three disjuncts had only two test cases.

- R5 broke the **fixture**: the case reaching `client_email_missing` omitted `client_email` entirely, so a mutant leaking that parsed field set `undefined`, the logger dropped the key, and the guard could not distinguish the mutant from safe code.
- R6 found two of the four mutants **not executable at the site they named** (the caught error and `parsed` are resolver-local, the emit is in the component body), and `requestId` left without a fixed oracle — `deriveRequestId` falls back to a random UUID, so the natural expectation is read back from the record and admits `requestId: rawNext`.
- R7 found the accept-set applied in Tasks 1, 2 and 4 but **not 3**, leaving two branches able to leak; and the **fail-open contract untested at all six sites** — deleting every `try`/`catch` left the whole plan green.
- R8 found the fail-open premise **vacuous at site 1** (`stampOauthClaim` emits before the branch, so a generic entered-flag is already true) and Task 5 claiming a natural RED it cannot have.

What closed the class each time was structural, and the pattern is the lesson: **one definition of the accept-set, referenced and never restated**, scoped to exactly the nine fields the sink persists and applied to every emit case without exception; **a table mapping each test input to the single guard disjunct it turns red**; **code-specific rather than generic premises**. Every round that instead patched the named instance bought exactly one round.

`docs/agents/writing-plans.md` already says to ship the structural defense at the FIRST occurrence when the class is nameable. It was nameable at R2 — "a guard narrower than the thing it guards" — and each of R3, R5, R6 and R7 was another instance of that same sentence at a different scope: context-only, then the fixture, then the mutant's reachability, then the set of tasks it governed. Shipping "the guard's scope must equal the contract's scope, everywhere, stated once" at R2 would plausibly have collapsed four rounds into one. That is the transferable lesson, and it is a rule-application failure, not a rule gap.

Worth separating from that: R7's two findings were genuine **coverage** gaps, not repair-incompleteness — nothing had ever tested fail-open, and no earlier round had looked. A reviewer finding new ground at round 7 is not the same failure as a reviewer finding the same ground again, and the round-count lesson above should not be read as blaming it.

## plan — 5 rounds

**Examined:** plan-stage R1-R5, run after the spec's APPROVE so the plan could be judged as an executable instruction set rather than as a design. Findings by round: 2, 2, 1, 1, 0 — six total, all accepted, none refuted, APPROVE at R5. The plan had already been in scope from spec-R3 on, so these rounds found only plan-specific defects: vacuous fixtures, missing cardinality, contradictory snippets, and uncovered guard conditions.

**Judgment:** One decision, settled and never reopened: AC-6 (ledger archival) is verified by inspection rather than by a test, because no executable gate discriminates it — `_metaLedgerInProgress` passes whether or not the step happens. Declaring that honestly, instead of dressing bookkeeping up as a TDD task, was itself a finding (spec-R2 #3) and the right resolution.

**Mechanizable:** none.

**The same class as the spec stage, and the same fix.** Every plan finding was a contract asserted in more than one place, or in a narrower place than it governs:

- R1: cardinality was checked in Task 1 only, so a duplicate emit passed everywhere else; and site 3's fixture was allowed to be an absent `next`, which cannot catch a leak conditional on the value being present.
- R2: the cardinality repair left **two contradictory snippets** in the shared section — following the first literally would fail a correct implementation.
- R3: Task 5 asserted a weaker "unchanged refusal" than Tasks 1-3 (no cataloged body, no wizard shell).
- R4: the case table covered the shape check's disjuncts but not the resolver's other two guards, and the untested one was the arc's worst failure mode — an empty `client_email` rendering as success, suppressing both the operator surface and its telemetry.

Three contracts converged only once each was **stated once and referenced**: the nine-field accept-set, cardinality, and the per-site refusal surface. The fourth, the case table, converged once it was reframed from one-input-per-disjunct to one-input-per-guard-condition. That is one rule with four instances: **a contract's definition must live in exactly one place and cover exactly the scope it governs.** Both stages of this arc are a demonstration of it, and the transferable practice is to write shared contracts as single referenced definitions from the first draft rather than discovering the need round by round.

**Infra:** none. All fourteen dispatches across both stages returned `status: "verdict"` on attempt 1 — no reaper interference, no `no_verdict`, no rollout-scrape recovery. Two dispatches were launched against brief files a failed generation step never wrote; both were killed by PID and re-run, costing no review time. The generation bug was the same both times: a heading rewrite applied before the substring search that depended on the old heading. A sibling session also overwrote a shared scratchpad brief path mid-arc, after which briefs moved to arc-prefixed filenames (`opslog-brief-rN.md`) — worth copying, since the scratchpad is shared across concurrent sessions and generic names collide. The plan-R5 reviewer noted a sandbox `EPERM` blocking a Vitest baseline run; that is the reviewer's sandbox, not a repo or plan defect.

## diff — 4 rounds

**Examined:** whole-diff R1-R4 against the merge base, after all five TDD tasks landed. Findings by round: 1, 1, 1, 0 — three total, all HIGH, all accepted, none refuted, APPROVE at R4. Every one was probe-backed: R1 and R3 shipped a passing mutant run, R2 shipped a rendered predicate dump. No round relitigated a settled decision, and no round touched the production code — **all three findings were in the tests**, which is the notable fact about this stage.

**Judgment:** none. The design forks were settled at spec stage and none reopened. The diff stage found no control-flow defect, no behavioral divergence in the resolver restructure, and no leak the shipped emits actually produce.

**Mechanizable:** none new. The three findings share a shape that already has a name in this repo — "a guard narrower than the thing it guards" — and the spec-stage filing above records that the same sentence generated four of its rounds. It generated three more here, which is the finding worth carrying forward: **the class did not transfer from the spec stage to the diff stage even though the same author wrote both.** The spec filing named it, the plan encoded the fix as "one definition, referenced", and the implementation still shipped three fresh instances of it, because the spec-stage lesson was written as a statement about the ACCEPT-SET's field list and the diff-stage instances were about its RANGE:

- **R1 — the record set.** Every helper filtered captured records to the expected `code` before checking cardinality and shape, and the secrets backstop serialized only that subset. A second durable record under a DIFFERENT code, carrying the raw rejected `next` or the whole service-account JSON, passed all 32 tests. Not exotic on this route: the adjacent shipped emits deliberately persist forensic codes distinct from the user-facing one, so "add a sibling emit under a new code" is the most likely next edit anyone makes in these files.
- **R2 — the case set.** The R1 repair converted the five OAuth fail-open cases and missed the sixth, which lives in the other file. The sweep was per-file, and "five of six" is what a per-file sweep looks like from the inside.
- **R3 — the path set.** Every case drove a REFUSAL, so all were blind to an emit hoisted above its guard: the record still appears with the right `reason` on the branch they exercise, while healthy traffic files durable FALSE failure rows. For sites 1 and 2 the success-path case is the ONLY thing in the suite that catches that hoist — their refusal cases still pass under it.

Three rounds, three ranges of the same quantifier: which RECORDS the assertion covers, which CASES carry it, which PATHS are exercised at all. The transferable rule is sharper than "state the contract once": **a completeness guard must name the set it quantifies over, and that set must be the whole set the contract governs — not the subset the current fixture happens to produce.** Filtering by the expected code was the R1 instance of exactly the same mistake as testing only refusal paths at R3.

After R3, the vector was re-analysed comprehensively rather than waiting for R4 to name instance four. Enumerating the remaining ranges turned up two untested NEIGHBOUR branches — the callback's no-`code` `OAUTH_STATE_INVALID` refusal, and google-start's absent-`next` path, the other side of the `rawNext !== null` conjunct spec §2.1 calls out. Both were closed pre-emptively and both are mutation-proven. That pre-emption is the practice the spec-stage filing said was owed at its own R2 and did not happen; here it did, and R4 returned zero findings.

Worth recording because it nearly produced a false conclusion: the OBVIOUS mutant for the no-`code` case is EQUIVALENT. Widening site 1's guard to `!nextOutcome.ok` changes nothing on that path, because the branch returns at the `!code` early return long before the emit — so the case passes, and reporting that as "verified non-vacuous" would have been precisely the vacuity `docs/agents/writing-plans.md` exists to stop. The discriminating mutant is a hoist ABOVE that return. **A guard verified by an equivalent mutant is not verified.**

**Infra:** one `no_verdict`, and it was the dispatcher's fault rather than Codex's or the reaper's. The R4 dispatch command and its wait loop shared a single shell invocation, so a 600s foreground timeout SIGTERM'd the process group and killed the child with it — `failureReason: "interrupted"`, `error: "signal SIGTERM"`, killed at exactly 600s, with the reaper log for that minute reading "gated: 6 live codex tree(s) active; no orphans". **Dispatch and wait must be separate invocations**; a `nohup … & disown` inside the same call as the wait offers no protection, because the timeout kills the group. The lost dispatch cost one re-run and no review time.

It also produced the stage's most useful artifact by accident. Its final probe survived in the dispatch stderr and named a real gap the verdict never got to report: site 5 is one emit statement but TWO runtime paths, since its `reason` is a ternary, and the fail-open case used the 5a fixture (no `t`, intent unverified). A regression scoped to the target-mismatch arm — `catch (error) { if (intent) throw error; }` — left it green, because 5a's fixture never produces an `intent` at all. The two arms share a wrapper, not a code path through it. **Read the stderr of a `no_verdict` dispatch before re-running it**; the wrapper records everything the child printed, and a reviewer killed mid-run has usually already done most of the work. The gap is fixed and the mutant now fails exactly one test.

That gap is also the fourth range of the same quantifier, arriving from outside: "one case per emit SITE" counted statements when the contract governs PATHS.
