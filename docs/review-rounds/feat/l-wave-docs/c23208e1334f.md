## diff — 4 rounds

**Examined:** the six dispatches recorded in the sibling JSONL — R1 as three dispatches (one
whole-diff attempt that died mid-run at 684k input tokens, then a Part A / Part B tight-scope split),
then R2, R3, R4 as single whole-diff rounds. Declared findings: 4 (dead dispatch) / 5 / 5 / 6 / 3 / 2.
Verdicts BLOCKING → NEEDS-ATTENTION → NEEDS-ATTENTION → BLOCKING. Sixteen findings were raised across
the surviving rounds and every one was verified against the code before repair; none was refuted.

**Judgment:** the round count is honest, not padding — but it is dominated by ONE class, and that
class is the branch's own repairs.

The subject was ~13 prose "coverage claims" asserting e2e coverage from suites that do not execute.
Deleting a false claim is easy; replacing it with a TRUE one turned out to be the hard part, and each
round found the previous round's replacement over-corrected in the opposite direction:

| Round | The claim at that point | Why it was still wrong |
| --- | --- | --- |
| pre-R1 | "the e2e compound tests cover those cases" | the suite is `describe.skip` |
| R1 | "exercised nowhere" | data-level compound coverage EXISTS and runs every PR |
| R2 | "covered at the data level by `tests/visibility/`" | only ONE case is directly composed |
| R3 | "carried only by the skipped compound audits" | that block makes ZERO `shows.dates` mutations — it never covered them, skipped or not |
| R4 | (repair clipped mid-sentence) | a self-contradictory comment with an unmatched paren |

That progression is the finding worth keeping. **A false coverage claim does not have one truth
value to flip; it has a shape that keeps being slightly wrong in a new direction**, and each round
peeled one layer: is the suite skipped → is it named by a workflow → does an executing test cover it
at some other level → does the cited block do the thing at all. The R3 discovery was the deepest and
the most surprising: prose everyone had preserved through three rounds said the compound audits
handled the `unknown`/`dateless` endpoints, and probing showed that block performs no `shows.dates`
mutation at all. The claim had been false since long before those blocks were skipped. Two earlier
rounds had faithfully relabelled a false statement instead of checking it.

**Mechanizable:** partly, and the cheap part is worth doing if this class recurs.

- **A "cited suite actually runs" check is mechanizable** — resolve every `<name>.spec.ts` cited in a
  comment, and fail if the citing prose asserts coverage while the target is `describe.skip` or is
  named by no workflow. That is a grep plus a workflow scan, both of which this branch wrote by hand
  four times. **It is deliberately NOT built here:** the user ratified that this sentence class is
  DELETED, not guarded (spec §1.1 item 1, §4 limit 1), because prose coverage claims are unguardable
  in general. The narrow filename-resolution check is a different, smaller thing than the general
  class, and would be its own decision.
- **The counts were mechanizable and were the cheapest findings in the corpus.** "66 allowlist rows,
  not 67", "43 UNSEEN, not ~60", "six skipped blocks, not five", "seven compound tests, not six" —
  every one was settled by a one-line probe, and every one had been asserted from memory or from
  stale prose. Rounds 2 and 3 both spent findings on counts. **The lesson: count with a command in
  the commit that makes the claim**, and paste the output. This arc did that for the mutation-child
  hole counts (derived from `RAW_HOLES`, reproducing the umbrella's own figure exactly as a check)
  and zero findings landed on those.

**Infra:** two infrastructure faults cost real wall clock and are worth recording.

1. **The first whole-diff dispatch died silently** — `exit 0`, 0-byte transcript, no `result.json`,
   363 KB of stderr ending mid-turn at 684k input tokens. Diagnosed rather than blindly re-dispatched
   (per the AGENTS.md silent-death guidance): NOT the documented reaper (its last action predated the
   run, and the run was ~60s against a 600s threshold) and not the wedge watchdog. Two contributing
   causes: the reviewer read the full spec AND plan (both very large) before touching the diff, and
   the wrapper was launched via `nohup … &` inside a backgrounded Bash call, so it was torn down when
   that call returned. **Fixes applied and worth reusing:** run the wrapper in the FOREGROUND of a
   backgrounded tool call, and put a BUDGET DISCIPLINE block at the top of every brief naming the
   large documents NOT to read and inlining what the reviewer actually needs. Every later dispatch
   completed.
2. **Splitting into tight-scope reviews worked**, matching the documented #500 precedent. The split
   pair (ledger dispositions / code+guards+probe) both returned real findings where the whole-diff
   attempt returned nothing at all.

**One finding was refused, and the refusal is recorded rather than silent.** R2 read
`tests/visibility/capabilityTransitions.test.ts:272` as self-contradictory. The entry being archived
ratifies that exact site as already-honest and instructs preservation verbatim (spec §2.1.1 item 3),
so actioning it would have been the branch overriding its own ratified scope. The challenge and the
reason are written into the archive entry so a future reviewer does not re-derive it; R3 and R4 did
not re-raise it, which is the outcome that mechanism exists to produce.

**Would fewer rounds have been better?** Rounds 1-3 each found defects that were real, probe-backed,
and would have shipped false statements into the tree. Round 4 found one broken comment introduced by
round 3's own repair — a genuine defect, but the kind a careful re-read of the diff would have caught
for free. **The cheapest available saving was not fewer rounds: it was re-reading each repair in
context before dispatching the next round**, which would likely have collapsed R4 into R3.
