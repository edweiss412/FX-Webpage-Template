# Review-round economy — `feat/a11y-privacy-cluster` @ `3c12f7cc5849`

Arc A of the ABC batch (a11y/privacy cluster). Spec and plan each converged on
their own branch before this one opened; the rounds below are the whole-diff
review only.

## diff — 6 rounds

**Examined:** R1 NEEDS-ATTENTION (2 findings), R2 NEEDS-ATTENTION (1), R3
NEEDS-ATTENTION (1), R4 BLOCKING (1), R5 BLOCKING (4). Nine findings across five
rounds. The count declined 2 → 1 → 1 → 1 and then ROSE to 4, which is the
number that matters most here.

**The brief's cap was 4, and R5 overran it deliberately** — merging over a
BLOCKING verdict without confirming its repair was not available. R5 then
returned the clearest stop signal in the corpus: of its four findings, one was a
genuine P0 process defect (the impeccable gate attestation predated 91 lines of
later UI change, so the shipped surface was not the gated one), one a genuine P1
(the clock-time shape accepted a bare `31`, so a day-of-month rendered as a call
time), one REFUTED against `origin/main` as pre-existing and untouched, and one a
doc-accuracy correction about a change that is strictly an improvement.

That mix — a process defect, one real bug, and two findings that are not defects
in the diff — is the boundary. Rounds 1 through 4 bought correctness; round 5
bought one bug and two paragraphs.

**R6 was therefore SCOPED rather than another hunt,** and the distinction is the
point: its brief asked one question — are R5's four findings correctly
dispositioned? — and told the reviewer that anything else belonged under a
`NEW:` heading rather than as a finding. APPROVE, 0 findings, each disposition
verified against source and `origin/main`. A scoped confirmation is what closes a
BLOCKING verdict without reopening the enumeration; a sixth *hunt* would have
been the ratchet.

**The most valuable single round was the gate RE-RUN, not any review round.**
R5's P0 was that the impeccable gate had run at `048c26b30` while five later
commits changed UI — so the shipped surface was never gated. Re-running it
scoped to that 91-line delta immediately caught that the `CLOCK_TIME_RE` I had
added one commit earlier SILENTLY DELETED nine legitimate call-time spellings
(`1730`, `0800`, `noon`, `6p`, `8h00`, …). That fix was reverted and the residual
ruled a documented limit. The transferable rule: **a gate attestation is only
true for the diff it ran against, and a fix landed after the gate is unreviewed
UI.** Nothing in the pipeline was checking that until a reviewer did.

**Judgment:** four of the five findings were one class the first round did not
name, and neither did the spec. The spec enumerated the fields whose PURPOSE is
a date and gated those five paths. What no round-1 reading caught is the other
way a date reaches a protected viewer: landing in a field that is not a date
field at all, because the parser fills it with whatever tokens are left. R3 found
it in the flight card's unvalidated remainder (`flightNo`, `airline`, `conf`,
itinerary `confirmation`); R4 found it in the ground leg's author-typed `stage`
and `time`; R2 found the inverse — a withheld row being read as evidence a date
existed, producing a FALSE explanation.

Each round I repaired the named instance and then swept what I believed was the
class. Twice the sweep was too narrow, because I was sweeping "sites that render
dates" when the actual class is "fields that can CONTAIN one". Stating that class
correctly after R2 would have collapsed R3 and R4 into one round. That is the
transferable cost: **the class-sweep is only as good as the class statement, and
a sweep over the wrong class reads exactly like a completed sweep.**

The convergence criterion held where it was meant to. Every fix is a WITHHOLD
keyed on a closed question — "can this field's own shape express a date?" — never
a date recognizer over field contents. Recognizing date spellings (`MAY13`,
`05132026`, `2026-05-13`, `5/14`) does not terminate and hands each round a wider
target; "render only the route, the times, and a value that parses as a clock
time" terminates. Round 4 landed a P1 rather than trailing off into P3 noise,
which is the signal that the rounds were still buying correctness rather than
ratcheting a recognizer.

**Mechanizable:** partly, and the honest answer is "not the interesting part".
The leak class is a data-flow question — does any parser-derived string reach a
suppressed viewer's DOM — and the shipped tests approximate it the only cheap
way available: sweep the WHOLE rendered output for the fixture's own date
strings rather than scoping to where the date was expected. That idiom is what
makes the R3 and R4 cases non-tautological, and it generalizes to any future
suppression surface. A structural guard that enumerated "fields a parser fills"
would need the parser's own type information and is not worth building for one
component.

**Infra:** the reviewer could not execute Vitest in any of the four rounds — the
read-only sandbox denied its temporary `ssr`/`client` worker directories with
`EPERM`, so it reported zero tests executed each time and verified by
TypeScript plus its own server-render probes instead. That cost nothing here,
because the probes were the load-bearing evidence and they were better than a
suite run would have been. It is worth knowing for briefs that lean on the
reviewer running the suite: on this machine, they cannot.
