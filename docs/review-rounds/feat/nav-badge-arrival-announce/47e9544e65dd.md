# Review rounds — feat/nav-badge-arrival-announce @ 47e9544e65dd

## spec — 4 rounds

**Examined:** Four spec rounds on one design document, across two sessions (the
arc was taken over at round 2 after the originating account hit its wall). Five
findings total: R1 three, R2 one, R3 one. Every finding was confirmed against
the live tree before repair and none was disputed. No round produced a code change, and only R1
changed the design: it changed what the join reads and when. R2, R3 and R4
corrected statements the spec made ABOUT a design that was already right, plus
one factual error about the React runtime.

The shape worth recording is that the last two rounds both found the same kind
of defect, and it is not the kind the convergence machinery is built to catch.
R2: §3.8 and AC-11 asserted that opening the bell panel suppresses the bell
sentence, when nothing latches that suppression and two live routes restore the
count. R3: AC-8 announces the true count above nine while the pills cap at
`9+`, contradicting the bound clause's phrase "what the badge displays." In
both cases the code the spec describes was correct and the sentence describing
it was not. Both were found by a reviewer reading the spec against itself,
which is the one thing a mutation score cannot do.

R4 is the round that says the most about the shape. It returned four findings
after a round that returned one, and two of them were defects the PREVIOUS
round's repair introduced: R3's referent invariant was stated as total, and at
desktop widths the attention control is out of the accessibility tree, so it
has no referent there (finding 3); and the §3.11 closure claim, inherited from
R1's guard deletion, asserted a closure that covers the bell projection only
(finding 2). A third, finding 1, was an over-generalization written while
repairing R2. That is the fix-round regression budget landing exactly where
`docs/agents/writing-plans.md` says it lands, and it is the argument for
stopping at the cap rather than for buying one more round: three of four
findings existed because of repairs, not because of the design.

Finding 4 is the one that is not that shape and the one worth keeping in mind
generally. The spec asserted that React StrictMode remounts and creates a fresh
ref, which was simply false for the installed runtime (19.2.4 replays effects
and preserves refs). Nothing in the review machinery would have caught it: it
is a claim about a dependency, stated confidently, in a document whose lint
passes at 0 hard. The reviewer caught it by running it.

**Judgment:** R3 is chargeable to this arc's own briefs, and saying so is the
point of the filing. The bound clause carried "never speaks a count that
differs from what the corresponding badge displays" verbatim through rounds 1,
2 and 3. The spec's §3.3 had said since round 1 that the utterance matches the
names rather than the pills, so the brief and the artifact disagreed for three
rounds and the reviewer was correct to take the brief at its word. A bound is
the reviewer's admissibility test; an imprecise one does not merely fail to
catch things, it manufactures findings against the artifact. The repair was to
name the referent in the spec (§3.3, one invariant the rest is stated against)
and to correct the clause in the round-4 brief, with the correction stated in
the brief so the reviewer could see what moved and why.

The generalizable rule: when a bound names an observable, it must name the
observable the design is actually about. Here the design is about an accessible
NAME and the bound named a rendered PILL, two things that agree at every value
except the one the spec had already singled out. That is a bound authored
against the feature's surface instead of its referent.

**Mechanizable:** none of the nine findings. All were natural-language
consistency defects between sections of one document, or between the document
and a brief. `pnpm spec:lint` ran at 0 hard on every round including the ones
that produced findings, which is the honest measure of how far a lint reaches
here. A checker for "AC contradicts the stated bound" would need the bound as a
formal object; it is prose in a brief that is not even in the tree. Not filed
as a row: the process mint freeze binds this, and the arc files no ledger row
of any facing per its brief.

**Infra:** one dispatch lost. Spec round 2's first dispatch died by SIGTERM
13 minutes in, recording `status: no_verdict`, `failureReason: interrupted`,
and no `-o` file. It was NOT the codex reaper, which is the standing suspect:
`codex-reap-kills.log` holds no entry after 2026-08-29, and the reaper's own
last action that afternoon read `gated: 5 live codex tree(s) active; no
orphans`. The dispatch died with the session that backgrounded it, when that
account hit its five-hour wall. The corpus row survives because the wrapper
emits it at completion regardless, which is what made the diagnosis possible at
all from a takeover session that never saw the original turn. Re-dispatched at
the same stage and round to a fresh out-dir per the arc's infra rule; the
retry returned a verdict in 11 minutes. Fleet consequence, since it generalizes:
a completed dispatch's result survives the wall, an in-flight one does not, so
a takeover session must presume an in-flight dispatch dead until it sees a
`result.json`.

## plan — 4 rounds

**Examined:** Four plan rounds on one plan document. Findings by round: 10, 7,
8, 4. Every finding was confirmed against the live tree
before repair and none was disputed. The plan is for a five-task TDD arc whose
spec had already closed at its own cap, so nothing here is a design argument;
all of it is whether the tests would have caught what they claimed to.

The round-1 haul is the one that justifies the whole stage. Four acceptance
criteria had NO case that could fail before the implementation, so the coverage
map asserted a bound the tasks did not meet: AC-7's `(1,1)` passed the task's
own red scaffold, and AC-10 was claimed to be discharged by a live-region walk
that pushes a hit only when `gated(el)` is true, so the unconditional
`role="log"` the criterion actually forbids sailed through it. The same round
found a plan claiming four mutants had already run with their results in the
commit, when neither the module nor its suite existed yet.

Rounds 2 and 3 kept finding real test-design holes rather than prose defects,
which is the difference between this stage and the spec stage. Round 3's best
three: a `spokenRef` set only on a non-null message passes every silence case
and then announces after a `(0, 0)` resolution; a parent that latches attention
on any promise resolution passes both settle orders because React batches the
hook commit with the latch, so neither order observes the wrong rule; and every
callback case passes with the inline `aria-label` ternary left in place, which
would have shipped §3.3's "one decision, two callers" as prose while the drift
it prevents stayed representable. None of those is a wording problem. Each
would have shipped a worse feature.

**Judgment:** The repair-induced share stayed high and did not fall. Four of
round 2's seven and roughly half of round 3's eight were defects introduced by
the previous round's repairs, mostly of one shape: a repair lands in a task body
and the inventories that describe it, the file table, the red-command validation
record, the AC declaration count, the tracked-target count, are not carried
along. Round 3 was told this had been swept after round 2 and found six more
instances.

What broke the pattern was changing the sweep's form rather than its diligence,
and round 4 is the evidence it worked: findings fell from eight to four, and not
one of the four was an inventory restatement, the class that had appeared in
every previous round. Through round 2 each inventory was fixed where the
reviewer pointed. After round 3 the same class was closed by deriving instead: the validation table is now
keyed by task so a task without a row is visible as a gap, the transition
audit's site list is derived from the merge-base diff rather than hand-written,
and the numeric claims about the document (five tasks, twenty criteria, four
tracked line targets) are checked against the document itself before dispatch.
That is the class-sweep rule's own instruction, sweep to a derivation and not to
a longer list, and it took three rounds to actually apply.

Round 4's own two repair-refutations are worth recording precisely, because both
are cases where a repair was not merely incomplete but aimed at the wrong layer.
Round 3 asked for a case forcing the `bellAccessibleName` refactor; the case I
wrote compared the rendered label against the selector, and round 4 ran it: the
inline ternary already returns exactly the selector's outputs, so the comparison
passes with the refactor skipped. The property is behaviour-preserving by
construction, which is the whole point of "one decision, two callers", so no
behavioural assertion can reach it. It is now a source assertion, which is where
the property actually lives. The lesson generalises past this arc: when a repair
is specified as a behavioural test and the thing under test is a structural
identity, the test will pass for the wrong reason, and the tell is that the
"before" and "after" implementations agree on every input.

The other durable lesson is about a rule that could not be followed as written.
`docs/agents/writing-plans.md:9` makes a transition-audit TDD task mandatory
when the spec carries a Transition Inventory. Round 1 found the task missing and
was right. The standalone task added in response could not work, and round 2 was
also right: placed after the join it passes on arrival, placed before it has no
production change of its own to turn it green, and it sat after the closeout
task that must be the PR's last commit. The rule's red/green shape assumes an
ANIMATED component, and this arc adds no animation surface. The audit now ships
inside the task whose red it genuinely shares. That is a documented deviation
from the rule's letter, taken deliberately, and it is recorded here so the next
plan meeting the same wall does not spend two rounds rediscovering it.

**Mechanizable:** Three recurring classes, all parked against existing slugs
rather than filed, since the process mint freeze binds and this arc files no row
of any facing.

- declined: LIM-NONDISCRIMINATING-FIXTURE, the plan-stage instance of a class
  already named by seven arcs — the coverage-map rows whose cases could not
  fail before the implementation (AC-7 passing its own red scaffold, AC-10
  passing on the pre-implementation tree), and round 4's cross-wired
  singularization mutant passing all twelve builder cases because `(1,1)` and
  `(3,2)` agree under cross-wiring. The repair shape is the one that slug
  already records: give the assertion a contest it can lose. Here that is
  `(1,2)` and `(3,1)`, and splitting the map into implementation-driven cases
  versus disclosed non-red regression pins.
- declined: LIM-INDEX-RESTATEMENT-DRIFT, the inventory-residue class — "these
  six commands" over a five-row table, "two tracked line targets" over four,
  "Extends: none" against a task that extends. Every instance was a restatement
  of the plan by the plan. Closed here by keying the validation table to tasks
  and deriving the numeric claims from the document.
- declined: LIM-HAND-LISTED-POPULATION-SET, the transition audit's site list —
  and this arc is a clean demonstration of why the slug exists. The audit's
  enumeration was hand-written, and round 4 showed it was incoherent under both
  possible derivations at once: it listed a pre-existing conditional that no
  added-line set can contain, while a whole-file reading would have swept in
  five conditionals it omitted. Deriving from the merge-base diff, and scoping
  the table to what the arc ADDS, is the repair that slug prescribes.

**Infra:** None at this stage. All five red command strings parsed under
`sh -nc` at every round. Every plan round's reviewer reported the same sandbox
limit, `EPERM` creating Vitest's temporary directories under a read-only mount,
so no round returned an executed test result; each said so plainly and did not
charge it against the artifact, which is the correct handling. It does mean the
plan stage's verdicts rest on reading and on static probes, never on a run, and
the first executed evidence for any of these twenty criteria arrives with Task 1.
