## spec — 8 rounds

**Examined:** every finding across all eight spec rounds, plus what the repair for each one changed.
R1 BLOCKING (2), R2 NEEDS-ATTENTION (2), R3 BLOCKING (3), R4 BLOCKING (2), R5 NEEDS-ATTENTION (1),
R6 BLOCKING (2), R7 NEEDS-ATTENTION (1), R8 NEEDS-ATTENTION (2). Fifteen findings on a document whose subject is a five-line
SQL function — and the shape of that number is the point: two findings were
against the design, seven against the document's own claims and test design.

**Mechanizable:** two of the seven, both of a shape a checker could own.

- **Stale prose surviving a design change (R2 P2).** One sentence describing the deleted two-table seed
  survived because it said "prune gate" with a space while the author's sweep grepped `prune_gate`.
  **declined: a lint here is a recognizer over prose, and prose recognizers are this repo's measured
  losing move** — the sweep set would have to model every case-and-separator variant of every removed
  identifier, and the corpus already carries an arc that grew a 1207-line detector one grammar corner
  per round. The durable form is the author-side rule, not a checker: a removal is swept by the CONCEPT,
  and the cheap mechanical proxy is a case-insensitive grep with separators collapsed, run once. Cost of
  the miss was one finding, not one round — R2 carried two findings and would have run regardless.
- **Bare `N/A` in a completeness matrix (R2 P1) — filed as `BL-SPECLINT-MATRIX-BARE-NA`.** The
  spec-self-review rule already says every cell is an action or an `N/A — reason`. Twenty-one cells said
  bare `N/A`, and two of them were false — the falsehood hid behind the missing reason, because writing
  "N/A — the tables carry no trigger" forces the author to check. The check is a cell equal to `N/A`
  with nothing after it, inside a table block; no grammar, no recognizer growth. Incident: this arc's
  R2 P1, corpus row `docs/review-rounds/feat/validation-prune-db-side-gate/50ca72a566b0.jsonl` round 2.

**Judgment:** seven of the nine were design findings that no checker reaches, and they are the reason
the rounds were worth their cost.

- **R1 P0 killed the design, not a detail.** Two rows encoding one fact can disagree; the reviewer
  produced three lifecycle states where they do, permissively. The repair was subtraction — the second
  table is gone — and that is a strictly better artifact than any patch to the seed would have been.
- **R3 P0 was the sharpest finding of the arc.** The acceptance criteria, written to catch a broken
  gate, would have performed the global deletion they existed to detect, on the live validation project.
  Nothing mechanical finds that: it requires reading the criteria as a program and asking what happens
  when the thing under test is broken rather than when it works.
- **R1 P1, R3 P2 ×2, R4 P2** were citation-fidelity findings against live state (parity compares
  signatures not bodies; `sync_log` retains SELECT behind `admin_only`; D4's boundary is
  PostgREST-scoped; `service_role` holds direct DELETE so the prunes are not the only delete path). Each
  is a claim the author could have probed and did not, and each was settled by the reviewer's probe in
  one round. The corrective that actually worked was §3.10 — deriving the grant/RLS state from a command
  instead of recalling it — and it should have been drafted before round 1, not after round 3.
- **THE SAME AXIS RAN THREE ROUNDS: R3 P0, then R4 P0.** Both said the acceptance probes could commit
  the deletion they exist to detect. The R3 repair was per-instance (wrap the default call; declare one
  limb harmless because a 100-year window is empty) and R4 broke exactly that argument — the emptiness
  was checked in a separate autocommitted statement, so it bounds nothing under concurrent traffic. The
  R4 repair is structural instead: EVERY call to either prune, in every criterion, probe and script,
  is inside a rolled-back transaction, and no call may be exempted by an argument that it cannot delete.
  Two limbs replaced three. The rule that generalises: when a safety argument about a specific call is
  refuted twice, stop arguing about calls and make the safety a property of the harness.

**Infra:** none. All four dispatches returned a verdict on the first attempt — no reap, no
`no_verdict`, no retry ladder, no `CONVERGENCE_ACK` override. Reviewer probes ran against the local tree
only: the sandbox cannot resolve the validation pooler host, so every claim about the live validation
project in this document rests on the author's transcripts in §3, not on reviewer re-measurement. That
limit is recorded here because an APPROVE is bounded by what the reviewer could execute.

**What the author would do differently, stated as a rule rather than a regret:** probe the acceptance
criteria the way the implementation is probed. Three of the four rounds' most expensive findings were
against the TEST design, not the design — the ACs were prose about what would be asserted, while the
implementation had already been dry-run against a real database twice. The asymmetry is the whole story
of this arc's round count.

### Rounds 5 to 8, past the cap, with `CONVERGENCE_ACK`

The cap was reached at R4 and this record was filed there; these rounds continued because R4's own P0 was a live
defect in the acceptance design, and a stage that stops on a known-broken criterion has bought nothing.

**Judgment:** the axis changed after R4, which is the signal worth recording.

- R1 was the design. R3 and R4 were the harness. R5 and R6 were the DOCUMENT: a handler with no success
  path, a rule whose scope over-claimed against the arc's own history, a closed criterion naming a
  one-function probe. None of those would change a line of shipped SQL.
- **R7 broke that pattern and is the reason continuing past the cap paid.** It found an asymmetry
  nobody had looked at: `sync_log_prune`'s cron row has `command`, `schedule` and `active` pinned
  (`tests/db/syncLogIndexesAndPrune.db.test.ts:214-223`) while `app_events_prune` has only its NAME
  checked (`tests/log/appEventsSchema.test.ts:108-111`). A cron row rewritten to
  `prune_app_events(interval '5 days')` passes every gate criterion — the gate has no opinion about the
  argument — refuses on validation exactly as designed, and silently deletes events aged 5 to 60 days
  on production. That is the production half of the consequence bound, broken by a change the suite
  cannot see. AC-8 pins it. Cost of the finding: one round. Cost of missing it: a silent retention
  change on prod that no test in the repo would have caught.
- That is the shape a stage looks like when it is done finding design defects and has started finding
  prose defects. The deliverable stopped moving at R4; the document kept moving because each round
  found a true statement to fix in it.
- **The honest reading of rounds 5 to 7 is that the acceptance criteria were prose standing in for a
  test file.** Every finding in them is a defect a real suite would have surfaced by failing to run:
  a plpgsql block with no success path, a rule contradicted by a script in the same document. The suite
  the plan writes settles all three by execution.

**R8 closed the stage by disposition, not by convergence** — the orchestrator ruled it terminal, with
one named exception (a NEW prod-reachable deletion path would have bought one more scoped round;
neither finding was one). Its two findings were repaired here: the acceptance suite never exercised the
PostgREST channel after the change, closed by pinning the gate's body (AC-9) rather than by adding a
REST call that could not be rolled back — applying the arc's own rule to its last channel instead of
exempting it; and one sentence called the REST probe "the same call" as the default form when the
transcript sent the parameterised one.

**The record this stage leaves: the DESIGN converged at R4 and rounds 5 to 8 were criterion-hardening.**
Not one of those eleven findings changed a line of the shipped SQL. Four of them changed what the
acceptance criteria would catch — and R7's would have let a rewritten cron row silently delete
production events — so they were not free, but they are a different kind of finding than R1's, and a
stage that cannot tell the two apart cannot know when it is done.

Nothing in rounds 5 to 8 was mechanizable beyond the two items dispositioned above: a checker for "your
prose about your own probes matches your probes" is a recognizer over prose, declined for the same
reason. No dispatch in any of the seven rounds needed a retry.

## plan — 5 rounds

**Examined:** every finding across all four plan rounds and what each repair changed, plus the two
dispatches that produced no verdict. R1 BLOCKING (8), R2 BLOCKING (3), R3 BLOCKING (3), R4 BLOCKING (1), R5 BLOCKING (2).
Two uncounted dispatches sit between them: the first r2 attempt died with the network on 2026-08-22
(`total_timeout`), and r3 was killed deliberately, mid-run, by its own author.

**The one story worth telling about this stage is a section that did not exist when it began.** R2's
findings 2 and 3 were two instances of one shape — a command in the plan that could not run as written —
so the repair, correctly per this repo's class-sweep rule, was to sweep the whole document rather than
patch two lines. That sweep became §0.1: an extraction command, a table of every command, and its
outcome. It was forty lines when it landed.

It then produced a finding in every subsequent round.

- Self-review before the r3 dispatch found the parity suite appears in the plan in TWO forms, `env -u
  TEST_DATABASE_URL …` and ambient, and the table carried only the first. They prove different halves of
  Task 2. Caught by the author, so it cost no round — but only because the author re-ran the extraction
  rather than trusting the table written from it.
- R3 found two more. The `awk` anchored its fence at column zero, so the indented fence inside Task 2's
  numbered list was skipped and both validation `psql` calls went unswept. And the `rg` presented as the
  savepoint inventory's derivation returns about sixty hits across seven files, most of them the
  destructive-statement guard's own corpus strings, because that literal IS the input that guard is
  tested against.

That is the arms-race shape this repo has measured in code detectors, running inside a PLAN document:
each round hardened the sweep, and each hardening was a larger surface for the next round. The repair at
R3 was therefore not a better extractor. §0.1 went from fifty-one lines to twenty-two, the table came
out, and the plan stopped carrying a proof of its own commands. **The commands being correct is what a
plan owes; a proof inside the plan that they are correct is not, and it was costing more rounds than it
closed.**

**Mechanizable:** one candidate, declined, and the reason is the same one the spec stage recorded.

- **A checker for "every command in a plan runs as written."** It would have caught R2's `pnpm heavy`
  with no argument, R2's non-executable heredoc, and R4's reliance on an undefined
  `$TEST_DATABASE_URL` — three of this stage's fifteen findings, directly.

declined: a checker for this must first decide which fenced spans and inline backticks in a
markdown document ARE commands, which is a recognizer over prose. §0.1's own two-line extractor did
exactly that job in this arc and got it wrong twice — once on fence indentation, once on the
difference between a call and a corpus string — and a checker would fail the same way with more code
to maintain. `pnpm spec:lint` already owns the mechanical part and earned its keep here. No ledger row
is filed, because filing one would commit someone to building the recognizer this entry declines.

**Judgment:** the findings that mattered were about whether a test would actually execute, and no
checker reaches them.

- **R2's P1 was the best finding of the stage.** Task 1 put every prune call in one rolled-back
  transaction and then, after catching the expected rejection, read a row back inside that same
  transaction. Postgres aborts a transaction at its first uncaught error, so AC-2's read-back — the
  statement carrying the entire non-deletion claim — could not have run at all. The criterion would have
  reported an error, not a failure, and the difference is whether anyone would have believed the
  suite. Reading a test as a program and asking what the database does at the moment the expectation
  fires is exactly what a linter cannot do.
- **R3 found two acceptance criteria owned by tasks that did not run their assertions.** AC-8 names both
  cron rows; Task 3 ran only the `app_events` suite while `sync_log_prune`'s three assertions sit in a
  file Task 3 never opened. AC-9 spans local AND validation by the spec's own wording, and validation has
  no migration until Task 2 applies one, so no single task can hold both halves — yet the plan asserted
  sole ownership in a sentence. One is a fixable oversight; the other is a genuine two-owner criterion
  the plan was denying. Both were invisible to every gate the repo has.
- **R4's single finding is the same axis as R2's, and naming that axis is the point of this filing.**
  Task 2's validation commands all read `$TEST_DATABASE_URL`, and NOTHING in a worktree shell defines
  it: not the shell, and not vitest, whose `tests/setup.ts` reads no dotenv file — a fact
  `scripts/preflight-env.mjs:12` states in a comment because it had to parse `.env.local` itself. Two
  consequences, and the second is the bad one. `psql "$TEST_DATABASE_URL"` with the variable unset does
  not error on a missing DSN; it falls back to the local Unix socket. And
  `tests/db/validation-schema-parity.test.ts:93` returns `LOCAL_DB_URL` when the variable is undefined,
  so AC-7's command would have passed while comparing local to local. The surgical apply would have
  landed on the wrong database, AC-6 would have refused for the wrong reason, and every one of those
  steps would have reported success. **That is precisely the shape this arc's own consequence bound
  calls silently wrong**, committed by the plan for proving the bound.

  R2's P1 was a transaction that aborts before the assertion carrying the claim can run. R4's is a
  connection that silently retargets so the assertion runs against the wrong database. Both are
  "the step reports success and proves nothing," and both were invisible to `spec:lint`, to the docs
  meta-tests, and to the author. A stage looking for its own blind spot should look here first.

- **The lesson this stage failed to carry forward is the one the spec stage filed.** That section closes
  with "probe the acceptance criteria the way the implementation is probed," because three of four spec
  rounds' most expensive findings were against test design rather than design. R2's P1 is that finding
  again, one stage later, on the same arc. Writing a rule at the end of a stage does not apply it to the
  next one; the durable form would have been to dry-run Task 1's transaction shape against the local
  database before drafting it, which is a five-minute cost that would have removed the stage's best
  finding.

**Infra:** two dispatches produced no verdict, and neither counted.

- The first r2 attempt died on 2026-08-22 with `total_timeout` when the network failed and took every
  in-flight Codex dispatch on the machine with it. Recorded as `no_verdict`, re-dispatched unchanged,
  still round 2.
- r3 was killed on purpose about a minute in. Self-review found §0.1's ambient-form hole while the
  reviewer was already reading, and a verdict returned against a tree the author had already superseded
  is a wasted round. Killed, repaired, re-dispatched at a new head. Records as
  `no_verdict`/`interrupted`. The orchestrator ruled the accounting: catching your own predicted hole
  before the reviewer does is the cheap form of the round, and three minutes of dispatch is worth less
  than one of four.
- The convergence gate blocked the r4 brief before dispatch. The brief carried a bound, a fence and a
  probe domain, but stated the bound in its own words while the gate matches a phrasing. Adding the
  acceptance posture in the recognized form was the correct repair rather than `CONVERGENCE_ACK` — the
  bound genuinely reads better for it — but it is worth recording that the gate fired on the words
  "guard" and "recognizer" appearing in prose ABOUT the round economy, in a brief whose subject is a
  five-line SQL function and no detector at all.

**What the author would do differently, and it is not the rule the spec stage wrote.** That rule said
to probe the acceptance criteria. This stage's author DID probe — the migration was dry-run against a
real database inside a rolled-back transaction before Task 1 was drafted, and validation's posture
marker was read before Task 2 was. The probes were run from a shell that had been prepared BY HAND,
with `set -a; . ./.env.local; set +a` typed once, hours earlier and never written down. So the probes
were sound and the plan was still wrong, because the plan is what someone else executes and it did not
carry the step that made the probe work. **The rule is narrower than the spec stage's and it is the one
this stage actually earns: a probe proves a command only when the plan carries every line the probe's
shell needed.** An exported variable, a sourced file, a working directory — anything the author's
terminal knew and the document does not is a step the plan is missing, and it will read as green until
someone runs it clean.

### Round 5, past the cap, scoped and terminal

The cap was reached at R4 and this record was filed there. The orchestrator granted exactly one more
round, bounded to two questions — does Task 2 now reach validation, and does any other command depend
on a shell fact the plan does not carry — on the reasoning that R4's finding class has quiet siblings
and its blast radius on THIS arc is a migration applied to the wrong database while every step reports
success. The round returned two findings, both inside the bound. It paid.

**R5's P0 is the finding this whole filing should be remembered for.** The R4 repair added a step 0
that loaded the DSN and then checked `current_database()` and that the connection was over TCP. Local
answers that check identically: its database is also named `postgres`, and the local stack listens on
`172.18.0.2`, so the guard returned `postgres|t` against precisely the database it existed to exclude.
**A guard that passes on the value it exists to reject is worse than no guard, because it reads as
one** — and this one was written by an author who had just spent a round on the same axis, in the step
whose entire purpose was to close it.

The repair is two guards, both verified in both directions against both databases before being
written down: the DSN must carry the validation project ref `vzakgrxqwcalbmagufjh`, which is
authoritative because the session pooler routes by it, and the answering server must report a public
address, which local cannot. The general form is the one worth keeping: **a guard is not finished when
it passes on the good input; it is finished when it has been shown to FAIL on the bad one.** Neither
R4's repair nor R5's would have been believed under that rule without the second measurement, and only
one of them survived it.

**R5's P1 found the sibling the orchestrator predicted.** `SCHEMA_MANIFEST_DB_URL` overrides the local
target in `localManifestDbUrl()` (`scripts/generate-schema-manifest.ts:41-46`), so a stale value makes
`pnpm gen:schema-manifest` introspect some other database and commit THAT as the manifest. The same
variable selects parity's Layer 3 target (`tests/db/validation-schema-parity.test.ts:105-106`), and
Layer 3 returns early rather than failing when its target is unreachable
(`tests/db/validation-schema-parity.test.ts:238-239`) — so the local-freshness comparison silently
disappears from every parity run in the plan. Same shape as R4's, one variable over, exactly as the
disposition reasoned. §0.2 now carries both variables, and the note that a green `pnpm preflight`
promises neither: its `HARD` set does not include `TEST_DATABASE_URL` at all
(`scripts/preflight-env.mjs:53-61`), which the R4 repair had also overstated.

**Infra, round 5.** The first dispatch attempt exited 127 without running: the command was built as
`CONVERGENCE_ACK=1 node …` and invoked through `exec $(cat …)`, so the shell tried to execute the
assignment as a program name. No wrapper ran and no corpus row was written, which is the correct
behaviour and the reason the round is numbered 5 exactly once. Re-dispatched as `env
CONVERGENCE_ACK=1 node …`.

**The stage's closing number: five rounds, seventeen findings, and not one line of shipped SQL
changed.** Every finding was against the plan's own instructions — whether a command runs, whether a
criterion is proven by the task claiming it, whether a guard discriminates. The SQL was dry-run
against a real database before round 1 and has not moved since. That asymmetry is the same one the
spec stage closed on, and it is the honest measure of where this arc's risk actually lived.
