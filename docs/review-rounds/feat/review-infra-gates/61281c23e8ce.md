### Two failures were mine, and both are mechanizable

**A string replace that does not match is a silent no-op, and a success message printed
after it proves nothing.** This happened TWICE — R2 finding 4 (caught by R3) and R3
finding 4 (caught by R4) — and in both cases the commit message described a change the
commit did not contain. The second time had a subtler mechanism worth writing down: the
edit script asserted its anchor, but a LATER assertion in the same script failed, and
because the script writes once at the end, the earlier successful edit was discarded
along with it. The assertion was not the problem; the write granularity was.

**Mechanizable, and cheap:** after any scripted source edit, grep the TREE for the new
content before reporting success. The reviewer caught both by running the mutant against
the tree instead of reading the diff summary — which is exactly what the finding-3 brief
line now asks for explicitly ("verify against the TREE, not against this description").

### The dominant finding shape: a repair that closes its instance, not its class

R2 found three (an unplaceable check testing the raw line; a fail-open ceiling parse; a
`not-ui` token removed from suppression but left out of targeting). R4 found four
UNPINNED repairs — correct code with no case that would notice its removal. Both are the
same defect at different altitudes: **the fix was aimed at the reported example rather
than at what the example was an example of.**

**Mechanizable:** the class-sweep rule already covers the first half. The second half —
"every repair ships a case that fails against the pre-repair code" — is not written down
anywhere as a rule, and it is what R4 spent its entire round on. Five mutants were run
after R4 and all five died; that step should have preceded the round, not followed it.
